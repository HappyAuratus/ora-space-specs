# 进行中的模型请求不随令牌到期取消，改由空闲超时和总上限约束，被切断时中止响应；取代固定的 5 分钟总时限

一次模型请求开始后，只在吊销（会话结束、执行中断、Node 删除授权、Cloud 关闭）或 Agent 断开时取消；临时令牌到期只拒绝
新请求和续期。上游请求不再有固定的 5 分钟总时限，改为空闲超时（连续多久收不到上游数据）加总上限，两者都是部署配置，
默认 2 分钟和 30 分钟。因空闲超时、总上限、吊销或上游失败而在响应头发出之后停止时，Cloud 中止这个响应，Agent 读到的是
一次失败，而不是一个正常结束的流。影响面只在 Cloud 的模型代理；Node 和 Agent 插件不改。

本 ADR 处于 `proposed`，等 owner 评审。它是 [模型接入根决策](0-in-process-model-proxy-with-deployment-connections.md)
（下称“根决策”）之后的第一份后续决策，回答根决策“本决策未解决的问题”第 1 条。依据是 circus #1075 的实测和 owner 在
#1122 的结论（2026-11-13）。读取的代码版本为 cloud `b03ac2b4`（`v2-server/internal/nodeservices`、
`requestmetrics`、`executionruntime`）、desktop `dcff8afe`（`apps/ora-node` 的 `model_proxy`），实测用 OpenCode 0.6.11。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`。
- **不涉及**：desktop 的 Node、Agent 插件。Agent 收到失败后怎么重发和显示，由 circus #1132 跟进，不在本文。
- **新增两项部署配置**，不设置时取默认值；没有数据迁移。

## 问题

实测（circus #1075，生产常量，真实 Node 与 OpenCode，本地慢速上游）确认根决策记下的风险会发生，而且后果比预想的更隐蔽：

| 现象 | 原因 |
| --- | --- |
| 在令牌剩 70 秒时发起、需要 3 分钟的请求，在第 69.9 秒被切断；Node 已在第 11 秒续期成功 | 请求的截止时间固定为它开始那一刻的令牌到期时间，续期不延长它。Node 在剩约 60 秒时续期，所以最坏只剩约 1 分钟 |
| 任何超过 5 分钟的流式请求在第 300.0 秒被切断 | 上游客户端的 5 分钟总时限包含读完整个响应体 |
| 被切断后 Agent 没有看到错误：OpenCode 把半截内容当成一条完整回答，带上它继续请求，25 分钟里被切断 5 次，这一轮始终不结束 | 响应头 200 已经发出，切断后流照常结束，没有 `finish_reason`，也没有 `[DONE]` |

## 决策

### D1：令牌到期只拒绝新请求，进行中的请求只随吊销和断开取消

- 用有效令牌发起的请求，不因为这个令牌之后到期而被取消。
- 进行中的请求只在两种情况下取消：授权被吊销（会话结束、执行中断、Node 删除授权、Cloud 关闭），或 Agent 断开。
- 到期的令牌不能发起新请求，也不能续期，这一条不变。

为什么：令牌的期限是为了限制泄露后还能用多久，限制的对象是“还能发起多少新请求”。进行中的请求必然是用有效令牌发起的，
它的去留应由会话是否还活着决定，而这正是吊销表达的东西。根决策 D3 也只承诺了吊销时取消进行中的请求。

代价：Node 失联、不再续期时，已经开始的请求不会在令牌到期那一刻停下，最长还能跑到 D2 的总上限，或者直到执行被标为中断、
授权被吊销。这段时间消耗的是上游额度，不会让失联的 Node 拿到新的能力。

### D2：上游请求由空闲超时和总上限约束，两者是部署配置

- **空闲超时**：从发出请求起计时，每收到一段上游数据就重新计时；连续这么久没有数据（包括等待响应头）就停止这次请求。
  默认 2 分钟。
- **总上限**：一次请求从发出起最多持续这么久。默认 30 分钟。
- **配置**：部署环境变量 `V2_MODEL_IDLE_TIMEOUT`、`V2_MODEL_MAX_DURATION`，两种协议共用；值是正的时长，空闲超时不能大于
  总上限，否则 Cloud 拒绝启动。改了要重启 Cloud（同根决策 D1）。

为什么：请求“长”本身不是失败。长推理和长输出在持续产出数据，应该让它跑完；真正要防的是上游卡住不动，这由空闲超时负责。
总上限只是兜底，防止一个始终在产出的请求无限占用连接和额度。做成部署配置，是因为合适的值取决于部署用的模型和网关。

代价：上游在思考阶段完全不输出、超过空闲超时的模型会被切断；这类模型需要部署方调大空闲超时。

### D3：中途停止时中止响应，让 Agent 看到失败

- 响应头发出之后，因空闲超时、总上限、吊销或上游失败而停止时，Cloud 中止这个响应（HTTP/1.1 不写结束块就关闭连接，
  HTTP/2 重置流），不让它像正常结束的流那样收尾。
- 响应头发出之前停止的，照旧返回固定的错误码（根决策 D4）。
- 请求记录照常写下这次请求的结果：超时或上游失败记为中断，吊销或 Agent 断开记为取消。

为什么：正常结束的流会被 Agent 当成完整回答。实测里 OpenCode 把半截内容写进对话，再带着它继续请求，失败被静默地掩盖成
重复内容和成倍调用。中止响应后，Agent 至少能区分“答完了”和“断了”。

Agent 收到中止后的实际反应（OpenCode 0.6.11，circus #1122 实测，空闲超时与总上限临时设为 20 秒和 60 秒）：

- 把它当作网络失败，**原样重发同一个请求**（不再带上半截内容），指数退避，共 5 次（首次加 4 次重发）后放弃，这一轮以
  `stop_reason: cancelled` 结束，**不给出失败原因**。
- 每次重发期间已经流出的片段会拼在一起显示。
- 按默认值估算：空闲超时断开约 11 分钟后放弃；总上限断开最坏约 2.5 小时、5 倍调用量才结束。

这些是 Agent 一侧的行为，由 circus #1132 跟进（总上限断开后不再重发、空闲超时断开后最多重发 1 次、显示可读的失败原因、
可见文字不重复拼接）。本文只承诺 Cloud 一侧：中途停止的响应一定以失败呈现。

## 不变量

1. 用有效令牌发起的模型请求，不因为令牌之后到期而被取消。
2. 授权被吊销或 Agent 断开时，进行中的模型请求被取消。
3. 连续超过空闲超时收不到上游数据的请求被停止；持续时间超过总上限的请求被停止。
4. 在响应头发出之后停止的请求，Agent 读到的是失败，不是正常结束的流。
5. 空闲超时和总上限只来自部署配置；非法值使 Cloud 拒绝启动，不会静默回退到默认值。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 续期时同时延长进行中的请求，保留“到期即停” | 语义更严：Node 失联时请求在令牌到期时停下 | 要为每个授权维护可延长的计时器；Node 续期失败或延迟时照样切断。D1 的代价有总上限和吊销兜底，换来的严格程度不值得这份复杂度 |
| 只把总时限改成可配置 | 改动最小 | 无论设多大，都会切断合法的长请求，同时对卡住的上游反应很慢 |
| 维持 5 分钟总时限，只把上限写进本文 | 不改代码 | 长推理、长输出照样被切断，而且切断表现为重复内容和成倍调用 |
| 切断时照常结束流，只在流里补一个错误事件 | 不断开连接 | 两种协议的流式格式都没有统一的“代理错误”事件；Agent 是否识别不可控，实测中正常结束会被当成完整回答 |
| 在 Cloud 一侧挡住重发：总上限切断后，拒绝紧接着的同一请求，返回明确的错误码 | 不用等 Agent 插件修改 | 要先实测 OpenCode 收到这种 4xx 会不会停止重发；作为 circus #1132 的备选方案，实测后再定，不在本文 |

   适配，也可能采用上表最后一行的 Cloud 侧方案；采用后者时在本文之上追加后续决策。
