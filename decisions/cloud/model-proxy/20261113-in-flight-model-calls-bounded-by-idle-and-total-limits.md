# 进行中的模型请求不随令牌到期取消，改由空闲超时和总上限约束，被切断时中止响应、同一轮里不再放行重发；取代固定的 5 分钟总时限

一次模型请求开始后，只在吊销（会话结束、执行中断、Node 删除授权、Cloud 关闭）或 Agent 断开时取消；临时令牌到期只拒绝
新请求和续期。上游请求没有固定的总时限，由空闲超时（连续多久收不到上游数据）加总上限约束，两者都是部署配置，默认
2 分钟和 30 分钟。因空闲超时、总上限、吊销或上游失败而在响应头发出之后停止时，Cloud 中止这个响应，Agent 读到的是一次
失败，而不是一个正常结束的流；同一轮里，Agent 对被限值切断的请求的重发由 Cloud 在响应头前拒绝（总上限切断后一律拒绝，
空闲超时切断后放行一次），这一轮以切断原因失败。影响面只在 Cloud；Node 和 Agent 插件不改。

本 ADR 处于 `approved`：owner 2026-11-13 在 circus #1133 评审通过 D1–D3，D4 按 owner 在 circus #1132 的结论（方案 B）
加入。D1–D3 已由 ora-space/cloud#367（merge commit `4183eb9b`）实现，D4 由 ora-space/cloud#369 实现；全部合并后转
`implemented`。核心用例见 [模型接入用例](../../../test-cases/cloud/model-proxy/in-process-model-proxy.md)。它是
[模型接入根决策](0-in-process-model-proxy-with-deployment-connections.md)（下称“根决策”）之后的第一份后续决策，回答根决策
“本决策未解决的问题”第 1 条。依据是 circus #1075、#1132 的实测和 owner 在 #1122、#1132 的结论。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/` 与 `frontend-v2/`（显示失败原因）。
- **不涉及**：desktop 的 Node、Agent 插件和上游 Agent。D4 只在 Cloud 一侧限制重发，不改 Agent 的重发策略。
- **两项部署配置**，不设置时取默认值；没有数据迁移。

## 问题

根决策记下的风险会发生（circus #1075 实测）：请求的截止时间曾固定为它开始那一刻的令牌到期时间，而 Node 在令牌剩约
60 秒时才续期，所以续期前不久开始的请求最坏只能跑约 1 分钟；上游客户端另有 5 分钟的总时限，包含读完整个流式响应体。
被切断时响应头已经发出，流照常结束，Agent 把半截内容当成完整回答并带着它继续请求，失败被掩盖成重复内容和成倍调用。

## 决策

### D1：令牌到期只拒绝新请求，进行中的请求只随吊销和断开取消

- 用有效令牌发起的请求，不因为这个令牌之后到期而被取消，包括 Node 已续期和没能续期两种情况。
- 进行中的请求只在两种情况下取消：授权被吊销（会话结束、执行中断、Node 删除授权、Cloud 关闭），或 Agent 断开。
- 到期的令牌不能发起新请求，也不能续期。一个已到期、但还有请求在进行的授权仍然登记着：清理过期授权和拒绝续期都不取消
  这些请求，吊销仍能找到并取消它们；最后一个请求结束后它被移除。

为什么：令牌的期限是为了限制泄露后还能用多久，限制的对象是“还能发起多少新请求”。进行中的请求必然是用有效令牌发起的，
它的去留应由会话是否还活着决定，而这正是吊销表达的东西。根决策 D3 也只承诺了吊销时取消进行中的请求。

代价：Node 失联、不再续期时，已经开始的请求不会在令牌到期那一刻停下，最长还能跑到 D2 的总上限，或者直到执行被标为中断、
授权被吊销。这段时间消耗的是上游额度，不会让失联的 Node 拿到新的能力。

### D2：上游请求由空闲超时和总上限约束，两者是部署配置

- **空闲超时**：从发出请求起计时，每收到一段上游数据就重新计时；连续这么久没有数据就停止这次请求。等待响应头也只受它
  约束，没有另外的响应头时限。默认 2 分钟。
- **总上限**：一次请求从发出起最多持续这么久。默认 30 分钟。
- **配置**：部署环境变量 `V2_MODEL_IDLE_TIMEOUT`、`V2_MODEL_MAX_DURATION`，两种协议共用；值是正的时长，空闲超时不能大于
  总上限，否则 Cloud 拒绝启动。改了要重启 Cloud（同根决策 D1）。

为什么：请求“长”本身不是失败。长推理和长输出在持续产出数据，应该让它跑完；真正要防的是上游卡住不动，这由空闲超时负责。
总上限只是兜底，防止一个始终在产出的请求无限占用连接和额度。做成部署配置，是因为合适的值取决于部署用的模型和网关。

代价：上游在思考阶段完全不输出、超过空闲超时的模型会被切断；这类模型需要部署方调大空闲超时。

### D3：中途停止时中止响应，让 Agent 看到失败

- 响应头发出之后，因空闲超时、总上限、吊销或上游失败而停止时，Cloud 中止这个响应（HTTP/1.1 不写结束块就关闭连接，
  HTTP/2 重置流），不让它像正常结束的流那样收尾。中止由拥有这个响应的 Agent 模型路由执行；不经这条路由的进程内调用方
  （纯模型轮次）不受影响。
- 响应头发出之前停止的，照旧返回固定的错误码（根决策 D4）。
- 请求记录照常写下这次请求的结果：超时或上游失败记为中断，吊销或 Agent 断开记为取消。

为什么：正常结束的流会被 Agent 当成完整回答，失败被静默地掩盖成重复内容和成倍调用。中止响应后，Agent 至少能区分
“答完了”和“断了”。

只有 D3 还不够：Agent 把中止当作网络失败，原样重发同一个请求。OpenCode 0.6.11 最多发 6 次（首次加 5 次重发，次数写死在
上游 OpenCode 里，配置改不了；circus #1122 实测只看到 5 次，是 Node 45 秒的无进展看门狗先触发了取消），Claude Code 0.4.5
发 11 次以上；重发期间流出的片段会拼接显示。没有 D4 时，默认值下一次总上限切断最坏约 3 小时、6 倍调用量（circus #1132
实测）。

### D4：同一轮里不再放行被限值切断后的重发，这一轮以切断原因失败

- **范围**：一个 Agent 会话的一轮。每个模型请求都绑定在当时进行中的那一轮上，每一轮开始时重新计算，不论这一轮由谁发起。
- **总上限切断后**：这一轮之后的模型请求，Cloud 在发往上游之前、响应头之前拒绝。
- **空闲超时切断后**：放行下一个请求（一次重发）；它也被空闲超时切断，之后的请求同样拒绝。一次卡住同时切断的几个请求
  （例如附带的标题请求）只算一次；切断之前已经开始的请求不计入。
- **清零**：中间有请求正常结束，之前的空闲超时切断不再计数。
- **拒绝的应答**：HTTP 422，按请求的协议给出错误格式（OpenAI 兼容的 `error` 对象、Anthropic 的 `type: error`），文字写明
  切断原因和代码（`model_max_duration`、`model_idle_timeout`），不含 Agent 据以重发的字样（网络失败、超时、5xx 状态码等）。
  被拒绝的请求不发往上游，也不写请求记录：请求记录只记发往上游的请求，被拒绝的次数不出现在用量里。
- **这一轮的结果**：最后的请求是被限值切断、而这一轮不是用户自己停的时，这一轮按失败结束，失败原因就是切断原因，页面
  显示可读的文字（如“模型请求超过时长上限被切断”“模型长时间没有输出被切断”）。

为什么用 422、不用 408、409、429：Agent 把 408、409、429 和 5xx 都当成可以重发的错误（OpenCode 的 provider SDK 和 Claude
Code 都如此），只有确定的客户端错误才会让它停下。为什么限制文字：OpenCode 还会按报错文字匹配一组表示网络失败或超时的
说法决定是否重发，文字里出现它们就仍会重发。为什么由 Cloud 自己拒绝：上游返回的 4xx 经代理会被换成固定的 502
（根决策 D4），Agent 会重发；只有 Cloud 在响应头前自己给出的 422 能让它停下。

为什么空闲超时放行一次：卡住常是偶发的，重发一次往往能成功；连续两次卡住再停，用户多等一次空闲超时，换来偶发故障不
直接失败。总上限切断不放行：请求本身就超过了上限，重发只会再跑满一次。

实测（circus #1132，真实 Node 与 OpenCode 0.6.11、Claude Code 0.4.5）：OpenCode 收到这样的 422 只发 1 次就停；Claude Code
在 0.1 秒内连发几次后停下，并显示错误文字。

代价：每次被限值切断后还会多一个被拒绝的请求（不发往上游，不消耗额度）；空闲超时切断时，可见文字最多重复一次（首次的片段
和那一次重发的片段拼在一起）。

## 不变量

1. 用有效令牌发起的模型请求，不因为令牌之后到期而被取消。
2. 授权被吊销或 Agent 断开时，进行中的模型请求被取消。
3. 连续超过空闲超时收不到上游数据的请求被停止；持续时间超过总上限的请求被停止。
4. 在响应头发出之后停止的请求，Agent 读到的是失败，不是正常结束的流。
5. 空闲超时和总上限只来自部署配置；非法值使 Cloud 拒绝启动，不会静默回退到默认值。
6. 同一轮里，一个请求被总上限切断后，或连续两次被空闲超时切断后，之后的模型请求不发往上游，Agent 收到 422 和不会触发
   重发的错误文字。
7. 因请求被限值切断而结束的一轮，以失败结束，失败原因是切断原因。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 续期时同时延长进行中的请求，保留“到期即停” | 语义更严：Node 失联时请求在令牌到期时停下 | 要为每个授权维护可延长的计时器；Node 续期失败或延迟时照样切断。D1 的代价有总上限和吊销兜底，换来的严格程度不值得这份复杂度 |
| 只把总时限改成可配置 | 改动最小 | 无论设多大，都会切断合法的长请求，同时对卡住的上游反应很慢 |
| 维持 5 分钟总时限，只把上限写进本文 | 不改代码 | 长推理、长输出照样被切断，而且切断表现为重复内容和成倍调用 |
| 切断时照常结束流，只在流里补一个错误事件（circus #1132 方案 A） | 不断开连接；对 OpenCode 少一次请求，错误文字还能经它报出 | 实测挡不住 Claude Code：它会改发一次非流式请求，最后仍要靠 D4 的拒绝；还改了 D3 的中止语义 |
| 空闲超时切断后也一律拒绝，不放行重发 | 可见文字完全不重复 | 偶发的卡住也会直接让这一轮失败；owner 在 circus #1132 选择保留一次重发 |
| 透传上游的 4xx 让 Agent 停下 | 不需要 Cloud 记状态 | 根决策 D4 把上游错误换成固定的 502，Agent 会重发；被切断的请求也根本没有上游的 4xx |

## 本决策未解决的问题

1. **重发期间可见文字的拼接**：上游 OpenCode 重发时写进同一条助手消息、不删前一次的片段，流式增量也不标出重发边界，
   Node 和 Cloud 都分不出哪段属于哪次。D4 把它限制在最多两段，彻底解决只能改上游 OpenCode。
2. **Node 把一轮的所有失败都记成 `Cancelled`、丢掉错误文字**：D4 的失败原因由 Cloud 自己记下，不依赖 Node；Node 一侧由
   circus #1138 跟进。
