# 模型接入：模型代理在 Cloud 进程里，模型连接是部署级的、来自环境变量，Key 只在进程内存，Node 为每个 Agent 会话申请临时令牌；取代 v1 的 model-gateway 和个人模型连接

模型请求由 Cloud 进程自己代理，没有独立的 model-gateway。能用哪个上游和模型由部署的环境变量决定，所有租户共用；
Key 只在 Cloud 进程的内存里，不入库，不下发给 Node。Node 为每个 Agent 会话向 Cloud 申请一个临时令牌，Agent 只拿到
临时令牌和代理地址；会话结束或执行中断时令牌立即失效。Cloud 转发时强制使用会话冻结的模型，客户端不能选择上游地址、
认证头和模型。这些都是 v2-server 现在的做法，本文把它们定为第一版的承诺，不新增机制。第一版没有个人或团队的模型
连接，没有限流和配额，也不对用量计量作承诺。

本 ADR 为 `implemented`：所述行为由 v2-server 实现，核心用例的每一条都有直接测试（最后两项由 ora-space/cloud#377 补齐）；
它是领域 `cloud/model-proxy` 的根决策。前提是
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）。依据是 circus #1043 的
结论 4、#1023 第四节的 O2 加 O3。2026-11-11 owner 在 circus #1073 把第一版收窄，本文据此重写：原先的部署配置文件
（多上游、企业 CA）、代理挪到 Cloud 入口、用项目令牌申请授权和计量承诺都已删除。起草时读取的代码版本为 cloud `80e9c9f1`
（`v2-server/internal/nodeservices`、`executionruntime`、`agentruntime`）、desktop `dcff8afe`（`apps/ora-node` 的
`model_proxy`）。改为 `implemented` 时按 cloud `7a4e0203`（cloud#377 的 head）核对。核心测试用例见
[模型接入用例](../../../test-cases/cloud/model-proxy/in-process-model-proxy.md)。进行中请求的时限由后续决策
[长请求的空闲超时与总上限](20261113-in-flight-model-calls-bounded-by-idle-and-total-limits.md)规定，它回答了本文原先
“未解决的问题”中的长请求一条。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`。desktop 的 Node 不改。
- **不做数据迁移**：v1 的个人模型连接、密文、运行绑定和用量记录都不迁移。

## 决策

### D1：模型连接是部署级的，来自环境变量，Key 不入库

- **配置**：部署的环境变量给出上游地址、Key 和模型名。`openai-completions` 和 `anthropic-messages` 两种协议各至多
  一个上游、一个模型；Anthropic 协议的 Key 可以用 `x-api-key` 或 `Authorization: Bearer` 送出。一组里缺任何一项，
  Cloud 拒绝启动。
- **地址**必须是 `https`，不带用户信息、查询串和片段。上游可以是模型供应商，也可以是企业自己的模型网关。
- **共用**：整个部署一份，所有租户、项目和用户都能用。
- **Key 的位置**：只在环境变量和 Cloud 进程的内存里。不写进 PostgreSQL，不出现在 API 应答、日志和下发给 Node 的
  任何消息里。模型目录接口只返回标识和显示名，显示名就是配置的模型名。
- **修改**：改环境变量后重启 Cloud。
- **没有个人和团队连接**：用户不能自己添加模型连接或 Key。是否要加，由 circus #809 决定。

为什么是部署级：这是现有的做法，不需要连接管理界面和 Key 的加密存储。代价：用量不能按个人的 Key 隔离，一个项目可以
用掉整个部署的上游额度。

为什么 Key 可以进 Cloud 进程：v1 把解密单独放在 model-gateway，代价是多一个服务、三个 TLS 监听和一个要与数据库一起
备份的主密钥卷。A1 已经接受这个泄露面。

### D2：代理和授权接口由每个项目的本机服务提供

- Cloud 为每个项目在本机回环地址上提供一份服务，包含授权接口（`/internal/v1/model-grants`）和两条代理路径
  （`/runtime/openai/v1/chat/completions`、`/runtime/anthropic/v1/messages`）。其他路径和方法一律拒绝。
- Node 用这份服务签发给它的客户端证书调用授权接口；Agent 用临时令牌调用代理。
- 证书和它的 CA 不能让运行超过 24 小时的项目失效（A1 D2，circus #1074）。
- 一个项目的服务只认自己签发的证书，所以一个项目的 Node 申请不到另一个项目的授权。

### D3：Node 为每个 Agent 会话申请临时令牌

- **先登记，再申请**：Cloud 在让 Node 启动一个 Agent 会话之前，先在进程内记下“这个会话的执行标识可以用这个模型绑定”。
- **申请**：请求体只有 `{bindingId, executionId}`，与登记的不一致就拒绝。
- **期限**：临时令牌 10 分钟有效；Node 在到期前续期，续期延长同一个令牌。同一个执行再次申请时，旧令牌作废。
- **吊销**：会话结束、执行中断或 Node 主动删除授权时，令牌立即失效，用它发起的进行中的请求同时被取消。
- **存放**：只在 Cloud 进程的内存里。Cloud 重启后全部失效；重启前的执行都已标为中断（A1 D3）。
- 令牌只在自己的协议路径上有效。

### D4：转发时强制使用冻结的模型

- 客户端不能选择上游地址、认证头和模型。Cloud 把请求体里的模型名改成这个会话冻结的那一个，换上上游的 Key，其余字段
  原样转发。
- Agent 的请求头和临时令牌都不转发；只有 `Anthropic-Version` 和 `Anthropic-Beta` 透传。
- 成功的应答边收边转。上游的非成功应答不转给 Agent，只返回固定的错误码。
- 不重试，不跟随重定向，不使用环境里的代理设置。

### D5：第一版不做的

- **用量计量不是本文的承诺。**v2-server 现有的请求记录（对话和任务的 Agent 会话）保持现状，可以继续用，但范围、
  字段和读取方式都不受本文约束。
- **限流、配额和预算。**
- **个人或团队的模型连接**（#809）。
- **多个上游、多个模型、不重启更换 Key、更多协议。**

## 不变量

1. 上游的 Key 只出现在部署的环境变量和 Cloud 进程的内存里，不入库，不下发给 Node，不出现在 API 应答和日志里。
2. Cloud 只向部署配置的上游地址发模型请求。
3. 一个项目的 Node 申请不到另一个项目的会话的临时令牌。
4. 临时令牌只能用于它绑定的那个会话的模型绑定，转发时的模型一定是这个绑定的模型。
5. 会话结束或执行中断之后，临时令牌不能发起新请求，用它发起的进行中的请求已被取消。
6. Cloud 重启后，重启前签发的临时令牌全部无效。
7. 上游的错误应答正文不会转给 Agent；Cloud 不自动重试模型请求。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 保留独立的 model-gateway（#1023 的 O1） | Key 不进 Cloud 进程 | 多一个服务、三个监听和主密钥卷；#1043 结论 4 已否定 |
| Key 注入 Node，Agent 直连上游（O4） | 最简单，没有代理 | 违反 A1 D4 |
| 个人模型连接 | 额度按人隔离 | 要做连接管理、Key 加密存储和发起时的校验；第一版不需要（#809） |
| 部署配置文件，多上游，企业 CA（本文 2026-11-11 之前的版本） | 一个部署能配多个模型 | 第一版没有这个需求；需要时在本文之上追加 |
| 把用量计量和配额写进承诺 | 部署方能看到并限制消耗 | owner 定为不是第一版该做的事（D5） |
