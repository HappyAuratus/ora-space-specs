# 启动意图未登记时允许撤回；已登记的未知执行只请求结束并保留对账责任

Cloud 区分首条提问与启动意图、派发登记、Node 受理和真实记录。未登记的启动意图遇到结束、明确能力拒绝或超时，可原子撤回并声明清理；已登记且尚无启动记录的执行，超时只进入带安全原因的结束等待，保留成果与资源责任。

本文为 `proposed`，尚待 owner 审阅。继承 [IssueRun 根决策](0-agent-run-in-disposable-isolated-workspace.md) 和前序 [续接提案](20261010-resume-run-from-latest-issue-revision.md)，补充根 D3/D6 的启动缺口；续接提案的 Revision 选择与恢复规则不改。Thread 继承 [根决策](../thread/0-durable-agent-thread-with-user-turns.md) 与 [个人模型输入权限](../thread/20261010-personal-model-initiator-controls-input.md)。控制面仍遵循 [派发前登记与同事务接缝](../controller-integration/20260928-agent-run-executions-thread-and-upload-grants.md)。

## 继承与修改

| 前序约定 | 本文处理 |
|---|---|
| 一个 Run 一个运行 Workspace、派发前登记、冻结输入、先接管再 ACK | 继承 |
| `pending` 与首条 prompt 的声明 | 明确它不证明 Node 受理，清理边界以派发登记为准 |
| 普通 end 为 `202/ending` 的请求 | 继承，终结由后续周期对账完成 |
| Thread `ended` 来自会话终态 | 增加未登记意图的 Cloud 撤回终态；不伪造 Node 结果、历史或收据 |
| 已登记执行的交付与 Workspace 释放 | 继承，超时不跳过这些责任 |

## 决策

### D1：未登记是受事务保护的执行不存在证据

撤回必须与派发登记使用同一事务锁，确认没有 Agent 执行登记、已绑定 work 或已投递命令。控制面撤回未派发 work/命令；业务层结算 Thread、丢弃未执行的 queued 轮次并声明 owned delete。任何一步失败全部回滚。迟到派发不能复活已撤回输入。

普通结束或取消在此边界结算为 `cancelled`，`deliveryState=skipped`，不声明 Agent 成功。明确模型代理能力拒绝使用 `model_proxy_unavailable`，未派发启动超时使用 `agent_start_failed`，两者结算为 `failed`。主 Workspace、历史 Revision 和其他运行不受影响；Project 忙时沿用已有清理重试。

### D2：预算由数据库时间判断，输入不续期

预算起点拟统一为运行 Workspace 的 `create_workspace` 成功时间，声明和派发登记不重置预算，用户追加轮次、重放和控制连接恢复也不续期。Workspace 的 clone、插件下载/安装在 provisioning 阶段完成，`finishPluginGate` 完成后才打开 admission 并进入 starting，因此它们不计入本段启动等待，不能用下载耗时为 starting 的 30 分钟等待辩护。

普通新启动推荐默认候选 2 分钟。Controller 的领取兜底周期为 10 秒，部署中 Node 内的 Agent ready 等待为 30 秒；以下稳定时钟实测中，ready 到首条 Node 记录的最大值为 13.059 秒，2 分钟约有 9.2 倍于本组最大值的观测余量。它是含调度与启动余量的评审候选，尚未批准为部署默认值；不再以 provisioning 中的插件安装为 starting 等待 30 分钟辩护。

恢复 prior Revision 的下载、校验和 Git restore 发生在登记之后，推荐 Cloud 恢复启动窗口候选 6 分钟，仍从同一 Workspace ready 起点计算，覆盖恢复和之后的 Agent 启动，不能理解为先等普通 2 分钟、再额外等 6 分钟。缺模型代理的已初始化当前 Node 是明确拒绝证据，可立即处理；未知或暂时断开的实例不能被当作明确拒绝。

**恢复窗口的成立条件**：现有 Node `RestorePolicy::DEFAULT.deadline=5m` 包住授权等待、下载及大小/SHA-256 校验；之后的 bundle 结构检查/Git 阶段没有共享这个截止时间，Git 的远程补基础提交还受独立 network timeout 控制。因此 6 分钟不能声称已大于现有 Node 的“整体恢复上限”。推荐为完整恢复（授权、下载、校验、Git）补一个可停止并确认结束的 5 分钟整体预算，再为 Cloud 的 6 分钟窗口留下声明、登记、启动与扫描余量；Node 的该项契约与取消责任须在实施前同步审阅。若保留现有 Node 边界，Cloud 的 6 分钟只能是发起 D3 结束等待的策略上限，实际恢复和资源责任继续按 D3/D4 处理，不能据此宣称已物理停止。

#### 稳定时钟分段证据与适用范围

### D3：已登记的未知执行进入可恢复的结束等待

超时后 Thread 为 `ending`，公开读取给出安全 `failureCode=agent_start_failed`，停止接受新轮次。已有用户结束原因保留；没有结束请求时声明一个策略取消。工作、登记、未结算轮次、Workspace 和冻结输入保留，Controller 继续按稳定身份对账与投递结束。

策略超时取消最终经 Node 终态和交付结算后，业务结果为 `failed`；此前已接受的用户结束/取消保持原结果。真实终态之前不能伪造 Node 历史、收据或 Revision，也不能删除 Workspace。迟到的真实记录仍按既有接管顺序保存，终态只结算一次。

### D4：永久失联必须有业务收尾边界，物理释放需要独立证据

只有 D3 不足以形成有界结算：Fleet 的连接观测和 Node 超过 30 秒未心跳只证明当前不可达，并不证明原实例或一个迟到 ensure 已经停止；现有 `DeliveryUnreachableAfter` 只扫描 delivering/releasing，也不会自动收尾 starting/ending。不能直接借它宣称此路径已被覆盖。

本文提出一个独立的结束确认窗口，候选 5 分钟，从 Cloud 首次持久化启动超时的 ending 等待开始，由数据库时间判断，重放和迟到记录不续期。窗口内继续投递既有结束请求并接管真实证据。窗口耗尽后的收尾须由 owner 在下列边界中确认；当前实现原型尚未把任一候选当成批准规则：

| 候选 | 有界承诺与责任 | 代价 |
|---|---|---|
| 有界放弃业务运行，保留残留资源 | Run 以 failed/done 关闭业务等待，明确标记结果未知、交付未确认与残留 Workspace；Node 结果、work、冻结输入与登记原样保留。禁止再次派发新启动/用户轮次，迟到真实终态可保存但不能复活该 Run；残留由运维对账清理 | ready 后普通启动的业务等待候选最多 2+5 分钟，恢复候选最多 6+5 分钟，另加可用扫描延迟；provisioning 与物理资源释放有各自责任，不包含在该承诺中。需要残留资源可见与运维责任，与 IssueRun D8 的如实保留残留原则一致；仍是新增入口，需新批准 |
| 确认强停后再结算和删除 | 使用稳定隔离身份，完成实例终止与 late ensure fencing 的真实确认后，结算失败并沿 owned delete 清理 | 可自动回收，但要扩展管理强停的授权边界，不能伪造既有 `impactConfirmed`；Substrate 永久不可用时也不能承诺固定时刻物理释放，仍需有界放弃的兜底 |

建议采用第一项作为业务等待上限，第二项作为后续经授权的资源回收路径。批准时须一并固定残留责任、迟到事件的接管和禁止重新派发的规则，不能只改 phase 或把未知结果伪装成 Node 取消成功。确实停止的证明可以缩短等待；断线或心跳超时不能替代它。D2 的正常 end 实测不证明永久失联的 5 分钟上限；本轮没有注入永久失联或 Substrate 永久不可用，最终收尾仍需独立故障验证。

## 不变量

1. 登记与撤回只能有一方获得未派发输入的后续责任。
2. 请求超时、缺回复、Controller 断开均不证明已登记执行未发生。
3. 原始模型 Key、临时授权与供应商正文不进入失败原因或证据。
4. 未登记撤回的清理声明与业务终态原子提交；已登记结果继续沿用交付/清理链路。
5. 用户、租户、冻结配置和既有结束原因不被恢复流程扩大或替换。

## 替代方案与代价

| 方案 | 取舍 |
|---|---|
| 所有 pending 继续等待 Node | 简单，但明确无法派发的输入与结束请求可永久悬挂 |
| 把所有 pending 当作未执行并删除 | 收尾快，但会丢失已登记、响应未知的实际执行与成果 |
| 结束前仍启动完整 Agent | 可复用原终态链路，但可能触发用户已请求停止的模型/工具操作，能力拒绝仍无解 |
| 未登记撤回，已登记保留对账 | 增加状态证据和预算策略；保留已接受外部效应的责任，作为本文方案 |

## 未决与落地

owner 需确认普通结束未登记时的 `cancelled/skipped`、D2 的预算起点与新启动/恢复窗口及 Node 整体恢复截止的取舍，以及 D4 的业务放弃与残留责任。D2 已有稳定时钟的普通栈分段样本，尚不能替代高负载/低带宽与失联故障证据。管理强停的授权扩展、全局 ClaimWork 公平性、公开取消 API 和新结算 SSE 不在本文范围。

批准后再维护对应核心用例；直接验证须覆盖未派发结束、能力拒绝、超时、登记与结束竞态、迟到登记/终态、重复、回滚、Project 忙、正常多轮、冻结输入和租户隔离。随后核验真实 Controller/Node 链路，并按真实交付证据决定实施状态。现有迁移与历史执行结果不重写。
