# 同一任务的 Agent 执行串行，成果保存与释放确认后才交接

Cloud 在任务层持久化 Agent 输入顺序与交接屏障，保证同一 Issue 至多一个 Agent 执行占用。
切换 Agent 后的消息先等待，前一轮及先前已接收消息完成、成果交付和释放确认后才启动下一位。

本提案等待 owner 决策。既有 Run、Revision 和 Workspace 的身份及终态不改写；新增调度约束覆盖所有
Agent 启动入口。Workflow、Team 内部调度和多 Agent 并行成果合并不在本提案范围。

## D1：串行约束由数据库状态决定

排队消息按任务内接收顺序处理，同一 Agent 的消息可复用当前合法 Thread。首个改变 Agent/发起者的
消息建立交接屏障；后续消息即使又指定原 Agent，也不能越过屏障插入旧 Thread。手动创建 Run、旧
评论 targets 入口与新对话入口都经过同一准入与派发约束，多窗口和多 Cloud 实例不能绕过。

派发在短事务中重新检查任务占用并获取资格。已在执行、保存或释放中的 Run 仍持有占用，不能仅以
thread_state=ended 或会话进程退出作为释放证据。队列和屏障持久化，重启后按同一顺序恢复。

## D2：交接等待完成，不隐式取消工作

仅切换输入框目标无副作用。发送后，前一执行完成当前轮和此前已接收消息，达到 idle 安全点再请求
结束。结束确认后走原有交付/释放路径；保存成功或确认无新改动且释放完成后，下一运行冻结最新可用
成果与上下文并启动。用户继续补充消息不无限延长已建立的交接屏障。

当前会话不是新消息发起者可结束的会话时，不代替其用户强行结束；待合法结束后交接。界面明确显示
正在等待哪个执行和原因。无效目标、配置与权限变更不能自动替换为另一 Agent。

## D3：停止与失败形成可恢复的暂停点

手动停止保留既有取消语义，尝试交付当前成果，后续队列暂停。Agent 失败、启动失败、交付失败和释放
未确认也阻止自动交接。消息保持可查，用户可取消未执行消息，或在问题解决后显式恢复队列。

恢复操作必须重新校验权限、配置、前一执行的资源状态与可用成果；无法确认最新成果时不得自动退回
更早 Revision。明确选择放弃未保存成果属于另一个显式动作，必须说明丢失范围，不能作为重试默认值。

## D4：升级不任意终止已有并发运行

新增表和约束以迁移实现。升级时已存在的并发执行保持原身份并允许完成，但该任务禁止派发新执行，
直到所有旧占用结束并确认成果基线。不能按最后更新时间静默选一个分叉覆盖另一个。

## 不变量

1. 新准入的 Agent 执行不能与同任务仍占用资源的运行并行启动。
2. 已建立交接屏障之后的消息不能越序进入旧 Thread。
3. 成果登记和释放确认都成立后，交接才获得派发资格。
4. 超时、浏览器断线和重试次数不构成释放成功证据。
5. 失败暂停保留待执行消息，不自动重放被取消或已执行的输入。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 仅禁用前端按钮 | 简单，但多个窗口和旧 API 可同时派发。 |
| 新消息立即取消旧执行 | 切换快，但破坏用户已经请求的工作及保存边界。 |
| 每个 Agent 单独串行 | 允许多 Agent 并行，仍会产生同任务 Revision 分叉。 |
| 长事务等待交付 | 易表达，但跨进程 I/O 持有数据库锁，破坏现有事务边界。 |

## 风险与落地

先实现队列、占用与所有入口的准入，再接入界面；功能启用前验证双窗口、多实例、重启、旧并发数据、
保存失败和权限变化。需要真实 PostgreSQL 的竞争测试与真实 Agent 的交接验收，单纯按钮测试不足。
本提案不改变原生 Agent 执行环境的资源所有权，也不负责并行分支合并。
