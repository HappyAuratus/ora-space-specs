# 任务统一排队 Agent 与工作流，保存并释放后交接代码和有界历史

本提案把同一任务的 Agent 与工作流调用放进一个持久化接受顺序，数据库保证至多一个执行占用。选择工作流只
打开表单，Confirm 锁定版本与输入并排队；前序执行、成果核验和资源释放完成后自动启动下一项。Agent 仍拥有
自己的 Thread，WorkflowRun 仍拥有图执行，两者通过任务层交接代码和有来源的文字结果。

本文为 `proposed`，不宣称现有部署已经支持混合接力。涉及任务协作、队列与读模型、两个调度器、上下文及默认
对话 UI；成果底座依赖[WorkflowRun 交付提案](../workflow/20261025-run-owned-git-delivery-and-history.md)。
历史记录身份、已发布快照、已登记 Revision 和个人模型授权都是兼容边界，不以更换界面重解释已有事实。

## 背景与范围

用户希望一次提交“Agent 实现 → 工作流检查 → Agent 汇总”，而不必人为协调当前运行、代码保存和释放。
已有 Agent 队列只覆盖 Agent，工作流独立执行；同屏显示两者不能提供混合顺序和成果传递保证。

覆盖所有关联任务的 Agent/Workflow 启动入口，包括旧任务动态、手动运行、Confirm 与任务对话。没有任务关联的
独立 WorkflowRun 不进入任务队列；Team、跨任务并行合并、自动解析一条文本里的多个 @ 和自动生成任务 DAG 均不在范围。
一个任务内串行，不同任务可以并行；工作流内部执行方式仍由 workflow 领域拥有。

## D1：任务执行请求是接受顺序，运行仍是执行身份

任务执行请求表示一次已经明确提交的执行意图，包含类型化目标、发起者、任务内单调序号和原始来源引用。
它可以指向 Agent 消息、手动运行或工作流 interaction，不复制原始消息为可独立编辑的第二份事实。
普通评论与未确认表单不进入执行队列。序号在接受事务中分配，不用客户端时间、目标类型或 Run 创建时间排序。

工作流 Confirm 在同一事务中绑定执行请求、interaction、调用 IssueRun 和 WorkflowRun；该 WorkflowRun 在等待时
只是已接受的执行身份，不能提前推进纯计算节点、解析当前上下文或建立工作区。Agent 消息仍可在派发时物化 Run，
同 Agent 同发起者的合法消息可复用当前 Thread，多条消息对应同一 Run 不制造额外占用。

两个执行器共用任务级准入和持久化占用，数据库保证每个任务至多一位占用者。队头的顺序检查、暂停检查、占用
获取及请求关联在短事务中完成；后续工作区建立和外部调用不持有事务。失联不是释放证据，占用不能只靠租约
到期移交。领取失败的重放沿用同一请求和运行身份，不产生另一执行。

工作流自身的 run 排他事务与任务事务须采用一致的锁顺序；不能在持有工作流锁时等待任务锁、另一条路径反向
获取造成死锁。扫描只是候选读取，所有资格都在写事务中复查；有界扫描必须跨过等待/暂停任务，避免队头一组
工作流阻塞其他任务。直接 WorkflowRun 没有任务占用，仍受工作流自身排他控制。

## D2：所有入口共享屏障，同目标后续输入不能越队

新任务输入接受到队尾；老的 Thread 追加只有在同发起者、授权有效且没有较早异目标/异发起者请求时才可复用。
一个 Workflow 请求就是交接屏障，不需要先执行到 Agent 节点才产生约束。屏障之前已接受的 Agent 消息先处理，
屏障之后即使又发给原 Agent 也只能等待新运行。手动入口和旧任务动态不能绕过队列。

Agent 达到既有安全点且调用者有合法结束资格时，正常结束当前会话并交付；不以“切换目标”取消当前工作。
没有结束权限时等待合法结束，不能借统一队列扩大授权。工作流获得占用后直到整图结束、交付和释放都结算才让位。
`retrying` 和 `awaiting_input` 仍占用；后续请求不能暗中替代工作流的人工输入或强行结束其节点。

同一目标可以接受多个不同请求，按顺序执行；去重依据请求幂等身份，而非目标名字或相同正文。
为此，任务队列替代该范围内旧的相同 executor 待执行唯一限制；独立/不受此队列管理的运行继续沿用原准入规则。
取消一个未开始的请求只取消该项，后续相对顺序保持不变，已创建的调用实体明确结算为未启动取消。

## D3：确认锁定意图，派发锁定交接事实

| 时点 | 冻结内容 | 允许再变化的内容 |
|---|---|---|
| Agent 发送/Workflow Confirm 接受 | 发起者、类型化目标、正文或表单值、来源；Workflow 快照、插件版本、槽位绑定与 Project 身份 | 前序尚未产出的代码和历史 |
| 获得任务占用、实际准备执行 | 最新可接续 Revision、已完成前序的有界历史及范围/缺失标记、任务材料快照 | 执行及交付结果 |
| 交付开始 | 本次成果与归档声明、交付位置 | 各次尝试的核验结果；不再增加执行写入者 |

等待期间发布新版本或修改活稿不能改写已确认的表单和运行。派发前重新验证成员、目标、Project、冻结插件及
发起者模型绑定的有效性；失效就留下明确失败/阻塞，不自动替换模型、槽位、版本或发起者。用户修复配置后，
若原冻结绑定仍无效，需要取消并重新确认新请求；“重试”不能悄悄重绑个人模型。

确认与派发之间代码基线可能变化，这是有意接受的差异，不是漏冻结。用户确认时看到的表单值、已发布快照、
插件与发起者就是实际执行的那一份，按设计会变的只有派发时才成立的交接事实：代码基线、历史范围与任务
材料快照。按任务队列的定义，接力基线是“轮到执行时同任务最近一份已核验成果”。若把基线也定在确认时刻，
排队中的后继只能看到前序尚未完成的旧状态，用户为了接续必须先猜前序何时结束；把基线定在启动时刻，后继
得到的正是前序真实保存的结果，这也正是选择自动排队时接受的语义。可接受性取决于三点：基线只沿同任务已
验证的保存向前移动，不回退，也不由其他任务或发起者提供；快照、表单值、插件、槽位、发起者与模型绑定都
不被悄悄替换；卡片与详情显示实际接续的 Revision、历史范围与任务材料，并与派发事实一致。需要精确基线的
用户应在任务空闲时确认，或取消尚未启动的请求后按新的任务状态重新确认。

Confirm 接受需要持久化幂等身份，覆盖创建 interaction 与确认的响应丢失窗口；单靠组件内的 ref 无法跨刷新去重。
同幂等键同请求返回原身份，不同载荷拒绝。interaction 已确认的再次提交返回既有运行引用并说明已确认，不重复
执行，也不把后来的表单值覆盖到旧输入。失败或结果未知时 UI 先按稳定请求身份对账，不猜成功或另建一次调用。

## D4：代码基线与文字历史分开恢复

任务只自动接力同一 Project/仓库中的已核验成果。选择任务前序时同时接受 Agent 和 WorkflowRun 的 Revision，
沿任务顺序使用最近安全成果；纯计算、没有工作区的步骤保留现有代码基线。后继在自己的新 Workspace 恢复，
不继承旧 Thread、沙盒或凭据。第一步没有前序成果时按项目既有快照初始化。

如果最近一步有未保存成果、核验失败、不可读取前序或尚未释放，必须阻塞；不能跳过它自动选择更旧 Revision。
任务 Project/仓库在排队期间变化时原请求失败且保留身份，不自动迁移队列。界面说明自动接力的任务基线，
表单中的启动字段不能偷偷改变它；作者声明的同名业务变量仍按快照 schema 处理，不能被当成基础设施授权。

文字交接使用一个有来源的历史投影：Agent 使用已有用户/助手可见正文；工作流使用最终 output 节点输出和该
请求的显式任务输入。一个工作流结果算一个历史单元，多 output 按冻结图中的稳定节点顺序表示；没有最终
output 时说明“没有最终输出”，不自行总结内部节点。失败/取消结果只在显式恢复后作为带状态的历史事实进入，
不能写成成功结论。来源为 Run、节点/轮次及活动引用，不因同时出现在评论和卡片重复计入。

沿用最近 20 个历史单元和最多 64 KiB UTF-8/序列化正文预算：由近到远选取，按原顺序交付，超大单元在字符
边界截断并标记；当前显式输入仍有独立限制。前序不可读则标记缺失，不借别人的凭据读取；不能声称恢复完整历史。
节点 prompt 与此上下文分别表达；上下文作为外部任务材料进入 Agent 初始提示，不改表单值或工作流变量 schema。
不自动传原始工具记录、思考、系统提示或模型秘密，也不另调用模型生成摘要。

## D5：失败暂停、停止和恢复按真实执行者处理

任务读模型区分等待、执行、保存、释放、需要处理及终结；状态来源是各领域的权威事实，不用一个 `completed`
字段代替三个结论。停止当前执行先记录任务暂停，再路由到 Agent/Workflow 的取消路径；不能仅取消卡片显示。
失败、取消、交付 skipped/failed、释放 abandoned/未知保持屏障，前端断线或服务重启不能清除暂停。

恢复者必须有管理该阻塞运行及任务的资格；重新验证前序成果、资源状态和队头发起者授权。确认失败结果可继续
仅表示恢复后续队列，不重跑终态工作流，不把它的 resume 501 改成成功。重新执行工作流需要新的显式 Confirm。
放弃未保存成果必须单独说明范围、由有资格者明确授权，并在保存基线及真实释放可验证后才允许继续。

一个较晚请求或另一成员无权确认的运行不能被拿来跳过较早失败。取消等待项由该请求发起者或已有授权的管理员
执行，不扩大运行停止和个人模型授权。UI 显示阻塞原因和下一可执行动作，而不是持续显示无解释的“排队中”。

## D6：默认对话整合类型化入口与运行记录

默认输入区“发送给”和 @ 菜单区分 Agent 与工作流。一次选择一个目标，正文里的 @ 只是文本。Agent 沿用
`agentId + body`；工作流走已有表单/Review/Confirm，选中未发布、失效或不可用目标时给出可处理提示。
取消表单不执行；切换目标保留未发送的 Agent 草稿，不将它悄悄提交为工作流变量。

对话读取新增类型化执行队列投影；原 Agent 消息保持原义，不给工作流伪造 agentId 或 Thread。
工作流卡片显示冻结版本、等待原因、实际接续的 Revision 与历史范围、执行/交付/释放状态、最终输出和
详情入口。稳定定位以调用 IssueRun 和 WorkflowRun 为依据，刷新、重入和从执行记录进入都找到同次运行；
授权拒绝后清除旧可见内容。历史浏览不会改变当前输入目标或停止对象，新结果不会强行切走用户正在看的
旧运行。

仅评论、旧任务动态表单、Agent 会话引用及既有停止/恢复入口保留；旧入口创建的任务运行也必须遵守新队列。
工作流内部日志继续在运行详情读取，不将原始工具更新塞进任务 Timeline。运行中及排队期间刷新状态，终结后
停止无用轮询，权限撤销后不继续请求旧租户资源。

## 不变量

1. 同任务所有 Agent/Workflow 入口按同一接受顺序仲裁，至多一个执行占用。
2. 已确认工作流的快照、输入、发起者不因排队、发布或重试改变。
3. 前序执行、成果与资源事实满足交接条件之后，后继才取得启动资格。
4. 任务历史和代码成果各有来源与独立恢复证据，不能互相替代。
5. 失败暂停跨重启持久化；停止、目标切换和取消等待项均不隐式丢弃成果。
6. 一个显式请求最多一次初始执行，重复确认与失去响应不会制造第二个运行。
7. 工作流保持自己的运行身份，Agent 输入权限不会被卡片整合扩大。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 仅在前端等待 | 改动小，但多窗口、旧接口、服务重启和两个调度器能绕过 |
| 对两个调度器分别检查对方状态 | 不引入队列，但无法原子处理同时领取与已接受顺序，检查后派发仍竞争 |
| 把工作流伪装成一个 Agent | 可复用消息表，却把图执行身份和 Thread 混淆，模型授权与详情路由错误 |
| 提交时就冻结前序成果和历史 | 输入完全静态，但排队中的后继看不到尚未完成的前序产物 |
| 轮到工作流时再次 Confirm | 用户可再检查，但破坏已明确确认后的连续接力；等待后的基线语义由 D3 说明，不在启动前二次打断 |
| 运行状态终结即可启动后继 | 降低等待，但成果未核验、旧工作区仍可能写入，不能安全接力 |

## 兼容、风险与落地

新增持久化执行请求与唯一任务占用约束，保留既有 Agent 消息 ID、seq、Thread、interaction、Run 和 Revision。
统一队列是执行顺序唯一权威；旧消息等待状态是同事务维护的兼容投影，不能让两套 worker 各自派发同一请求。
冻结请求与运行引用、跨类型暂停、取消和恢复需同步 OpenAPI、前端生成物及接口测试。

采用排空升级：先停止新准入，完成或由有权用户明确取消待执行请求，处置未解决的交付/释放后备份并升级。
不自动取消、删除、重放旧请求，不给已结束历史编造新队列序号；新队列只承载升级后接受的意图。
升级后旧版本调度进程不得继续工作。发现旧在途/残留时拒绝启用新队列，不能以启动成功掩盖未迁移的占用。

落地依次为成果底座、统一队列与全入口屏障、上下文与默认对话，最后在真实多实例栈验证混合接力与故障。
每阶段不能单独宣称已实现完整接力。验收草案见[混合任务交接](../../../test-cases/cloud/issue-run/mixed-task-handoffs.md)。
全文不授权跨任务自动合并，不改变工作流图内部节点调度和失败运行 resume 的已有边界。
