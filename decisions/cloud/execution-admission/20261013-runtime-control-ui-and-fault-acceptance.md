# 运行时控制的前端交互与联合故障验收独立交付

独占、强停和运行时使用权限的后端分别按已实现承诺落档；本 ADR 承接三处前端交互及五份后端
决策尚未覆盖的联合故障矩阵。它保持 approved，批准的是待交付的 UI 与直接验证义务，不是
宣告多人控制产品体验及所有故障路径已经完成。

本决策涉及 Cloud frontend、Cloud/Controller/Node 与 Sandbox Server 的联合验收，不改变
后端角色、创建者、控制代次、稳定执行身份、真实终止和持久数据边界。不新增共享授权、自动夺锁、
实时共同编辑或云端文件/PTY 的隐含开放义务。核心用例见
[UI 与故障验收](../../../test-cases/cloud/execution-admission/runtime-control-ui-and-fault-acceptance.md)。

## 决策

### D1：独占 UI 显式获取，续期与恢复跟随服务端事实

只读查看不隐式获取操作权。进入操作模式前请求 Cloud 分配会话，acquiring 时不能显示已获得
写资格；held 后按 20 秒续期契约维持 60 秒资格。第二页面不因同用户而复用第一页面绑定。

界面区分无使用权限、被占用、获取中、持有中、收尾中和待对账；按钮和输入依据最新服务响应
控制。释放不立即承诺别人可接管，必须等待服务端结清旧责任。网络断开立即停止新的发送和
自动提交；恢复先重查绑定及可用操作，不自动重放离线内容、旧 session 或历史成功响应。
错误提示应帮助用户选择等待、释放或联系管理员，不能建议用新 ID 绕过占用。

### D2：强停 UI 明确影响，但服务端仍独立授权

管理员发起强停前确认目标运行时及影响：中断该目标所有成员/Agent 工作，可能丢失未保存数据，
已保存代码保留，其它运行时不受本次请求影响。必须提供非空原因，提交当前 version、
impactConfirmed 与本次稳定幂等键；普通 stop 不隐式升级成强停。

接受后显示已请求/终止中，而非已停止。响应未知时查询原意图；不换幂等键制造第二次责任，
页面关闭不撤销终止。只有服务端确认真实终止后才能显示 stopped，强停不附带启动、接管或删卷。
普通成员及跨租户管理员无该入口，直接调用仍由后端拒绝。

### D3：权限 UI 展示安全概况，以创建者及当前管理员区分内容能力

提供“我的运行时”和管理员全部运行时视图，展示创建者、占用及服务计算的可用能力。其它成员
的共享概况不能附任务文本、命令、输出、路径或凭据引用；无使用权与有权但占用明确区分。
main 不因名称变成公共内容入口，unknown 创建者只向当前管理员开放使用。

控件隐藏/禁用不构成授权；详情、直接链接、重试及事件都必须经当前服务事实核验。停用或
管理员降级后清除当前受限视图及交互状态。不引入成员共享授权表、授予/撤销页面或创建者转让。

### D4：联合故障矩阵要求真正跨过所声称的边界

| 风险边界 | 必须补的直接验收 | 对应稳定用例 |
| --- | --- | --- |
| 多实例与页面独占 | 两个 Cloud 实例/独立连接同步获取、续期到期竞争，核对唯一持有者、幂等历史与零重复副作用 | exclusive-runtime-control |
| 派发/撤回与未知接受 | 在 Cloud–Controller–Node 的接受前后丢响应、分区及重启；未知责任阻止交接，稳定 ID 不重复执行 | fenced-runtime-control-delivery |
| 旧消息与重连 | 真正排队的旧字节、旧连接和重启节点在交接后尝试文件/Git/进程动作，不能新写 | fenced-runtime-control-delivery |
| 管理身份与工作负载 | 失效证书、错租户/实例/用途、生产轮换及工作负载直接伪造管理入口；私钥/日志/端点拒绝 | fenced-runtime-control-delivery |
| 强停与迟到 ensure | 真实 ensure/terminate 并发及响应丢失、协调器崩溃；旧 sandbox 不能重建可写，同项目其它目标不受影响 | safe-stop-and-administrative-force-stop |
| 持久数据与未知终止 | Node 不可达时禁止交接/启动/删卷；恢复后停止、强停、重启、显式删除分别核对代码、进程、卷和审计 | safe-stop-and-administrative-force-stop |
| 历史升级与回滚 | 软删除/在途 execution/effect 完整历史快照、新旧组件组合、旧旁路拒绝与真实部署回滚；不猜 creator 或丢证据 | runtime-workspace-use-permissions 与 fenced-runtime-control-delivery |
| 插件与最新期望 | 真实 Node 的安装/移除/下载、未知旧结果、期望改变、目标删除及维护/用户竞争；旧结果不覆盖新版本 | admin-selection-and-idle-maintenance |

下层单元测试、注入 acknowledgement、模拟 Node 或持久表本身只证明对应局部义务。要求真实
Git/进程/容器时必须核对这些对象；不得把运行脚本输出 passed 当成未检查边界的证据。

### D5：先交付 UI，再按故障边界推进验收

三处 UI 可分别提交和验证，每项配生成客户端、角色/状态/版本测试及所属模块中英文文档。
随后逐行完成故障矩阵，每条保存明确源码基线、同资源定位、注入点、允许结果和恢复/清理结果。
证据中不保留 Key、Cookie、令牌或私钥。

只有三处 UI 和表中尚缺义务都有直接证据时，本 ADR 才能改为 implemented；不能借已实现后端
状态推导完成。新发现的产品能力边界另立后续决策，不在验收过程中放宽既有安全约束。

## 不变量与取舍

1. UI 不建立另一份权限/占用权威，重连不复活旧资格。
2. 强停接受与真实终止明确区分，不扩大目标或自动删数据。
3. 共享概况不泄漏受限内容，控件状态不能代替服务授权。
4. 未知执行/终止继续保留责任，验证不能以超时推断完成。
5. 每个 Covered 结论对应能直接证伪该义务的边界证据。

拆出交互与矩阵能让已实现后端形成清晰契约，但需要单独维护验收归属；通过双向 ADR 链接及
原稳定核心标题保留追溯关系。代价是后端 implemented 不再等同整个多人控制产品体验完成。
