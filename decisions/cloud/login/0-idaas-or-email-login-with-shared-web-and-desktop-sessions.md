# 登录与会话：部署版只走华为 IDaaS、按工号邀请，开发版用无密码邮箱，由 `V2_LOGIN` 二选一；网页和 desktop 两种会话落在同一个账号上；取代 v1 Gateway 的登录与 desktop 会话

Cloud 进程自己处理登录，没有独立的 Gateway。同一个程序有两种登录方式，由启动配置 `V2_LOGIN` 二选一：`idaas` 是部署版
（内网演示和正式部署），只能用华为 IDaaS 登录，没有邮箱登录的入口；`email` 是开发版（公网演示），沿用现在的无密码
邮箱登录。IDaaS 账号以 IDaaS 的 `uuid` 认人，以工号对上邀请：任何员工都能登录并自动得到账号，但被管理员按工号邀请
之前看不到任何团队。网页用 Cookie 会话；desktop 经系统浏览器和本机回环地址登录，拿到一个 30 天不用就过期的令牌。
两种会话指向同一个账号，看到的团队、权限和数据完全一样。第一版不做的：其他登录提供方、会话轮换、和 IDaaS 同步离职、
desktop 的部署身份校验。

本 ADR 处于 `proposed`：等 owner 评审，评审通过后再补核心测试用例。它是领域 `cloud/login` 的根决策，前提是
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）。依据是 owner 2026-11-12
在 circus #1050、#1093 的结论（只接华为 IDaaS；开发版邮箱、部署版 IDaaS，同一程序靠配置切换；首次登录自动建账号、
被邀请后才看到团队；部署版按工号邀请；desktop 会话沿用 30 天不用即过期）。读取的代码版本为 cloud `0ca0a9a0`
（`v2-server/internal/server`、`internal/store`；v1 的 `internal/gateway/idaas`）、desktop `dcff8afe`。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/` 和 `frontend-v2/` 的登录页、邀请表单。desktop 一侧的实现由 circus #1084 承担。
- **不在本文**：desktop 本地怎么存令牌、断网和服务端错误时怎么处理、界面怎么显示连接状态，属于 desktop 的
  [Cloud 连接根决策](../../desktop/cloud-connection/0-host-owned-cloud-connection-and-session.md)，由 #1084 按本文的
  Cloud 一侧契约写后续 ADR（D6）。租户内的授权判定见 A1 D4。
- **不做数据迁移**：v1 Gateway 的账号、会话和身份别名不迁移。开发版现有的邮箱账号照旧可用；同一个库不在两种
  登录方式之间切换（D1）。
- 本文同时修改 A1 的三处，见“[对 A1 的修改](#对-a1-的修改)”。

## 决策

### D1：`V2_LOGIN` 二选一，两种方式不共存

- **配置**：`V2_LOGIN` 必填，取值 `email` 或 `idaas`；不填或填别的值，Cloud 拒绝启动。没有默认值，是为了不让一个
  忘了配置的内网部署对外开放无密码的邮箱登录。`task v2:demo` 显式设为 `email`。
- **`email`（开发版）**：现在的无密码邮箱登录，只给公网演示和本地开发用。规则不变：只有 `users.json` 预设或被邀请
  过的邮箱能登录，未知邮箱返回 `403 email_not_invited`，不建账号。
- **`idaas`（部署版）**：只接华为 IDaaS。邮箱登录的接口拒绝请求（`400 unknown_provider`），页面不显示邮箱输入框。
- **前端怎么知道**：`GET /auth/providers` 只返回当前的那一种，前端据此显示邮箱输入框或“使用华为账号登录”按钮。
- **不接其他提供方**：不接 GitHub，不做通用 OIDC。

为什么不共存：部署版开着邮箱登录，任何知道成员邮箱的人都能冒充他，因为邮箱登录没有密码。两种方式也各有一套认人
和邀请的规则（D3、D4），同时开放就要处理同一个人有两个账号、要不要合并。代价：一个库定了用哪种方式之后不能换，
要换只能重建库。第一次部署本来就从空库开始（A1 D5、circus #1051），这个代价现在不发生。

为什么是同一个程序：开发版和部署版只差登录方式和是否写入演示数据，分成两套构建会让演示环境测不到部署版的代码。

### D2：IDaaS 登录走授权码流程，Cloud 自己是机密客户端

- **配置**：`V2_PUBLIC_URL`（浏览器访问 Cloud 的公开地址，必须是 `https`）、`V2_IDAAS_BASE_URL`（默认
  `https://uniportal.huawei.com`，只能是 `https` 的 origin，不带路径）、`V2_IDAAS_CLIENT_ID`、`V2_IDAAS_CLIENT_SECRET`。
  显示名和工号取自 userinfo 的哪个字段、要申请哪些 scope，也是部署配置，默认值由 I2 #1052 实测后定（见 D3）。
  `V2_LOGIN=idaas` 时缺任何一项，Cloud 拒绝启动。
- **回调地址**固定为 `<V2_PUBLIC_URL>/auth/callback/huawei-idaas`，只从配置得出，不看请求头，必须和 IDaaS 上登记的
  完全一致。
- **流程**：
  1. 前端同源 `POST /auth/login`（`provider=huawei-idaas`，可选 `returnTo`）。Cloud 校验 `Origin` 等于
     `V2_PUBLIC_URL` 的 origin，生成随机 `state` 和登录尝试密钥，把尝试密钥放进只发往回调路径的 Cookie，返回 IDaaS
     的授权地址，由前端导航过去。
  2. IDaaS 回调后，Cloud 核对 Cookie 和 `state` 属于同一次尝试，然后用 `client_secret_post` 换 token，再用
     `access_token` 表单取 userinfo。不发 PKCE，不发 `display`。
  3. 按 D3 找到或建出账号，开网页会话（D5），重定向到规范化后的 `returnTo`。无论成功失败，都清掉登录尝试的 Cookie。
- **登录尝试只放在进程内存**，10 分钟过期，有数量上限。Cloud 重启后进行中的登录失效，用户重新点一次登录。
- **凭据只在请求内存里**：授权码、access token、client secret 和完整的 userinfo 不写库、不进日志、不回给浏览器；
  userinfo 里只留下 `uuid`、工号和显示名。
- **错误**：IDaaS 明确拒绝、OAuth `error` 或遗留的 `errorCode`、非法或超过 64 KiB 的响应、缺 `uuid`，返回
  `401 login_failed`；网络错误、超时、429 和 5xx 返回 `503 login_unavailable`。调用 IDaaS 有独立超时，不跟随重定向。

这些协议细节都继承自 v1 的 IDaaS 适配器，它们是对着 IDaaS 实测出来的：IDaaS 的示例把 client secret 写在查询串里，
会进访问日志；`client_secret_basic` 在应用按 post 登记时返回 `invalid_request`；`uuid` 的示例值带尾部空格。

为什么登录尝试不入库：v1 要入库，是因为 Gateway 有多个副本，回调可能落到另一个副本。Cloud 是一个进程（A1 D1），
放内存就够了。代价是重启时进行中的登录要重来，最多影响 10 分钟内点了登录的人。

`V2_PUBLIC_URL` 必须是 `https`，是 IDaaS 对回调地址的要求。TLS 由 Cloud 自己终止还是由前面的网关或反向代理终止，
不在本文，由第一次内网部署 circus #1059 定；无论哪种，Cloud 都只用配置里的公开地址，不信任转发头。

### D3：IDaaS 账号以 `uuid` 认人，工号只用来对上邀请

- **身份**：IDaaS 账号记为 `source=huawei-corp`、`subject=<uuid 去掉首尾空白>`。一个 `uuid` 只对应一个账号。
- **工号**：账号上记一个工号，在整个部署内唯一。每次 IDaaS 登录都用 userinfo 里的工号刷新它。工号不参与认人，
  只用来让管理员在这个人登录之前就能邀请他（D4）。
- **显示名**每次登录用 userinfo 刷新；取不到时，用工号，再不行用 `uuid`。
- **账号可以先于第一次登录存在**：管理员按工号邀请一个还没登录过的人时，Cloud 先建一个只有工号、还没有 `uuid` 的
  账号。这个人第一次登录时，Cloud 按工号找到它并补上 `uuid`。

登录时按下表决定用哪个账号（`U` 是本次的 `uuid`，`E` 是本次的工号）：

| 已有账号 | 结果 |
| --- | --- |
| 有账号的 `uuid` 是 `U` | 用它；它的工号改成 `E`，除非 `E` 已属于另一个账号，那样返回 `409 identity_conflict` |
| 没有 `uuid` 为 `U` 的账号，有工号为 `E`、还没有 `uuid` 的账号 | 用它，补上 `U` |
| 没有 `uuid` 为 `U` 的账号，工号为 `E` 的账号已有别的 `uuid` | `409 identity_conflict` |
| 都没有 | 新建账号，记下 `U` 和 `E` |
| userinfo 里没有工号 | 只按 `U` 找或建；这个账号没有工号，没人能邀请它，页面提示“账号缺少工号，请联系管理员” |

账号已删除或已停用，返回 `403`，不新建、不复活，和现在邮箱账号的规则一样。

为什么用 `uuid` 认人、不用工号：`uuid` 是 IDaaS 分配的稳定键，v1 一直用它。工号由人事系统分配，离职再入职等情况
可能变，用它认人会把两个人对成一个账号，或把一个人拆成两个。反过来，管理员能报出来的只有工号，不知道别人的
`uuid`，所以邀请只能按工号。

为什么冲突时拒绝、不自动合并：冲突说明两个账号都声称是同一个人，合并要搬动成员关系、小队和技能等数据，自动做
很可能搬错。冲突只会在罕见情况下出现（例如工号被重新分配，或者一个人登录时没拿到工号、之后又被按工号邀请）。
由管理员删掉多余的账号后重新邀请。

**工号从 userinfo 的哪个字段来，是前提，不是本文的决定**。owner 已确认能拿到工号；具体字段名和要不要额外申请
scope，由 I2 #1052 在 IDaaS 测试环境实测后，写进默认配置。v1 读的 `globalUserId` 是通讯录的人员编号，不是工号，
不能拿来用。

### D4：进团队靠管理员邀请；部署版按工号、开发版按邮箱

- **登录不等于入队**：IDaaS 的任何员工都能登录，并按 D3 得到账号，但不属于任何团队，页面显示“还没有加入团队，
  请联系管理员邀请”。
- **邀请即加入**：沿用现在的语义，管理员邀请一个人，就在同一个事务里找到或建出他的账号，并把他加为团队成员；没有
  “待接受”的邀请。部署版的邀请表单填工号，开发版填邮箱；表单只显示和 `V2_LOGIN` 对应的那一种。
- **被邀请的人下次打开页面**就能看到团队，不用重新登录：会话只说明是谁，团队成员身份每个请求都重新判定（A1 D4）。
- **第一个管理员**：来自启动时的 `users.json` 预设。部署版的预设按工号列出管理员，Cloud 启动时按 D3 建出只有工号的
  账号并设为团队的 owner；开发版的预设照旧按邮箱。
- **移出团队**由管理员操作，被移出的人账号还在、还能登录，但看不到这个团队了。

为什么不用邀请链接：邀请链接不依赖身份字段，但要多一套令牌的签发、过期和吊销，管理员还要另外把链接发给对方。
既然能拿到工号，按工号邀请和现在按邮箱邀请是同一套代码、同一种体验。

### D5：网页会话：Cookie，绝对过期 7 天，登出只删本会话

- 规则沿用现在的做法：登录时签发一个随机令牌，放进 `HttpOnly`、`SameSite=Lax` 的 Cookie；PostgreSQL 只存它的
  SHA-256；从登录起 7 天后过期，使用不会延长；登出删除这一个会话。
- 部署版的 Cookie 加 `Secure`。
- 改变状态的登录接口（发起登录、登出）校验 `Origin` 等于公开地址的 origin。
- 账号停用或删除后，它的所有网页会话和 desktop 令牌立即失效。
- 登出不退出 IDaaS 的单点登录；IDaaS 仍登录着时，再点登录会直接回来。

为什么不缩短到 v1 的 12 小时：v1 用 12 小时限制“员工离职后，会话还能用多久”。但 desktop 令牌 30 天不用才过期
（D6），网页单独缩短并不能缩短这个窗口。第一版处理离职的办法是管理员把人移出团队（D4）；和 IDaaS 同步离职留到
以后（见“未解决的问题”）。

### D6：desktop 经系统浏览器和本机回环地址登录，拿到落在同一账号上的令牌

Cloud 一侧的契约如下，接口路径是示意，最终以 #1029 的正式契约为准：

1. desktop 在 `127.0.0.1` 或 `[::1]` 上监听一个系统分配的端口，生成随机 `state` 和 PKCE verifier，用系统浏览器打开
   Cloud 的 desktop 登录页，带上回环回调地址、`state` 和 `S256` 的 `code_challenge`。
2. 浏览器没有网页会话时，先按 D1 当前的方式正常登录，再回到这一页。
3. 页面显示“允许 Ora desktop 以 <显示名> 的身份登录”，用户点了“允许”，Cloud 才签发一次性授权码。授权码 2 分钟内
   有效，只能用一次，只放在进程内存，绑定这个账号、`code_challenge` 和回调地址。浏览器随后跳回回环地址，带上
   授权码和 `state`。
4. desktop 核对 `state`，用授权码、verifier 和回调地址换 desktop 令牌。三者有一项对不上，授权码作废。
5. desktop 之后在请求头带 `Authorization: Bearer <令牌>` 调 Cloud 的 API。请求带了这个头，Cloud 就只按它判定身份，
   不看 Cookie。

令牌的规则：

- PostgreSQL 只存令牌的 SHA-256，记下所属账号和最近使用时间。连续 30 天没有用过就过期；最近使用时间可以按小时粗略
  刷新。没有绝对上限，不轮换。
- **同一个账号**：令牌和网页会话指向同一个 `users` 行，团队、权限和数据都按这个账号判定，没有 desktop 专用的权限。
- **每个请求都校验**：令牌过期、被吊销或账号停用，返回 `401`；desktop 据此要求用户重新登录。
- **吊销**：desktop 登出时吊销自己这个令牌，不影响网页会话和其他设备。网页登出也不影响 desktop 令牌。
- 回调地址只接受回环地址（RFC 8252 §7.3），端口任意，不接受其他主机和自定义 scheme。

为什么用回环地址、不用 deep link：desktop 已有打开系统浏览器的能力，回环监听只需要一个本地端口；deep link 要在三个
平台上分别注册 scheme，还会被其他应用抢注。

为什么要用户点“允许”：浏览器里已有网页会话时，不确认就会悄悄给 desktop 签发一个 30 天的令牌。多一次点击，让签发
令牌这件事一定由人发起。

**desktop 一侧不在本文**：令牌只进系统安全存储、网络错误和 5xx 不清令牌、`401` 时重新登录、登出时清掉本地缓存，这些
规则由 #1084 在 desktop 的 Cloud 连接决策目录写后续 ADR。那份根决策里第一版不做的（部署身份校验、自签证书和内网 HTTP、
会话轮换、活动上报、60 秒内发现吊销），也在那份后续 ADR 里标出。

### D7：第一版不做的

- 华为 IDaaS 以外的登录提供方；同一个库在两种登录方式之间切换。
- 按 `globalUserId` 或通讯录搜索加人、邀请链接。
- 和 IDaaS 同步离职或停用。
- 会话和令牌轮换、desktop 令牌的绝对上限、列出和远程吊销自己的 desktop 登录。
- desktop 的部署身份校验和能力协商。
- 登录限流。

| D2“运维”、D6“第一版不做” | 离线部署包等运维项在第一次部署之后按需要再定 | 第一次内网部署之前由 circus #1059 准备 |
| 落地顺序 | 第 3 步列着暂停的事项 | 这些事项已在 2026-11-12 作废关闭，改为一句说明 |

## 被取代的 v1 决策

A1 的“被取代的 v1 决策”一节已经把 v1 登录的三份 ADR 列为由本文取代，标记时机是 I11 #1061 删除 v1 Gateway 时，
本文不提前改它们的状态：

- [Gateway 外部身份根决策](../identity-access/0-gateway-mediated-external-identity.md)：IDaaS 协议细节由 D2 继承，
  Gateway 进程、服务间 JWT 和 GitHub 适配器放弃。
- [华为 global ID 别名](../identity-access/20260923-huawei-global-id-alias.md)：由 D3 的工号取代。
- [部署绑定的 desktop 会话](../identity-access/20261019-deployment-bound-desktop-sessions.md)：会话规则由 D6 继承，
  部署身份、能力协商和轮换放弃。

## 不变量

1. 一个运行中的 Cloud 只开放一种登录方式，由 `V2_LOGIN` 决定；不配置就不启动。
2. `V2_LOGIN=idaas` 时，没有任何不经 IDaaS 就能得到会话的路径。
3. 一个 IDaaS `uuid` 至多对应一个账号；一个工号至多对应一个账号。
4. 登录永远不会自动合并两个账号；两个账号都声称是同一个人时，登录被拒绝。
5. 登录本身不授予任何团队成员身份；成员身份只来自管理员邀请或启动预设。
6. 网页会话和 desktop 令牌都只以哈希存储；明文、授权码、IDaaS token 和 client secret 不入库、不进日志。
7. 同一个人的网页会话和 desktop 令牌指向同一个账号，按同一套租户授权判定。
8. 账号停用或删除后，它的所有会话和令牌在下一个请求就失效。
9. desktop 授权码只能用一次，只能由签发时的 verifier 和回调地址换成令牌，回调地址只能是回环地址。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 部署版同时保留邮箱登录 | 演示和应急时不依赖 IDaaS | 邮箱登录没有密码，知道邮箱就能冒充（D1） |
| 按邮箱邀请 | 和开发版一样 | owner 定为工号；v1 也从不按邮箱匹配身份 |
| 用工号认人 | 不用处理“先有工号、后有 `uuid`”的账号 | 工号可能变或被重新分配，认人会出错（D3） |
| 邀请链接 | 不依赖任何身份字段 | 多一套令牌，管理员还要另外发链接；能拿到工号时没有必要（D4） |
| “待接受”的邀请表，登录时才入队 | 账号只在第一次登录时才出现 | 和现在“邀请即加入”的代码和界面不一致；成员列表在对方登录前看不到被邀请的人 |
| 登录尝试和授权码入库 | Cloud 重启不打断进行中的登录 | 单进程不需要（D2）；重启本来就会中断执行（A1 D3），多一次登录点击可以接受 |
| desktop 也用 Cookie，经内嵌 webview 登录 | 不用另一种令牌 | 内嵌 webview 拿不到系统浏览器里已有的 IDaaS 单点登录；RFC 8252 不推荐原生应用用内嵌 webview 登录 |
| desktop 令牌带轮换 | 令牌泄露后窗口更短 | 轮换要处理并发刷新和失败恢复，v1 为此写了一整节；第一版只适合互相信任的成员（A1 D2） |
| 网页会话缩短到 12 小时 | 离职后网页会话很快失效 | desktop 令牌 30 天，单独缩短网页会话收效不大（D5） |

## 本决策未解决的问题

1. **工号字段**：来自 userinfo 的哪个字段、要不要额外 scope，由 I2 #1052 实测确定（D3）。实测发现拿不到，就要回到
   本文重新选择邀请方式。
2. **离职和停用**：第一版靠管理员移出团队，不和 IDaaS 同步。要自动同步，需要另外接通讯录或 IDaaS 的回调，另写决策。
3. **多个团队**：现在一个部署只有启动预设的一个团队，没有新建团队的接口。要支持自助建团队时，另写决策。
4. **desktop 一侧的规则**：由 #1084 在 desktop 的 Cloud 连接目录写后续 ADR（D6）。

## 落地顺序

1. **I2 #1052（网页登录）**：`V2_LOGIN`、IDaaS 授权码流程、按 D3 找账号、按工号邀请和预设、登录页和邀请表单按
   `V2_LOGIN` 显示。先在 IDaaS 测试环境确认工号字段。完成条件：`V2_LOGIN=email` 时 `task v2:demo` 照常起来，
   演示场景可用；`V2_LOGIN=idaas` 时邮箱登录被拒绝，按工号邀请的人第一次登录就能看到团队。
2. **#1084（desktop 登录）**：Cloud 一侧的确认页、授权码和 desktop 令牌，以及 desktop 一侧的实现。依赖第 1 步的
   账号模型，可以在第 1 步合并前先做 preflight。完成条件：开发版和部署版下 desktop 都能登录、调用 API、登出。
3. 本文 `approved` 后补核心测试用例，两步实现合并后改为 `implemented`。

从第 1 步起，部署版只能用 IDaaS 登录；开发版的行为不变。
