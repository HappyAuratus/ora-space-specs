# WorkflowRun 拥有 Git 授权与整次成果，核验交付后才释放工作区

本提案让一个 WorkflowRun 在所有写入尝试结束后交付一次逻辑 Revision，复用 Git 交付 ref、Cloud 核验和有界重试，
同时归档整次运行的节点会话清单。工作流会话可以读本 Project 的仓库，只能快进本 Workspace 的分支；取消、
节点换尝试和进入交付都会撤销旧会话写资格。工作流的执行结论、交付结果和资源释放分别记录。

本文为 `proposed`，尚不改变现有系统承诺。涉及 Cloud workflow/revision/Git 授权、Controller 固定输入转交和
Node 交付。既有 Agent IssueRun 身份、交付结果与单会话历史保持原义；历史 WorkflowRun 不补造 Revision。
任务层如何选择前序成果和排队由[混合交接提案](../issue-run/20261025-mixed-task-execution-handoffs.md)负责。

## 问题与边界

当前工作流有独立 Workspace，但终态后只释放资源，不登记 Revision；现有交付以一个已结束的 Agent 会话为输入。
把工作流最后一个节点塞进此输入会漏掉先前节点及失败重试的历史，也不能证明全部写入者已经停止。
直接让工作流推任意分支则把分支变成未经核验的事实成果，无法提供安全的恢复依据。

本提案覆盖任务调用和独立运行的 WorkflowRun。工作流内部依然串行执行 Agent 节点；不增加节点并行、检查点、
失败运行 resume、外部仓库发布或原始记录浏览界面。产出文本仍归节点结果，文本不是代码成果的核验证据。

## D1：一个运行一份逻辑成果，归属不可伪装

Revision 的所有者恰好是 Agent IssueRun 或 WorkflowRun 之一，租户、Project、Workspace 和执行工作项必须一致。
数据库用对应外键和互斥约束验证两种归属，不撤销约束后靠 UUID 碰巧匹配，也不为每个工作流节点创建 IssueRun。
工作流调用 IssueRun 仍只是调用记录，经既有 invocation 关联找到成果；独立 WorkflowRun 无需伪造任务。

一次运行至多登记一份逻辑 Revision。交付重试拥有独立尝试及固定 ref，不创建第二次逻辑运行；成功登记后，
迟到成功或失败只保留尝试事实，不替换已登记成果。重复回执不能重复核验登记或再次释放。

没有创建 Workspace 的纯计算运行记交付 `not_required`，不建空 Revision、不清除任务原成果。创建过 Workspace
但尚无 Agent 会话的启动失败同样不捏造会话历史；确认没有执行写入后可记 `not_required`，执行失败仍阻塞任务接力。
曾派发写入会话却无法确认它是否停止时，不能用 `not_required`、`unchanged` 或超时冒充安全结算。

## D2：会话读写资格属于当前节点尝试

工作流会话访问 Git Server 必须同时满足：可信执行证书与当前 Node/Workspace 代次一致；执行登记属于该
WorkflowRun、节点及当前尝试；运行仍在执行、没有取消请求；节点仍 `running`，会话尚未进入结束或交付屏障。
资格在每次请求时根据权威状态复核。排队、`retrying`、`awaiting_input`、已结束、旧尝试和旧代次不授予会话写权限。

| 执行种类 | 可读 | 可写 |
|---|---|---|
| 当前合法 Agent 节点会话 | 本 Project 的 upstream、Workspace 分支及已登记交付 ref | 仅自身 Workspace 的 `refs/heads/workspaces/<workspaceId>/**`，只允许快进 |
| 当前合法交付执行 | 固定输入所属 Project 的仓库 | 新建自己的不可变 `refs/ora/deliveries/<workItemId>`；可尝试快进自己的 workspaceRef |

拒绝跨 Project、跨租户、别人的 Workspace 前缀、修改或删除既有交付 ref。取消立即撤销会话资格，但收尾交付
使用独立资格保存已有成果，不借用被撤销的会话权限。敏感材料不进入运行输入、数据库正文或日志。

同一 Workspace 的多个节点按尝试串行持有会话写资格。请求证据保留 WorkflowRun、节点、尝试、execution ID
及目标 ref；这证明谁获得写授权，不声称能仅靠最终 Git diff 精确归属每一行修改。旧尝试的迟到写请求拒绝。
当节点从 `running` 退出前，必须确认该尝试写入进程已停止；不能因下一节点已经被调度而推断旧进程停止。

## D3：工作区目录记录运行归属，不泄露授权

在现有同 Project、最多最近 100 个 Workspace 的目录规则内纳入工作流 Workspace，含已结束运行留下的分支。
目录提供 Workspace、WorkflowRun、工作流名称与可选任务关联，明确区分 Agent IssueRun；不放模型绑定、凭据、
原始提示或会话内容。名称取冻结运行身份，删除/归档后仍能解释历史来源，不重新解析成另一个同名工作流。

目录是会话启动时冻结的发现信息，既非实时列表，也非访问授权。读取权与写入权始终按 D2 独立验证；目录里
存在某 Workspace 不意味着当前执行有权写它。目录变更不要求复用已释放 Workspace。

## D4：整次归档不能伪装成最后一个节点的会话

工作流交付输入采用明确的工作流变体，保留原 Agent 单会话变体。Cloud 固定 WorkflowRun、checkout、所有已登记
节点会话尝试及各自 execution ID、交付 ref、归档对象键和前序 Revision；Controller 原样转交并校验，Node 不自行
选择“最近一个会话”。工作流终态不等于这些会话的进程都已结束，交付前须逐个验证停止与相同 checkout 归属。

Node 将每个已经建立的会话按原始字节归档，并生成带 schema 版本的清单。清单逐项记录节点、尝试、execution ID、
历史对象键、字节数和 SHA-256；排序按节点执行顺序及尝试，重复身份拒绝。失败尝试与被替代尝试仍有各自记录。
没有建立会话的尝试明确记 `not_started`；已建立却缺少历史记 `unavailable` 并使本次交付失败，不能偷偷省略。

Cloud 在事务外核验固定 ref 指向声明的最终提交，并逐一核对清单及对象的身份、大小和摘要；随后在短事务中
重新检查执行归属与冻结声明，一并提交核验结论、Revision、回执和交付状态。外部服务暂时不可用保持可重放，
确定不匹配才记核验失败。旧 Agent JSONL 不改写为清单，读取端按显式历史类型区分，不能靠文件扩展名猜。

完整归档的读取继承原运行授权。本文只交付保存与可验证引用，不增加完整节点日志 UI，也不把原始历史自动
注入下一位 Agent。工作流的对外最终输出来自已提交 output 节点结果，和历史清单分别维护。

## D5：一次恢复，整次保存，资源释放有证据

任务调用可以携带任务层已经冻结的前序 Revision；独立运行没有任务前序。WorkflowRun 的第一条实际写入会话
在创建的 checkout 上恢复前序，恢复完成事实按运行与 checkout 持久化。后续节点和自动重试使用同一已推进的
checkout，不再执行前序恢复。若恢复中断，只有确认未让 Agent 接触半恢复 checkout 后才能按原固定输入重试。
恢复失败不启动模型、不自动改用更早 Revision；任务层记录可解释阻塞。

工作流没有剩余可调度节点、自动重试或人工等待，并且所有已派发写入者结束后，冻结整次交付声明和代码快照。
Node 使用现有不改工作区/暂存区的内部快照机制保存剩余改动。相对前序没有新改动仍须有自己的已核验交付 ref，
不能引用易变 Workspace 分支冒充成果。

执行结果、交付状态、释放状态是三个事实。运行可以展示“执行成功，保存中”，但任务执行占用不能因成功标签
而释放。保存成功或核验无改动后才正常释放；执行失败或取消仍尝试保全现有成果，队列仍需显式恢复。
进入交付后禁止新增节点尝试或重新解释图，重新执行使用新的 WorkflowRun；失败运行 resume 继续按原契约不可用。

交付失败继承既有有界重试、放弃和迟到事实接管原则，重试不改冻结输入。基础设施缺失导致 `skipped` 必须可见，
不能推进任务。达到系统放弃边界不等同于成果成功或真实释放；已有残留/隔离与拒绝终态规则继续适用。
用户明确放弃未保存成果与恢复队列是独立动作，不能以停止、切目标或重试隐式授权丢弃。

## 不变量

1. 每份 Revision 有且仅有一种可验证运行归属；每个 WorkflowRun 至多一份逻辑成果。
2. 所有写入会话停止之后才能冻结交付；旧节点尝试不能继续写仓库。
3. 多节点历史包含全部已建立会话尝试，最后一段历史不能代表整次运行。
4. 代码 ref 与归档均核验成功后才能登记成功；未知不等于无改动、成功或释放。
5. 同一 checkout 只在首个实际写入节点前恢复任务前序，后续节点与重试不覆盖已产生的改动。
6. 失败/取消不把部分成果冒充成功；保存与真实释放不会自动解除任务的失败暂停。
7. 会话与交付授权互相独立，只覆盖本 Project 和允许的 ref；目录出现不授予访问权。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 只开放 Workspace 分支写入 | 改动较小，但分支未经核验、可继续移动，不能证明任务成果安全可恢复 |
| 为每个节点建立 IssueRun 和 Revision | 便于沿用单会话代码，但把调用记录与执行节点混在一起，制造错误的任务交接边界 |
| 最后一个节点的历史代表整次运行 | 节省归档改动，却丢失先前节点、失败尝试和上下文证据 |
| Cloud 拼接原始 JSONL | 可沿用一个对象，但 Cloud 必须理解不同 Agent 原生日志；清单保持原格式与来源 |
| 任一节点结束就交付并允许下一任务启动 | 启动更早，却可能与后续工作流节点并发写入，违背整次运行聚合 |
| 恢复到同一旧 Workspace 继续接力 | 少一次恢复，但把历史与沙盒生命周期绑定，无法安全回收或隔离授权 |

## 兼容、风险与落地

以追加迁移扩展成果所有者、清单形状和交付状态，保留已有 Agent 行及校验约束，不回填不存在的历史成果。
工作流协议扩展须同时更新 Cloud/Controller/Node 及生成物；旧 Node 不得领取无法理解的工作流交付变体。
采用排空升级：停止新准入，待在途执行、交付、待执行请求处理完且残留完成明确处置，备份后升级和迁移。
未知残留阻止切换；不能为完成升级自动取消任务或清空数据库。历史缺口保持可见。

先批准本文及对应验证义务，再落地归属约束与协议、Git 授权与目录、恢复/交付/释放，最后验证真实多节点工作流。
工作流纯计算、失败、取消、重试后成功、历史缺失、上传失败、Git 拒绝和进程重启都必须有直接证据。
验收草案见[整次成果与授权](../../../test-cases/cloud/workflow/run-owned-delivery.md)，所有新增义务当前为 Missing。
本提案不决定跨任务成果合并、外部仓库发布或终态运行的原地 resume。
