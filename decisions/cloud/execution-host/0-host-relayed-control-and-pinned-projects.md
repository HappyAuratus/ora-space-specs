# 多机执行层：每台机器一个执行宿主转发 Node 控制帧，Node 用项目令牌直连 Cloud 的数据服务，项目固定在一台机器上，断开即中断，取代 v1 的 Controller 领取与租约

每台运行 Node 的机器上跑一个[执行宿主](../../../domain/glossary.md#execution-host)（下称“宿主”）。宿主主动连上 Cloud，
只保持一条长连接，把本机所有 Node 的控制协议帧原样转发；Node 仍在本机通过 Unix socket 收发帧，控制协议不改。
模型授权、Git 和插件包这些数据服务，由 Node 用[项目令牌](../../../domain/glossary.md#project-token)直接访问 Cloud 的
HTTPS 入口，不经过宿主。一个项目固定在一台机器上；宿主和 Cloud 之间断开时，两端各自把这台机器上的执行结束掉：
Cloud 标为中断，宿主停掉本机的 Node 容器，不续传。宿主不建数据库，不做意图登记、证据接管和租约；它重新连上后报告
本机的容器，由 Cloud 对照记录决定留下哪些。单机部署时，宿主以内嵌模式跑在 Cloud 进程里，走同一套接口。

本 ADR 处于 `approved`：owner 已评审通过，尚未实现；它是新建领域 `cloud/execution-host` 的根决策。前提是
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”），依据是 circus #1043
的 Q1 结论，以及 #1065 里 owner 定下的"Node 改为用项目令牌"。读取的代码版本为 cloud `ad324c77`
（`v2-server/internal/node`、`internal/nodeservices`）、desktop `dcff8afe`（`apps/ora-node`、`crates/node-protocol`）。核心测试用例见
[多机执行层用例](../../../test-cases/cloud/execution-host/host-relayed-control-and-pinned-projects.md)。

范围与兼容性边界：

- **涉及**：cloud 新写的宿主程序和 Cloud 一侧的宿主接入、调度；desktop 的 Node 只改数据服务的认证方式（D7），
  控制协议不变。
- **不在本文**：容器的用户、文件布局、网络规则和资源上限由 A3（circus #1047）规定；Git server 的读写范围由 A4（#1048）
  规定；模型代理的临时令牌由 A5（#1049）规定。本文只定它们共用的项目令牌，以及令牌怎么交到 Node 手里。
- **演示约束**：继承 A1 D7，只改凭据这一处。演示结束前，`task v2:demo` 仍走"后端直接拉起本地 Node 子进程 + 本机配套服务"
  的路径，但本机配套服务和 Node 之间也改用项目令牌，不再签发客户端证书（D7，owner 2026-11-11 定）。这是 A1 D7"新路径不改变
  演示路径"的一处例外：凭据只有一种形态，Node 就不用同时维护两套配置。
- **不做数据迁移**：Node 的数据目录不是权威数据（A1 D3），项目换机器时在新机器上重建，不搬旧数据。

## 决策

### D1：控制帧经宿主转发，数据服务由 Node 直连 Cloud

| 流量 | 路径 | 认证 |
| --- | --- | --- |
| Node 控制协议（Hello、执行、事件、ACK、心跳） | Node ⇄ 本机 Unix socket ⇄ 宿主 ⇄ 一条长连接 ⇄ Cloud | 宿主令牌（宿主到 Cloud） |
| 模型授权与模型请求 | Node → Cloud HTTPS 入口 | 项目令牌申请会话级临时令牌（A5） |
| Git（clone、fetch、push） | Node → Cloud HTTPS 入口 | 项目令牌（A4 规定读写范围） |
| 插件包 | Node → Cloud HTTPS 入口 | Cloud 签发的短期签名 URL（D6） |
| 宿主管理（注册、容量、起停容器、上报） | 宿主 ⇄ 同一条长连接 ⇄ Cloud | 宿主令牌 |

宿主不解析 Node 的帧内容，只按 Node 分路转发。Cloud 一侧把每个 Node 的转发通道当作一条普通的字节流，交给现有的
`internal/node` 客户端，所以握手、心跳、ACK 和重放的逻辑只有一份。

为什么数据服务不经宿主：Git 和模型流量远大于控制帧，经宿主转发会让宿主成为瓶颈，而且宿主就得懂每种数据协议、
替每个项目做授权。直连时，授权只在 Cloud 一处判定。

### D2：宿主到 Cloud 是一条 WebSocket 长连接，按 Node 分路

- **建立**：宿主用 `wss://` 连 Cloud 入口，请求头带宿主令牌；Cloud 校验后接受，一台机器同时只允许一条连接，
  新连接会顶掉旧连接（旧连接上的 Node 按 D3 处理）。
- **注册**：连上后宿主先发注册消息：宿主协议版本、机器容量（按 A3 的容器资源上限折算成可放的 Node 数）、本机已有的
  Node 镜像 digest、本机现存的 Node 容器和数据卷。版本不兼容时 Cloud 拒绝连接并记录原因。
- **分路**：每个 Node 一条逻辑通道，用 Cloud 分配的 Node 标识区分。每条通道有自己的有界发送队列；某个 Node 的队列满了，
  只断开这一条通道（按 Node 退出处理），不阻塞也不断开整条连接。
- **存活**：两端每 10 秒互发心跳，30 秒收不到任何帧就认为断开。数值可由部署配置调整，但必须在两端一致。
- **内嵌模式**：单机部署时宿主跑在 Cloud 进程里，Cloud 和宿主之间是进程内调用，没有网络和令牌，但消息和状态机与
  远程宿主相同。

为什么宿主主动连：企业内网里，执行机器通常能访问 Cloud，Cloud 却不一定能访问每台执行机器；宿主往外拨只要求开放
Cloud 入口一个端口。WebSocket 跑在普通 HTTPS 之上，企业的反向代理和负载均衡都能直接转发。

### D3：断开即中断，两端各自收尾

| 事件 | Cloud | 宿主 |
| --- | --- | --- |
| 宿主连接断开（心跳超时、连接关闭、被新连接顶掉） | 这台机器上所有未结束的执行标为中断，吊销这台机器上所有 Node 的项目令牌 | 停掉本机所有 Node 容器，保留数据卷，然后重连 |
| 单个 Node 通道断开（Node 进程退出、通道队列满） | 这个 Node 上未结束的执行标为中断，吊销它的项目令牌 | 停掉这个容器，保留数据卷 |
| Cloud 重启 | 按 A1 D3 先把所有未结束的执行标为中断，再接受宿主连接 | 连接断开，按第一行处理 |

- **两端都停**是为了保证"中断"在现实里成立：Cloud 标了中断，Node 却还在跑 Agent、往 Git 推代码，后续的推送和模型请求
  就成了没人认领的副作用。宿主停掉容器、Cloud 吊销项目令牌，两道都不依赖对方。
- **重放的事件**：Node 的数据库在数据卷里，下一次启动后 Node 可能重放之前没确认的事件。对已经被 Cloud 结束的执行，
  Cloud 照常 `EventAck`，但不把内容写进业务记录。
- **不续传**：断开后不缓存帧、不在重连后补发。需要续传时另写决策（A1 未解决问题第 2 条）。

代价：一次网络抖动超过 30 秒，这台机器上的所有执行都会中断，预热好的 Node 也要重新启动。企业内网里这类抖动很少见，
换来的是两端都不用保存"断开期间发生了什么"。

### D4：项目固定在一台机器上，失联超过宽限期才换机器

- **放置**：项目第一次需要 Node 时，Cloud 在在线、未停用、有这个镜像 digest、还有容量的机器里，选已放置项目最少的一台，
  把项目固定在这台机器上，记录在 PostgreSQL。之后这个项目的 Node 都在这台机器上起停，直到下面两种情况之一。
- **失联超过宽限期**：宿主断开后，项目先保留在原机器上；宽限期（默认 10 分钟，部署可配）内这个项目的新执行请求
  直接返回"执行机器不可用"，不排队等待。超过宽限期，Cloud 解除这台机器上所有项目的固定，下次使用时重新放置。
- **管理员停用机器**：停用的机器不再接收新项目；已固定的项目在它的 Node 空闲回收后解除固定，下次使用时重新放置。
- **容量**：每台机器的容量由宿主按 A3 的容器上限报告；满了就不再放新项目。已固定项目的 Node 被空闲回收后，
  仍占用这台机器的固定关系，但不占容量。#1026 的预热和空闲回收由 Cloud 按项目决定，在项目所在的机器上执行。
- **Node 的数据目录不是权威数据**（A1 D3）：重新放置后，新机器从 Git server 重新 clone，旧机器上的 checkout 里
  没推送的改动丢弃，Agent 的安装缓存重建。

为什么固定而不是每次挑最空的机器：Node 的数据卷里有 checkout 和 Agent 安装缓存，换机器意味着重新 clone 和安装
（#1023 测得 clone 约 13–15 秒、插件约 3 秒，O5 之后 clone 会大幅缩短，但安装仍在）。固定之后，只有机器真的出问题才
付出这个代价。宽限期内直接报错而不是排队，是因为用户看得到原因，比卡住更好。

### D5：宿主只做四件事，不保存任何状态

宿主只做：**注册并上报容量和存活、按 Cloud 的指令起停 Node 容器、转发 Node 控制帧、上报容器和数据卷清单**。

- 不建数据库，不保存执行、项目或调度信息；它知道的只有本机 Docker 里现有的容器和数据卷（按 Cloud 打的标签识别）。
- 不做意图登记、证据接管、租约和代次围栏。Cloud 发出的起停指令，宿主执行后回报结果；回报丢了，以下一次注册时
  上报的清单为准。
- **重启或重连后的对照**：宿主在注册消息里上报本机的 Node 容器和数据卷，Cloud 对照 PostgreSQL 的记录：
  - 不该在跑的容器（例如断开期间执行已被标为中断）让宿主停掉；
  - 已经解除固定、不再属于这台机器的项目，让宿主删除它的数据卷；
  - 认不出来源的容器和数据卷（没有 Cloud 的标签）不动，记录告警。
- 宿主复用 v2-server `internal/node` 里起停监督、残留清理和独占锁的做法；进程隔离和容器布局由 A3 规定。

为什么不让宿主保存状态：v1 的 Controller 为了在崩溃后续上进度，保存了意图、证据和租约，规模到了 1.2 万行加 0.7 万行
协议（#1023）。D3 已经定了断开即中断，宿主不需要记住任何事；Cloud 的 PostgreSQL 是唯一的事实来源，宿主每次连上都
从清单重新对齐。

### D6：宿主令牌、项目令牌和插件签名 URL

- **宿主令牌**：管理员在 Cloud 上登记一台机器时生成，只显示一次；Cloud 只保存它的哈希。一台机器一个令牌，令牌就是
  机器的身份。管理员可以吊销，吊销后 Cloud 立即断开这台机器的连接，按 D3 处理。
- **项目令牌**：Cloud 每次让宿主启动一个项目的 Node 容器时签发一个新令牌，经长连接交给宿主，宿主把它写进容器的私有
  配置目录（A3 规定位置和权限）。Cloud 只保存哈希，记录它属于哪个项目、哪台机器、哪一次启动。
  - 只能访问所属项目的 Git、模型授权和插件包；具体读写范围由 A4、A5 规定。
  - 容器停止、通道断开、宿主断开、项目换机器时，令牌立即吊销；旧容器即使还活着，也访问不到 Cloud。
  - 不设固定过期时间：生命周期就是这次容器启动；需要轮换时，Cloud 发新令牌给宿主，宿主覆盖文件，Node 下一次请求就用
    新的（D7），旧令牌随即吊销。
- **插件包签名 URL**：Cloud 下发安装执行时，包地址带上短期签名（绑定项目、包摘要和过期时间）。Node 已经按摘要校验包，
  不需要再带令牌，所以插件安装这条路径 Node 不用改。
- **Cloud 入口**：只有服务端 TLS，证书由企业 CA 签发或自签；Node 和宿主信任部署配置给它们的 CA，或系统根证书。

为什么项目令牌按"每次启动"签发：令牌和容器同生共死，吊销规则只有一条——容器不在了，令牌就失效。这样 D3 的"两端
都停"在凭据层面也成立。

### D7：Node 改为用项目令牌访问 Git 和模型授权

desktop 的 `ora-node` 做以下修改（实现由新开的 desktop task 承接，见"落地顺序"）：

- `git_access` 和 `model_proxy` 增加令牌配置：令牌文件的绝对路径；CA 改为可选，不配时用系统根证书。
- Git：每条访问 Cloud 的 git 命令启动时读一次令牌文件，通过环境变量里的 `GIT_CONFIG_*` 设置
  `http.extraHeader: Authorization: Bearer <令牌>`；令牌不写进 checkout、git 配置、日志或 journal。
- 模型授权：Node 申请会话级临时令牌时，请求头带上项目令牌；每次申请前重新读令牌文件。Agent 拿到的仍然只是
  临时令牌（A5）。
- 令牌文件读不到或格式不对时，这次请求失败，错误码不含令牌内容。
- **不保留证书配置**：Node 只支持令牌这一种形态。演示路径也一起切换：v2-server 的本机配套服务改为签发项目令牌、
  校验 bearer 请求头，服务端证书仍是本机自签，Node 信任配置给它的 CA；同时把 `prepare-node.sh` 固定的 desktop 版本
  推到包含本修改的提交。v2-server 的切换和固定版本的推进必须在同一个 PR 里，因为新版本的 Node 不再接受证书配置。

为什么改 Node 而不是保留客户端证书：保留证书要在 Cloud 入口做客户端证书认证，企业的反向代理就得透传 TLS；吊销要靠
Cloud 自己维护的名单；模型客户端只在启动时读证书，轮换就得重启容器。令牌在这三点上都更简单，代价是 desktop 多一个
小改动。

**令牌对同一项目的 Agent 可见**：git 进程必须拿到令牌，而 git 和 Agent 用同一个工作负载用户（A3），所以同项目的 Agent
在技术上能读到它。这和现在的客户端私钥一样，属于 A1 D4 第 4 条接受的范围：令牌只能访问本项目的数据，Git 只能写
Agent 工作分支和交付 ref（A4）。

## 不变量

1. 每台机器同时最多有一条宿主连接，连接必须带有效的宿主令牌。
2. Node 的控制帧只经宿主转发；宿主不改写、不缓存帧的内容。
3. Node 访问 Git、模型授权和插件包时不经过宿主。
4. 一个项目在任一时刻最多固定在一台机器上，最多有一个运行中的 Node 容器。
5. 宿主连接断开后，这台机器上所有未结束的执行都已标为中断，所有项目令牌都已吊销，宿主也停掉了所有 Node 容器。
6. 被 Cloud 结束的执行，Node 重放的事件不改变业务记录。
7. 宿主不保存执行、项目或调度状态；重连后以 Cloud 的记录为准对齐本机容器和数据卷。
8. 项目令牌只能访问所属项目的数据；签发它的容器停止后，它立即失效。
9. 令牌明文只出现在宿主内存、容器的私有配置目录和请求头里；Cloud 只保存哈希。
10. 失联机器在宽限期内不接收新执行；超过宽限期后，它上面的项目都已解除固定。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| Cloud 主动调用每台机器上宿主的 HTTP API | 实现最简单，不需要长连接 | Cloud 要能访问每台机器，企业内网常常不满足；Node 的事件流是持续推送，还得再开回调或轮询（#1043 Q1 选项 b） |
| Node 直接用 TLS 拨 Cloud，不要宿主 | 少一个程序 | 要改 Node 的传输层；起停容器仍然需要每台机器上有一个程序；每个 Node 都要穿防火墙（#1043 Q1 D1） |
| 数据服务也经宿主代理 | Node 的认证可以不改，跨机器只需宿主令牌 | 宿主成为 Git 和模型流量的瓶颈，还要替每个项目做授权，等于把一部分 Cloud 搬进宿主（D1） |
| 保留客户端证书作为项目凭据，Node 不改 | 不改 desktop，演示路径不用动 | Cloud 入口要做客户端证书认证，反向代理要透传 TLS；吊销要自建名单；模型客户端轮换证书要重启容器（D7） |
| 宿主断开后容器继续跑，重连后续上 | 网络抖动不打断执行 | 需要宿主缓存帧和执行状态，正是 v1 Controller 变重的原因；断开期间的副作用无人认领（D3） |
| 每次执行都挑最空的机器 | 负载更均匀 | 每次都要重新 clone 和安装 Agent，抵消预热的收益（D4） |

## 本决策未解决的问题

1. **断线续传**：断开即中断（D3）。真有需要时另写决策，至少回答宿主怎么缓存未确认的帧、多久内重连算续上。
2. **跨机器搬迁数据卷**：换机器只重建、不搬数据（D4）。如果以后 Agent 安装缓存或大仓库的 clone 成本高到需要搬迁，另写决策。
3. **异构机器**：容量现在只按"能放几个 Node"计算，不区分 CPU 架构、GPU 等资源。需要时由 A3 的后续决策扩展。

1. **Node 改用项目令牌**（circus #1066）：desktop 按 D7 修改 Node；v2-server 的本机配套服务改为项目令牌，并推进固定的

   按令牌授权。
