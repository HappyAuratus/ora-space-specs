# 删除对话时回收它的工作目录：成果能从交付恢复、或用户明确丢弃时才删；先在删除的事务里登记，再按精确归属删除，失败和崩溃后可重试

用户显式删除一个普通对话时，Cloud 判断这个对话的工作目录里的成果能不能从回合交付恢复。能恢复的，目录随对话一起
回收；不能恢复的（还没交付、最近一次交付失败、#1108 之前的旧会话），默认保留目录，只有用户在删除时明确选择丢弃
未交付的改动，才一起回收。删除前，界面和 API 先告诉用户目录会怎样、会丢什么。回收不在删除请求里直接删目录了事：
删除对话的同一个事务里先登记一条**工作目录回收**，记下目录的身份和路径，再按登记去删；删除失败或 Cloud 崩溃，登记
还在，下次启动接着做。删的时候确认目录确实只属于这个对话、没有会话还在用、路径没有经符号链接逃出项目的 checkout
根，才删。

本 ADR 为 `proposed`，供 owner 评审。依据是 owner 2026-11-16 在 circus #1191 选定的方案 A 第二阶段，以及 2026-11-19
在 #1196 列出的判断条件；实测依据是 #1119：24 小时内 101 个工作目录全部保留，其中 45 个属于已删除的普通对话。它是
[回合交付](20261112-single-machine-turn-delivery.md)（下称“交付 ADR”）的后续决策，同时修改
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）D3 里“工作目录被删除，
改动就没有了”所默认的“目录永远不被 Cloud 删除”。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（删除对话、回收登记、启动、工作目录模块）和 `frontend-v2/` 的删除确认框；对话删除
  接口多一个可选参数、多一个预览接口。desktop 的 Node 不改。
- **只回收普通对话的工作目录**。工作流运行（共享目录，含整体删除）、任务运行的目录不在本文，以后另写决策。活跃会话
  的目录永远不回收。
- **不在回收范围**：Node 的会话历史 JSONL、PostgreSQL 记录（含 `v2_workspaces`、交付记录）、项目镜像、快照 ref、交付
  ref。ModelAccess 的临时目录和服务临时包继续由原有生命周期释放。不加任何定时清理。
- **不做数据迁移**：本文落地之前已经删除的对话，目录的归属已随对话记录删除，本文不去找回它们；它们只能由运维在停服后
  `-cleanup` 整体清理。本文落地之后删除的对话才按本文处理。

## 继承与修改

| 前序约定 | 本文处理 |
| --- | --- |

## 决策

### D1：什么样的工作目录算“能从交付恢复”

对话的工作目录能从交付恢复，当且仅当下面三条同时成立：

1. **会话登记过交付**：对话的会话至少有一条回合交付记录。一条都没有的，是交付 ADR 落地之前的旧会话（或者一轮都没
   结束的会话），不算能恢复。
2. **会话已经静止**：会话的所有回合都已结束，并且这个对话没有剩余的交付义务（交付 ADR D3）。还有回合在跑、在交付，
   或者交付义务留给了下次启动的，都不算能恢复。
3. **最后一轮的交付成功了**：会话最后一个回合的交付记录结果是 `delivered` 或 `empty`。最近一条交付记录不属于最后一个
   回合的（例如后面的回合没有登记交付），不算能恢复。

为什么只看最后一轮：每次交付都是相对起点的完整快照（交付 ADR D2），最后一轮交付成功，就说明会话结束时工作目录里
所有未被忽略的改动都在交付 ref 里；前面某一轮失败过不影响，因为后面的交付已经包含它的改动。反过来，只看“最近一条
交付记录”会漏掉一种情况：后面的回合因为某种原因没有登记交付义务，最近一条记录就落在更早的回合上，那之后的改动不在
任何交付里。

为什么要求会话静止：判定和删除之间，不能再有回合往目录里写、或者有交付正在读目录。删除对话本来就先结束会话；结束
会让最后一轮交付，这次交付完成之前，结论是“还不知道”，按 D3 等它完成再判定。

被 `.gitignore` 忽略的文件（依赖目录、构建产物、本地配置）按交付 ADR D2 不进交付。本文不把它们算作成果：交付的
定义就是“未被忽略的改动”，验收、patch 下载也都只给这些。删除前把这一点告诉用户（D2）。

### D2：删除前告诉用户，删除时由用户选

- **删除前预览**：新增一个只读接口，返回这个对话的工作目录在删除后会怎样：
  - `none`：没有工作目录（会话没有准备过 checkout，或目录已经不在）；
  - `recoverable`：能从交付恢复（D1），删除对话时一起回收；
  - `undelivered`：不能从交付恢复，附原因 `delivering`（还有回合在跑或在交付）、`delivery_failed`（最后一轮交付失败
    或没有交付）、`legacy`（旧会话，没有登记过交付）。
  预览和 D3 的判定用同一个规则。预览只说明当时的状态，删除时以 D3 的判定为准。
- **删除时的选择**：删除对话的请求多一个可选参数 `workspace`：
  - `reclaim`（默认）：能恢复就回收；不能恢复就保留目录，对话照样删除；
  - `discard`：用户明确丢弃未交付的改动，不管能不能恢复都回收。
  参数缺省就是 `reclaim`，所以现有的调用方不会因为本文丢失任何未交付的改动。
- **界面**：删除确认框按预览说明后果。`recoverable` 时说明“改动已保存在交付里，工作目录会一起删除；被忽略的文件
  不在交付里，会一起删除”；`undelivered` 时说明原因，默认保留工作目录，另给一个需要用户主动勾选的“同时丢弃未交付的
  改动”，写明丢弃的是工作目录里还没交付的改动、删除后无法找回。`none` 时不提工作目录。

为什么默认保留不能恢复的目录：#1191 否决了方案 C（删除即删目录），首次默认行为不能悄悄丢掉唯一的一份成果。

为什么不提供“能恢复也保留目录”：成果已经在交付 ref 里，对话又删除了，留下的目录没有任何入口能再访问，只占磁盘。

为什么删除时不先补一次交付：删除先结束会话，结束本身会让最后一轮交付（交付 ADR D1、D5）。这次交付失败就是失败，
在删除路径里重试会让删除变慢、可能卡住，结果仍要按失败处理。

### D3：先在删除对话的事务里登记，再回收

- **登记**：删除对话时，在删除对话记录的同一个事务里，为它的工作目录写一条**工作目录回收**，记下目录的身份
  （`WorkspaceID`）、项目、路径、来源对话、用户选的模式（`reclaim` / `discard`）和登记时间，状态为待处理。对话记录
  删除之后，对话 → 会话 → 工作目录这条链路就断了，所以必须在同一个事务里先取出目录的身份和路径；不允许先删对话记录、
  事后再去目录里找哪些没有主人。会话没有工作目录的，不登记。
- **执行**：删除请求在事务提交后立即执行一次回收；Cloud 启动时，在确认旧 Node 进程停止之后、开始服务请求之前，把所有
  待处理的回收再执行一遍。不加定时任务。
- **每次执行先重新判定**：
  - 还有回合未结束或还有交付义务：保持待处理。交付完成后再执行一次，没能执行的留给下次启动。
  - `reclaim` 模式下判定为不能恢复：这条回收以“保留”结束，记下原因，目录不动。
  - 其余情况：按 D4 删除，删除成功后以“已回收”结束，记下释放的字节数和文件数。
- **失败**：D4 的任一检查不通过，或删除本身出错，这条回收保持待处理并记下最近一次的原因，下次启动再试；检查不通过
  属于不该发生的情况（路径越界、符号链接、有活着的会话），以“保留”结束并记录，不反复重试。
- **`v2_workspaces` 不删**：交付记录和重启恢复都按 `WorkspaceID` 查它，数据库记录不在回收范围。回收登记就是“这个目录
  已经删了”的记录。

为什么不在删除请求里直接删目录：删目录可能失败，Cloud 也可能在删到一半时崩溃。没有登记，失败或崩溃之后目录就成了
没有主人的目录，以后只能整项目 `-cleanup` 或者盲扫，#1191 明确禁止这两种做法。

为什么不把对话改成软删除、等目录删完再删记录：回收只需要目录的身份和路径，对话的其余内容没有用处；软删除要让所有
读对话的地方都过滤已删除的对话，改动面大，也会让“删除的对话不可读”依赖每处查询都没写漏。

### D4：只删精确属于这个对话的目录

回收只经读工作目录的那个模块（A1 D7 第 3 条）进行，删除前依次确认：

1. **数据库**：没有未结束的执行会话指向这个 `WorkspaceID`；用过这个 `WorkspaceID` 的会话只有这个对话的那一个。对话
   独占自己的工作目录，工作流运行共享目录，所以这一条也挡住了误删共享目录。
2. **进程内**：没有存活的 Agent 会话占用这个 checkout；先从进程内的 checkout 缓存和技能投影要遍历的 checkout 列表里
   去掉它，并且在技能投影的同一把锁里做，避免投影进行到一半时目录消失。
3. **路径**：登记的路径必须位于这个项目在 Cloud 数据卷上的 checkout 根之下；从 checkout 根到目录的每一级都不能是
   符号链接；删除在以 checkout 根打开的受限目录里进行，不跟随目录里的任何符号链接到根之外。目录已经不在，当作已经
   回收。

三项都通过才删。删除不碰 Node 的会话历史、Node 的账本、镜像、快照 ref 和交付 ref。

为什么要在进程内也确认：数据库只知道会话结束了没有，不知道进程里还挂着哪些对这个目录的引用。技能投影会遍历记下的
checkout 逐个写链接，目录在它检查完存在之后、打开之前被删，会让整次投影失败，影响同项目的其他会话。

为什么路径要逐级确认：登记的路径来自 Node 的回复，第一版 Agent 和 Cloud 是同一个系统用户（A1 D2），Agent 可以在
磁盘上改动目录结构。删除跟随了符号链接，就可能删到项目之外的文件。

### D5：并发

- 同一个对话的删除、发消息、停止仍按现状在同一把对话锁里串行；回收在对话记录删除之后执行，这时已经没有请求能再找到
  这个对话。
- 同一个工作目录的回收同时只执行一次（删除请求里的那次和启动时的那次、或者交付完成触发的那次，不会同时删同一个
  目录）。
- 回收和交付互斥：回收前要求没有交付义务（D3），交付对同一个目录本来就串行（交付 ADR D1）。

## 不变量

1. 只有用户显式删除的普通对话的工作目录会被 Cloud 回收；活跃会话、工作流运行、任务运行的工作目录不会被回收。
2. `reclaim` 模式下，只有能从交付恢复（D1）的目录会被删除；未交付、最后一轮交付失败、旧会话的目录保留。
3. 被删除的目录，要么能从交付恢复，要么用户在删除时明确选择了 `discard`。
4. 每个被回收的目录在删除对话的同一个事务里有一条回收登记；没有登记的目录 Cloud 不删。
5. 删除只发生在：没有未结束的会话指向它、没有别的来源用过它、路径位于项目 checkout 根之下且不经过符号链接。
6. 回收失败或 Cloud 崩溃后，待处理的回收在下次启动时继续，不会留下没有登记的孤立目录，也不会因为重试删到别的目录。
7. 回收不删除、不修改交付记录、交付 ref、快照 ref、项目镜像、`v2_workspaces` 和 Node 的会话历史。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 删除对话就删目录，不看交付（#1191 方案 C） | 最直接，磁盘释放最多 | owner 已否决：会永久丢失未交付、交付失败和旧会话的改动 |
| 只给日志限额，目录全部保留（#1191 方案 B） | 不引入删除语义 | owner 已否决：磁盘随对话数量和仓库大小增长，不能宣称数据卷有上限 |
| 删除请求里直接删目录，不登记 | 少一张表 | 失败或崩溃后目录没有主人，只能盲扫或整项目清理（D3），违反不变量 4、6 |
| 对话改软删除，回收完再真删 | 不用新表 | 所有读对话的地方都要过滤，改动面大，“删除的对话不可读”依赖每处都不写漏（D3） |
| 只看最近一条交付记录是否成功 | 判定更简单 | 后面的回合没有登记交付时会误判能恢复，丢掉那之后的改动（D1） |
| 删除时先补一次交付再判定 | 能恢复的比例更高 | 结束会话本身已经让最后一轮交付；在删除路径里重试会让删除变慢、可能卡住（D2） |
| 删除时连 `v2_workspaces` 一起删 | 数据库更干净 | 交付记录和重启恢复按 `WorkspaceID` 查它；数据库记录不在回收范围（#1191） |
| 定时扫描已删除对话的目录 | 不用改删除路径 | 归属随对话记录删除后已经不可知，扫描只能靠猜（D3）；#1191 也不加定时任务 |

## 本决策未解决的问题

1. **工作流运行、任务运行的目录**：共享目录和运行整体删除的回收以后另写决策。
2. **多机**：单机下 Cloud 直接删磁盘上的目录（A1 D2）。Node 不和 Cloud 在同一台机器上时，回收要改为经 Node 协议请求
   Node 删除它的 checkout，并清掉 Node 账本里对应的 clone 执行；第一版 Node 账本里这条记录不删，它只在工作流运行重启后
   接回目录时被读，对话不会接回。
3. **本文落地之前已删除的对话的目录**：归属已经不可知，本文不处理；需要释放时由运维停服后整体清理。
