# 回合交付：每轮结束由 Cloud 在进程内把工作目录做成提交，写进项目镜像里只新建的交付 ref；变更视图、验收和 patch 下载都读它；修改 A4 D5 与 A1 D3 的"第一版不交付"

Agent 每一轮结束（对话的一轮、任务运行的一轮、工作流 Agent 节点的一次尝试），Cloud 在自己的进程里把这次的工作目录
做成一个提交：父提交是会话的起点提交，在工作目录之外用临时索引收进所有未被忽略的文件，不碰 Agent 自己的索引、
分支和工作目录。提交写进项目在 Cloud 数据卷上的镜像仓库，挂在一个只新建、不改写的**交付 ref** 上，PostgreSQL 记一条
**回合交付**。变更视图和验收读最近一次交付，不再读工作目录；用户可以从交付下载整份 patch，拿回去自己提交。回合的
终态要等交付记录写入才公开，所以任务要等这一轮的交付完成才进入待验收。Node 不改，也不提供 Git server 的 HTTP 入口；
以后上多机时改由 Node 推送同名的 ref。

本 ADR 为 `implemented`：owner 在 circus #1121 确认评审意见，由 circus #1108 实现（运行 circus #1277，cloud PR #410，
`7fb7c972`），实现中对本文未写明之处的决定已写进各 D 节；核心测试用例见
[回合交付用例](../../../test-cases/cloud/project-git/turn-delivery.md)。它是
[项目仓库根决策](0-external-repository-pull-and-encrypted-token.md)（下称“A4”）的后续决策，同时修改
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）D3 的一句话。
依据是 owner 2026-11-12 在 circus #1102、#1107 的结论：恢复交付，选单机最小交付；沿用 2026-11-11 原 A4 的三点
（每轮交付、对话也每轮交付；交付完成才进待验收，失败记原因、任务回到可再次执行；交付第一版全部保留）。D7 是
以后多机时的做法，第一版不实现。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（交付、变更视图、patch 下载、任务状态、启动）和 `frontend-v2/` 的工作区面板。
  desktop 的 Node 不改。
- **不在本文**：推回外部仓库、开合并请求（A4 未解决问题 1，以后另写决策）；回合进行中实时看到改动。
- **不做数据迁移**：本文落地之前的会话没有交付义务，它们的变更视图照旧读工作目录，工作目录被删除后就看不到了；
  这样的会话从第一个登记了交付的回合起改读交付（D4）。

## 决策

### D1：什么时候交付

- **每个被接收的回合结束都交付一次**：对话的一轮、任务运行的一轮、工作流里 Agent 节点的一次尝试。一轮以成功、失败
  还是被停止结束都交付，因为失败和停止的回合也可能已经改了文件。回合被接收时就登记交付义务（D3），所以“要不要交付”
  在回合开始时就确定，不取决于回合怎么结束。
- **工作流**：同一次运行的 Agent 节点共用一个工作目录，所以每个节点尝试结束时交付的是整个运行到这一刻的工作目录。
  - 节点尝试在任何提示被接收之前就失败（角色、MCP、模板配置错误，派发被放弃）的，不交付：Agent 没有跑过，不会有改动。
  - 交互节点按每个被接收的提示交付一次；完成一个停在等待输入的节点时不另交付，因为完成节点不产生新的回合。
- **三类来源之外不交付**：定时任务里单独发起的 Agent 对话不属于对话、任务运行或工作流运行，第一版不交付。
- **只在回合结束时交付**，回合进行中不交付；进行中的改动要等这一轮结束才看得到。
- 同一个工作目录的多次交付按顺序进行：前一次的交付记录写入之后，后一次才开始收集。

为什么每轮都交付：只在任务结束或会话结束时交付，中途 Cloud 重启或工作目录被清理，前面所有回合的改动都会丢；对话
本来就没有"结束"这个时刻。每轮交付让每一轮结束时的状态都有一份 Cloud 保管的副本。

### D2：交付提交怎么做

- 在 `workspacefs` 模块里，于工作目录之外的临时 Git 目录中，以起点提交初始化一个**临时索引**，收进工作目录里所有
  未被忽略的文件，生成树，再生成一个提交：
  - **父提交固定是会话的起点提交**（`v2_workspaces.base_commit`），不是上一次交付，也不是 Agent 当前的 `HEAD`；
  - 作者和提交者是固定的 Ora 身份，提交说明写明来源（对话、任务运行或工作流运行及节点尝试）和第几轮。
- **忽略规则**：Git 从工作目录读 `.gitignore`，Agent 仓库的 `info/exclude` 复制进临时仓库使用。已被跟踪、后来又
  被忽略的文件照样计入交付，与 Git 的行为一致。子仓库（gitlink）按 Git 默认方式记录为一个提交指针，不单独判失败。
- **物化的技能不进交付**：Ora 物化技能时把路径写进 `info/exclude` 里 Ora 的那一块，交付按这一块强制剔除，`.gitignore`
  的反向规则也不能把它们收回来。
  - `info/exclude` 的位置按 Git 的方式解析：`.git` 可以是目录、gitfile 指针（含 linked worktree，此时本地与共享的
    排除规则都生效）或指向目录的符号链接。排除文件的链接只能解析到工作目录或对应的 Git 目录之内，无法安全读取时
    这次交付失败，不冒把技能带进交付的风险。
  - Agent 删掉了 `.git` 时，交付不依赖 Agent 的仓库，照常进行；但记录物化技能的那一块也随之消失，所以只要
    `.opencode/skills` 或 `.claude/skills` 下相对起点有改动，这次交付就失败，因为这时分不清哪些是物化的技能。
- **不碰 Agent 的状态**：Agent 的索引、`HEAD`、分支、stash 和工作目录都不变。Agent 自己做的提交照样体现在树里，
  但交付提交不引用它们。
- **共享工作目录的状态**：交付取的是收集那一刻 Git 看到的工作目录，不暂停同一工作流运行里并行的兄弟节点。暂停兄弟
  节点会让交付改变执行语义（D5），而交付只承诺保存这一刻的现场。
- **没有改动**：树和起点提交的树完全相同时，记为一次“无改动”的交付，不写 ref。
- **加固**：临时仓库不使用 Agent 仓库和系统级的配置，不执行 Agent 配置的 filter、hooks、fsmonitor、外部 diff 和
  textconv，不弹认证提示。第一版 Agent 和 Cloud 是同一个系统用户（A1 D2），这些操作不增加 Agent 的权限。
- **大小上限**：上限由 `V2_DELIVERY_MAX_OBJECT_BYTES` 配置，默认 64 MiB（暂定值，实测后再调）。写对象之前先按工作
  目录里变更和未跟踪的普通文件大小检查一次，避免先写入大量对象再失败；提交之后再按相对起点新增对象的逻辑大小检查
  一次。任一次超限，这次交付失败，原因写明“改动过大”，镜像不留下这次的对象。
- Agent 的协议在报告终态时出错、又无法确认 Agent 已经停止写入时，不取快照，这次交付记为失败（工作区状态无法确认），
  因为这时的快照可能不是这一轮的最终状态。

为什么父提交固定是起点：每次交付都是“相对起点的完整快照”，任意一次交付都能单独拿出来看、单独打成 patch，不依赖
前面的交付是否成功；Agent 在回合里改写自己的历史（`reset`、`rebase`）也不影响交付。代价是相邻两次交付之间的差异
要由两次交付对比得出，不能直接读一个提交的父子关系。

### D3：交付写到哪里

- **交付 ref** 写在项目的镜像仓库里：`refs/ora/deliveries/<projectId>/<deliveryId>`，`deliveryId` 是这次交付的
  UUID。对象先在临时仓库生成，通过大小检查后导入镜像；交付 ref 只新建，不改写，不删除，和快照 ref 的规则一样（A4 D2）。
- **交付义务与记录**：回合被接收时，在同一事务里登记一条交付义务（`v2_turn_delivery_work`）；回合交付记录
  （`v2_turn_deliveries`）每个回合至多一条，记下来源、第几轮（工作流记节点尝试）、起点提交、交付提交、结果
  （`delivered`、`empty`、`failed`）和失败原因。
- **先写 ref，再写记录**：ref 写好之后，才在同一事务里写结果为 `delivered` 的记录并公开回合的终态。两步之间 Cloud
  崩溃，只会留下一个没有记录引用的 ref，它不出现在任何视图里，不影响使用；交付义务还在，启动时重新交付（D5）。
- **同步不碰交付 ref**：A4 D3 的同步只把绑定的分支取进快照 ref；fetch 带 `--no-prune --no-auto-gc`，不读、不删、
  不改 `refs/ora/deliveries/` 下的任何 ref，外部分支被强推也一样。
- Node 仍经本机服务只读访问镜像（A4 D2）。同一项目的 Node 在技术上能读到本项目的交付 ref，这和“项目就是信任
  边界”一致；第一版新会话仍从当前快照开始，不从某次交付开始。

为什么写进镜像、不另建仓库：镜像已经是项目在 Cloud 上唯一的仓库，和 PostgreSQL 一起备份（A1 D2）；交付提交的父提交
是快照里的提交，放在同一个仓库里不用复制历史。

为什么 ref 名用交付 ID、不用“会话/第几轮”：一次交付的身份由 PostgreSQL 的记录决定，ref 名只要唯一且永不复用。
按会话和轮次命名，在重试、并发或以后多机由 Node 推送时容易撞名。

### D4：变更视图、验收和 patch 下载都读交付

- **变更视图**（对话、任务运行、工作流运行三处的工作区面板）显示这个会话或运行**最近一次结果为 `delivered` 或
  `empty` 的交付**相对起点的改动：文件列表、增删行数、单文件 diff；单文件 diff 也可以指定读某一次交付。接口同时
  返回 `deliveryState`：是否有回合正在交付或进行中、最近一次结果、最近一次失败。回合进行中照旧显示上一次交付，
  面板标明“本轮进行中”。
- 工作目录被 `-cleanup` 删除之后，变更视图照常可读。
- **浏览文件**（列目录、读文件）仍读工作目录：它看的是 Agent 现在的现场，不是交付；工作目录被删除时照旧返回
  `410 workspace_removed`。
- **下载 patch**：`GET …/workspace/deliveries/{id}/patch` 从某一次交付下载相对起点的完整 patch，包含新文件和二进制
  文件，能在起点提交上用 `git apply` 应用；空交付返回 `204`。patch 超过 `V2_DELIVERY_MAX_PATCH_BYTES`（默认 16 MiB，
  最大 256 MiB）时返回 `413 patch_too_large`，面板提示“改动过大，无法在线下载”，交付本身仍保留。同时最多生成 4 份
  patch，其余请求排队，避免大 patch 耗尽 Cloud 的内存。
- **读取权限**沿用工作区查看：对话的交付只有对话的主人能读；任务运行和工作流运行的交付，团队成员都能读。交付 ID
  只在它自己的来源里有效。来源被删除（例如对话被删除）后，它的交付都不可读，交付 ref 留在镜像里（D6）。
- **交付失败**时，变更视图仍显示失败之前最近一次成功的交付。工作流运行页一直显示最近一次失败的交付，并注明是哪个
  节点，因为后面节点的成功交付不说明前面节点的改动已经保存；对话和任务只在最近一次结果是失败时显示失败原因，因为
  后一轮的成功交付已经包含整个工作目录。
- 第一版不提供交付历史的接口：面板只需要最近一次结果和最近一次失败，按交付 ID 下载 patch 已能取回任意一次交付。
- **旧会话**：没有登记过交付义务的会话照旧读工作目录，面板不显示交付状态和下载入口；从第一个登记了交付的回合起，
  变更视图只读交付，此前尚未交付时显示为空，不再回头读工作目录。

### D5：交付和任务、对话、工作流的状态

| 来源 | 一轮结束后 | 交付失败时 |
| --- | --- | --- |
| 任务运行，一轮成功或失败结束 | 交付完成（`delivered` 或 `empty`）后，任务进入待验收 | 任务回到待处理，记下失败原因；用户可以重新执行，下一轮结束时再交付 |
| 任务运行，一轮被停止 | 照常交付，任务回到待处理（现状） | 同左，记下失败原因 |
| 对话 | 交付完成后对话照常可以发下一条 | 对话里显示这一轮交付失败和原因；会话不结束，下一轮结束时再交付 |
| 工作流 Agent 节点 | 节点结果照常写入，运行照常推进 | 节点和运行的结果不受影响，运行页显示这次交付失败和原因 |

- 回合的终态先私下暂存，交付记录写入时在同一事务里公开终态事件。所以对话的下一条消息、任务进入待验收、工作流节点
  结算都排在交付之后；交付完成前，对话发下一条被拒绝（工作区忙），人工推进任务返回 `409 run_active`（现状的规则）。
  交付门槛只加在任务的 Agent 运行上，处理任务的工作流的结算方式不变。
- 交付进行中收到停止请求时，等交付完成，不结束健康的会话：Agent 已经结束了这一轮，停止只针对执行。
- **收尾失败**：交付记录在关机以外的情况下写不进时，这一轮记一条 `failed`、原因 `delivery_unavailable` 的交付；终态
  尚未暂存的回合以 `failed / delivery_unavailable` 结束。连这条失败记录也写不进时，终态照常公开（`failed /
  delivery_unavailable`），任务照常回到待处理，交付义务留到下次启动补交付；这时同一工作流运行的共享工作目录可能已经
  有后续节点的改动，补交付会把它们一起收进去（已知限制，见不变量 1）。关机打断的收尾不写失败，直接留给启动。
- **Cloud 重启**：启动时清理交付的临时目录，按 A1 D3 把未结束的执行标为中断，再为所有还有交付义务的回合各补一次
  交付（工作目录不在的记为 `failed`），然后才恢复工作流、接手拆解任务、启动调度器和开始监听。补交付只是把磁盘上的
  现场存一份，不重做执行；任务仍回到待处理（A1 D3）。某个回合的补交付连失败记录都写不进时，启动记下错误、继续处理
  其余回合，只有数据库不可用时启动才失败；这个回合留到下次启动。

为什么交付完成才进待验收：待验收的任务在 Cloud 上一定有一份可以看、可以下载的成果。先进待验收再异步交付，会出现
“待验收却看不到改动”的窗口。

为什么收尾失败也要让回合结束：交付记录写不进多半是数据库暂时不可用；让回合一直挂着，会把任务卡在进行中、把对话
卡在不能发下一条。先结束回合、把交付义务留给启动，代价是共享工作目录里的补交付可能晚于这一轮的现场。

为什么工作流节点不因交付失败而失败：工作流的结果是节点输出和变量池，改动是附带的产物；让交付失败改变节点结果，会把
一个存储问题变成执行语义的变化，还要处理 Loop、Iteration 里的失败策略。

### D6：保留

- 第一版**全部保留**：交付 ref 和回合交付记录不自动清理。删除项目时，镜像连同所有交付一起删除。
- 删除对话、删除工作流运行时，它们的交付记录和交付 ref 留着，但不再可读（D4）。
- 清理策略（按时间、按数量、随来源删除）以后另写决策。

### D7：以后上多机时怎么改

A1 D7 预留的接缝在这里继续成立：多机时 Cloud 读不到 Node 的工作目录，改为由 Node 在回合结束时做同样的提交，推到
Cloud 内嵌的 Git server 的同名 ref `refs/ora/deliveries/<projectId>/<deliveryId>`；回合交付记录、变更视图、patch
下载和任务状态的规则都不变。本文不为多机预先写 Node 协议或 Git server 的细节，第一版也不实现。

## 不变量

1. 每个被接收的回合恰好得到一条回合交付记录，结果是 `delivered`、`empty` 或 `failed` 之一；同一回合不会有第二条。
   已知限制：收尾时连失败记录都写不进的回合，记录要等某次启动补交付才写入，在那之前它只有交付义务、没有记录。
2. 结果为 `delivered` 的记录，它的交付 ref 一定存在于项目镜像里，并指向记录里的交付提交。
3. 交付提交的父提交总是会话的起点提交；交付 ref 一经写入不再改变，第一版不删除。
4. 交付不改变 Agent 的索引、`HEAD`、分支和工作目录，也不执行 Agent 配置的任何 Git 外部程序。
5. 同步不读、不删、不改交付 ref。
6. 任务只在这一轮的交付结果为 `delivered` 或 `empty` 之后进入待验收。
7. 登记过交付义务的会话，变更视图和 patch 下载只读交付，不读工作目录；对话的交付只有对话的主人能读。
8. Ora 物化的技能不进入任何交付。
9. Node 和 Agent 不能经 Cloud 提供的任何入口向镜像写入 ref。第一版不隔离（A1 D2），Agent 作为同一个系统用户在磁盘上
   改动镜像不在这条承诺之内。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 维持现状：变更视图读工作目录 | 不用新增任何东西 | 工作目录被清理后改动就没了，验收的人也拿不走改动（A1 D3 的已知缺口） |
| 内嵌 Git server，Agent 用凭据助手直接推送（2026-11-11 之前的 A4） | 成果由 Agent 自己推送，多机可用 | 要改 Node、凭据助手和 `ora-git`；单机下 Cloud 能直接读工作目录，用不上（A1 D2） |
| 用 Node 协议已有的 `DeliverRevision` 让 Node 交付 | Node 侧能力现成 | 它绑定 v1 的对象存储和上传授权，要把这套搬回 Cloud；单机下没有必要 |
| 交付提交以上一次交付为父，串成一条历史 | 相邻两轮的差异直接可读 | 中间一次失败或缺失，后面的交付就没有可靠的父提交；每次相对起点的快照可以单独使用（D2） |
| 只在任务结束或会话结束时交付 | ref 少 | 对话没有结束时刻；中途重启或清理会丢掉前面所有回合（D1） |
| 只提供 patch 下载，不留 ref | 最简单 | 工作目录被清理后就没法再生成 patch，也没法以后推回外部仓库 |
| 回合进行中也定期交付 | 进行中能看到改动 | 推送和记录随工具调用次数增长；owner 定为回合结束交付，以后需要再加 |

## 本决策未解决的问题

1. **推回外部仓库、开合并请求**：以交付为输入，另写 A4 的后续决策。
2. **交付的清理**：第一版全部保留（D6），镜像会随使用增长。
3. **人用 Git 客户端取交付**：第一版只提供 patch 下载，不提供 `git fetch` 入口。
4. **回合进行中的实时改动**：以后需要时再加，不改变本文的交付规则。
5. **Agent 进沙箱的前提**：物化技能时，Cloud 跟随检出里的 gitfile、`.git` 符号链接和排除文件链接去写 `info/exclude`。
   第一版不隔离（A1 D2），这不扩大 Agent 的权限；以后让 Agent 进沙箱，物化器必须先不再跟随这些由检出控制的指针写入，
   否则 Agent 能借它写到沙箱之外。这属于隔离的决策，不在本文。
