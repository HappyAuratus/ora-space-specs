# 回合交付：每轮结束由 Cloud 在进程内把工作目录做成提交，写进项目镜像里只新建的交付 ref；变更视图、验收和 patch 下载都读它；修改 A4 D5 与 A1 D3 的"第一版不交付"

Agent 每一轮结束（对话的一轮、任务运行的一轮、工作流 Agent 节点的一次尝试），Cloud 在自己的进程里把这次的工作目录
做成一个提交：父提交是会话的起点提交，用临时索引收进所有未被忽略的文件，不碰 Agent 自己的索引、分支和工作目录。
提交写进项目在 Cloud 数据卷上的镜像仓库，挂在一个只新建、不改写的**交付 ref** 上，PostgreSQL 记一条**回合交付**。
变更视图和验收改为读最近一次交付，不再读工作目录；用户可以从交付下载整份 patch，拿回去自己提交。任务要等这一轮的
交付完成才进入待验收。Node 不改，也不提供 Git server 的 HTTP 入口；以后上多机时改由 Node 推送同名的 ref。

本 ADR 处于 `proposed`：等 owner 评审，评审通过后改为 `approved` 并补核心测试用例。它是
[项目仓库根决策](0-external-repository-pull-and-encrypted-token.md)（下称“A4”）的后续决策，同时修改
[Cloud 单进程根决策](../lifecycle/0-single-process-cloud-on-enterprise-intranet.md)（下称“A1”）D3 的一句话。
依据是 owner 2026-11-12 在 circus #1102、#1107 的结论：恢复交付，选单机最小交付；沿用 2026-11-11 原 A4 的三点
（每轮交付、对话也每轮交付；交付完成才进待验收，失败记原因、任务回到可再次执行；交付第一版全部保留）。
读取的代码版本为 cloud `0ca0a9a0`（`v2-server/internal/workspacefs`、`projectrepos`、`store` 的 `v2_workspaces`
和任务状态转移、`taskrun`、`workflowhost`、`chat`）。

范围与兼容性边界：

- **涉及**：cloud 的 `v2-server/`（交付、变更视图、patch 下载、任务状态）和 `frontend-v2/` 的工作区面板。desktop 的
  Node 不改。
- **不在本文**：推回外部仓库、开合并请求（A4 未解决问题 1，以后另写决策）；回合进行中实时看到改动。
- **不做数据迁移**：本文落地之前的会话没有交付，它们的变更视图照旧读工作目录，工作目录被删除后就看不到了。

## 决策

### D1：什么时候交付

- **每一轮结束都交付一次**：对话的一轮、任务运行的一轮、工作流里 Agent 节点的一次尝试。一轮以成功、失败还是被停止
  结束都交付，因为失败和停止的回合也可能已经改了文件。
- **工作流**：同一次运行的 Agent 节点共用一个工作目录，所以每个节点尝试结束时交付的是整个运行到这一刻的工作目录。
- **只在回合结束时交付**，回合进行中不交付；进行中的改动要等这一轮结束才看得到。
- 交付在这一轮的执行结束之后进行，不阻塞执行服务接受同一会话的下一轮以外的工作；同一个工作目录的两次交付按顺序
  进行。

为什么每轮都交付：只在任务结束或会话结束时交付，中途 Cloud 重启或工作目录被清理，前面所有回合的改动都会丢；对话
本来就没有"结束"这个时刻。每轮交付让每一轮结束时的状态都有一份 Cloud 保管的副本。

### D2：交付提交怎么做

- 在 `workspacefs` 模块里，对工作目录用一个**临时索引**收进所有未被忽略的文件（遵守 `.gitignore` 和
  `.git/info/exclude`；Ora 物化进去的技能已经写在 `.git/info/exclude` 里，所以不进提交），生成树，再生成一个提交：
  - **父提交固定是会话的起点提交**（`v2_workspaces.base_commit`），不是上一次交付，也不是 Agent 当前的 `HEAD`；
  - 作者和提交者是固定的 Ora 身份，提交说明写明来源（对话、任务运行或工作流运行）和第几轮。
- **不碰 Agent 的状态**：Agent 的索引、`HEAD`、分支、stash 和工作目录都不变。Agent 自己做的提交照样体现在树里，
  但交付提交不引用它们。
- **没有改动**：树和起点提交的树完全相同时，记为一次“无改动”的交付，不写 ref。
- **加固**沿用 `workspacefs` 现有的 git 调用方式：关闭 hooks、fsmonitor、外部 diff 和 textconv，不读系统级配置，
  不弹认证提示。第一版 Agent 和 Cloud 是同一个系统用户（A1 D2），这些操作不增加 Agent 的权限。
- **大小上限**：一次交付新增的对象超过部署配置的上限（默认值实现时实测后定）时，这次交付失败，原因写明“改动过大”。

为什么父提交固定是起点：每次交付都是“相对起点的完整快照”，任意一次交付都能单独拿出来看、单独打成 patch，不依赖
前面的交付是否成功；Agent 在回合里改写自己的历史（`reset`、`rebase`）也不影响交付。代价是相邻两次交付之间的差异
要由两次交付对比得出，不能直接读一个提交的父子关系。

### D3：交付写到哪里

- **交付 ref** 写在项目的镜像仓库里：`refs/ora/deliveries/<projectId>/<deliveryId>`，`deliveryId` 是这次交付的
  UUID。交付 ref 只新建，不改写，不删除，和快照 ref 的规则一样（A4 D2）。
- **回合交付记录**存在 PostgreSQL：交付 ID、租户、项目、来源（对话 / 任务运行 / 工作流运行及其 ID）、第几轮
  （工作流是节点尝试）、起点提交、交付提交、结果（`delivered`、`empty`、`failed`）、失败原因、时间。
- **先写 ref，再写记录**：ref 写好之后才写结果为 `delivered` 的记录。两步之间 Cloud 崩溃，只会留下一个没有记录
  引用的 ref，它不出现在任何视图里，不影响使用。
- **同步不碰交付 ref**：A4 D3 的同步只把绑定的分支取进快照 ref，不读、不删、不改 `refs/ora/deliveries/` 下的任何 ref。
- Node 仍经本机服务只读访问镜像（A4 D2）。同一项目的 Node 在技术上能读到本项目的交付 ref，这和“项目就是信任
  边界”一致；第一版新会话仍从当前快照开始，不从某次交付开始。

为什么写进镜像、不另建仓库：镜像已经是项目在 Cloud 上唯一的仓库，和 PostgreSQL 一起备份（A1 D2）；交付提交的父提交
是快照里的提交，放在同一个仓库里不用复制历史。

为什么 ref 名用交付 ID、不用“会话/第几轮”：一次交付的身份由 PostgreSQL 的记录决定，ref 名只要唯一且永不复用。
按会话和轮次命名，在重试、并发或以后多机由 Node 推送时容易撞名。

### D4：变更视图、验收和 patch 下载都读交付

- **变更视图**（对话、任务运行、工作流运行三处的工作区面板）显示这个会话或运行**最近一次结果为 `delivered` 或
  `empty` 的交付**相对起点的改动：文件列表、增删行数、单文件 diff。回合进行中照旧显示上一次交付，并标明“本轮
  进行中”。
- 工作目录被 `-cleanup` 删除之后，变更视图照常可读。
- **浏览文件**（列目录、读文件）仍读工作目录：它看的是 Agent 现在的现场，不是交付；工作目录被删除时照旧返回
  `410 workspace_removed`。
- **下载 patch**：从某一次交付下载相对起点的完整 patch，包含新文件和二进制文件，能在起点提交上用 `git apply` 应用。
  patch 超过下载上限时提示“改动过大，无法在线下载”，交付本身仍保留。
- **读取权限**沿用工作区查看：对话的交付只有对话的主人能读；任务运行和工作流运行的交付，团队成员都能读。来源被
  删除（例如对话被删除）后，它的交付都不可读，交付 ref 留在镜像里（D6）。
- **交付失败**的那一轮在面板上显示失败原因，变更视图仍显示失败之前最近一次成功的交付。

### D5：交付和任务、对话、工作流的状态

| 来源 | 一轮结束后 | 交付失败时 |
| --- | --- | --- |
| 任务运行，一轮成功或失败结束 | 交付完成（`delivered` 或 `empty`）后，任务进入待验收 | 任务回到待处理，记下失败原因；用户可以重新执行，下一轮结束时再交付 |
| 任务运行，一轮被停止 | 照常交付，任务回到待处理（现状） | 同左，记下失败原因 |
| 对话 | 交付完成后对话照常可以发下一条 | 对话里显示这一轮交付失败和原因；会话不结束，下一轮结束时再交付 |
| 工作流 Agent 节点 | 节点结果照常写入，运行照常推进 | 节点和运行的结果不受影响，运行页显示这次交付失败和原因 |

- 任务在交付完成之前保持进行中，这段时间人工推进任务返回 `409 run_active`（现状的规则）。
- **Cloud 重启**：启动时先按 A1 D3 把未结束的执行标为中断，再对这些被中断的回合各补一次交付（工作目录还在时），
  然后才开始服务请求。补交付只是把磁盘上的现场存一份，不重做执行；任务仍回到待处理（A1 D3）。补交付失败照常记为
  `failed`。

为什么交付完成才进待验收：待验收的任务在 Cloud 上一定有一份可以看、可以下载的成果。先进待验收再异步交付，会出现
“待验收却看不到改动”的窗口。

为什么工作流节点不因交付失败而失败：工作流的结果是节点输出和变量池，改动是附带的产物；让交付失败改变节点结果，会把
一个存储问题变成执行语义的变化，还要处理 Loop、Iteration 里的失败策略。

### D6：保留

- 第一版**全部保留**：交付 ref 和回合交付记录不自动清理。删除项目时，镜像连同所有交付一起删除。
- 删除对话、删除工作流运行时，它们的交付记录和交付 ref 留着，但不再可读（D4）。
- 清理策略（按时间、按数量、随来源删除）以后另写决策。

### D7：以后上多机时怎么改

A1 D7 预留的接缝在这里继续成立：多机时 Cloud 读不到 Node 的工作目录，改为由 Node 在回合结束时做同样的提交，推到
Cloud 内嵌的 Git server 的同名 ref `refs/ora/deliveries/<projectId>/<deliveryId>`；回合交付记录、变更视图、patch
下载和任务状态的规则都不变。本文不为多机预先写 Node 协议或 Git server 的细节。

## 不变量

1. 每一轮结束（成功、失败或被停止）都恰好产生一条回合交付记录，结果是 `delivered`、`empty` 或 `failed` 之一。
2. 结果为 `delivered` 的记录，它的交付 ref 一定存在于项目镜像里，并指向记录里的交付提交。
3. 交付提交的父提交总是会话的起点提交；交付 ref 一经写入不再改变，第一版不删除。
4. 交付不改变 Agent 的索引、`HEAD`、分支和工作目录。
5. 同步不读、不删、不改交付 ref。
6. 任务只在这一轮的交付结果为 `delivered` 或 `empty` 之后进入待验收。
7. 变更视图和 patch 下载只读交付，不读工作目录；对话的交付只有对话的主人能读。
8. Node 和 Agent 不能向 Cloud 的镜像写入任何 ref。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 维持现状：变更视图读工作目录 | 不用新增任何东西 | 工作目录被清理后改动就没了，验收的人也拿不走改动（A1 D3 的已知缺口） |
| 内嵌 Git server，Agent 用凭据助手直接推送（2026-11-11 之前的 A4） | 成果由 Agent 自己推送，多机可用 | 要改 Node、凭据助手和 `ora-git`；单机下 Cloud 能直接读工作目录，用不上（A1 D2） |
| 用 Node 协议已有的 `DeliverRevision` 让 Node 交付 | Node 侧能力现成 | 它绑定 v1 的对象存储和上传授权，要把这套搬回 Cloud；单机下没有必要 |
| 交付提交以上一次交付为父，串成一条历史 | 相邻两轮的差异直接可读 | 中间一次失败或缺失，后面的交付就没有可靠的父提交；每次相对起点的快照可以单独使用（D2） |
| 只在任务结束或会话结束时交付 | ref 少 | 对话没有结束时刻；中途重启或清理会丢掉前面所有回合（D1） |
| 只提供 patch 下载，不留 ref | 最简单 | 工作目录被清理后就没法再生成 patch，也没法以后推回外部仓库 |
| 回合进行中也定期交付 | 进行中能看到改动 | 推送和记录随工具调用次数增长；owner 定为回合结束交付，以后需要再加 |

## 本决策未解决的问题

1. **推回外部仓库、开合并请求**：以交付为输入，另写 A4 的后续决策。
2. **交付的清理**：第一版全部保留（D6），镜像会随使用增长。
3. **人用 Git 客户端取交付**：第一版只提供 patch 下载，不提供 `git fetch` 入口。
4. **回合进行中的实时改动**：以后需要时再加，不改变本文的交付规则。
