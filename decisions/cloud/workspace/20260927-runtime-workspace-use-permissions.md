# 共享项目下按运行时创建者限制使用权限，管理员操作也遵守独占规则

项目继续由协作空间成员共享；运行时工作区增加独立的使用权限。第一阶段普通成员只能使用自己创建的运行时，当前有效管理员可以使用同协作空间全部运行时。获得使用权限只是必要条件，任何会改变运行时的普通操作还须取得[独占操作权](../execution-admission/20260927-exclusive-runtime-control.md)。管理员不能因为角色更高就同时写入他人正在使用的目录。

本 ADR 于 2026-09-28 经用户明确批准，状态为 `approved`；规则进入开发依据，尚未实现。涉及 Cloud、Ora 前端及执行入口；第一阶段不建立运行时授权关系、授予或撤销接口、授权界面，也不实现实时共同编辑。后续显式共享必须另行批准，不能以预留能力为由开放访问。核心用例见[运行时使用权限](../../../test-cases/cloud/workspace/runtime-workspace-use-permissions.md)，新保障的直接证据为 `Missing`。

## 现状与依据

最初代码核查基线为 Cloud `67dcbf95b408559acd5680cf36e84f30e4caad4a`、desktop `652af715cbca5f50c892299ea815a08896f41b35`、specs PR #55 `a81c263`。批准时 Cloud PR #33 与 specs PR #55 均已合入；本决策继承 #55 的一租户一空间及成员规则。specs 已同步上游 `e2c8dce`，并继承 Controller 过渡监听及 minicloud 退役规则；历史核查链接不表示最新代码已经提供本决策能力。

- [Cloud workspace 查询](https://github.com/ora-space/cloud/blob/67dcbf95b408559acd5680cf36e84f30e4caad4a/internal/core/store.go)与[执行准入](https://github.com/ora-space/cloud/blob/67dcbf95b408559acd5680cf36e84f30e4caad4a/internal/core/node.go)按活动租户成员身份放行，没有运行时创建者权限或操作者独占权。
- [创建流程](https://github.com/ora-space/cloud/blob/67dcbf95b408559acd5680cf36e84f30e4caad4a/internal/core/public.go)让运行时继承项目 `owner_user_id`，另以 operation 的 actor 记录请求者；不能将继承的 owner 当成实际运行时创建者。
- 每个运行时独立克隆仓库，解决目录隔离，不意味着当前 API 已实现个人专属使用权限。完整云端文件编辑、终端和 Agent 使用链路尚未交付；文档中的目标权限不代表这些功能已存在。

## 继承与修改

本叶子继承[协作空间根决策](0-collab-space-boundary.md)，当前成员规则以[一租户一空间](../tenancy/20260923-one-space-per-tenant.md)为准。

| 前序约定 | 本决策处理 |
| --- | --- |
| 一个租户恰有一个可见协作空间，租户成员关系是唯一角色与状态来源 | 继承，不变；不恢复独立空间成员表或空间 owner |
| 活动成员访问共享项目及创建运行时 | 继承，不变；其他成员仍可在共享项目创建自己的运行时 |
| 成员身份足以使用同租户任意运行时 | 修改：内容与操作再检查运行时创建者或当前管理员身份 |
| 项目 owner 与运行时继承 owner 保持持久外键和凭据关联 | 继承，不变；新增创建者事实，不重解释 owner |
| 项目级生命周期串行，独立克隆 | 继承，不变；不能代替运行时使用权限及独占控制 |

## 决策

### D1：身份有不同职责

| 名称 | 含义与权威来源 |
| --- | --- |
| 协作空间 | 用户可见的租户；不是执行目录或沙盒 |
| 项目持久归属 | `Project.owner_user_id` 及现有外键、凭据引用归属；不产生额外成员访问特权 |
| 运行时工作区 | 同一项目下具有自己代码目录、持久数据和生命周期的 Workspace；停止后业务身份仍保留 |
| 运行时创建者 | 实际创建请求的已验证用户，单独持久记录；main 运行时使用项目创建请求者 |
| 当前操作者 | 持有有效独占权的用户及其操作会话；既不改写创建者，也不转移项目或凭据归属 |
| 任务发起者 | 发起该执行的已验证身份，永久保留在执行和审计记录中 |
| 管理员 | 当前租户的有效 `admin` 成员；管理员平权，无跨租户权限 |

用户或 Agent 自报的 userId、创建者、角色不能参与授权。系统维护以有持久计划的系统执行身份记录，同时保留触发用户，不能伪装为创建者。

### D2：概况共享，内容与操作受限

下表以有效租户成员为前提。其他租户或已停用成员均不得访问。只读不要求独占，但仍要求内容使用权限；读取不承诺与并发写入形成文件系统快照。

| 行为 | 普通成员自己的运行时 | 普通成员他人的运行时 | 同空间管理员 |
| --- | --- | --- | --- |
| 查看名称、创建者、生命周期、忙闲概况 | 允许 | 允许 | 允许 |
| 查看代码、文件、命令与任务输出、受限操作详情 | 允许 | 拒绝 | 允许 |
| 只读进入已支持的内容界面 | 允许 | 拒绝 | 允许 |
| 进入操作模式、取得独占权 | 空闲时允许 | 拒绝 | 空闲时允许 |
| 编辑、Git 变更、执行命令、启动任务 | 有效独占权及写活动准入 | 拒绝 | 有效独占权及写活动准入 |
| 启动、普通停止、重启 | 有效独占权及生命周期前提 | 拒绝 | 同左 |
| 删除独立运行时 | 创建者，有效独占权且无活动 | 拒绝 | 有效独占权且无活动 |
| 接替已释放、过期或撤回的操作会话 | 自己的运行时，完成安全交接后 | 拒绝 | 完成安全交接后 |
| 强制停止正在运行的工作 | 拒绝 | 拒绝 | 按独立强停规则处理 |

main 运行时不因名称而向所有成员开放，也仍不能单独删除。项目删除继续要求管理员，并检查项目下所有运行时的活动和清理条件，不能成为绕过占用的入口。

概况不包含命令文本、路径、代码差异、任务提示词、输出或凭据引用。operation 查询、重试和事件订阅同样按目标资源校验，不能仅因“请求是我发起的”或“知道 operation ID”获取内容或执行能力。成员停用后，新 HTTP 请求与准入立即拒绝；事件流在下一次投递前重新校验。现有事件只作刷新提示，不加入受限内容。

### D3：第一阶段不交付共享授权

后续可以把使用权限扩展为“创建者、管理员或获得授权的成员”，但本次没有第三条授权来源。不得创建授权表、接受授权字段，或展示可成功操作的共享入口。被拒绝时明确提示无使用权限；有权限但占用时提示当前不可操作，两者不能混为同一种错误。

前端展示“我的运行时工作区”、创建者、当前占用状态与可用操作，管理员可切换查看全部。按钮依据服务端能力信息展示，实际请求仍重新授权。第一版通过各自运行时中的分支、提交、推送和代码评审合并协作；远端分支冲突由 Git 与仓库平台处理，不自动合并未提交目录。

### D4：历史归属迁移必须可证明

新增前向迁移；核查时最新编号为 0017，实施时按最新序号追加，不改写已发布迁移。独立运行时从原始创建 operation 的已验证 actor 回填，main 从原项目创建记录回填；只采用目标与创建动作确实对应且唯一的记录，不取最近操作人、项目 owner 或任意管理员猜测。

缺失、冲突或无法证明的历史创建者记为明确的未知状态，仅管理员使用。保留回填来源和异常可查性；本次不提供无审计的创建者转让。应用新授权前关闭旧的新操作入口，存量执行按独占协议对账和收尾，不把无独占记录解释为空闲。

创建者离开后，目录、项目、执行及清理引用保留，其他普通成员不因此继承权限；管理员可在安全交接后操作。最后管理员保护仍由租户规则承担。[凭据连续性](../project/20260927-repository-credential-continuity.md)另行处理仓库远程访问，不改写历史 owner。

## 同类产品与适用边界

以下官方资料核查于 2026-09-27，用于比较选择，不构成统一行业标准。

| 产品与来源 | 可借鉴行为 | 不直接套用的边界 |
| --- | --- | --- |
| [Multica runtime](https://multica.ai/docs/daemon-runtimes) | 默认私有，由拥有者显式开放其他成员使用 | 对应个人机器与工具；管理员也不能代替拥有者发布。Ora 本阶段是管理员可管理的云端运行时 |
| [Multica 项目资源](https://multica.ai/docs/project-resources) | 同目录任务串行，独立 Git worktree 支持并行 | 不能据此声称所有编辑、终端和 Agent 自动共用一套锁；Ora 当前按运行时独立 clone |
| [Coder 工作区共享](https://coder.com/docs/user-guides/shared-workspaces) | 显式共享同一环境，区分使用与管理能力 | 文档要求移除共享后重启生效；不符合 Ora 停用成员立即拒绝新请求的要求 |
| [Codespaces 安全](https://docs.github.com/en/codespaces/reference/security-in-github-codespaces)与[Live Share 协作](https://docs.github.com/en/codespaces/developing-in-a-codespace/working-collaboratively-in-a-codespace) | 个人环境与显式共同编辑可以分开设计 | Live Share 实时协作不是本次单操作者规则，也不能作为 Ora 已有冲突合并能力的证据 |

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 所有成员默认共同使用全部运行时 | 使用方便，但无法满足“未经授权不能操作他人的运行时” |
| 仅靠独立目录，不增加权限 | 解决目录互相覆盖的一部分问题，不能阻止成员进入并修改同一运行时 |
| 第一阶段即交付成员授权 | 表达能力更强，但需同时设计授予、撤销和历史访问；当前明确只交付创建者与管理员权限 |
| 管理员普通编辑绕过占用 | 管理便捷，却直接破坏单写者保证；紧急处置使用可审计强停 |

## 不变量与预期验收

1. 租户角色、项目归属、运行时创建者和操作者不能互相替代；跨成员创建不改写项目归属。
2. 知道资源 ID、持有旧链接、历史 actor 身份或前端按钮可见均不授予使用权限。
3. 同租户其他成员只能看约定的概况，不能经详情、输出、事件或重试旁路访问内容。
4. 管理员正常操作仍受独占控制；成员停用、管理员降级会影响下一次权限校验。
5. 新库、从 0017 升级、历史创建者缺失及创建者离开均保留数据与清理引用，不静默猜测归属。
