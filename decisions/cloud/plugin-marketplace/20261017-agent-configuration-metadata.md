# Cloud 从发布元数据读取 Agent 声明，配置与安装始终绑定同一发行目标

Cloud 同步市场时读取发布工具生成的静态 Agent 配置副本，页面只读已校验的目录快照；取得 schema
不运行插件、不创建 Workspace，也不默认下载 `.orax`。Node 安装时核对实际包内声明与派发的发行
关联一致。本文已实现；偏离 approved 版本之处写在 D1–D3 与“兼容与发布顺序”的“实际采用”条目里，
不扩大现有安装证据的覆盖范围。声明式个人 Agent 运行由部署开关控制：`plugins.personal_agent_target`
为空（默认）时一律以 `agent_adapter_unavailable` 拒绝，显式配置当前 Node 支持的 Linux target 后才接纳。

声明的格式和摘要归[Agent 声明决策](../../desktop/plugin/manifest/20261017-agent-configuration-declarations.md)，
个人值归[个人 Agent 配置](../model-access/20261017-personal-agent-configurations.md)。
本文只扩展 catalog、发布快照和安装交接，不让 Cloud 保存插件运行进度或接管 Node 安装职责。

## D1：同步静态副本，不在配置读取时运行外部工作

发布流水线从最终包生成声明副本与关联；Cloud 在受控市场 checkout 内读取，验证编码、大小、普通
文件、条目内 containment、声明版本、摘要和 release/target 对应关系。不能跟随链接逃出 checkout，
不能在 `$ref`、默认值或文件名中发现新的网络下载入口（声明里没有未知成员的容身之处）。结构与上限复用声明所有者的契约。

实际采用与已知缺口：副本路径的语法（无 `..`、绝对路径、盘符、空段）在清单解析时排除，读取时要求
最终文件是普通文件；但只检查了最后一段，副本路径上的**中间目录**若是符号链接仍会被跟随，“不能跟随
链接逃出 checkout”目前只对最终文件成立。读到的字节仍须通过声明摘要与编译才会成为可消费声明，
不能借此读出任意内容，但这与上述承诺不符，属于待修复的缺口。
Cloud 只校验每个 release 一份关联（声明版本、摘要、编译）；target 与声明的对应由 Node 对每个包的核验承担，
因为同一清单的所有 target 携带字节相同的声明。

目录读取只返回数据库快照，不在 HTTP 读取或 SQL 事务中拉取包、启动 adapter、探测模型或读取个人
Key。解析和摘要计算先在事务外完成，再原子提交源快照；同步失败保留上次完整快照的原有规则不变。

单个条目的声明无效时，不产生可消费的声明，记录有界原因。其他有效条目仍可同步；错误条目的旧
声明不得被挂到新 release 上（整源快照在一个事务里整体替换，没有旧行合并路径）。

实际采用：声明无效有两种形态。副本缺失、摘要不符、编译失败时，条目仍可见并带有界 issue，包本身
仍可安装、只是不能提供个人配置；而 `[agent_configuration]` 关联段本身格式错误（路径语法非法、未知键、
非 agent kind 携带、版本为 0）时整条 listing 在清单解析阶段被跳过，只记日志、从目录消失。已经冻结的安装/运行快照不被目录替换破坏。旧无声明插件仍可按已有
目录语义展示，但“未声明”与“声明无效/不支持”必须不同，后者不能隐式进入旧凭据路线。

## D2：选定版本的副本随发布快照保存，不跟随 latest

Space 管理员选择插件版本后，Cloud 按既有规则冻结 release，并同时保存对应声明及完整关联。
后续 catalog 更新不能给该选择换上新版本的 schema。声明身份包括来源、identifier、精确版本、
target/universal、包摘要与声明摘要；显示名称或下载 URL 变化不能代替这些身份。

个人配置页按用户正在浏览的空间解析发行上下文：入口出现在某个空间的插件页时，读取该空间
选定发行的声明；不落在具体空间的入口必须先选定空间或说明无法解析，不混用多个空间的发行。
没有运行 Workspace 也能显示声明；目标解析不明确时，
页面可以说明缺少可用目标，但不得以某个“相近”target 宣称配置可执行。安装可用性、声明有效性、
个人配置完整性和真实模型执行成功是四项独立事实。

同一用户可能在两个空间使用同一插件的不同版本。只有当前发行目标的声明指纹与该用户配置一致，
才可按个人配置决策启动；指纹不一致的空间里创建运行明确拒绝并说明原因，不通过静默回退某一
空间版本解决冲突。首期每用户每插件只有一份配置，至多与一个空间的声明指纹一致，在其中一个
空间修复会使另一个空间失配，见
[个人配置决策 D1](../model-access/20261017-personal-agent-configurations.md#d1连接与插件配置各有唯一的个人归属)。
保存提交包含编辑时的选择版本与声明指纹，服务器重新确认当前选择与指纹；编辑期间管理员升级，
旧页面得到冲突并保留草稿。

实际采用：提交携带的“选择版本”是空间插件选择行的版本计数，不是来源、版本、target、包摘要这组
发行身份；服务器据当前冻结发行校验指纹，冲突码区分发行变化与声明变化。因为安装进度写回也会推进
该计数，编辑期间仅安装状态变化也会触发发行冲突，属于偏宽的冲突判定，后果是多一次重新核对，
不会放过真正的版本变化。

## D3：Node 验证真实包，Cloud 不把元数据当安装成功

安装输入自包含已选择的发布目标及声明关联，Node 不自行同步市场。包摘要校验成功后，Node 对包内
`assets/config.json` 做静态编译和声明摘要核对；身份、target 或声明不匹配时该插件安装失败，不
发布一个可用于个人模型的新 installed descriptor。已有被租约占用的包不被替换，沿用维护规则。

Node 的安装结果必须让 Cloud 能把验证结果关联回原计划及精确声明身份；结果缺项、重复、错版本或
错摘要不能被接管为成功。具体协议字段由共享生成契约扩展，不只靠一个无上下文的 `installed=true`。
同一次安装重试使用原计划关联，不取新的 catalog 内容修补旧输入。

本决策按“结果绑定不可变计划并经 Node 核验即满足”解释：计划已冻结声明版本与摘要，Cloud 始终
保存原计划，并在接管结果时核对执行身份与计划一致。安装结果通过执行身份绑定原计划，携带插件
身份与 Installed 版本，不重复回显声明版本或摘要。结果只在原计划与执行上下文中构成声明证据；
脱离执行上下文的 `installed=true` 不是声明证据，结果自洽也不能替代 Node 对包内声明的核验。

实际采用：声明与包不符时 Node 只以通用的无效包失败码拒绝，协议里没有“声明不符”的专用原因，Cloud
无法据结果区分声明不符与其他包无效；Node 只在计划带发行关联时核对，计划没有关联（未声明或声明
无效）的包即使带有 `assets/config.json` 也按惰性元数据安装，个人配置路线由 Cloud 的声明门禁另行
拦住。Node 另在执行前持有包收据（记录包摘要与 target），启动前在租约内连同声明指纹、Settings 与协议
一并复验；Cloud 在派发前核对节点登记的模型 adapter 能力。

运行 Workspace 的本次 Agent 准备必须使用 Run 已冻结的发行关联，不能按准备时 Space 的最新期望
重新选择包。冻结发生在创建运行的事务里，覆盖 IssueRun；WorkflowRun 不在本期范围。管理员在运行排队期间升级，只影响之后创建的运行；旧运行若无法取得或验证原包，
按既有准备失败路径收尾，不改装新包后宣称满足旧绑定。其他 Workspace 的普通安装维护规则不变。

执行前还要再次核对所持安装租约、冻结发行关联与 adapter 能力；安装检查不是永久授权。目录副本
通过验证但实际包不可用时，报告安装/准备失败，不将模型缺凭据或用户设置错误混为一类。

## D4：个人配置入口不改变空间管理权

插件页可以展示“我的配置”，但个人配置的读写归已认证用户；空间管理员只管理安装期望、共享元数据
和安全汇总。任何成员查看他人的配置、连接或凭据都不能借用管理员安装权限。

内联新建连接调用同一个个人连接模块；Key 写入直接走受控凭据入口，不进入 catalog/Settings
元数据。配置成功不把 pending/failed 安装改为 installed；安装成功也不把未填写的个人配置标为可用。

## 兼容与发布顺序

新增元数据是持久快照的扩展，数据库用追加迁移，不回写历史运行或将旧包“补造”为已核验新声明。
保留已选 release 的能力来自其原快照，不能靠重新下载同版本但不同字节的包恢复。新格式不支持时
显示明确原因，缺配不能以旧版目录中同名插件兜底。迁移前已选择的版本没有关联，个人配置读取得到
“需要声明”，只有升级到带声明的版本才能获得资格（同版本重选不改变快照）。

离线产物若携带 Agent 插件，要求同时携带发布元数据与对应包并使用相同关联验证；离线不意味着跳过
schema/包摘要或执行能力检查。现场域名、密钥和个人配置不进入发布副本。发布方改了声明却未更新关联，
应在发布校验失败，不能等用户首次运行时才用“没有 schema”掩盖。

实际采用与缺口：官方发布工具从已构建归档读回字节再生成关联，在自己的流水线里按构造不会失配，
发布副本、清单与包作为同一次 release 的资产产出；但独立的离线产物机制与对应的安装验证尚未提供，
市场仓库自身也没有校验关联与副本一致性的检查，失配最终在 Cloud 同步时才暴露为条目 issue。
官方插件的发布开关按插件逐个打开，市场条目携带声明的时机晚于支持新 shape 的 Desktop 发行版。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 配置页启动插件获取声明 | 灵活，但未配置凭据/无 Workspace 时不可用，且读取页面产生执行副作用 |
| 每次打开页面下载完整包 | 字节来源直接，但大包/多 target 放大延迟、下载和归档解析成本 |
| 目录只保留最新声明 | 省空间，但旧 Space 选择与排队运行被最新内容改写 |
| 将个人值写入 Space 插件配置 | 集成简单，但把个人模型额度和权限变成空间共享资源 |
| 安装结果额外回显声明版本/摘要 | 结果自身携带精确声明身份，消费者可直接比对；但消费者仍须在原计划与执行身份内核对，且不能替代 Node 对包内声明的核验，还要同步扩展生成契约、两侧映射与结果校验 |

## 不变量与落地

1. 配置读取不启动 Agent、不创建 Workspace、不发模型请求。
2. 展示/保存/安装/运行的声明都能追溯到同一精确发行关联。
3. catalog 更新不改写已冻结意图；无效声明不回退为未声明。
4. 空间安装权和个人配置权相互独立，安装与模型可用性不能互相证明。

落地顺序是先完成发布和索引，再扩展安装输入/结果，最后接入个人配置与运行门禁。
验收见[配置元数据分发用例](../../../test-cases/cloud/plugin-marketplace/agent-configuration-metadata.md)。
动态模型发现、完整包镜像分发和跨源迁移不由本文扩大；Agent 接入必须经后续真实运行验收。
