# 协作空间插件由管理员选择，运行时变更等待空闲并取得维护独占权

插件选择仍属于协作空间，即用户可见的租户；安装状态属于该空间各项目下的运行时工作区。第一阶段只有管理员可以修改空间插件选择，普通成员可查看。安装和移除的真实副作用必须等待目标运行时空闲并取得维护独占权，不能借空间级配置绕过运行时占用。

本 ADR 为 `proposed`，修改 Cloud 插件权限和调度语义，不把插件改为成员私有或逐运行时独立选配，也不宣称现有 Node 已有真实插件执行器。

## 现状与继承

前序[插件市场根决策](0-plugin-marketplace.md)使用 `space_plugins` 保存期望选择、`workspace_plugin_instances` 保存逐运行时状态。[Cloud 当前实现](https://github.com/ora-space/cloud/blob/67dcbf95b408559acd5680cf36e84f30e4caad4a/internal/core/plugins.go)允许成员安装和移除，按项目下 live 运行时展开计划；项目忙时冲突，同项目其他实例可能保持 pending。不能声称现有 pending 已有无需再次请求的完整自动收敛。

| 前序约定 | 本提案处理 |
| --- | --- |
| 空间期望状态与逐运行时实例状态分离 | 继承，不变；空间明确指协作空间 |
| 成员可以修改插件选择 | 修改：当前有效管理员可修改，成员只读 |
| 同项目只能推进一个普通 operation | 继承；其余实例持久等待 |
| 忙时整个安装请求冲突，部分 pending 依赖后续请求 | 修改：保存管理员期望，执行等待可用条件并自动继续 |
| 外部 effect 先持久计划、固定版本、校验哈希、同次请求幂等 | 继承，不变 |
| 真实 Node 执行器接线尚未交付，新建运行时自动补装另行处理 | 继承；本次不能用 Cloud 模拟器宣布执行端完成 |

## 决策

### D1：只有管理员改变空间期望

安装、移除及显式版本变更检查当前租户管理员身份、资源版本和幂等键；普通成员发起时拒绝且不产生期望、operation 或 effect。市场读取与空间插件选择状态可由成员查看，受限运行时详情与执行日志仍按[运行时权限](../workspace/20260927-runtime-workspace-use-permissions.md)过滤。

管理员在界面上看到受影响运行时数量及“已完成、等待占用、等待启动、失败”等汇总。接受请求只表示期望已保存，不能显示为全部安装完成。记录管理员和期望版本；后续执行是已接受的系统维护责任，发起管理员离开不自动丢弃该责任。

### D2：维护与用户写入共用互斥边界

安装和移除均属于修改运行环境，执行前必须获得[独占准入](../execution-admission/20260927-exclusive-runtime-control.md)中的系统维护资格。没有有效人类操作会话、没有活动或未知执行，且运行时具备所需能力时才可领取。不能只检查 ready，更不能在卸载路径绕过同样的检查。

人类持有会话即使暂时没有活动，维护也不抢占；界面提示有维护等待，持有者可主动释放。维护已取得独占权时，用户获取返回占用；管理员普通编辑也等待。系统维护身份不获得任意项目操作权，仅能执行固定目标及期望版本的插件计划。

### D3：持久等待与幂等收敛

| 状态 | 条件与处理 |
| --- | --- |
| 待处理 | 期望与目标实例已保存；等待运行时无占用及项目普通 operation 槽位 |
| 等待启动 | 运行时已停止；不为装插件自行启动沙盒，后续正常启动后继续判断 |
| 执行中 | 原子取得维护资格并持久登记 effect 后派发；同项目其他实例继续等待 |
| 待对账 | 响应丢失、Node 重启或结果未知；查询原 effect，不新建重复安装 |
| 已完成 | 真实结果匹配目标插件与固定版本；释放维护资格，更新聚合状态 |
| 失败 | 记录安全的错误状态，仍完成已接受执行的对账；明确业务重试才建立新的执行尝试 |

调度器在可用状态变化或恢复扫描后继续处理 pending，不要求管理员再次点击安装。相同期望的幂等重放不制造新的实例操作；同版本安装的快捷返回不能阻止已有待办继续完成。

管理员改变期望时使用版本检查。尚未派发的旧期望可按新期望重新计划；已经派发的先确认原结果，再向最新期望收敛，不并发安装与卸载。同一实例等待期间被删除时保留删除/清理关联并退出安装候选，禁止恢复已删除运行时。不同项目可并行，仍须逐运行时互斥。

### D4：范围不随本次扩大

本次修复既有请求所覆盖的 live 运行时实例及持久 pending 的收敛；新建运行时自动补齐全部历史空间插件仍遵循根决策的后续范围，不默认为已解决。下载安全、固定版本和校验哈希保持原有契约。

真实插件执行器未接线时，相应生产执行能力不可开放，状态不能凭 Cloud 计划标为安装成功。若第一阶段要求开放该功能，Controller、Node 以及插件进程的停止、文件变更都必须满足[跨进程交付](../controller-integration/20260927-fenced-runtime-control-delivery.md)，作为同批依赖验收。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 保留普通成员可修改空间插件 | 日常方便，但会改变其他成员运行时的共同配置，越过本次使用权限边界 |
| 改为每个运行时独立选择插件 | 隔离更细，但改变已经确定的空间插件模型，非本阶段选择 |
| 管理员点击立即执行，不理会占用 | 操作快，但可能在 Agent/命令执行中替换文件或卸载运行依赖 |
| 只返回忙，让管理员反复重试全部实例 | 实现简单，但部分实例的责任不清，失败与等待难区分 |

## 不变量与预期验收

1. 普通成员修改被拒绝，不产生空间期望或跨运行时副作用；跨租户隔离继续成立。
2. 安装、升级与卸载均不能与人类或 Agent 写活动并行，管理员也不能绕过。
3. 多运行时、同项目槽位不足、运行时停止与 Controller 重启不会丢失 pending；释放后无需重复点击可继续。
4. 相同期望重放、期望变更、结果丢失和删除竞争不会重复执行或恢复已删除运行时。
5. 聚合状态区分接受、等待、成功与失败；受限日志不因空间汇总而泄露。

## 落地顺序与后续边界

批准后维护核心用例，先实现管理员权限、持久等待与维护互斥，再以真实插件执行器验证文件和进程边界，最后开放前端。保留原有插件租户隔离与固定版本测试。逐运行时选配、新建实例自动补装与自动升级需后续决策，不通过本次提案隐式引入。
