# 仓库访问凭据按团队、个人或未知归属管理，成员离开不转移个人凭据

项目共享与 Git 平台访问是两种权限。Ora 管理仓库访问凭据的引用及其可用状态，真实凭据仍由部署侧保管。优先绑定团队凭据；关联个人或归属未知的成员离开后，拒绝新增使用该凭据的远程仓库操作，保留项目、本地代码、历史引用和已开始任务。管理员显式绑定并验证团队凭据后，才能恢复受影响的新远程操作。

本 ADR 于 2026-09-28 经用户明确批准，状态为 `approved`，整体实施与验收尚未完成；涉及 Cloud、Controller、Node 与部署凭据提供方。不自动转移项目 owner、个人 Git 身份或密钥，不代替 GitHub/企业 Git 的授权，也不承诺撤销用户在外部 Git 平台的个人账号权限。核心用例见[仓库凭据连续性](../../../test-cases/cloud/project/repository-credential-continuity.md)，新保障的直接证据按核心用例逐项登记为 `Partial` / `Missing`。

## 现状与继承

本叶子继承[共享项目根决策](0-project-space-scoping.md)，并回答[一租户一空间](../tenancy/20260923-one-space-per-tenant.md)明确保留的“创建者离开后仓库凭据如何处理”。

- [Cloud 执行契约](https://github.com/ora-space/cloud/blob/67dcbf95b408559acd5680cf36e84f30e4caad4a/docs/execution-contract.md)只提供凭据引用，由基础设施解析；项目和运行时仍沿用项目 owner 的持久外键。
- desktop [Node Git 配置](https://github.com/ora-space/desktop/blob/652af715cbca5f50c892299ea815a08896f41b35/apps/ora-node/src/repository/config.rs)使用部署指定的 Git/SSH 配置；尚无核实完成的“Cloud 按项目引用选择凭据、执行端及时拒绝失效引用”的端到端实现。
- 因而 owner 外键不能证明凭据一定属于个人，也不能据 Cloud 状态宣布部署注入的静态凭据已经失效。

| 前序约定 | 本决策处理 |
| --- | --- |
| Project 可见性按租户成员，owner 保留持久外键职责 | 继承，不变 |
| Cloud 只保存基础设施凭据引用，不保存秘密值 | 继承，不变 |
| 成员移除不自动转移凭据 | 继承；增加对个人/未知引用的新使用限制 |
| 已开始任务收尾，保留审计与清理引用 | 继承，不变 |
| 所有现有凭据只按 owner 关联，无团队语义 | 修改：增加经审计的归属类型、适用范围与可用状态，不按旧字段猜测 |

## 决策

### D1：引用分类与 Ora 使用权限分开判断

| 类型 | 说明 | 关联成员离开后的行为 |
| --- | --- | --- |
| 团队 | 部署明确提供给该租户/项目使用，具备可审计授权依据 | 不因某位创建者离开自动停用；仍检查引用有效性和 Git 权限 |
| 个人 | 外部授权属于已记录的个人主体 | 拒绝以该引用进行新的远程操作，不将凭据移交其他成员 |
| 未知 | 旧数据或无法证明实际授权归属 | 不能自动视为团队；其既有关联成员离开后按个人风险收紧 |

新建绑定应显式记录类型及依据。历史引用先标未知，保留旧关联，不能通过批量把类型改为团队绕开验证。管理员的分类声明必须匹配部署提供的受控引用及其允许范围，不能仅修改展示字段就获得另一租户的凭据。

Ora 中“可以操作此运行时”与“远程仓库凭据可用”都满足时才允许新的远程动作；Git 平台仍可能因仓库角色、分支保护、过期或吊销拒绝。Git 提交作者字段不作为 Ora 用户身份或凭据归属证明。

### D2：停用成员立即阻止新请求，冻结引用不删除工作

成员停用事务同时使其新的 Ora 请求与准入失败，并标记受影响的个人/未知引用不可供新远程操作使用。团队引用不因保留的 owner 外键指向离开成员就被误停。用户恢复成员关系不自动解除凭据冻结，仍需管理员重新核验，以免重新启用外部已撤销权限。

| 操作 | 受影响凭据不可用时 |
| --- | --- |
| 新 clone、fetch、pull、push 或其他新远程仓库访问 | 拒绝，返回可行动但不泄露秘密的错误 |
| 已有目录读取、本地编辑、无需远程的构建或 Git 操作 | 按运行时权限及独占规则处理，不因远程凭据冻结统一封锁 |
| 已开始的任务 | 按已接受的执行范围收尾，保留原执行与引用版本；不扩展成无限新增任务的授权 |
| 停止、终止、对账、清理 | 继续履行已有责任，不以凭据不可用为由丢弃 |
| 已有运行时重新启动且不需要 clone | 按生命周期执行；若某步骤确实需要远程访问，再检查该步骤的凭据 |

Cloud 保存的意图尚未在执行端开始时，派发前必须重新检查；结果不明时按稳定执行身份对账，不能把成员移除当成外部动作未发生的证明。外部 Git 平台在任务中途撤销凭据可能导致任务失败，“允许收尾”不是成功保证。

### D3：管理员显式绑定团队引用并验证

管理员选择部署侧已配置且允许用于该租户/项目的团队凭据引用，声明目标仓库及所需能力，通过版本与幂等检查保存候选验证意图。Cloud 不接收密钥、密码或 token，也不直接访问任意远端地址验证。

Controller/Node 在受控目标和网络策略下验证该引用，再回写有范围的结果。只验证读取不能被记录为已经拥有推送权限；结果包含引用版本、仓库及已验证能力，不能永久保证之后不会过期或被撤销。验证错误只返回安全分类，不返回远端认证输出或原始凭据。

候选验证成功且项目绑定版本未改变时，短事务原子切换有效引用并记录管理员与依据。验证失败不覆盖原绑定；若原绑定已冻结则继续冻结。并发成员停用、绑定更新或引用撤销后，迟到验证不能恢复过期候选。改变凭据绑定不改写项目或历史运行时的 owner、创建者与任务发起者。

| 状态 | 触发 | 结果 |
| --- | --- | --- |
| 可用 | 关联个人/未知成员离开，或引用已确认失效 | 冻结 / 不可用；拒绝新增远程操作 |
| 原绑定保留，候选验证中 | 管理员提交受控团队引用 | 只验证候选，不自动改用未验证引用 |
| 候选验证中 | 验证成功，候选与项目版本仍匹配 | 原子切换；保留历史引用及执行关联 |
| 候选验证中 | 失败、权限变化、版本冲突或结果不明 | 不切换；明确失败或按原验证身份对账 |
| 可用 | Git 平台实际拒绝后续请求 | 本次失败并暴露可行动状态，不偷偷回退个人凭据 |

### D4：执行端真正按引用选择，不能回退全局静态凭据

执行计划固定引用身份、版本、仓库与所需能力；派发前检查当前可用性，执行端只能在受控范围解析。找不到引用、范围不符或能力不支持时明确拒绝，不退回 Node 全局配置中的另一套可用密钥。

凭据提供方按执行范围临时提供所需访问，结束后回收，禁止把长期可复用材料复制到工作目录或日志。旧任务仅可用原接受范围收尾，不能向新任务转交资格。工作负载与管理凭据的隔离要求见[跨进程交付](../controller-integration/20260927-fenced-runtime-control-delivery.md)。

治理范围是 Ora 管理的引用和执行入口；用户自行在外部平台保有的权限并未被本系统撤销。若开放任意 shell 后仍能读取部署的长期 Git 密钥，就不能宣称本决策冻结生效；必须先交付受限凭据提供路径。当前缺少这条链路应在交付证据中明确，不用 Cloud 数据库状态掩盖。

### D5：兼容性和历史保留

追加迁移记录引用类型、关联依据、有效绑定和状态，不删除旧凭据引用，不改写 owner 复合外键。正在执行的动作继续关联原版本；完成后新动作读取新绑定。失败验证、冻结原因和管理员变更保留审计，审计不含秘密或不必要个人信息。

历史未知引用在关联成员仍有效时保留既有使用边界，并显式展示待分类；成员离开触发收紧。升级不能将历史全局 SSH 配置默认为已验证团队引用；未具备按项目引用解析能力的执行端拒绝该新能力，部署修正后再开放。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 成员离开就删除项目或目录 | 回收简单，但误伤其他成员工作且丢失清理、审计和恢复引用 |
| 自动把个人凭据转给另一管理员 | 表面保持可用，却没有外部 Git 授权依据 |
| owner 指向谁就认定凭据属于谁 | 实现容易，但历史引用可能实际是团队凭据 |
| 只在 Cloud 标冻结，Node 继续用全局 SSH 配置 | 状态清晰但不约束实际 Git 访问，是未兑现的保障 |

## 不变量与预期验收

1. 创建者离开后个人/未知引用的新远程操作被拒绝，团队引用不因旧 owner 关联被误停。
2. 本地代码、已开始任务、历史执行和清理引用保留；离开用户不能利用引用恢复 Ora 权限。
3. 新绑定必须通过范围和能力验证；失败、并发变更、迟到结果及同次请求重放不误切换。
4. 实际 Git 访问使用计划中的引用，失效后不回退静态个人凭据；秘密不进入 Cloud、前端、日志或持久工作目录。
5. 新库与旧库升级不猜测团队归属，不重写历史 owner；外部凭据过期/吊销产生可解释失败。

## 落地顺序与后续边界

核心用例已建立；先交付引用分类和成员停用的权威状态，再接通真实受限凭据提供方与 Node，验证后开放管理员绑定界面。未经真实链路验证只标部分完成。外部 Git 组织成员同步、自动转让个人账号、完整凭据保管服务及自动修复分支权限不在本决策范围。
