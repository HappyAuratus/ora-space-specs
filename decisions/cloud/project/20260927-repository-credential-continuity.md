# 仓库访问凭据按团队、个人或未知归属管理，成员离开不转移个人凭据

项目共享与 Git 平台访问是两种权限。Ora 管理仓库访问凭据的引用及其可用状态，真实凭据由独立的 Credential Store 保管，只被 Repo Executor 一次性兑换，Controller、Node 和沙盒从不接触。优先绑定团队凭据；关联个人或归属未知的成员离开后，拒绝新增使用该凭据的远程仓库操作，保留项目、本地代码、历史引用和已开始任务。冻结的引用不会解冻；管理员或所有者经 Credential Store 提交新凭据，并通过一次成功的候选同步后，才恢复受影响的新远程操作。

本 ADR 处于 `implemented`：规则已由 Cloud、Repo Executor、Credential Store 和 Node 落地，依据 upstream main 的 cloud `fc12dbe4`、desktop `8b79b4f2`、cluster `a1f42ce4` 核对。批准版本（2026-09-28）把验证和执行放在 Controller/Node、把真实凭据留给部署侧提供方；最终实现改走 Repo Executor 与 Credential Store，差异集中记录在文末“与批准版本的偏离”。核心用例见[仓库凭据连续性](../../../test-cases/cloud/project/repository-credential-continuity.md)，同步与发布、Credential Store 和 Repo Executor 的细节分别见后续 ADR。

本文不自动转移项目 owner、个人 Git 身份或密钥，不代替 GitHub/企业 Git 的授权，也不承诺撤销用户在外部 Git 平台的个人账号权限。

## 继承与修改

本文继承[共享项目根决策](0-project-space-scoping.md)，并回答[一租户一空间](../tenancy/20260923-one-space-per-tenant.md)明确保留的“创建者离开后仓库凭据如何处理”。

| 前序约定 | 本决策处理 |
| --- | --- |
| Project 可见性按租户成员，owner 保留持久外键职责 | 继承，不变 |
| Cloud 只保存基础设施凭据引用，不保存秘密值 | 继承，不变。秘密值保存在 [Credential Store](../identity-access/20261016-git-credentials-in-independent-credential-store.md)，Cloud 只有引用、版本和能力证据 |
| 成员移除不自动转移凭据 | 继承；增加对个人/未知引用的新使用限制 |
| 已开始任务收尾，保留审计与清理引用 | 继承，不变 |
| 所有现有凭据只按 owner 关联，无团队语义 | 修改：引用带经审计的归属类型和可用状态，不按旧字段猜测 |
| 执行端使用部署指定的 Git/SSH 配置 | 修改：Node 不再持有任何仓库凭据配置，外部仓库只经 [Repo Executor](../repo-executor/0-repo-executor-sole-external-git-boundary.md) 访问（D4） |

## 决策

### D1：引用分类与 Ora 使用权限分开判断

| 类型 | 说明 | 关联成员离开后的行为 |
| --- | --- | --- |
| 团队 | 由租户管理员创建、绑定和撤销，所有者字段只是创建者 | 不因创建者离开自动停用；仍检查引用有效性和 Git 权限 |
| 个人 | 外部授权属于创建它的成员，只有所有者能绑定它、批准用它发布 | 拒绝以该引用进行新的远程操作，不将凭据移交其他成员 |
| 未知 | 升级前的旧引用，无法证明实际授权归属 | 不能自动视为团队；其关联成员离开后按个人风险收紧 |

- 新建引用只能是个人或团队，团队引用只有管理员能创建；`unknown` 只来自升级，没有任何接口把引用改为 `unknown` 或把 `unknown` 批量改为团队。
- 租户管理员不能绑定他人的个人凭据，也不能批准用它发布。
- Ora 中“可以操作此运行时”与“远程仓库凭据可用”都满足时才允许新的远程动作；Git 平台仍可能因仓库角色、分支保护、过期或吊销拒绝。Git 提交作者字段不作为 Ora 用户身份或凭据归属证明。

### D2：停用成员立即冻结个人和未知引用，不删除工作

成员或账号停用的同一事务把受影响的个人/未知引用置为 `frozen`；准入前的恢复扫描补上漏掉的状态变化。团队引用不因保留的 owner 外键指向离开成员而被误停。冻结是单向的：没有任何路径把 `frozen` 改回 `available`，成员重新加入也不解冻，以免重新启用外部已撤销的权限。恢复的唯一路径是绑定新的凭据（D3）。

| 操作 | 受影响凭据不可用时 |
| --- | --- |
| 新的同步、发布（含批准）或其他新远程仓库访问 | 拒绝；用户发起时返回 `409 repository_credential_frozen`，不泄露秘密 |
| 已有 Workspace 的读取、本地编辑，以及从 Git Server 快照 clone | 不受影响：快照 clone 不使用外部凭据，不因远程凭据冻结统一封锁 |
| 已 `running` 的同步或发布 | 已兑换过凭据，按原范围收尾，不扩展成新任务的授权 |
| 停止、终止、对账、清理 | 继续履行已有责任，不以凭据不可用为由丢弃 |

Cloud 保存的意图尚未在执行端开始时，签发执行授权前必须重新检查；结果不明时按稳定执行身份对账，不能把成员移除当成外部动作未发生的证明。外部 Git 平台在任务中途撤销凭据可能导致任务失败，“允许收尾”不是成功保证。

### D3：绑定新凭据先用候选同步验证，成功后原子切换

管理员（团队）或所有者（个人）把候选凭据经浏览器直接提交到 Credential Store，Cloud 不接收密钥、密码或 token，也不直接访问任意远端地址验证。候选凭据随后在一次 `credential_candidate` 同步里由 Repo Executor 验证：

- 同步成功且 Binding 的版本自候选提交以来没有变化时，在记录快照的同一事务里改写 Binding 的凭据引用，并记录该版本已证明 `read`；
- 同步失败、权限变化、版本冲突或结果不明时不切换，原引用若已冻结则继续冻结；并发的成员停用、绑定更新或引用撤销之后，迟到的验证因版本检查不能恢复过期候选；
- 读取成功不等于可推送：`read` 与 `publish` 能力分别验证，推送能力的验证方式见 Credential Store ADR；
- 验证错误只返回安全分类，不返回远端认证输出或原始凭据；改变凭据绑定不改写项目或历史运行时的 owner、创建者与任务发起者，历史同步由每个 Operation 记录的引用与版本保留。

| 状态 | 触发 | 结果 |
| --- | --- | --- |
| 可用 | 关联个人/未知成员离开，或引用已确认失效 | 冻结 / 不可用；拒绝新增远程操作 |
| 原绑定保留，候选验证中 | 管理员或所有者提交候选 | 只验证候选，不自动改用未验证引用 |
| 候选验证中 | 同步成功，Binding 版本仍匹配 | 原子切换；保留历史引用及执行关联 |
| 候选验证中 | 失败、权限变化、版本冲突或结果不明 | 不切换；明确失败或按原验证身份对账 |
| 可用 | 外部 Git 平台实际拒绝后续请求 | 该版本标为 `invalid`，暴露可行动状态，不回退个人凭据 |

### D4：执行端按引用选择，不回退全局静态凭据

同步和发布授权固定引用身份、版本、仓库与所需能力；创建 Operation 和签发授权前各检查一次可用性。Repo Executor 逐字段核对一次性授权后兑换该版本的凭据，缺失、范围不符或能力不支持时明确拒绝，不退回任何部署级默认凭据；公开仓库匿名访问，私有仓库没有引用时以 `repository_requires_credential` 结束。

- 凭据明文只写入当次任务的材料目录，只经 `git-credential-ora` 交给作用域内的请求，任务结束后销毁；不进入工作目录、日志、数据库或返回给 Cloud 的字段。
- 旧任务只能用原接受范围收尾，不向新任务转交资格。
- Node 的 Git 配置禁止 SSH、清空 askpass、忽略系统 Git 配置，不让部署凭据或 helper 进入工作负载；Workspace 的代码输入只来自 Git Server，沙盒里没有外部仓库凭据。
- 治理范围是 Ora 管理的引用和执行入口；用户自行在外部平台保有的权限并未被本系统撤销。

### D5：兼容性和历史保留

迁移追加引用类型、关联依据、有效绑定和状态，不删除旧凭据引用，不改写 owner 复合外键。升级后的历史引用保持 `unknown`，保留既有关联；成员离开触发收紧。失败验证、冻结原因和管理员变更保留审计，审计不含秘密或不必要个人信息。升级不把历史全局 SSH 配置当作已验证的团队引用：部署侧预置凭据的路径已删除，所有仓库凭据只经 Credential Store 提交。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 成员离开就删除项目或目录 | 回收简单，但误伤其他成员工作且丢失清理、审计和恢复引用 |
| 自动把个人凭据转给另一管理员 | 表面保持可用，却没有外部 Git 授权依据 |
| owner 指向谁就认定凭据属于谁 | 实现容易，但历史引用可能实际是团队凭据 |
| 只在 Cloud 标冻结，Node 继续用全局 SSH 配置 | 状态清晰但不约束实际 Git 访问，是未兑现的保障 |
| 重新加入或管理员核验后让冻结引用恢复可用 | 能少提交一次凭据，但可能重新启用外部已撤销的权限，也没有新的授权依据 |
| 由 Controller/Node 持有凭据并验证候选 | 批准时的方案；凭据会进入工作负载可达的进程，被 Repo Executor 与 Credential Store 取代 |

## 不变量

1. 创建者离开后个人/未知引用的新远程操作被拒绝，团队引用不因旧 owner 关联被误停。
2. 本地代码、已开始任务、历史执行和清理引用保留；离开用户不能利用引用恢复 Ora 权限；冻结的引用不会解冻。
3. 新绑定必须通过范围和能力验证；失败、并发变更、迟到结果及同次请求重放不误切换。
4. 实际 Git 访问使用计划中的引用，失效后不回退静态个人凭据；秘密不进入 Cloud、前端、日志或持久工作目录。
5. 新库与旧库升级不猜测团队归属，不重写历史 owner；外部凭据过期/吊销产生可解释失败。

## 本决策未解决的问题

- 外部 Git 组织成员同步、自动转让个人账号、凭据过期前的主动提醒及自动修复分支权限，不在本决策范围。
- 界面不展示引用归属，也没有“待分类”入口；历史 `unknown` 引用只能经新建团队或个人凭据替换。归属展示留给前端后续工作。
- 多仓库作用范围和 Credential Store 的外部 KMS、多副本，见 [Credential Store ADR](../identity-access/20261016-git-credentials-in-independent-credential-store.md) 的未决项。

## 与批准版本的偏离

| 批准时的决策 | 最终实现 | 原因 |
| --- | --- | --- |
| 真实凭据由部署侧保管；管理员选择部署侧已配置、允许该租户使用的团队引用 | 真实凭据由独立的 Credential Store 保管，管理员和所有者经浏览器直接提交；部署侧预置凭据的路径删除；管理员的分类声明由创建者角色决定，不再匹配部署提供的受控引用 | 个人凭据无从预置，管理员也无法自助；独立保管使 Controller、Node、沙盒都接触不到明文 |
| Controller/Node 在受控目标和网络策略下验证候选，并回写结果 | Repo Executor 通过一次 `credential_candidate` 同步验证，读取能力由成功同步证明，推送能力单独验证 | 外部仓库只经 Repo Executor 访问，验证复用同一条出网与凭据边界 |
| 项目绑定保留原引用，另存“有效引用”，候选成功后原子切换 | Binding 只有一个凭据引用列和 `version`；候选成功且版本未变时在记录快照的事务里改写它 | 避免两列凭据的优先级歧义；原子性、版本检查和失败不覆盖原引用不变 |
| 用户恢复成员关系后，由管理员重新核验才能解除冻结 | 冻结的引用永不解冻，恢复只能绑定新的凭据 | 核验不会产生新的外部授权依据，永不解冻更不易重新启用已撤销的权限 |
| 执行端是 Controller/Node，未具备按项目引用解析能力的执行端拒绝新能力 | 执行端是 Repo Executor；Node 不再有任何仓库凭据路径；“旧新执行端兼容”条款作废 | 代码链路整体破坏性切换，不设过渡开关、不迁移数据，旧执行端不再存在 |
| 历史未知引用显式展示待分类 | 界面不展示归属，历史 `unknown` 引用只在后端按规则收紧 | 前端没有实现归属展示，也没有记录原因；列入未决项 |
