# 一轮以取消或失败结束后，Node 先停掉这一轮新起的进程再判定是否保留会话（轮次进程栅栏，Linux）；轮次边界清单按平台登记

一轮以取消或失败结束、Agent 已经回应之后，Node 在判定会话能否保留之前，先停掉这一轮新起的进程：范围是带本尝试
`ORA_SESSION_ATTEMPT` 标记（或经被认领的父进程认领）的进程中，启动时刻不早于这一轮开始、且所在会话 id（sid）不在
这一轮开始时本尝试已有进程的 sid 集合里的那些。Node 复用尝试环境标记的冻结、pidfd 杀与“连续两次扫描干净”，
称为**轮次进程栅栏**。只有栅栏干净、取消决策 D2 原有的三条静止条件也都成立，会话才保留；扫描不可判定、杀不干净
或超出上限时，会话以新的 detail `turn_processes_unstopped` 结束。轮次边界的含义随之从“上游 Agent 自身的属性”改为
“Agent 回应 + Node 的轮次进程栅栏”，清单按（插件，版本，平台）登记，一致性测试验证的是这个组合在该平台上的表现。
这一期只在 Linux 上实现栅栏，首个登记是 Linux 上的 `official/ora-space.opencode 0.6.11`；Windows 及其他没有栅栏的
平台照旧以 `turn_boundary_unverified` 结束会话。行为变化是：会话被保留的取消或失败之后，这一轮工具起的后台作业和
开发服务器会被杀掉；一轮正常完成后仍不发任何信号。

本 ADR 状态为 `proposed`，按 [circus #1339](https://github.com/ora-space/circus/issues/1339) 的 owner 结论
（2026-11-23，方向 B）起草，实现由 [circus #1340](https://github.com/ora-space/circus/issues/1340) 并行进行。它修改
[取消一轮并在轮次结束后保留会话](20261116-cancel-turn-and-keep-session-after-turn-ends.md)（下称“取消决策”，`approved`）的
D2、D3、D4 的结算期限和验证义务 10、13，以及
[会话尝试的进程带环境标记](../agent-runtime/20261120-attempt-mark-in-session-stop-evidence.md)（下称“标记决策”，
`implemented`）D4 中“保留会话的取消与失败不发任何停止信号”一条。涉及 desktop 的 `apps/ora-node/src/session/`
（轮次开始的快照、D2 判定中的栅栏、新 detail、按平台的清单）与 `crates/utils` 的标记扫描（在认领结果上按轮次筛选，
读出 sid）。Node Protocol 的消息形状不变，只给既有的 `agent_failed` 增加一个 detail 值；账本 schema 不变（D6）；
Controller 只需把取消结论的等待上限 T 放宽到 G + F + Q 以上（D4）。本决策不处理 Windows（Job Object 方案留待实测）、
Claude 插件的 A2（[circus #1381](https://github.com/ora-space/circus/issues/1381)）、Strong 纳管，也不弥补清空环境后成为
孤儿的进程这一已知缺口。

放在 `protocol` 叶子目录，因为本决策改变的是取消决策的会话保留条件、协议可见的终态 detail 与结论期限，是取消决策的
直接后续；它只复用标记决策的扫描手段，不改变尝试的停止证据、证明名与账本，对标记决策只修改“保留会话时不发信号”
这一条行为说明。

## 问题与约束

取消决策 D2 只对“回应之后不再有任何本轮工作”的 Agent 保留会话，并把这一点当作上游 Agent 的属性，由一致性测试按
版本证明。[circus #1340](https://github.com/ora-space/circus/issues/1340) 用部署的两个发布包实测，两者都不具备这一属性：
Agent 回应 `cancelled`、工具状态已是 `completed`，工具起的后台 shell 在回应之后仍写工作目录，之后也没有任何本轮的
消息。Node 的三层检测（回应栅栏、静止条件、跨轮次检测）只看 Agent 发来的流量，看不到这种写入，所以清单只能为空，
部署版在运行中取消一轮时会话一律结束（`turn_boundary_unverified`）。

两个 Agent 都把工具 shell 放进新的会话（OpenCode bash 的 `detached`，Claude Bash 里的 `cmd &`），后台作业在外层 shell
退出后被 init 收养；它们继承了标记决策给尝试设置的环境标记。另一方面，两个 Agent 都会在会话中途懒启动常驻进程，
例如 OpenCode 在第一次需要诊断时启动 `deno lsp`，它在 Agent 自己的会话里，之后跨轮次使用。所以方案必须满足：

- **只杀这一轮的工作**：轮次开始前已有的进程（Agent、前几轮留下的开发服务器、常驻的 LSP 与 MCP）不能被杀；这一轮
  里由 Agent 懒启动、要跨轮次使用的进程也不能被杀。实测“本轮新起的一律杀”会杀掉懒启动的 `deno lsp`，OpenCode
  之后一直报告过期的诊断。
- **先停再派发**：下一轮的 prompt 写出之前，被取消那一轮的进程必须已经不在，否则它们与下一轮并发修改 checkout。
- **失败即结束**：判断不了是否停干净时不能保留会话；兜底是取消决策 D3 的结束会话，它会停止整个尝试。
- **不卡住 Node、有界**：扫描与杀沿用标记决策 D2 的阻塞 worker 和上限；取消结论仍要在有界时间内本地结算。
- **不依赖 Agent 配合**：OpenCode 没有任何能排在取消回应之前执行的钩子；Claude 的任务表管不到普通的 `cmd &`。
- **无特权**：当前 Linux 部署与 cloud v2 都没有委派的 cgroup 子树，方案不能依赖新的部署权限。

## 决策

### D1：轮次范围与轮次开始时的快照

**何时取快照**：一轮的 `session/prompt` 写给 Agent 之前，满足以下全部条件时，Node 取这一轮的快照：

- 会话选择了 `keep_session_on_cancel` 或 `keep_session_on_failure`；
- Agent 的（插件，版本）在本平台的轮次边界清单中（D5），而本平台实现了栅栏（这一期只有 Linux）。

快照针对接收这次 prompt 的 Agent 尝试，依次取两样东西：先取 `turn_since_ticks`，即此刻的 `CLOCK_BOOTTIME` 换算成 `/proc/<pid>/stat` 使用的 clock tick，
与标记决策 D1 的 `since_ticks` 同一时钟；再对本尝试做一次标记决策 D2 的扫描，记下每个被认领的存活进程所在的 sid，
得到**豁免会话集合** E。然后才写出 prompt。不满足上述条件的轮次不取快照，也永远不运行栅栏，不增加任何扫描。

**轮次范围**：栅栏只作用于同时满足以下三条的进程：

1. 被本尝试认领：带本尝试的标记，或其父进程是被认领的候选进程（标记决策 D2 的认领规则，含父进程复核）；
2. `start_ticks >= turn_since_ticks`；
3. 所在 sid 不在 E 中。

扫描中，满足 2、3 而属于标记决策 D2“待定”的进程（环境不可读、属于尝试用户、Node 不是该用户），使栅栏的观察为
Unknown；不满足 2 或 3 的进程，无论是否被认领、是否待定，都与栅栏无关。

**快照失败**：扫描失败、有待定进程、观察超出预算（标记决策 D2 的 5 秒，含排队），或这个尝试不带范围记录标志、
范围记录缺失或损坏（标记决策 D1、D3；新 Node 登记的尝试总是带标志），这一轮
记为“没有栅栏”。Node 照常写出 prompt，不推迟这一轮；这一轮若正常完成，没有任何影响；若以取消或失败结束，会话以
`turn_processes_unstopped` 结束（D3）。

为什么用 sid 划界：进程的 sid 只能从父进程继承，或经 `setsid` 新建一个以自己为首的会话，不能加入另一个已存在的
会话。所以本轮新起的进程，sid 在 E 中，说明它从某个轮次开始时就存在的会话一路继承下来，中间没有进程新建会话，
例如 Agent 在自己的会话里懒启动的 LSP、MCP 及其子进程；sid 不在 E 中，说明这一轮里（或快照之后）有进程新建了它，
例如工具 shell。实测的两个 Agent 都把工具 shell 放进新会话、把懒启动的常驻进程留在自己的会话里，这一规则恰好
把两者分开。两者以后若改变这种安排，一致性测试会发现（D5）。

为什么还要启动时刻：它把轮次开始前就存在的一切排除在外，包括前几轮起的开发服务器和正常完成的轮次留下的后台作业，
它们即使所在会话不在 E 中、即使标记被伪造，也不会被栅栏碰到。为什么先取时刻再扫描：两者之间出现的进程若在扫描时
存活，它所在的已有会话进入 E；扫描之后、prompt 写出之前新建会话的进程归入这一轮的范围。这段窗口很短，其中的进程
只可能来自之前的工作，把它们算给这一轮，代价只是它们在这一轮被取消时被杀。

**范围对后代封闭**：轮次范围内进程的后代也在范围内：它启动得更晚，sid 要么继承自父进程（不在 E 中），要么是新建的
（也不在 E 中），并经父进程被认领。所以标记决策 D2“先冻结、再杀”保住清空环境的子进程的论证，对栅栏同样成立
（D2）。唯一的例外是 PID 复用：E 中某个会话在这一轮期间成员全部退出、它的编号又被这一轮新建的会话复用时，那个
新会话被误认为豁免。内核在会话仍有成员时不会复用它的编号，这要求这一轮内 PID 空间回绕到同一编号，属于与标记决策
D2“同一 tick 内 PID 回绕”同类的理论缺口，后果是漏杀而不是误杀。

### D2：栅栏：只冻结并杀轮次范围，两次扫描干净才算停止

一轮以取消或失败结束、Agent 已经回应、D5 的登记与取消决策 D2 静止条件 2 都已满足时，Node 运行栅栏。栅栏由一到
多次**观察**组成，每次观察：

1. **终止**：按标记决策 D2 第 1、2 步冻结并杀，但只对轮次范围内的进程发信号：逐轮扫描、冻结新出现的范围内进程，
   至多 32 轮，冻结至多 2 秒（看门狗保证），再全部 SIGKILL；每个信号发送前按 PID 与启动 tick 重新确认、经新开的
   pidfd 发出。不执行第 3 步：不终止任何进程组，不检查尝试锁与线索。
2. **判定**：连续两次扫描，轮次范围内既没有被认领的进程，也没有待定进程，结论为**干净**；任一次有范围内的被认领
   进程为 **Running**；扫描失败、有范围内的待定进程或观察超出预算为 **Unknown**。

观察在标记决策 D2 的同一个阻塞 worker 上，与这个 Node 所有会话的停止观察串行，每次观察连同排队至多 5 秒。结论为
Running 或 Unknown 时，按标记决策 D2 的退避（25 ms 起倍增到 1 秒）再观察，直到干净或栅栏期限 F（D4）用完；每次观察
只拿 F 剩余的时间，剩余为零时不再派发。栅栏的结果是最后一次观察的结论。干净则继续取消决策 D2 的静默窗口（D4）；
否则会话按 D3 结束。

栅栏从不向 Agent 进程、轮次开始前就存在的进程、豁免会话中的进程发信号。Agent 在栅栏期间照常运行，它的进程组与
停止线索不变。

为什么复用标记决策的手段与上限：冻结轮数、冻结时长、重新确认与单一 worker 都已为“读挂住、fork 风暴、PID 复用、
fd 耗尽”逐项评审过；栅栏面对的是同一批进程，只是范围更小。范围对后代封闭（D1），所以“冻结后它刚 fork 的子进程
仍以它为父”的论证不变。为什么不终止进程组、不查锁：本尝试的进程组和锁属于仍要继续服务的 Agent，栅栏不是停止
尝试。为什么在 F 内重试：标记决策 D2 已知的短暂情形（收尾时重新确认失败的冻结进程留到下一次观察、排在其他会话的
停止观察之后超出预算）会让单次观察不干净，重试一次通常就能消除；重试仍失败时按失败结束，不放宽。

### D3：栅栏不干净时结束会话，detail 为 `turn_processes_unstopped`

以下情况，Node 按取消决策 D3 结束会话，终态 `agent_failed`，detail `turn_processes_unstopped`：

- 栅栏在 F 内没有得到干净的结论：最后一次观察为 Running（杀不掉，例如处于不可中断睡眠，或 fork 快于冻结）或
  Unknown（扫描失败、范围内有待定进程、观察超出预算）；
- 这一轮记为“没有栅栏”（D1 快照失败）。

结束决定与并入这次停止的各个 `TurnCancelSettled{session_ending}` 按取消决策 D3 同一事务落账，之后停止整个尝试：
标记决策的停止会杀掉本尝试的全部被认领进程，包括栅栏没能杀掉的那些，终态仍要等停止证据。

为什么取这个名字：它说出 Controller 关心的事实，这一轮起的进程没有被证明停下，涵盖杀不掉、看不清与时间用完三种
情况；与既有的 `turn_cancel_unanswered`、`turn_boundary_unverified` 同为“对象 + 未达成的状态”的形式，Controller 一眼
能看出它与轮次进程有关，而不是 Agent 没回应或版本没登记。不用 `turn_stop_unconfirmed`：它会与会话 MCP 刷新 D5 的
`stop_unconfirmed`（整个执行的停止责任超期）混淆，后者是终态之前的另一种状态，与这里会话结束的原因无关。不用含
“fence”的名字：栅栏是 Node 内部的手段，detail 描述可观察的结果。也不细分 Running 与 Unknown：两者对 Controller 的
处理完全相同，细分只增加协议面。

新 detail 沿用 `AgentSessionEnded.detail` 这一有界 snake_case 字符串，不改变消息形状，也不需要新的能力：Controller
按取消决策 D5 在声明 `turn_cancel` 时已承诺理解取消决策的 detail，本值与它们一样只出现在 `agent_failed` 中；按 detail
分支的 Controller 要在登记生效前识别它（落地顺序第 3 步）。

### D4：先后顺序与期限

Agent 回应之后，Node 按以下顺序处理一轮的取消或失败：

1. 写 `TurnEnded{cancelled}`（取消决策 D1，不变）。
2. 检查（插件，版本）在本平台已登记（D5），否则 `turn_boundary_unverified`；检查静止条件 2，否则
   `turn_not_quiescent`。这两种情况不运行栅栏，直接按取消决策 D3 结束会话。
3. 运行栅栏，至多 F（D2）；不干净按 D3 结束会话。
4. 栅栏干净之后开始静默窗口 Q。
5. 检查自回应起（包括栅栏期间）有没有轮次流量，有则 `turn_not_quiescent`。
6. 按受理顺序写并入这次停止的各个 `TurnCancelSettled`（`stopped`，或因失败而停时为 `already_ended`），会话保留；
   之后才准入下一轮，下一轮按 D1 取自己的快照，再写出 prompt。

**栅栏期限 F**：第一版暂定 10 秒，实测后定值，写入 `approved` 版本。它自栅栏开始起算，覆盖每次观察、终止与等待。

**结论期限**：

| 这次停止 | 本地结算期限 |
| --- | --- |
| `CancelTurn` 发起，Agent 在截止时刻前回应，栅栏运行 | 自发起的命令受理起 G + F + Q |
| 一轮失败发起，栅栏运行 | 自 Agent 回应起 F + Q |
| 并入一次停止的 `CancelTurn` | 不晚于那一次停止的截止时刻加 F + Q，因此不超过自本命令受理起的 G + F + Q |
| Agent 没有回应、第 2 步已决定结束会话 | 不运行栅栏，与取消决策相同（G + Q 或立即） |

- **期限各自独立**：G 在 Agent 回应时结束，栅栏不占用 G；Q 在栅栏干净之后才开始，栅栏不占用 Q；会话 MCP 刷新 D5
  的停止确认期限（10 分钟）只在作出结束决定之后起算，与栅栏无关，栅栏不干净时它从那次结束决定开始。
- **并入与优先**：栅栏期间受理的 `CancelTurn` 按取消决策 D1 并入这次停止，与它同时结算；栅栏期间生效的
  `EndSession` 按取消决策 D4 优先，会话以它的原因结束，进行中的栅栏观察结束后不再继续，整个尝试随后被停止。Agent
  进程退出或 ACP 连接断开，按取消决策 D3 的既有 detail 结束会话。
- **Controller 的等待上限**：取消决策 D4 的 T 改为必须大于 G + F + Q 加上传输余量（按暂定值为 27 秒加余量）。T 更短
  时，Controller 会在 Node 仍在正常运行栅栏时判定 Node 未结算。

为什么栅栏在静默窗口之前：杀掉这一轮的进程可能让 Agent 作出反应，例如为被杀的工具补发输出，或像 Claude 那样在后台
任务结束后自己发起一轮；Q 放在栅栏之后才能观察到这些反应，并让“回应之后没有轮次流量”覆盖到杀完为止。反过来先等 Q
再杀，杀后的反应会在下一轮 prompt 发出之后才到，与下一轮的更新无法区分；两者并行能省下至多 F，但有同样的问题。为什么
栅栏在第 2 步之后：已经决定结束会话时，整个尝试都会被停止，栅栏多余，只会推迟结论。为什么下一轮等栅栏：从回应到
杀掉之间这一轮的进程仍可能写 checkout，这些写入属于被取消的这一轮；下一轮在栅栏干净之后才派发，才能保证它开始时
checkout 不再被上一轮的进程修改。

为什么 F 独立于 G：G 按 Agent 正常取消的最坏耗时定值（取消决策 D2）；把栅栏塞进 G，栅栏能用的时间就取决于 Agent 回应
得多快，回应慢的 Agent 栅栏时间不够。为什么暂定 10 秒：与标记决策 D2 的 `recheck` 总上限相同，那是现有唯一一个在
请求路径上有界地停一次进程的操作；正常情况下栅栏一次观察（几十毫秒）就干净，10 秒容得下一次因排队或挂住而超出
5 秒预算后的重试。代价是取消后最坏多等 F，以及 Controller 的 T 随之变大。

### D5：轮次边界是“Agent 回应 + 轮次进程栅栏”，清单按（插件，版本，平台）登记

取消决策 D2 的“可依赖的轮次边界”改为：Agent 回应一次 prompt 之后，不再为这一轮发出任何轮次流量；并且经过 Node 的
轮次进程栅栏之后，没有这一轮的、仍在运行而不报告的工作。栅栏范围之外的工作（Agent 自身进程内的工作、豁免会话中
的进程、被杀后自发起的新一轮）仍须由 Agent 自己保证不存在。

- **登记键**：（插件 ID，插件精确版本，平台）。插件锁定上游版本，精确版本仍是唯一确定 Agent 实现的方式（取消决策
  D2，不变）。平台是 Node 运行的操作系统，当前取值 `linux` 与 `windows`（Desktop 只支持这两个平台）。CPU 架构不进入
  登记键：同一插件版本在各架构上来自同一份上游源码，栅栏与进程会话语义只取决于操作系统；一致性测试的运行记录写明
  所用架构。
- **Node 如何使用**：Node 只认自己所在平台的条目，且只在本平台实现了栅栏时才认；这一期只有 Linux。在 Windows 上，
  清单对 Node 等于空，任何一轮的取消或失败都以 `turn_boundary_unverified` 结束会话。其他平台的条目不影响本平台。
- **一致性测试**（取消决策验证义务 13 的修改）：在该平台上，以真实的 `ora-node`（栅栏启用）运行该版本的真实 Agent，
  构造：取消运行中的 shell 工具；取消起了后台作业的一轮（新会话中的作业，例如 OpenCode 的 `detached`，以及普通
  shell 里的 `cmd &`）；在被取消的一轮里让 Agent 懒启动 LSP 或 MCP；取消带子代理和后台任务的轮次；模型请求错误。
  记录回应之后到达的全部流量、`TurnCancelSettled{stopped}` 之后 checkout 的写入，并在下一轮使用懒启动的进程。只有
  回应之后没有任何轮次流量、`stopped` 之后没有这一轮的进程写入、懒启动的进程在下一轮仍可用、Agent 没有自发起一轮
  的组合，才进入清单。
- **首个登记**：Linux 上的 `official/ora-space.opencode 0.6.11`，在 #1340 的实现上通过上述一致性测试后登记。
  `official/ora-space.claude 0.4.5` 不登记：它的后台任务被杀后会自己发起一轮，这是栅栏范围之外的轮次流量；它的 A2
  （关闭后台任务、发新插件版本）由 #1381 承担，发版并通过测试后再登记。

为什么边界改为组合：实测两个 Agent 自身都不满足“回应之后没有本轮工作”，原定义下清单只能为空；它们违约的方式恰好
是 Node 能看到、能杀掉的进程。把栅栏算进边界后，一致性测试验证的是部署中真正起作用的组合，而不是一个已知不成立的
单方承诺。为什么按平台：栅栏是操作系统相关的机制，这一期只在 Linux 上实现和实测；同一插件版本在 Windows 上没有
栅栏，按 Linux 的测试结果放行等于把未验证的组合当作已验证。

### D6：轮次范围只在内存中，Node 重启按原规则结束会话并停止整个尝试

轮次开始时刻与豁免会话集合只存于 Node 内存，不写账本。账本 schema 不变。这一点依据现有 ADR 成立，已逐条核对：

- **会话不跨重启**：协议 D6 规定 Node 重启后会话以 `interrupted` 结束，不恢复 Agent；取消决策 D3、D4 规定重启时没有
  结束决定的会话，在重启收口中写入以 `interrupted` 为原因的结束决定，同一事务为未结算的 `CancelTurn` 写
  `session_ending`。所以重启之后不存在需要继续保留、需要重建栅栏的会话。
- **整个尝试被停止**：标记决策 D3 的重启收口表规定，同一 boot 上先按持久的范围记录冻结并杀掉原尝试的全部被认领进程，
  再取停止证据；跨 boot 按宿主重启证据处理。轮次范围是尝试范围的子集（`turn_since_ticks` 不早于尝试的 `since_ticks`，
  认领规则相同），所以栅栏要杀的进程在重启收口中都会被杀，终态之前取得证据。
- **栅栏中途崩溃**：被栅栏冻结、还没被杀的进程停在 T 状态，按标记决策 D2 由重启收口认领并杀掉。

因此 Node 在栅栏之前、之中，或在 `TurnCancelSettled{stopped}` 写入之后崩溃，结果都是会话以 `interrupted` 结束、整个
尝试被停止，与本决策之前相同。将来若有决策让会话跨 Node 重启保留，它必须重新处理轮次范围（见“本决策未解决的问题”）。

### D7：豁免保护什么，不保护什么

| 进程 | 栅栏 |
| --- | --- |
| 轮次开始前已存在的任何进程：Agent、前几轮起的开发服务器、正常完成的轮次留下的后台作业、会话开始时启动的 MCP | 不发信号 |
| 这一轮里 Agent 在自己的会话中懒启动的 LSP、MCP，以及它们在同一会话中的子进程 | 豁免，跨轮次存活 |
| 这一轮的工具 shell 及其后台作业、开发服务器、文件监视进程（工具 shell 在新会话中） | 杀 |
| 这一轮的工具以 `setsid` 启动的长期守护进程 | 杀 |
| 这一轮里 Agent 以新会话懒启动的常驻进程 | 杀；一致性测试要证明该版本的 Agent 能承受，否则不登记（D5） |
| 豁免会话中的常驻进程代这一轮起的工作，例如 MCP 服务的工具在自己的会话里起的后台进程 | 不在范围内，漏掉 |
| 清空环境后成为孤儿的进程、经 `docker run` 或 `systemd-run` 代启的进程 | 不在证据内，漏掉（标记决策 D6，BestEffort） |

owner 接受的代价：

- 会话被保留的取消或失败之后，这一轮工具起的开发服务器、后台作业会被杀；一轮正常完成时不受影响。需要跨取消存活的
  服务，要在之前的一轮里或在 Ora 之外启动。
- 从回应到杀掉之间的写入算在被取消的这一轮里，留在 checkout 中，不回滚；下一轮在栅栏完成后才派发。
- 清空环境的孤儿作业仍会漏掉，与标记决策 D6 相同，是 BestEffort。

### D8：威胁说明

标记决策 D8 的前提不变：标记不是秘密，同 uid 的进程可以伪造它。对栅栏而言：

- 伪造者只能让自己在这一轮开始之后启动、且不在豁免会话中的进程被杀。轮次开始前的进程由启动时刻排除；豁免会话中的
  进程由 sid 排除，而 sid 只能由进程自己经 `setsid` 改变，伪造者不能把别人的进程移出豁免会话。
- workload 可以让栅栏一直不干净：持续 fork、进入不可中断睡眠，或在 Node 与 workload 不同用户的部署中让自己不可读。
  结果是会话以 `turn_processes_unstopped` 结束、整个尝试被停止，是失败即封闭，不会在仍有本轮进程存活时保留会话。
- workload 可以逃出栅栏：清空环境后成为孤儿，或请豁免会话中的常驻进程（例如某个 MCP 服务）代为启动后台工作。这与
  会话 MCP 刷新 D5“证据假定 workload 配合”一致：栅栏与标记对恶意或失控的 workload 都只是 BestEffort，不是对抗性
  隔离。用户配置的 MCP 服务不在一致性测试的覆盖范围内。

## 不变量

1. 只有选择了保留、本平台登记了该（插件，版本）、且本平台实现了栅栏的会话，才在轮次开始时、prompt 写出之前取快照；
   其他会话不因本决策增加任何扫描或信号。
2. 会话在一轮取消（或失败）后保留，当且仅当：这一轮的 prompt 从未写给 Agent；或者会话选择了对应一项，Agent 的
   （插件，版本）在本平台登记，Agent 连接仍在，静止条件 1、2 成立，轮次进程栅栏在 F 内干净，且自回应起到栅栏之后的
   Q 结束都没有轮次流量。
3. 栅栏只向同时满足“被本尝试认领、`start_ticks >= turn_since_ticks`、sid 不在豁免会话集合中”的进程发冻结与杀信号；
   从不向 Agent、轮次开始前已存在的进程、豁免会话中的进程发信号，不终止进程组。
4. 栅栏干净要求最后一次观察中连续两次扫描既无范围内的被认领进程，也无范围内的待定进程；Running、Unknown、超出 F
   或这一轮没有快照，会话都以 `turn_processes_unstopped` 结束。
5. `TurnCancelSettled{stopped}` 写入时，这一轮栅栏范围内的进程都已不在；下一轮的 prompt 在它之后才写出。
6. 栅栏运行时，自发起的 `CancelTurn` 受理起 G + F + Q 内结论落账（失败发起时自回应起 F + Q）；不运行栅栏的停止，
   期限与取消决策相同。
7. 一轮正常完成后不运行栅栏，不发任何信号。
8. 轮次范围只在内存中；Node 重启后会话以 `interrupted` 结束，整个尝试按标记决策停止，账本 schema 不因本决策改变。
9. Node 只认本平台、且本平台实现了栅栏的清单条目；没有栅栏的平台上，取消或失败的一轮一律以
   `turn_boundary_unverified` 结束会话。
10. 停止保证仍为 `StopContainment::BestEffort`；栅栏干净不宣称这一轮的全部工作已经停止。

## 为什么不是这些替代方案

| 方案 | 优势与取舍 |
| --- | --- |
| A1：Claude 桥接走 ACP 的 JetBrains AIR async-task 扩展，取消时先停掉本轮任务（owner 已否决） | 实测可行，由 Agent 自己停后台任务，Node 不必杀进程。但它是私有扩展；桥接要把取消回应压到停止完成之后再转发、吞掉多出来的消息；管不到普通的 `cmd &`；OpenCode 没有对应的钩子 |
| 只在插件侧解决（A2 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`，或各插件在取消回应前自己清理） | 不改 Node，边界仍是 Agent 的属性。但 OpenCode 没有排在取消回应之前的钩子；A2 只去掉 Claude 的后台任务，普通 Bash 里的 `cmd &` 仍会逃逸；每个插件版本各自实现，Node 无法验证，违背“不依赖 Agent 配合”。A2 对 Claude 仍然需要，是栅栏之外的补充（#1381） |
| 本轮新起的进程一律杀，不按 sid 豁免 | 规则最简单，Agent 懒启动的东西也被清理。但实测会杀掉懒启动的 `deno lsp`，OpenCode 之后一直报告过期诊断，保留下来的会话不可用 |
| 只观察不杀：回应时仍有本轮新起的进程就结束会话 | Node 不在保留会话的路径上发信号。但开发服务器、后台作业很常见，几乎每次取消都结束会话，而结束会话会停止整个尝试，进程照样被杀；用户既失去会话又失去进程，比“杀掉并保留”严格更差 |
| 每轮一个 cgroup v2 子树，或 Node 做 child subreaper 加启动时刻 | cgroup 是唯一能给出 Strong 的方向，进程无权离开。但它需要委派的 cgroup 子树，当前无 root 部署与 cloud v2 都没有（标记决策的否决理由相同）；subreaper 只让孤儿挂到 Node 下，不说明属于哪一轮，Node 崩溃后失效，还要新的回收循环。两者都还要另行区分懒启动的 LSP 与工具作业，豁免规则不可省；#1340 的原型用它们验证了 sid 规则，落地选用已实现的标记扫描 |
| 先等静默窗口 Q，再运行栅栏；或两者并行 | 取消后少等至多 F。但杀掉进程引起的 Agent 反应（补发输出、自发起一轮）会在下一轮 prompt 之后到达，无法与下一轮区分（D4） |
| 栅栏时间计入 G | Controller 的 T 不变。但栅栏可用的时间取决于 Agent 回应得多快，回应慢时栅栏来不及，本可保留的会话被结束（D4） |
| 轮次范围写入账本 | 重启后可以只杀这一轮的进程。但会话本来就不跨重启，重启收口杀掉整个尝试已经覆盖轮次范围；为一份重启后无人使用的数据升级 schema 只增加迁移和单向兼容的成本（D6） |
| 快照失败时推迟写出 prompt，直到取得快照 | 每一轮都有栅栏。但快照只服务于少见的取消路径；为它推迟每一轮，会让 worker 挂住时所有会话的对话都卡住，而不只是取消后的保留受影响（D1） |
| 按 Agent 进程的直接子进程或进程组划定豁免，而不是按 sid | 不依赖会话语义。但懒启动的 LSP 与工具 shell 都是 Agent 的直接子进程，工具 shell 也可能沿用进程组；只有 sid 能区分“Agent 在自己会话里起的”和“新建会话的工作” |
| 清单只按（插件，版本）登记，栅栏对所有平台一体适用 | 登记更少。但栅栏只在 Linux 实现和实测，Windows 上没有栅栏，按 Linux 结果放行会保留未验证的会话（D5） |

## 已知风险与待实测

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 某个 Agent 版本以新会话懒启动 LSP 或 MCP | 被取消的一轮里起的常驻进程被栅栏杀掉，下一轮功能退化 | 一致性测试包含懒启动场景，不通过的组合不登记（D5） |
| Agent 对子进程被杀作出反应，发出轮次流量 | 会话以 `turn_not_quiescent` 结束，本可保留的会话减少 | 这是设计上要捕获的违约；一致性测试照实记录 |
| 多个会话同时结束，栅栏观察排在后面超出预算；或某次 `environ` 读取挂住 worker | 栅栏为 Unknown，会话以 `turn_processes_unstopped` 结束 | 失败即封闭；F 内重试一次；worker 挂住时与标记决策 D2 的后果相同 |
| 每轮多一次 procfs 扫描 | 选择了保留且已登记的会话，每轮 prompt 写出前多几十毫秒 | 只对这些会话取快照（D1）；实现阶段测量 |
| 从回应到杀掉之间的写入 | 下一轮看到被取消一轮写了一半的文件 | owner 已接受（D7）；栅栏期间不派发下一轮 |
| 豁免会话成员全部退出、编号被这一轮新建的会话复用 | 新会话中的进程被当作豁免而漏杀 | 理论缺口，与 PID 回绕同类（D1） |
| 仍使用 G + Q 设定 T 的 Controller | 栅栏运行时 Controller 误判 Node 未结算 | 登记生效之前，接入 `turn_cancel` 的 Controller 先放宽 T（落地顺序第 3 步） |
| F 的暂定值 | 偏小则重试不够，偏大则 T 变大 | 实现阶段测量栅栏耗时分布后定值，写入 `approved` 版本 |

## 验证义务

以下各条转为[轮次进程栅栏核心用例](../../../test-cases/node/protocol/turn-process-fence.md)，编号一一对应。取消决策的
验证义务 10、13 按本决策修改，在[取消一轮用例](../../../test-cases/node/protocol/cancel-turn-and-keep-session.md)中以
“（轮次进程栅栏）”行登记，不另占编号。

1. 会话被保留的取消：这一轮工具起的新会话后台作业（`setsid`、`detached`、`cmd &`）在 `TurnCancelSettled{stopped}` 写入
   之前已不在，之后不再写 checkout；下一轮的 prompt 在 `stopped` 之后才写出。
2. 这一轮里 Agent 在自己的会话中懒启动的 LSP 或 MCP 在栅栏之后存活，下一轮仍可使用；轮次开始前就存在的进程（包括
   前几轮起的、所在会话不在豁免集合中的开发服务器）不收到任何信号。
3. 轮次范围内的进程 fork 出、清空了环境的子进程经父进程被认领，与父进程一起被杀；豁免会话中常驻进程的子进程不被杀。
4. 栅栏不干净：注入扫描失败、范围内的待定进程、观察超出预算、杀不掉的进程，以及快照失败的一轮。每种情况都以
   `turn_processes_unstopped` 结束会话，并入的 `CancelTurn` 得到 `session_ending`，之后没有 `session/prompt`；终态在
   停止整个尝试、取得停止证据之后才写入。
5. 先后与期限：静止条件 2 不成立或版本未登记时不运行栅栏；栅栏期间到达的轮次流量使会话以 `turn_not_quiescent` 结束；
   Q 从栅栏干净时起算；栅栏期间受理的 `CancelTurn` 与这次停止同一结论；栅栏期间的 `EndSession` 优先；结论在 G + F + Q
   内落账（失败发起时自回应起 F + Q）。
6. 一轮正常完成后不发任何信号，它的后台作业进入下一轮；没有选择保留、或版本未登记的会话不取快照、不运行栅栏。
7. Node 在快照之后、栅栏之中，以及 `TurnCancelSettled{stopped}` 写入之后被杀并重启：会话以 `interrupted` 结束，未结算的
   `CancelTurn` 得到 `session_ending`，被冻结或仍存活的本轮进程在重启收口中被杀，账本 schema 版本不变。
8. 伪造本尝试标记、在轮次开始前启动的进程不收到信号；在轮次开始后启动、在新会话中的伪造进程被杀；持续 fork 的伪造者
   只让会话以 `turn_processes_unstopped` 结束，不会在它存活时保留会话。

取消决策验证义务的修改：

- **10**：Agent 的（插件，版本）只在其他平台登记时，或 Node 运行在没有栅栏的平台（Windows）上时，一轮取消或失败后会话
  以 `turn_boundary_unverified` 结束。
- **13**：一致性测试按（插件，版本，平台）在该平台上以真实 Node 的栅栏运行，场景与通过条件见 D5；Linux 上的 OpenCode
  0.6.11 通过后才登记，Claude 0.4.5 不登记。

## 本决策未解决的问题

- **Claude 插件**：被杀的后台任务之后自发起一轮，栅栏无法消除；A2 与新插件版本的登记由 #1381 承担。
- **Windows**：私有 Job Object 加进程创建时间可能构成等价的栅栏，需要实测后另立决策；在此之前 Windows 清单为空。
- **豁免会话中代办的工作**：MCP 服务、LSP 代这一轮起的后台进程不在范围内，需要能区分“谁请求的”来源，超出进程属性
  能表达的范围。
- **清空环境后成为孤儿的进程与 Strong 纳管**：沿用标记决策的未解决问题，需要 cgroup 或 subreaper。
- **用过子代理的轮次**：仍由取消决策静止条件 2 排除，栅栏不改变它。
- **用户希望跨取消存活的服务**：目前只能在之前的一轮或 Ora 之外启动；是否提供显式保留的方式，留给后续决策。
- **会话跨 Node 重启保留**：若将来允许，必须持久化或重建轮次范围（D6）。

## 落地顺序

1. **评审本 ADR**（运行 1，[circus #1380](https://github.com/ora-space/circus/issues/1380)）：按评审意见纠正后改为
   `approved`，同时维护核心用例；定下 F 的暂定值和 detail 名。
2. **实现**（运行 2，#1340）：轮次开始的快照、只作用于轮次范围的冻结与杀、栅栏期限与先后、新 detail、按平台的清单
   （默认为空）。完成条件：“验证义务”第 1–8 条与取消决策第 10 条有直接测试；以部署的发布包在 Linux 上跑完一致性
   测试，测得栅栏耗时，据此确定 F。这一步清单仍为空，部署行为不变。
3. **Controller 放宽 T**：接入 `turn_cancel` 的 Controller（cloud v2-server）把 T 设为大于 G + F + Q 加余量，并识别新 detail。
   完成条件：Controller 的发布版本已部署。这一步先于登记，避免栅栏运行时 Controller 误判超时。
4. **登记 OpenCode 0.6.11（Linux）**：一致性测试在实现上通过后加入清单；v2-server 锁定的 Node 与插件版本随之更新。
   完成条件：部署版运行中取消一轮后会话保留，可以接着对话。
5. **落地**（运行 3）：本 ADR 改为 `implemented`，按最终实现同步正文与核心用例证据。

保持不变：一轮正常完成、未选择保留的会话、未登记的组合、Windows 上的全部行为，以及会话结束与 Node 重启时停止整个
尝试的规则。从第 4 步开始改变：Linux 上登记的组合在取消或失败后杀掉这一轮的进程，再保留会话。
