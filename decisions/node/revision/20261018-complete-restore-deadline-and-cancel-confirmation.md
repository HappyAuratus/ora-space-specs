# Node 恢复有覆盖全程的截止与命令边界的取消：到期以 prior_revision_unavailable 终态，取消在 Git 命令之间停止并回报确定结束，半恢复 checkout 由交付判定兜底

恢复从第一步到检出完成共用一个可配置截止（默认 5 分钟），覆盖授权等待、下载或拉取、校验、取入、检出与祖先检查全程，任何子步骤不重置；到期或永久失败时 Agent 插件从未启动，会话以 `agent_failed` 加 `prior_revision_*` 结束，这份报告是 Cloud 恢复窗口内的真实 Node 记录，不把失败留给 Cloud 的超时路径。取消（用户结束、Cloud 策略结束、Node 停止）在 Git 命令边界生效：已开始的单条命令等它结束或其自身超时，之后恢复不再写 checkout，会话立即按相应原因终态，该终态报告就是停止确认。任何停止点的 checkout 都停在可交付的一致状态，交付判定对基础提交与前序最终提交都给出确定结果。Node 截止与 Cloud 的 2/6/5 窗口互不重置、不叠加计窗。

本文为 `proposed`，承接 [有界启动决策](../../cloud/issue-run/20261012-bounded-agent-startup-and-undispatched-withdrawal.md)（下称“启动决策”）D2 明确留给“后续 Node 恢复 ADR”的两项：Node 完整恢复截止，以及 Git 取消/停止确认。继承 [Node 恢复前序 Revision 决策](20261010-restore-prior-revision-before-session.md)（下称“现行恢复决策”，implemented）的步骤与失败分类。撰写时内部线恢复改造（`20261017-push-delivery-ref-and-restore-from-git-server`，把恢复介质从对象存储 bundle 迁到 Git Server 拉取，ora-space/specs#111，`proposed`）尚未合并；本文的截止与取消语义与传输介质无关，对两条介质路径都成立，合并后取代其“拉取、重试与取入共用 5 分钟时限”的局部表述（D5）。涉及 desktop 的 `apps/ora-node/src/revision/restore.rs` 及会话结束路径；Cloud 与 Controller 的窗口和消息不变。兼容性边界：不改现行恢复决策的步骤顺序、失败码、交付判定与能力声明；`RestorePolicy.deadline` 的含义从“授权等待与下载”扩展为“恢复全程”。

## 决策

### D1：完整恢复截止覆盖全程，任何子步骤不重置

- 起点：恢复流程的第一步开始——现行 bundle 路径为发出下载授权请求，内部线方向为输入校验或建立传输仓库。终点：检出指向前序最终提交且祖先检查完成。
- 覆盖范围：授权等待、下载或拉取（含全部重试与退避）、大小/摘要或提交核对、取入、`checkout` 与祖先检查。现行 `RestorePolicy.deadline` 的语义从“授权等待与下载”扩展为上述全程；`retries`、`resend`、`backoff`、`expiry_margin` 语义不变，它们的任何触发不重置截止。
- 默认 5 分钟，可配置，必须为正的有限时长；配置缺省用默认值，非法值拒绝启动恢复（与启动决策 D2 对非法窗口的处理一致），不能以零或负值隐式关闭。
- 到期时：等待类步骤（授权、下载、拉取重试）立即中止；已开始的 Git 命令等它结束或其自身超时，之后不再开始新的命令。恢复以 `prior_revision_unavailable` 失败，会话以 `agent_failed` 结束（现行失败分类不变）。
- 祖先检查放在截止内：它只影响首条提问的提示不改成败，但让“截止耗尽”有一个单一、可测试的判据——恢复整体完成。

为什么仍取 5 分钟：Cloud 恢复窗口 6 分钟从 Workspace ready 起算，先经意图声明、派发与 Node 领取才到恢复起点，再包含恢复后的 Agent 启动与首条记录；Node 恢复截止默认 5 分钟，加上分钟级的领取与启动余量仍落在 6 分钟之内，使正常失败由 Node 先给出带原因的确定结果，而不是 Cloud 先超时。实测恢复分段为秒级（登记到恢复完成 6.5–6.8 秒，3 档 bundle），默认值不依据这些样本宣称上界；大仓库与慢网络的首拉取缺生产数据，取值留给落地阶段实测调参，这也是保留可配置的原因。为什么不是每步独立时限：总和仍不可控，还是需要一个总截止，只多出一套参数；单条 Git 命令已有受管执行的自身超时，负责“单步不无限挂”。

### D2：与 Cloud 2/6/5 窗口的衔接：互不重置，谁先到按谁结算

| 场景 | 谁先给出结果 | 行为 |
|---|---|---|
| 恢复失败（截止到或永久错误） | Node | `agent_failed` + `prior_revision_*` 的会话终态是真实 Node 记录，Cloud 在恢复窗口内正常接管结算，Run `failed`，走正常失败路径而非策略超时 |
| 恢复进行中，Cloud 恢复窗口（6 分钟）耗尽 | Cloud | 启动决策 D3 结束等待：Thread `ending`、停止新输入、投递结束请求，进入 5 分钟结束确认窗口 |
| 结束请求送达 Node | Node 取消点 | 恢复按 D3 停止，会话按结束原因终态；Cloud 在确认窗口内接管真实终态 |
| 结束请求不可达（Node 失联） | Cloud 确认窗口耗尽 | 启动决策 D4 业务收尾 `failed/done` 并登记残留账本；Node 迟到的恢复与启动活动按原执行身份作为迟到事实接管，资源清理由残留回收 ADR 承接 |
| 恢复成功 | Node | 后续 Agent 启动继续受 Cloud 窗口约束（首条 Node 记录前），Node 截止不再起作用 |

- 不重复计窗的规则：Cloud 窗口起点是 Workspace ready，Node 截止起点是恢复第一步，两者互不重置、互不延长；Cloud 窗口耗尽不取消 Node 截止（Node 仍按自身截止失败或完成，结果作为迟到事实），Node 截止也不给 Cloud 窗口续期。
- Node 侧不感知 Cloud 的窗口数值，只按自身截止与收到的命令行动；衔接的正确性来自上述顺序约束，不要求两侧时钟同步。

为什么由 Node 先给确定结果：带 `detail` 的真实失败让 Cloud、Issue 页与下一次续接都知道“恢复本身失败”，而不是把一切折叠成超时；超时路径留给真正失联的场景。为什么 Cloud 窗口耗尽后 Node 仍继续执行到自身截止：中断 Node 内部状态没有额外收益，迟到事实反而可能补出真实终态或交付证据；业务上 Run 已收尾，资源风险由残留账本承接，这条边界在启动决策 D4 已定，本文不改。

### D3：取消点模型：命令边界生效，运行中的命令等它结束

- 取消来源：会话收到 `EndSession`（用户结束或 Cloud 策略结束投递的结束请求）、运行被取消、Node 优雅停止（shutdown）。
- 取消点：每条 Git 命令完成后、下一条开始前检查取消；等待类步骤（授权等待、下载、拉取重试间隔）随时可取消，立即生效。
- 已开始的单条 Git 命令不被打断：等它结束或其自身超时。为什么不打断：中途终止 Git 进程可能留下锁文件或半写状态，而等待的代价有界——单命令自身超时加 D1 截止兜底；取消要的是“不再推进”，不是“立刻静止”。
- 取消生效后：不再开始任何后续步骤，恢复不再写 checkout；会话立即按取消来源终态——用户结束按结束原因，策略结束与优雅停止为 `cancelled`（现行恢复决策 D1），崩溃重启为 `interrupted`。临时目录与传输介质的清理沿用现行规则：恢复结束（无论成败）即删，Node 启动时清空私有目录。
- **停止确认的回报**：取消生效后会话的终态报告本身就是停止确认——终态即“恢复不再写”的承诺，不需要单独的确认消息或状态。Controller 与 Cloud 不需要区分“会话结束于恢复前/中/后”：会话终态是它们已有的接办事实，恢复进度不进入协议。

为什么不为恢复单独引入可查询的进度/停止状态：那会为一次秒级的本地操作增加协议状态机与对账义务，而所有消费者真正需要的只有“会话终态 + checkout 可交付”两件事，后者由 D4 的不变量保证。

### D4：半恢复状态的兜底：任何停止点都可交付

取消或崩溃可能把恢复停在任意两步之间，checkout 只可能处于两种状态之一：

| 停止点 | checkout 状态 | 交付判定（现行恢复决策 D5） |
|---|---|---|
| 取入前序 ref 之前 | clone 基线：HEAD 在基础提交，工作区干净 | 最终提交等于基础提交 → `unchanged` |
| 检出之后 | HEAD 是本地分支，指向前序最终提交，工作区干净 | 最终提交等于前序最终提交 → `unchanged`，不生成 bundle / 不推新内容 |

- 中间步骤只写 Git 对象、Node 私有目录或（内部线方向）传输仓库，不改变“HEAD 与工作区一致”这一交付前提；因此停止点不产生交付判定无法处理的第三种状态。
- 崩溃重启后恢复不重做（现行规则）：会话已以 `interrupted` 终态，checkout 停在上述两种状态之一，交付判定照常给出确定结果；已知的残留（复制到 checkout Git 目录的 bundle 副本、崩溃时未删的传输仓库）只影响磁盘占用，由启动清理与现行未决项处理，不影响正确性。
- 该会话终态后的下一次续接运行重新选取同一 Revision，从新 checkout 重新恢复；本文不为“续传上次恢复”设计状态。

为什么取消后不把 checkout 强制转回基础提交：那要求在“恢复不再写”的承诺之后再写一次 checkout，与 D3 矛盾，且交付判定已经能处理两种状态；留在一个一致状态、由交付兜底是最小承诺。

### D5：与传输介质及内部线方向的关系

- 本文的截止与取消语义绑定在恢复流程的步骤边界上，不绑定介质：现行 bundle 路径（授权→下载→校验→bundle 头→补取→verify→取入→检出→祖先检查）与内部线 Git Server 方向（输入校验→传输仓库→拉取交付 ref→核对→取入→检出→祖先检查）都按同一规则执行。
- 内部线改造 ADR（`proposed`）的“拉取、重试与取入共用 5 分钟时限”由本文的完整截止取代：时限终点延伸到检出与祖先检查完成。其取消表述（“在下一条 Git 命令开始前停止”）与本文 D3 一致，以本文的完整语义为准。
- 内部线方向的介质不变量（恢复不访问外部仓库、带证书的 Git 只在传输仓库中以 Node 身份执行、恢复不改 `refs/remotes/ora/**`）由该 ADR 承担，本文不改；截止到期不改变其失败分类——拉取路径的 `prior_revision_base_unavailable` 判定仍按 Git Server 应答划分，不因超时改判。
- 若内部线改造合并，本文按其步骤表同步 D1 的步骤枚举；截止与取消规则本身不变。

## 不变量

1. 恢复截止覆盖从第一步到检出与祖先检查完成的全程；授权、下载、拉取、重试、取入、检出的任何事件不重置它。
2. 截止到期或恢复失败时 Agent 插件从未启动，会话以 `agent_failed` 加 `prior_revision_*` 终态；该报告是 Cloud 恢复窗口内的真实 Node 记录。
3. 取消只发生在步骤边界或无副作用的等待中；已开始的 Git 命令等它结束或其自身超时，取消后不再开始新的步骤。
4. 取消后恢复不再写 checkout；会话终态报告即停止确认，恢复进度不进入协议。
5. 任何停止点的 checkout 处于“clone 基线”或“前序最终提交”两种一致状态之一，交付判定对两者都给出确定结果。
6. Node 截止与 Cloud 的 2/6/5 窗口互不重置、互不延长；Cloud 窗口耗尽不取消 Node 截止，Node 截止不给 Cloud 窗口续期。
7. 崩溃重启后恢复不重做，checkout 由交付判定兜底（现行规则不变）。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 只给授权与下载设时限（现状） | 改动最小；但 Git 阶段无界，恢复可无限挂起，失败被折叠进 Cloud 超时，丢失 `detail` 与可解释性（D1） |
| Node 截止取与 Cloud 恢复窗口相同的 6 分钟 | 单一数值好记；但与 Cloud 窗口同时到期，两侧竞争结算，Node 失去“先给确定结果”的作用（D2） |
| 每步独立时限 | 粒度细；总和不可控仍需总截止，多一套参数与调优负担（D1） |
| 取消时打断运行中的 Git 命令 | 停止更快；可能留下锁或半写状态，而单命令本有超时，等待代价有界（D3） |
| 为恢复引入可查询的进度与停止确认状态 | 对账完备；为秒级本地操作增加协议状态机，消费者只需要会话终态与可交付 checkout（D3、D4） |
| 取消后把 checkout 强制转回基础提交 | 回到“干净起点”；与“取消后不再写”矛盾，交付判定已覆盖两种状态（D4） |
| 崩溃后重启续传上次恢复 | 省一次下载；会话已终态、恢复不重做是既有规则，续传要新增跨进程恢复状态，实测分段为秒级不值得（D4） |

## 本决策未解决的问题

- 大仓库、慢网络下默认 5 分钟的实测调参：落地阶段以直接测量修正默认值，本文只固定语义与可配置性。
- 内部线改造合并后 D1 步骤枚举的同步（形状变化时按其步骤表改写，规则不变）。
- 复制到 checkout Git 目录的 bundle 副本在崩溃后的清理（现行恢复决策未决项，内部线方向删除 bundle 后自然消失）。
- Node 侧截止的配置项命名与默认值随 desktop 实现承接 issue 固定。

## 落地顺序

1. **截止贯穿恢复编排**（desktop）：`RestorePolicy.deadline` 从只包授权与下载改为包住恢复全程，到期中止等待类步骤、等当前 Git 命令结束后终止。完成条件：截止到期时插件未启动、会话 `agent_failed`/`prior_revision_unavailable`、临时目录已清理；任一子步骤的重试不重置截止。
2. **取消点接入会话结束路径**（desktop）：每条 Git 命令之间检查 `EndSession`/停止/取消，等待类步骤即时取消。完成条件：取消点矩阵（取入前、检出后、下载中）各有直接测试，取消后会话按来源终态、checkout 状态可被交付判定处理、无新的写入。
3. **窗口衔接验证**：与 Cloud 的 6/5 分钟窗口按 D2 表逐行联合验证（含结束请求送达与不可达两分支的迟到事实接管）。
4. 内部线改造合并后同步 D5 的步骤枚举。

保持不变：现行恢复决策的步骤顺序、失败分类、交付判定、能力声明；Cloud 三个窗口的起点与时长；恢复进度不进入协议。从第 1 步起改变：恢复有了覆盖全程的截止；从第 2 步起改变：取消有明确的停止边界与确认语义。核心测试用例在本 ADR 转为 `approved` 后按规范补充。
