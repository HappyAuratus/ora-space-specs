# Node 恢复截止覆盖全程并把命令预算裁剪到剩余时间：到期请求关闭运行中命令，执行预算、停止请求与停止确认分开；取得停止确认前不发终态、禁止交付与复用；取消在 Git 命令边界停止；Agent 未启动的会话交付不探查工作区，半恢复检出恒为 unchanged

恢复从第一步到检出与祖先检查完成共用一个可配置截止（默认 5 分钟），任何子步骤不重置；恢复的每条受管 Git 命令以开始时的剩余截止为预算上限，因此到期时等待类步骤立即中止、运行中的命令被请求关闭。执行预算、停止请求与停止确认是三件不同的事实：预算到期只说明恢复不再等它，停止请求只说明关闭已被提出，停止确认才是“该 Git 进程已不再写入”的证据（受管执行观测到原 Scope 已 Closed，且该 Run 的直接进程已退出）。取得停止确认后，恢复在有界清理预算内以 `agent_failed` 加 `prior_revision_*` 终态结束（取消先生效时按取消原因）；在清理预算内取不到（guardian 不可达、关闭失败、进程状态未知）则不发终态，保留原 Scope/Run 与 checkout 冲突责任，禁止该会话交付与资源复用，由 Cloud 按启动决策 D4 有界业务收尾，Node 取得原停止证据后才补报终态。取消（用户结束、Cloud 策略结束、Node 停止）在 Git 命令边界生效：已开始的命令等它结束——等待的上界就是截止——之后恢复不再写 checkout，会话终态报告以同样的停止确认为前提，取得后即停止确认。命令边界取消后 checkout 停在“clone 基线”或“前序最终提交”两种一致状态之一；检出命令中途失败、被截止终止或崩溃可能留下混合工作区，但恢复的 Git 步骤中只有检出移动 HEAD 且只会移到前序最终提交，而 Agent 从未启动的会话交付不探查工作区（最终提交取 HEAD），结果恒为 `unchanged`，半恢复内容不会成为成果。Node 截止与 Cloud 的 2/6/5 窗口互不重置、不叠加计窗，谁先到按谁结算，不承诺 Node 必然先报告。

本文为 `proposed`，承接 [有界启动决策](../../cloud/issue-run/20261012-bounded-agent-startup-and-undispatched-withdrawal.md)（下称“启动决策”）D2 明确留给“后续 Node 恢复 ADR”的两项：Node 完整恢复截止，以及 Git 取消/停止确认。[内部线恢复改造](20261017-push-delivery-ref-and-restore-from-git-server.md)（下称“内部线 ADR”，`approved`，实现进行中；desktop main 仍是 bundle 路径，作为尚未切换的现状）的恢复步骤、失败分类与清理规则是本文的前向基线。本文的截止与取消语义与传输介质无关，对两条介质路径都成立，并取代其“拉取、重试与取入共用 5 分钟时限”的局部表述（D5）；继承 [Node 恢复前序 Revision 决策](20261010-restore-prior-revision-before-session.md)（下称“现行恢复决策”，implemented）并修改其恢复时限与交付判定。涉及 desktop 的 `apps/ora-node/src/revision/`（恢复编排、受管命令预算、交付判定）及会话结束路径；Cloud 与 Controller 的窗口和消息不变。兼容性边界：不改两条路径的步骤顺序、失败码与能力声明；交付判定新增隔离规则——恢复未完成的会话不再探查工作区改动（此类会话此前会把混合工作区快照成新提交）；`RestorePolicy.deadline` 的含义从“授权等待与下载”扩展为“恢复全程”，并新增受管命令预算裁剪（现状按命令自身预算独立计时，未裁剪）；新增“停止证据未知时不发终态、不交付、不复用”的路径（D6），此前该路径会被折叠成 `prior_revision_unavailable` 终态，而受管执行只承诺关闭请求、不保证取得 Closed 证据。

## 决策

### D1：完整恢复截止覆盖全程，命令预算裁剪到剩余时间

- 起点：恢复流程的第一步——内部线（前向基线）为输入校验，现行 bundle 路径（尚未切换的现状）为发出下载授权请求。终点：检出指向前序最终提交且祖先检查完成。
- 覆盖范围：输入校验、授权等待与下载（bundle 现状）或传输仓库建立与拉取（含全部重试与退避）、大小/摘要或提交核对、取入、`checkout` 与祖先检查。现行 `RestorePolicy.deadline` 的语义从“授权等待与下载”扩展为上述全程；`retries`、`resend`、`backoff`、`expiry_margin` 语义不变，它们的任何触发不重置截止；重试间隔会越过截止时不再等待（内部线既有规则）。
- **命令预算裁剪**：恢复的每条受管 Git 命令以开始时的剩余截止为预算上限：预算 = min(命令自身预算, 剩余截止)。受管执行按该预算计时，到期向 host 请求关闭该命令的 Scope。这保证恢复不再开启任何越过截止的 Git 命令——包括缺省 10 分钟、上限 20 分钟的网络命令：在截止前一刻开始的慢拉取不会用满自身预算拖到十数分钟之后——但关闭请求本身不是物理停止证据，见 D6。
- 默认 5 分钟，可配置，必须为正的有限时长；配置缺省用默认值，非法值拒绝启动恢复（与启动决策 D2 对非法窗口的处理一致），不能以零或负值隐式关闭。
- 到期时：等待类步骤（授权、下载、拉取重试）立即中止；运行中的命令被请求关闭（受管执行关闭其 Scope，等待观测到 `Closed` 并取得该 Run 的直接进程退出）；恢复在有界清理预算内删除临时目录与传输仓库（失败仅记录，由 Node 启动清理兜底）。
- **终态只在停止确认之后**：取得停止确认时，恢复报告 `prior_revision_unavailable`（内部线 D6 的分类，到期不改判），会话以 `agent_failed` 结束；取消已先生效时终态按取消原因，不因到期改判（D3）。在清理预算内仍取不到停止确认时，恢复不报告终态，按 D6 保留原 Scope/Run 与 checkout 冲突责任：该会话不交付、checkout 不复用，由 Cloud 按启动决策 D4 在结束确认窗口耗尽后业务收尾；Node 继续查询原 Scope/Run，取得原停止证据后才补报终态，该终态是迟到事实。
- 祖先检查放在截止内：它只影响首条提问的提示不改成败，但让“截止耗尽”有一个单一、可测试的判据——恢复整体完成。

为什么仍取 5 分钟：Cloud 恢复窗口 6 分钟从 Workspace ready 起算，先经意图声明、派发与 Node 领取才到恢复起点，再包含恢复后的 Agent 启动与首条记录。Node 恢复截止默认 5 分钟，在领取与启动为秒级的常态下，取得停止确认后的失败报告落在 6 分钟窗口内，由 Node 先给出带 `detail` 的确定结果；但这是默认值的选取目标，不是时序保证——领取排队、截止配置调大，或停止确认要等到清理预算耗尽，都可让 Cloud 窗口先耗尽，衔接由 D2 矩阵结算。实测恢复分段为秒级（登记到恢复完成 6.5–6.8 秒，3 档 bundle），默认值不依据这些样本宣称上界；大仓库与慢网络的首拉取缺生产数据，取值留给落地阶段实测调参，这也是保留可配置的原因。为什么不是每步独立时限：总和仍不可控，还是需要一个总截止，只多出一套参数；预算裁剪让单条命令的“不无限挂”与总截止直接耦合，不再需要第二套数值。

### D2：与 Cloud 2/6/5 窗口的衔接：互不重置，谁先到按谁结算

| 场景 | 谁先结算 | 行为 |
|---|---|---|
| Node 截止先到或永久错误，报告落在 Cloud 恢复窗口内（常态：领取与恢复启动为秒级） | Node | `agent_failed` + `prior_revision_*` 的会话终态是真实 Node 记录，Cloud 在恢复窗口内接管结算，Run `failed`，走正常失败路径而非策略超时 |
| Cloud 恢复窗口（6 分钟）先耗尽（领取或恢复启动晚、Node 截止配置较大、命令挂起） | Cloud | 启动决策 D3 结束等待：Thread `ending`、停止新输入、投递结束请求，进入 5 分钟结束确认窗口；Node 不感知 Cloud 窗口，按自身截止继续，结果作为其后的真实记录 |
| 结束请求送达 Node，已取得停止确认且终态报告在确认窗口内到达 | Node | 恢复按 D3 停止——等待类步骤立即、运行中命令至其被裁剪预算结束并取得停止确认——会话按结束原因终态，该终态即停止确认；Cloud 在确认窗口内接管真实终态 |
| 结束请求送达 Node，已取得停止确认，但终态报告晚于确认窗口（运行中命令直到被裁剪预算才结束，或报告晚到） | Cloud | 确认窗口耗尽按启动决策 D4 业务收尾 `failed/done` 并登记残留账本；Node 随后的终态报告是迟到事实，按原执行身份接管 |
| 结束请求送达 Node，但停止证据未知（guardian 不可达、关闭失败、直接进程状态未知、Node 在恢复期间崩溃） | Cloud | 恢复不发终态（D6）：原 Scope/Run 与 checkout 冲突责任保留，该会话不交付、checkout 不复用；Cloud 按启动决策 D4 业务收尾 `failed/done` 并登记残留账本，不把已投递的结束请求当作 Node 已停止的证明；Node 取得原停止证据后补报的终态是迟到事实，按原执行身份接管 |
| 结束请求不可达（Node 失联） | Cloud | 同上按 D4 业务收尾；Node 迟到的恢复与启动活动作为迟到事实接管，资源清理由残留回收 ADR（specs#126，approved）承接 |
| 恢复成功 | Node | 后续 Agent 启动继续受 Cloud 窗口约束（首条 Node 记录前），Node 截止不再起作用 |

- 不重复计窗的规则：Cloud 窗口起点是 Workspace ready，Node 截止起点是恢复第一步，两者互不重置、互不延长；Cloud 窗口耗尽不取消 Node 截止（Node 仍按自身截止失败或完成，结果作为迟到事实），Node 截止也不给 Cloud 窗口续期。
- Node 侧不感知 Cloud 的窗口数值，只按自身截止与收到的命令行动；衔接的正确性来自上述顺序约束，不要求两侧时钟同步。
- **不存在“Node 必然先报告”的保证**：两侧独立计时、起点不同——Node 的终态最早落在其截止加停止确认处，取不到停止确认时还要更晚，Cloud 的恢复窗口从 Workspace ready 起算且包含领取与恢复后的 Agent 启动。领取排队、截止配置调大或命令挂起都可以让 Cloud 先结算；矩阵每一行都给出确定语义，正确性不依赖“Node 先到”的时序假设。
- **停止与否只由证据判定**：矩阵任何一行都不把“已投递结束请求”“执行预算到期”“结束确认窗口耗尽”当作 Node 已停止；停止确认只由 D6 的证据给出，Cloud 的业务收尾与其物理停止证明始终分开。

为什么以“Node 先给确定结果”为常态目标：带 `detail` 的真实失败让 Cloud、Issue 页与下一次续接都知道“恢复本身失败”，而不是把一切折叠成超时；默认值按这个目标选取（D1）。超时路径不只属于失联场景：恢复启动晚或命令挂起时，在线 Node 的报告也会迟到，矩阵的迟到分支就是为它准备的。为什么 Cloud 窗口耗尽后 Node 仍继续执行到自身截止：中断 Node 内部状态没有额外收益，迟到事实反而可能补出真实终态或交付证据；业务上 Run 已收尾，资源风险由残留账本承接，这条边界在启动决策 D4 已定，本文不改。

### D3：取消点模型：命令边界生效，运行中的命令等它结束

- 取消来源：会话收到 `EndSession`（用户结束或 Cloud 策略结束投递的结束请求）、运行被取消、Node 优雅停止（shutdown）。
- 取消点：每条 Git 命令完成后、下一条开始前检查取消；等待类步骤（授权等待、下载、拉取重试间隔）随时可取消，立即生效。
- 已开始的单条 Git 命令不被打断：等它结束或其自身超时——其预算已被裁剪到剩余截止（D1），这个等待的上界就是截止，不再是命令自身的 10–20 分钟预算；此后仍需取得停止确认才能发终态（D6）。为什么不打断：中途终止 Git 进程可能留下锁文件或半写状态，而等待的代价有界；取消要的是“不再推进”，不是“立刻静止”。
- 取消生效后：不再开始任何后续步骤，恢复不再写 checkout；会话按取消来源终态——用户结束按结束原因，策略结束与优雅停止为 `cancelled`（现行恢复决策 D1），崩溃重启为 `interrupted`。终态原因按先到者：取消先生效按取消原因，即使截止随后到期也不改判为 `prior_revision_unavailable`。终态只在取得停止确认后发出（D6）；崩溃重启时若前一个 Node 进程未取得停止确认，按 D6 保留原 Scope/Run 与冲突责任，不发 `interrupted`，取得原停止证据后补报。临时目录与传输介质的清理沿用现行规则：恢复结束（无论成败）即删，Node 启动时清空私有目录。
- **停止确认的回报**：取消生效后，会话终态报告同时是停止确认，前提是取消所等待的那条 Git 命令已取得停止确认（受管执行观测到原 Scope 已 `Closed` 且该 Run 的直接进程已退出）。取得时，终态即“恢复不再写”的承诺与“命令已结束”的证据，不需要单独的确认消息或状态；取不到时按 D6 不发终态、保留原 Scope/Run 与 checkout 冲突责任。Controller 与 Cloud 不需要区分“会话结束于恢复前/中/后”：会话终态是它们已有的接办事实，恢复进度不进入协议。
- **与截止到期的差别**：取消等运行中的命令自然结束，保持取消点的两态一致（D4）；截止到期则由受管执行请求关闭运行中的命令——恢复已在失败路径上，终止可能留下的混合工作区由 D4 的交付隔离兜底，而不是为保全 checkout 状态让截止失效。两条路径都必须先取得停止确认才发终态（D6）。

为什么不为恢复单独引入可查询的进度/停止状态：那会为一次秒级的本地操作增加协议状态机与对账义务，而所有消费者真正需要的只有“会话终态 + checkout 可交付”两件事，后者由 D4 保证。停止确认未知的路径（D6）同样不新增协议状态：它只表现为“会话没有终态”，由 Cloud 按已有业务收尾处理。

### D4：半恢复状态的兜底：取消停在一致状态，检出故障由交付隔离

取消只发生在命令边界或无副作用的等待中，因此取消点的 checkout 只处于两种状态之一：

| 停止点 | checkout 状态 | 交付判定（现行恢复决策 D5） |
|---|---|---|
| 检出命令开始前 | clone 基线：HEAD 在基础提交，工作区干净 | 最终提交等于基础提交 → `unchanged` |
| 检出命令成功后 | HEAD 是本地分支，指向前序最终提交，工作区干净 | 最终提交等于前序最终提交 → `unchanged`，不生成 bundle / 不推新内容 |

但检出命令本身不是原子的：`git checkout --force -B` 可以在分支 ref 已指向前序最终提交、部分文件已更新后失败——例如某个文件被外部锁定时 Git 以非零退出，留下 HEAD 已移动、工作区部分更新的混合状态（review 中以文件锁实验证实）；受管执行的到期请求关闭（D1）与进程崩溃同样可能落在逐文件更新的中间。因此故障路径存在第三种物理状态——混合工作区——不能靠“停止点只在边界”排除。

处理规则是交付侧隔离，不是回滚：

- **恢复未完成的会话不探查工作区**。带前序输入且恢复失败、取消或中断的会话，Agent 从未启动，工作区里只可能是恢复残留，不可能是成果：交付判定跳过工作区改动探查，最终提交取 HEAD。恢复的 Git 步骤中只有检出一步移动 HEAD，且只会把它移到前序最终提交（bundle 路径的 `fetch <bundle> <head>:<head>` 与内部线的取入都只写 `refs/ora/revisions/` 下的 ref 或 `FETCH_HEAD`，不动分支），因此最终提交恒等于基础提交或前序最终提交，交付结果恒为 `unchanged`，不生成 bundle、不推新内容；半恢复内容不会成为成果。
- **停止证据未知时不交付**。上面两条只在“该会话不再有 Git 写入”的前提下成立。D6 的路径（取不到停止确认）不满足这个前提：checkout 的 HEAD 仍可能被原 Git 进程移动，工作区仍在变化。此时交付被禁止，不只是“不探查工作区”：即使最终提交恰好落在两个合法值之一，也不能在可能仍写入的 checkout 上做快照、读 HEAD 或推新内容。交付以“该会话的恢复已终止”为前提，而恢复已终止只由停止确认给出。
- **混合工作区随 Workspace 消失**。运行 Workspace 一次性使用；下次续作重新选取同一 Revision、从新 checkout 重新恢复，残留只影响磁盘占用。崩溃重启后恢复不重做（现行规则），`interrupted` 会话同样适用上面的隔离判定。
- 临时状态清理沿用现行与内部线规则：恢复结束（无论成败）即删临时目录与传输仓库，Node 启动清空私有目录（`.ora-transport/` 保留尚在取入的 clone 传输仓库）；复制到 checkout Git 目录的 bundle 副本在崩溃后可能残留，是现行恢复决策的未决项，内部线切换后自然消失。
- 本文不为“续传上次恢复”设计状态。

为什么取消后不把 checkout 强制转回基础提交：那要求在“恢复不再写”的承诺之后再写一次 checkout，与 D3 矛盾，且交付判定已经能处理两种状态；为什么检出故障后也不修复（重跑检出或 reset）：见“为什么不是这些替代方案”。

### D5：与传输介质及内部线决策的关系

- 内部线 ADR（`approved`，实现进行中）已把恢复迁到 Git Server 拉取，其 D5 步骤表是本文的前向基线：校验输入 → 建立 `restore` 传输仓库（借用 checkout 对象）→ 以 Node 身份拉取交付 ref → 核对最终提交 → 以工作负载身份取入 → `checkout --force -B <Workspace 分支短名>` → 祖先检查（改写提示）→ 删除传输仓库。本文 D1 的步骤枚举即按这份已批准的步骤表。
- 其局部时限表述（“拉取、重试与取入共用 5 分钟时限”）由本文完整截止取代：终点延伸到检出与祖先检查完成，且每条命令预算裁剪到剩余截止；“下一次间隔会越过时限时不再等待”继承。其取消表述（“在下一条 Git 命令开始前停止，并等正在运行的那条结束”）与本文 D3 一致，以本文的完整语义为准。
- 其失败分类（D6）与清理规则继承：取得停止确认后，截止到期仍按 `prior_revision_unavailable`，`prior_revision_base_unavailable` 仍按 Git Server 应答划分，不因超时改判；传输仓库用完即删，Node 启动清理 `.ora-transport/` 残留（保留尚在取入的 clone 传输仓库）；请求关闭命令后的删除同样在有界清理预算内，删除失败只记录、不参与停止证据的判定（本文 D6）。
- 介质不变量（恢复不访问外部仓库、带证书的 Git 只在传输仓库中以 Node 身份执行、恢复不改 `refs/remotes/ora/**` 与仓库配置）由内部线 ADR 承担，本文不改。
- 现行 bundle 路径（desktop main 尚未切换的现状）同样套用本文规则：授权等待、下载、校验、bundle 取入与检出的每一步都在截止内、预算被裁剪；其临时目录 `revision-restores/` 的清理沿用现行规则。本文的截止与取消语义绑定在恢复流程的步骤边界上，不绑定介质，内部线合入后无需再改本文语义。

### D6：执行预算、停止请求与停止确认分开；证据未知时不发终态、不交付、不复用

受管执行只承诺“请求关闭并查询结果”，不承诺“一定能在有界时间内证明进程已停止”。现行 process 决策明确允许这些情况：guardian 不可达或被强杀且无独立清理证据时保持未知（[进程恢复根决策](../process/recovery/0-single-authority-and-failure-recovery.md) D1）、host 的关闭请求不等于 guardian 已观察的完成（[Run 尝试决策](../process/lifecycle/0-durable-run-attempts-and-scope-closure.md) D1）、超时与错误不得制造完成证据（[纳管保证根决策](../process/containment/guarantees/0-explicit-containment-and-cleanup-evidence.md) D2）、恢复先确认原 Scope 已 `Closed` 才观察和修复资源（[资源交接决策](../process/integration/0-shared-process-entry-and-resource-handoff.md) D3）。因此把“预算到期”直接推导成“任何 Git 活动不会越过截止”并把“截止加有界清理内必有终态”当作无条件承诺，是不成立的。本决策把三件事分开：

| 事实 | 含义 | 由什么给出 |
|---|---|---|
| 执行预算到期 | 恢复不再等这条命令 | 恢复自己的截止与命令裁剪预算（D1） |
| 停止请求 | 关闭已被提出 | 受管执行向 host 发送的 Scope 关闭（以及 Node 优雅停止时的同类请求） |
| 停止确认 | 该命令已不再写入 | 受管执行观测到原 Scope `Closed` **且** 该 Run 的直接进程已退出（`process_attempts` 中该 Run 已标记为已清理） |

- **正常路径**：停止确认在清理预算内取得 → 删除临时目录与传输仓库（失败仅记录，由 Node 启动清理兜底）→ 报告终态（`prior_revision_unavailable` 或取消原因）。终态即停止确认。
- **证据未知路径**（guardian 不可达、关闭失败或超时、直接进程状态未知、Node 在恢复期间崩溃）：
  1. **不发终态**。没有停止确认就不存在“恢复已结束”的事实，此时发出终态会同时虚构“已停止”与“checkout 可交付”两个结论。会话保持未终结，Cloud 侧按启动决策 D4 在结束确认窗口耗尽后作业务收尾（`failed/done` + 残留账本），那是 Cloud 的业务结算，不是 Node 停止证明。
  2. **保留原 Scope/Run 与冲突责任**。不删除 `process_attempts` 中该 Run 的记录（不标记 cleaned）、不放弃原 host/guardian 身份，也不为同一会话新建第二条恢复或第二个执行身份。该 checkout 的资源冲突责任保留：同一资源不得被新的会话、恢复或交付复用。
  3. **禁止交付与复用**。该会话的交付既不探查工作区也不读 HEAD（D4）；即使 Cloud 已业务收尾，也不得以“Run 已 `done`”为理由释放或复用该 checkout，不得在它之上开始新的恢复。
  4. **不把临时文件删除失败与进程未知合并**。临时目录、传输仓库等本地文件清理失败只记录并由 Node 启动清理兜底，不影响停止证据的判定；反之，进程状态未知也不因临时文件已删而缓解。两者分别报告、分别处理。
  5. **恢复后补报**。Node 继续查询原 Scope/Run（不复制新执行试探）；取得原停止证据后，按原执行身份补报终态，作为迟到事实接管（启动决策 D4），不重开输入、不重建会话、不重新结算。
- **不承诺无条件的物理硬截止**。本文不声称预算到期后 Git 一定不再写入。预算裁剪保证的是“不再开启越过截止的新命令”，以及“不把未确认的停止写成终态”；若要把“到期即物理静止”变成承诺，需先在进程层给出在 guardian 不可达时仍能取得的停止证据，这属于 process 决策范围，不由本文假定。
- **不新增协议状态**。停止证据未知不引入新的线上状态或对账义务：Cloud 侧的接办事实仍是启动决策 D4 的业务终态与残留账本，Node 侧的重试仍是对原 Scope/Run 的查询。

## 不变量

1. 恢复截止覆盖从第一步到检出与祖先检查完成的全程；授权、下载、拉取、重试、取入、检出的任何事件不重置它。
2. 恢复中每条受管 Git 命令的预算不超过其开始时的截止剩余时间。
3. 执行预算到期、停止请求与停止确认是三件不同的事实；预算到期与关闭请求都不构成停止确认（D6）。
4. 截止到期或恢复失败时 Agent 插件从未启动；会话以 `agent_failed` 加 `prior_revision_*` 终态，且终态只在取得停止确认之后发出。
5. 取消只发生在步骤边界或无副作用的等待中；已开始的 Git 命令等它结束（上界为截止），取消后不再开始新的步骤、不再写 checkout；会话终态同样以停止确认为前提。
6. 取消点的 checkout 处于“clone 基线”或“前序最终提交”两种一致状态之一；检出中途失败、被终止或崩溃可能留下混合工作区，但 HEAD 只可能是基础提交或前序最终提交之一。
7. Agent 从未启动（带前序输入、恢复未完成）且已取得停止确认的会话，交付不探查工作区改动，最终提交取 HEAD，结果恒为 `unchanged`。
8. 停止确认未知时（D6）不发终态、不交付、不复用 checkout，保留原 Scope/Run 与资源冲突责任，直到取得原停止证据。
9. Node 截止与 Cloud 的 2/6/5 窗口互不重置、互不延长；Cloud 窗口耗尽不取消 Node 截止，Node 截止不给 Cloud 窗口续期。
10. 崩溃重启后恢复不重做，交付按第 7 条兜底；崩溃时未取得停止确认的恢复按第 8 条保留责任。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 只给授权与下载设时限，命令用自身预算（现状） | 改动最小；但 Git 阶段无界，恢复可无限挂起，失败被折叠进 Cloud 超时，丢失 `detail` 与可解释性（D1） |
| 软截止：到期只停止开启新步骤，运行中命令用满自身预算 | 语义最简单；但网络命令缺省 10 分钟、上限 20 分钟，截止前一刻开始的慢拉取可让 Node 在十数分钟后才报告，晚于 Cloud 6 分钟恢复窗口与 5 分钟确认窗口之和，截止承诺名存实亡（D1） |
| Node 截止取与 Cloud 恢复窗口相同的 6 分钟 | 单一数值好记；但与 Cloud 窗口同时到期，两侧竞争结算，Node 失去“先给确定结果”的常态作用（D2） |
| 每步独立时限 | 粒度细；总和不可控仍需总截止，多一套参数与调优负担（D1） |
| 取消时打断运行中的 Git 命令 | 停止更快；可能留下锁或半写状态，而等待代价有界——预算已被裁剪到剩余截止（D3） |
| 为恢复引入可查询的进度与停止确认状态 | 对账完备；为秒级本地操作增加协议状态机，消费者只需要会话终态与可交付 checkout（D3、D4） |
| 取消后把 checkout 强制转回基础提交 | 回到“干净起点”；与“取消后不再写”矛盾，交付判定已覆盖两种状态（D4） |
| 检出中途故障后修复或回滚 checkout（重跑检出、reset） | 回到一致状态；但修复需要截止之外的额外预算，且可因同一持续故障（如被外部锁定的文件）再次失败；交付正确性不需要它——Agent 未启动的会话不探查工作区，混合工作区随一次性 Workspace 消失，下次续作从交付 ref 重新恢复（D4） |
| 崩溃后重启续传上次恢复 | 省一次下载；会话已终态、恢复不重做是既有规则，续传要新增跨进程恢复状态，实测分段为秒级不值得（D4） |
| 预算到期即发 `prior_revision_unavailable` 终态，把关闭请求当作已停止（上一版） | 终态总是有界到达，Cloud 侧简单；但 guardian 不可达、关闭失败或进程状态未知时 Git 仍可能写入，该终态同时虚构“已停止”与“可交付”，违反进程恢复根决策 D1 与纳管保证 D2（D6） |
| 取不到停止证据时无限期等待，不交业务终态 | 不虚构停止；但 Cloud 的业务等待会永久悬挂，违反启动决策 D4 的有界收尾（D6） |
| 取不到停止证据时删除 checkout、重建 Workspace | 看似恢复可用性；但在可能仍在写入的 checkout 上做删除或替换只是把冲突变成数据竞争，且丢掉原执行身份的残留责任（D6） |

## 本决策未解决的问题

- 大仓库、慢网络下默认 5 分钟的实测调参：落地阶段以直接测量修正默认值，本文只固定语义与可配置性。
- 复制到 checkout Git 目录的 bundle 副本在崩溃后的清理（现行恢复决策未决项；bundle 路径现状，内部线切换后自然消失）。
- 混合工作区在 Workspace 释放前的磁盘占用与可观测性（不影响交付正确性，是否需要显式标记留给实现承接）。
- 停止证据未知（D6）时 checkout 与残留账本的长期处置：本文只固定“不发终态、不交付、不复用、保留原 Scope/Run”，具体如何与残留回收 ADR 的对账证据合并、何时可由运维显式处置，由该 ADR 与实现承接固定。
- 停止确认的轮询上限与重试节奏（D6 的“继续查询原 Scope/Run”）：本文只要求不放弃原责任、不复制新执行，具体退避参数随 desktop 实现承接 issue 固定。
- Node 侧截止的配置项命名、预算裁剪在受管执行中的传参方式与默认值，随 desktop 实现承接 issue 固定。

## 落地顺序

1. **截止贯穿与预算裁剪**（desktop）：`RestorePolicy.deadline` 从只包授权与下载改为包住恢复全程；每条受管 Git 命令以 min(自身预算, 剩余截止) 为预算交给受管执行；到期时等待类步骤立即中止、运行中命令由受管执行请求关闭。完成条件：截止到期且取得停止确认时，插件未启动、会话 `agent_failed`/`prior_revision_unavailable`、临时目录已清理；截止前一刻开始的长网络命令随裁剪预算在截止处被请求关闭；任一子步骤的重试不重置截止。
2. **停止确认与未知路径**（desktop）：终态只在“原 Scope 已 `Closed` 且该 Run 的直接进程已退出”后发出；取不到时不发终态、不删除 `process_attempts` 记录、保留资源冲突责任，并禁止该会话交付与 checkout 复用。完成条件：guardian 不可达、关闭请求失败、关闭在清理预算内未返回 `Closed`、直接进程状态未知四种注入场景下，会话保持未终结且无终态事件发出、原 Run 记录保留、该 checkout 的交付被拒绝且同一资源的新会话/恢复被拒绝；随后 guardian 恢复并观测到 `Closed` 时，按原执行身份补报终态一次。
3. **交付判定隔离**（desktop）：带前序输入且恢复未完成的会话，快照不探查工作区改动，最终提交取 HEAD。完成条件：检出中途失败（注入文件锁复现非原子检出）、检出中被截止终止（已取得停止确认）、崩溃后重启三类故障下，交付结果均为 `unchanged` 且最终提交等于 HEAD（基础提交或前序最终提交），不生成 bundle、不推新内容；Agent 启动过的会话判定不变；停止确认未知的会话交付被拒绝而非返回 `unchanged`。
4. **取消点接入会话结束路径**（desktop）：每条 Git 命令之间检查 `EndSession`/停止/取消，等待类步骤即时取消，取消先生效时终态按取消原因，且同样以停止确认为前提。完成条件：取消点矩阵（取入前、检出后、下载中）各有直接测试，取消后会话按来源终态、checkout 停在两种一致状态、无新的写入；取消期间停止证据未知时走第 2 步的未知路径。
5. **窗口衔接验证**：与 Cloud 的 6/5 分钟窗口按 D2 矩阵逐行联合验证，含「Node 失败报告晚于恢复窗口」「结束请求已送达但停止确认晚于确认窗口」与「停止证据未知、Cloud 按 D4 业务收尾后 Node 补报迟到终态」三条路径。

保持不变：两条路径的步骤顺序、失败分类、能力声明；Cloud 三个窗口的起点与时长；恢复进度不进入协议。从第 1 步起改变：恢复有了覆盖全程、预算被裁剪的截止；从第 2 步起改变：终态只在取得停止确认后发出，取不到时保留原 Scope/Run 与冲突责任而不虚构停止；从第 3 步起改变：恢复未完成的会话不再可能把半恢复工作区当作成果交付；从第 4 步起改变：取消有明确的停止边界与确认语义。实现承接待 owner 批准后另开承接 issue；本文规则对 bundle 现状与内部线（实现进行中）同样适用，合入先后由承接 issue 按当时的 desktop main 协调。核心测试用例在本 ADR 转为 `approved` 后按规范补充。
