# Linux 强纳管通过独立特权 Helper 建立权限边界

Eric 于 2026-09-17 批准先实现独立特权 helper 部署：helper 管理受控 cgroup，业务工作负载以无迁出权限的身份运行。
本决策确认部署方向，不表示已完成特权安装、平台证明或生产接入。

## 当前范围与未来 ADR 责任（2026-09-18）

现有 helper 仅有部署预检、inspect 管理通道和底层 exec 前入组／降权能力；没有启动 IPC、持久 Run／Scope 协调或 guardian 交接，特权正向测试未运行。允许实现不等于允许安装或提权。

本 ADR 保留 approved，表示平台方向曾获批准，而不是当前版本交付义务或 implemented。
下文尚未实现的机制、不变量和验收保留为未来 ADR 的设计输入；恢复此路线时，必须在本叶子
追加 ADR，继承已批准方向并明确具体部署、机制、身份与直接证据，再开始宣称平台支持。
不通过删除其全部实质范围把本文标为 implemented。当前最小闭环不等待此路线完成。

## 继承与修改

继承[根决策](0-cgroup-v2-containment.md)，并细化其尚未冻结的权限部署方式。

| 约定 | 本次处理 |
|---|---|
| 业务执行前纳管、Run／Scope 隔离、空子树证据 | 继承，不变 |
| 不依赖 systemd、仅管理获委派范围 | 继承，不变；可提供 systemd 部署模板 |
| 权限限制迁出 | 细化：独立特权 helper 控制子树，工作负载不能持有迁移权限 |
| 三个 library、两个薄 app | 增加 Linux 专用薄 app `ora-process-helper`；实现仍归 runtime，不引入机器级运行管理器 |

## D1：特权边界独立于业务身份

Helper 的安装、配置、受管目录和管理入口由受信任部署控制。调用方不能选择任意 root 命令、
目标 UID、主机 PID 或委派外 cgroup；工作负载身份不能充当管理身份。普通用户可写的配置或目录
不能作为特权事实来源。具体启动与授权协议随实现冻结，但不得扩大到通用提权接口。

同 UID 可写的用户级委派不足以保护其内部 Run 边界；迁移权限同时取决于目标及共同祖先的
`cgroup.procs` 写权限，见[内核委派规则](https://docs.kernel.org/admin-guide/cgroup-v2.html#delegation-containment)。

## D2：部署验证与纳管证明分开

部署门禁先验证受信任配置、分离身份、实际 cgroup v2 目录及管理权限。检查通过只说明这些前提成立，
不产生 `Strong` 保证或清理完成证据。创建时纳管、降权、禁止重新提权、后代迁出、guardian 强杀及
helper 重启恢复必须经过真实特权进程测试后，才能启用生产强模式。

## 为什么不是这些替代方案

| 方案 | 取舍 |
|---|---|
| 业务与管理同 UID 的普通用户委派 | 部署简单，但不能据此排除 Run 之间迁移 |
| 让业务命令自行使用 sudo | 扩大提权接口，并使纳管依赖业务协作 |
| 自动安装／提权启动 helper | 安装和服务变更需要单独授权，不能由实现许可推导 |

## 未来 ADR 的落地与验收输入

先提交部署门禁及薄 app，再实现认证管理通道与创建时纳管，最后接入 guardian 与恢复。
现有入口在真实平台闭环验收前保持不变。核心义务补充到
[Linux 用例](../../../../../test-cases/node/process/containment/linux/cgroup-ownership-and-cleanup.md)。

## 本决策未解决的问题

inspect 管理通道已有实现；完整启动管理协议、启动句柄交接、持久恢复、安装包与服务存续关系
交由未来 ADR 定义并实施；macOS／Windows 不受本决策替代。
