# 更新清单携带最近 10 个版本的日志，用户在确认安装之前看到

公开版的更新清单 `latest.json` 带上双语日志，内容从 `release-notes/` 的同一份文件写入；客户端在用户确认安装之前，展示当前版本到
目标版本之间的变化。日志只是附带内容：清单里的日志缺失、损坏或超限时只隐藏日志，客户端的检查、下载、安装不变。

本文为 `proposed`。D1–D5 按 owner 的结论写；只剩一项待定（Q8，在哪里展示），它有结论、并入 D3 之后改为 `approved`。

- **涉及**：desktop 的打包检查、更新清单生成脚本、Tauri 更新模块与它交给前端的状态、确认安装的界面。
- **不涉及**：日志文件的字段、内置、更新后卡片和设置页历史；更新的检查、下载、安装行为；清单的平台集合与签名。
- **不承担的迁移**：已发布版本的清单不改写；已安装的旧客户端忽略新字段。

## 继承与修改

前一个决策是[更新日志根决策](0-release-notes-in-main-bundled-at-packaging.md)。

| 约定 | 处理 | 说明 |
|---|---|---|
| D1 文件格式 | **修改** | 每个版本最多 50 条；其余字段和内容规则不变 |
| D3 打包检查、不变量 2 | **修改** | 超过 50 条也算不合格，带 `--tag` 时不产出安装包。仓库里还没有日志，没有迁移成本 |
| D1 唯一手写来源、不变量 1 | 继承，不变 | 清单里的日志由文件生成，不另写 |
| D2 由谁写、覆盖范围，D4 内置 | 继承，不变 | — |
| D5 更新后卡片与历史 | 继承，不变 | 更新前看过也照弹（D5） |
| D6 更新前弹窗放第二步，字段、版本数和手动更新由后续 ADR 定 | 由本文落实 | 可达性规则不变：能检查到更新的安装才看得到；展示位置见待定 Q8 |
| D7 起始版本 | 继承，不变 | 旧客户端没有这个展示，从第一个带它的版本往后才看得到 |
| 不变量 6、7、8（纯文本、失败只隐藏、清单日志不可信并限长限条数） | 继承，不变 | 本文给出数值（D2） |
| 不变量 3–5、9 | 继承，不变 | — |

## 背景

- 清单由 `desktop-build` 的 `release` job 生成，这个 job 有自己的检出，能读到 `release-notes/`。它只在带版本号的构建之后运行，同一个
  提交已经通过打包检查。现在 `notes` 写成 `Ora <tag>`。
- 更新器插件（`tauri-plugin-updater` 2.10.1）把清单的 `notes` 当字符串解析，类型不符会让**整份清单**解析失败；它同时保留原始
  JSON，多余字段不影响解析。
- 清单不在安装包签名的范围内，应用的 `csp` 为 `null`。
- 由用户手动更新的安装（如 deb）现在显示红点，但按钮禁用。

以上依据 desktop `main` 提交 `7b2112af` 和插件源码。

## 决策

### D1：清单用带 `schema` 的自定义字段携带最近 10 个版本，生成失败就不发布

```json
{
  "version": "0.8.0",
  "notes": "Ora v0.8.0",
  "ora_release_notes": {
    "schema": 1,
    "notes": [{ "version": "0.8.0", "date": "2027-01-12", "entries": [] }]
  }
}
```

（示例省略了条目；条目格式与日志文件相同，且不能为空。）

| 规则 | 内容 |
|---|---|
| 标准 `notes` | 保持字符串 `Ora <tag>`。它的类型一旦变化，新旧客户端都会检查不到更新 |
| 版本范围 | 目标的正式版本取自 tag（去掉预发布后缀和 `+build`）。带不高于它的最近 10 个版本，必须包含它 |
| 字段 | 生成器只投影 `version`、`date`、`entries` 里的 `category`、`zh-CN`、`en-US`，不整份复制文件，以后文件加字段不会泄漏到清单 |
| 失败 | 复用打包检查的校验和版本归一化；目标版本没有日志、任一文件不合格时不写清单，`release` job 失败 |

生成失败只意味着不产出新的 Release 草稿，挡不到已安装的客户端，与根决策不变量 7 不冲突。同一个提交已经通过打包检查，走到这里
还失败只能是代码缺陷；照常发布会静默产出没有日志的清单。

清单体积：最坏情况是 10 个版本、每版 50 条、每条中英文各 500 码点，按中文 3 字节、英文 1 字节约 1 MB，全用 4 字节码点约 2 MB；按每版 30 条、每条中英文合计约
300 字节估算约 90 KB。每次检查都会下载，多数在几十 KB 量级；版本数固定为 10，不随发版增长。

### D2：日志字段是跨客户端版本的协议，客户端整体接受或整体隐藏

清单由新版本生成、由所有已安装的旧版本读取，所以日志字段按协议对待：

| 情形 | 客户端行为 |
|---|---|
| 没有 `ora_release_notes` | 没有日志，不算异常 |
| `schema` 不认识 | 整组隐藏 |
| 未知字段 | 忽略 |
| 未知 `category` | 内容不合格，整组隐藏；增加分类要提升 `schema` |
| 版本数超过 10、任一版本超过 50 条、任一文字超过 500 码点 | 整组隐藏 |
| 任一版本不满足内容规则 | 整组隐藏 |

内容规则与日志文件相同：正式版本号、真实存在的日期、四种分类、两种语言都必填且不能只有空白、不含控制字符、双向控制字符和行
分隔符。生成端和客户端用同一组样例测试，保证两边判断一致。

整组隐藏而不是只丢坏的那一部分：客户端不知道坏的是哪一部分、丢掉之后还剩多少意义，展示剩下的会让人以为没有别的变化。范围裁剪
（D1 的最近 10 个、D3 的区间）不同，它按版本号划定，用户知道看到的是哪些版本。隐藏的原因写进 Desktop 日志，不给用户报错。

上限只约束检查成功之后的日志处理；更新器先下载并解析整份清单，这一步按更新器自己的规则执行。

### D3：展示 `(当前正式版本, 目标正式版本]` 之间的日志，取自同一次检查

两端都先取正式版本，区间不含当前、包含目标：`0.7.0` 检查到 `0.8.0-rc.1` 时展示到 `0.8.0`；`0.8.0-rc.1` 检查到 `0.8.0` 时没有新日志。
按版本倒序，按界面语言，只按纯文本，排版与更新后卡片相同；内容多时可以滚动，安装操作始终由用户明确点击。没有日志时不显示这一块，
更新照常可用。清单里没有的中间版本不补，也不联网另取。

日志在 Rust 更新模块里解析、限制、筛选，前端拿不到原始清单。解析用的是产生当前 `Ready` / `ManualUpdate` 状态的那一次检查的清单，
日志与状态放在一起：之后的检查失败而保留旧的 `Ready` 时，日志仍是那个版本的。

展示的位置见待定 Q8。

### D4：手动更新的安装也能看日志，没有安装操作

`manual_update` 时入口可用，内容相同，按 `ManualUpdateReason` 显示固定文案，不给安装按钮，也不使用清单里的任何链接。

### D5：更新前看过，更新后的卡片照弹

规则最简单，也不用区分“打开过”和“看过”。跨版本更新时清单最多 10 个版本，而卡片列出全部未提示的版本，两者内容不一定相同。

## 待定

### Q8：在哪里展示

根决策 D6 写的是更新前弹窗。现有的更新确认弹窗从设置里打开，已经是叠在设置对话框上的第二层弹窗，放进日志后更明显。

| 选项 | 内容 | 代价 |
|---|---|---|
| a | 放进现有的更新确认弹窗（根决策 D6 的写法） | 弹窗叠弹窗，内容要在小弹窗里滚动 |
| b（用户提议） | 入口按钮切换到设置的更新日志页，页面顶部显示可更新的版本、日志和“立即更新”，下面是已安装版本的历史；不再有确认弹窗 | 修改根决策 D6 的“弹窗”；点“立即更新”后直接安装并重启，少一次确认，但同一处已写明会重启 |

## 不变量

1. 更新器成功解析清单之后，客户端的检查、下载、安装结果不因清单里有没有日志、日志是否合格而改变。
2. 标准 `notes` 在任何清单里都是字符串。
3. 清单里的日志是同一提交的内置日志的子集，条目逐字相同。
4. 只展示 `(stable(当前), stable(目标)]` 区间的日志，且与当前更新状态来自同一份清单。
5. 同一 `schema` 下，生成端的上限不高于任何已发布客户端的上限；提高上限或增加分类必须提升 `schema`。
6. 客户端不截断日志：整组展示区间内的内容，或整组隐藏。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 把日志写成 Markdown 放进标准 `notes` | 只用标准字段 | 两种语言要从一个字符串里切分，还要处理标记，违反根决策不变量 6 |
| `notes` 改成对象 | 不用自定义字段 | 插件解析整份清单失败，违反不变量 2 |
| 只带目标版本，或带全部版本 | 最小，或最全 | 前者跨版本看不到中间版本；后者清单随发版增长，每次检查都下载 |
| 生成时丢掉超限的版本 | 打包检查不用改 | 可能丢掉的正是目标版本，用户看到的只剩旧版本 |
| 日志不合格时照常发布不带日志的清单 | 发布不会停 | 静默发出没有日志的清单；走到这一步只能是代码缺陷（D1） |
| 把原始清单交给前端解析 | Rust 改动少 | 不可信输入进入 webview |
| 更新前看过就不弹卡片 | 不重复 | 弹窗可能只有部分版本，会把其余未读版本一起跳过 |
| 展示时再联网取日志 | 清单小，可随时改正 | 多一个网络依赖和失败路径；与更新检查的可达性不再一致 |
| 给日志单独签名 | 可以信任 | 要新增密钥用法和验证路径，而纯文本加限制已经限制了影响 |

## 本决策未解决的问题

- Release 正文是否从同一份文件生成，根决策已推迟，本文不改。
- 主界面上的更新入口（例如红点）不在本文范围。
- 黄区能否访问更新清单的地址没有核实；访问不到时没有更新前日志，按根决策 D6 处理。

## 风险

| 风险 | 说明 |
|---|---|
| 篡改清单伪造说明文字 | 纯文本和上限只限制影响，不能防止文字本身是假的；安装包仍由签名保证 |
| 发布后发现日志有误 | 在 `main` 修正源文件，更正随下个版本的清单和安装包发布（根决策 D4） |
| 超大的清单 | 更新器先下载并解析整份清单，D2 的上限管不到这一步；清单被篡改到很大时，检查更新可能变慢或失败。现在没有日志时也是如此，本文不新增也不消除 |
| 以后提高上限 | 旧客户端会隐藏全部日志；不变量 5 要求同时提升 `schema`，旧客户端的表现仍是隐藏 |

## 落地顺序

1. **specs**：Q8 有结论后并入 D3，改为 `approved`，补核心测试用例。
2. **desktop，前置**：更新后卡片、历史页和共用的日志排版（根决策第一步）先合并。
3. **desktop**：打包检查的条数上限、清单生成、更新模块解析与状态、展示，一个 PR。完成后公开版清单开始带日志；旧客户端行为不变。
4. **specs**：按最终实现同步本文，改为 `implemented`。

发布一个带日志的清单之后，才能从旧版本实测一次更新前的展示；在此之前只有单元测试。
