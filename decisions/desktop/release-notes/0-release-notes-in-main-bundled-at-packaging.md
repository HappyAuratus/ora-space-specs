# Desktop 更新日志随 main 维护，打包时检查并内置到安装包

Desktop 每个正式版本有一份中英文[更新日志](../../../domain/glossary.md#release-notes更新日志)，存为 desktop `main` 里的普通
文件 `release-notes/<版本>.json`。日志由准备发版的人在本地用 AI 生成、人工改好，经普通 PR 合并；
`scripts/package-desktop.ts --tag` 打包时检查日志，安装包内置全部日志，客户端在更新后提示和设置页历史里展示。可观察的变化：

- 带 `--tag` 打包的版本没有合格的日志就不产出安装包；不带 `--tag` 的测试包不受影响（D3）。
- 用户更新后能看到新版本的变化，也能在设置页离线查看历史（D4、D5）。
- 更新前弹窗和公开版 `latest.json` 的日志放在第二步（D6）。

本文为 `proposed`。D1–D7 是 owner 已定的方案；只剩一项待定（P13），它有结论、并入 D2 之后，本文才能改为 `approved`。

- **涉及**：desktop 的 `release-notes/`、打包脚本与现有测试、前端构建、`packages/app-shell` 的更新后提示与设置页，以及宿主向
  前端提供“数据库是否本次新建”（D5）；第二步还有更新清单生成脚本与 Tauri 更新模块。
- **不涉及**：更新的检查、下载、安装行为，签名与校验，清单的平台集合，发版由谁触发和 tag 的管理。本文不改变它们，也不
  为它们补根决策。
- **不承担的迁移**：不回填 v0.6.0 及更早版本的日志，不改写已发布的 Release 和清单。

## 归属

specs 里没有更新日志的根决策，也没有 desktop 更新或发布的根决策。最接近的
[支持平台](../platform/0-windows-and-linux-only.md) D3 只定 CI、打包和 `latest.json` 覆盖哪些平台，与日志内容不是一个
领域。因此新建叶子 `desktop/release-notes`，本文是它的根决策，范围只到日志的**格式、归属、内置和展示**。

## 背景

- **没有稳定的内容来源。** 更新清单的 `notes` 由脚本写成 `Ora <tag>`，客户端拿不到真正的日志。清单在创建 Release
  草稿之前生成，写在 Release 正文里的内容进不了客户端；Release 正文本身也没有固定流程，v0.4.0 是 PR 标题列表，
  v0.5.0 为空，v0.6.0 是人工整理的双语说明。
- **没有展示入口。** 应用内没有查看日志的地方。更新控件只在设置弹窗里，只有更新包就绪时可点；由用户手动更新的安装
  方式（如 deb）点不开。
- **安装包不只来自 tag 构建。** [黄区包](../../../domain/glossary.md#yellow-zone-build黄区包)和本地公开包直接用
  `scripts/package-desktop.ts` 打，CI 也用同一个脚本。只存在于 tag 的日志会让这些包没有内容。

以上依据 desktop `main` 提交 `768166ae`。

## 决策

### D1：日志是 `main` 里的普通文件，每个正式版本一份 JSON

日志存放在 desktop 仓库 `main` 的 `release-notes/<版本>.json`，每个正式版本一份。`<版本>` 是归一化后的正式版本号，不带
`v`，例如 `release-notes/0.7.0.json`；文件名必须等于文件里的 `version`。

```json
{
  "schema": 1,
  "version": "0.7.0",
  "date": "2026-12-10",
  "entries": [
    { "category": "feature", "zh-CN": "……", "en-US": "…" }
  ]
}
```

| 字段 | 规则 |
|---|---|
| `schema` | 格式版本 |
| `version` | 正式版本号，等于文件名 |
| `date` | 计划发布日期。日志先于 tag 合并，所以可能与实际发布日不同；以文件为准，不回改 |
| `entries[].category` | `important`、`feature`、`improvement`、`fix` 之一（重要、新功能、改进、修复） |
| `entries[].zh-CN`、`en-US` | 都必填，纯文本，限长 |

日志内容不含来源 PR、提交范围和省略列表。安装包以及第二步的 `latest.json` 都从这份文件得到日志，没有第二处手写来源。

放在 `main` 而不是 tag 里，是因为安装包不全从 tag 打，日志跟着源码走，任何检出都带着它之前的全部历史；tag 移动或
重建也不会丢日志。中英文写在同一条目里，两种语言的条数不会不一致。不记来源 PR，是因为日志不做自动核对（D2）；以后要
核对时再加字段，已有文件和客户端沿用。

### D2：准备发版的人本地用 AI 生成、人工改好，经普通 PR 合并

准备发版的人在本地让 AI 看上个版本到 `main` 的提交，生成日志并人工改好，提普通 PR（成员从 fork 提）；owner 合并就是
第二人审核。tag 打在日志合并之后的提交上。生成只用本地 git，不依赖 GitHub 接口，不要求团队 AI 账号；用哪个 AI 工具、
用什么提示词不是系统承诺，系统只认合并后的文件。

只读成员因此也能准备日志，不需要为此授予写权限，也不需要为日志增加必过检查或 tag 规则。接受的代价：

- 没有自动防漏，靠写的人和审 PR 的人看。
- AI 主要依据提交和标题，面向用户的表述要人工多改。

日志 PR 合并之后、发版提交之前又合并的改动归哪个版本，见待定 P13。

### D3：带 `--tag` 打包时检查日志，不合格就不打包

| 打包方式 | 行为 |
|---|---|
| 带 `--tag <版本>`，检查全部通过 | 照常打包 |
| 带 `--tag <版本>`，任一项不通过 | 失败，不产出安装包 |
| 不带 `--tag`（测试包、开发构建） | 不检查 |

带 `--tag` 时检查：

1. **本版本有日志。** 从 tag 取正式版本号（去掉 `v`、预发布后缀和 `+build`）找文件：`v0.7.0`、`v0.7.0-rc.1` 和
   `0.7.0+yellow` 都要求 `release-notes/0.7.0.json`。
2. **所有会被内置的文件都合格。** 逐个检查格式、文件名与 `version` 相符、没有重复版本，因为内置的是全部日志（D4）。
3. **`release-notes/` 没有未提交的改动**，包括未跟踪的文件。只查这个目录，因为黄区包本来就要在本地替换别的文件。

同一份校验（第 2 项）也放进现有的测试，不新增必过检查。PR CI 按路径决定跑哪些测试，目前的路径不含 `release-notes/`，
只改日志的 PR 不会触发；这些测试的触发路径要加上它。

CI 和本地共用打包脚本，所以 tag 触发的构建、带版本号手动运行的 `desktop-build`（不论是否发布）、本地公开包和黄区包走同一个
检查。规则只取决于有没有 `--tag`，不取决于构建的目的。检查不联网，也不核对日志是否写全，后者由 D2 的 PR 审核负责。

### D4：安装包内置全部日志，离线可用

前端构建时把打包所用检出里的全部日志注入安装包，不只是本版本那一份；运行时不读文件、不联网。更新后提示和设置页历史
只用内置内容，跨多个版本更新的用户也能看到中间版本。注入或解析失败只隐藏日志，不影响应用。没有日志时历史页为空，不弹
提示。

公开包与黄区包的日志一致，前提是从同一个提交打，并且 `release-notes/` 没有未提交的改动。后一个条件由 D3 第 3 项保证；
前一个条件没有机制保证，由准备包的人负责。

代价是已安装的内容不能单独修正：日志有误时改 `main` 里的文件，随下个版本发布；已安装的版本继续显示原来的内容。

### D5：第一步展示更新后提示和设置页历史

| 时机 | 位置 | 来源 |
|---|---|---|
| 更新到新版本之后 | 一张可关闭的卡片 | 安装包内置 |
| 随时 | 设置页的更新日志历史 | 安装包内置 |

两处都不依赖更新清单，所以不受网络环境和安装方式影响。共同规则：只显示不高于当前正式版本的日志，按版本倒序，按界面
语言（`zh-CN` 或 `en-US`）取文字。当前正式版本按 D3 第 1 项的办法从应用版本取，所以 `0.7.0-rc.1` 显示到 `0.7.0`。

**卡片。** 本机记录“已提示过的最高版本”。第一步只有这一种卡片，不按版本大小或分类换形式；它列出（已提示过的最高版本,
当前正式版本] 里的全部日志，展示之后把记录提高到当前正式版本。下列情形不提示：

| 情形 | 说明 |
|---|---|
| 当前正式版本不高于记录 | 同一版本再次启动，或降级；记录不降低 |
| 构建里没有当前正式版本的日志文件 | 不带 `--tag` 的构建沿用检入的 0.1.0，而 0.1.0 是真实发布过的版本，光看版本号分不出来，所以按有没有日志文件判断；这时也不改记录 |
| 没有记录，并且是全新安装 | 只把记录设为当前正式版本 |

**没有记录时怎么区分全新安装和升级。** 宿主打开数据库时，已应用的迁移为空表示这个数据库是本次新建的；v0.6.0 就已经用
同一个条件判断是否写入首次安装数据。新建就是全新安装；已有迁移记录就是从不写记录的版本升级上来的，这时没有下限，卡片
列出全部不高于当前正式版本的日志。跳过首个支持版本直接升级的用户同样适用。这个信号是读代码核实的，没有实测升级；现在
宿主没有把它提供给前端，实现时要加上。

它的边界：

- 重装但保留了数据目录的用户按升级处理；清空数据目录后按全新安装处理。
- 数据库建好、记录写下之前应用就退出的全新安装，下次启动会看到一次提示。
- 本机记录丢失时按没有记录处理，可能把看过的日志再提示一次。

没有选“没有记录就不提示”，因为那会跳过全部首批升级用户；也没有选“没有记录就提示”，因为会打扰全新安装的用户。

### D6：更新前弹窗放第二步，公开版 `latest.json` 从同一份文件写入

更新前弹窗要在安装之前拿到目标版本的日志，只能来自[更新清单](../../../domain/glossary.md#update-manifest更新清单)。第二步由
公开版的 `latest.json` 带上日志，内容从 `release-notes/` 的同一份文件写入，不另写一份；客户端在更新前弹窗里展示。

更新前弹窗和更新检查读同一份清单，地址写死在应用配置里：检查得到更新的安装才看得到更新前的日志，检查不到的两者都没有，
仍有更新后提示和历史页。第一步不改更新的检查、下载、安装行为，也不改清单。

清单字段、带几个版本、手动更新的用户怎么看，由第二步的后续 ADR 定，但不得违反不变量 6 和 7。

### D7：从 v0.6.0 之后的下一个正式版开始

第一个必须有日志的版本是 v0.6.0 之后的下一个正式版。v0.6.0 之后、日志流程生效之前已经合并的改动，由人工补写进这一版
的日志。v0.6.0 及更早的版本没有日志文件，历史页从这一版开始。

- **更新后提示**由新版本显示，与旧版本有没有展示功能无关。从 v0.6.0 升级上来的用户没有记录，但数据库已有迁移记录，按 D5
  判为升级，能看到提示。
- **更新前弹窗**由旧版本显示。v0.6.0 没有这个弹窗，所以第二步从第一个带它的版本往后才看得到。

## 不变量

1. 每个版本的日志只有一个手写来源：`release-notes/` 下该版本的文件，文件名等于 `version`。
2. 带 `--tag` 的打包，本版本没有日志、任一内置文件不合格，或 `release-notes/` 有未提交的改动时，不产出安装包；CI 与本地
   使用同一个检查。
3. 不带 `--tag` 的打包不因日志失败。
4. 日志检查和内置不访问网络，不依赖 GitHub 接口或 tag 的存在。
5. 安装包内置打包所用检出里的全部日志；更新后提示和设置页历史在联网和离线时内容相同。
6. 任何位置展示日志都只按纯文本，不解析 HTML 或 Markdown，不生成链接。
7. 来自更新清单的日志不可信：限制长度和条数。日志缺失、格式错误或解析失败时只隐藏日志，不影响应用，也不阻止更新的检查、
   下载和安装。

不变量 6、7 是因为应用的 `csp` 为 `null`，而更新清单不在安装包签名的范围内：日志一旦被当成标记解析，篡改清单就能在应用
里执行内容。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 每个 PR 写面向用户的说明，PR 检查必过，发版时汇总并逐个核对 | 写的人最了解影响；能自动防漏 | 步骤多，和 GitHub 绑得紧，黄区包照顾不到。以后需要时可以加上，文件格式和客户端沿用 |
| 日志提交只存在于 tag，一条命令打 tag 发版，另加 tag 规则和发版人名单 | 操作少，`main` 不变 | 步骤多，和 GitHub、tag 绑得紧；不从 tag 打的黄区包和本地包没有日志 |
| 仓库里每个 PR 加一个片段文件 | 随代码评审，合并后不易被改动 | 容易冲突或遗漏，测试和重构的 PR 也要写 |
| 用提交或 PR 标题自动生成 | 没有额外负担 | 面向开发者、中英混杂，v0.4.0 就是这样 |
| 客户端直接读 GitHub Release | 改正即时生效 | 依赖网络和接口限额；要从 Markdown 里切分语言 |
| 自建日志服务或静态站 | 可随时修改，支持任意版本范围 | 多一个要维护和保障的服务 |
| 中英文各一份 Markdown | 人直接编辑更顺手 | 两种语言条数可能不一致（D1），客户端还要处理 Markdown 安全（不变量 6） |
| 先补 desktop 更新与发布的根决策，再写更新日志 | 领域完整 | 要先把现有更新机制补成 ADR，多一轮评审 |
| 并入[支持平台](../platform/0-windows-and-linux-only.md) | 不用新叶子 | 归属不清 |
| 不写 ADR，直接实现 | 最快 | 不落档 |

## 待定

### P13：日志 PR 合并之后、发版提交之前又合并的改动归哪个版本

tag 打在日志合并之后的提交上（D2），这些改动会随本版交付；打包检查不核对日志是否写全（D3）。方案原文把它写成代价：
“日志 PR 之后又合并的改动要补写，否则归到下个版本”。评审指出，按“否则归到下个版本”，随本版交付的修复在本版日志里看不到，
下个版本又把它写成自己的变化。

| 选项 | 规则 | 代价 |
|---|---|---|
| 13a 方案原文 | 要补写；没补写的归到下个版本 | 没补写时日志与实际交付的版本不一致 |
| 13b 按打包所用的提交划分（评审提出） | 发版前按打包所用的提交再核对一次，补写已纳入本版且应向用户说明的改动；随下一版交付的才记入下一版 | 发版前多一次核对，补写要再走一次 PR，期间可能又有新改动合并 |
| 13c tag 打在日志 PR 的合并提交上 | 从该 tag 对应的提交打包时，日志 PR 之后合并的改动不进本版，归下个版本；日志 PR 合并前仍要核对期间合入的改动 | 收紧 D2 的 tag 位置；急需带上的修复要先合并再更新日志。只约束从 tag 打的包：`--tag` 只设版本号，手动构建按触发时选的 ref 检出，从较新的 `main` 本地打包或手动构建同一版本仍会带上之后的改动；要覆盖这些入口，得同时约束它们的检出 |

## 本决策未解决的问题

- **desktop 更新与发布的根决策。** 更新生命周期、签名清单、发版与 tag 的约束不在本文范围；以后补时另写，本文的规则
  只在与它们的接口处（D3 的 `--tag`、D6 的清单）受影响。
- **更新清单里的日志字段。** 由第二步的后续 ADR 定（D6）。
- **Release 正文。** 是否从同一份文件生成推迟，目前不改 Release 正文的写法。
- **自动防漏。** 按 D2 接受人工核对；需要时另写后续 ADR。
- **预发布通道。** 不在本文范围；D3 只规定带预发布后缀的打包用哪份日志。

## 风险

| 风险 | 说明 |
|---|---|
| 漏写或写成内部术语 | 没有自动核对，靠 PR 审核；是 D2 接受的代价 |
| 本地 AI 受提交内容误导 | 提交信息可能来自外部；AI 在没有写权限的环境里运行，输出经格式校验并由人确认后才提 PR |
| 检查通过但不是要发布的提交 | 检查只保证 `release-notes/` 与检出的提交一致，不保证检出的是哪个提交（D4） |
| 起始版本的日志不全 | v0.6.0 之后已合并的改动靠人工补写（D7） |
| 全新安装判断没有实测 | 依据读代码的结果（D5）；实现时要在真实升级和全新安装上各验证一次 |

## 落地顺序

1. **specs**：P13 有结论后并入 D2，本文改为 `approved`，并在镜像目录 `test-cases/desktop/release-notes/` 补核心测试用例；
   `proposed` 阶段不编写核心用例，目录里只有占位文件。
2. **desktop，第一步**：日志文件格式、打包检查与测试、内置、更新后提示和设置页历史，以及第一份日志。完成后带 `--tag` 的打包
   开始要求日志，更新的检查、下载、安装保持不变。
3. **specs 与 desktop，第二步**：后续 ADR 定清单字段，然后公开版 `latest.json` 从同一份文件写入，更新前弹窗展示。
4. **specs**：按最终实现同步本文，改为 `implemented`，登记用例证据。

第一步不碰更新通道，可以独立验收；第二步依赖第一步的文件格式，单独评审清单字段和不可信输入的处理。
