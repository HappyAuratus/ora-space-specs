# Desktop 更新日志随 main 维护，打包时检查并内置到安装包

Desktop 每个正式版本有一份中英文更新日志，存为 desktop `main` 里的普通文件 `release-notes/<版本>.json`。日志由准备
发版的人在本地用 AI 生成、人工改好，经普通 PR 合并；`scripts/package-desktop.ts --tag` 打包时检查对应文件存在且格式
正确，安装包内置全部日志，客户端在更新后提示和设置页历史里展示。可观察的变化：

- 带 `--tag` 打包的版本没有合格的日志就不产出安装包；不带 `--tag` 的测试包不受影响（D3）。
- 用户更新后能看到新版本的变化，也能在设置页离线查看历史（D4、D5）。
- 更新前弹窗和公开版 `latest.json` 的日志放在第二步（D6）。

本文为 `proposed`：D1–D7 写 owner 已经定下的方案，供评审核对表述；“待定”一节列出 owner 没有定过的取舍，逐项等
owner 选定，本文不替 owner 选。待定项全部有结论、并入 D1–D7 之后，本文才能改为 `approved`。

- **涉及**：desktop 的 `release-notes/`、打包脚本、前端构建、`packages/app-shell` 的更新后提示与设置页；第二步还有更新
  清单生成脚本与 Tauri 更新模块。
- **不涉及**：更新生命周期、签名与校验、清单的平台集合、发版由谁触发和 tag 的管理。本文不改变它们，也不为它们补
  根决策。
- **不承担的迁移**：不回填 v0.6.0 及更早版本的日志，不改写已发布的 Release 和清单。

## 归属

specs 里没有更新日志的根决策，也没有 desktop 更新或发布的根决策。最接近的
[支持平台](../platform/0-windows-and-linux-only.md) D3 只定 CI、打包和 `latest.json` 覆盖哪些平台，与日志内容不是一个
领域。owner 决定为更新日志新建叶子，本文是它的根决策，范围只到日志的**格式、归属、内置和展示**。

叶子的位置和名字没有定。本文暂放 `decisions/desktop/release-notes/`，只为让草稿有地方评审，见待定 P1。

## 背景

- **没有稳定的内容来源。** 更新清单的 `notes` 由脚本写成 `Ora <tag>`，客户端拿不到真正的日志。清单在创建 Release
  草稿之前生成，写在 Release 正文里的内容进不了客户端；Release 正文本身也没有固定流程，v0.4.0 是 PR 标题列表，
  v0.5.0 为空，v0.6.0 是人工整理的双语说明。
- **没有展示入口。** 应用内没有查看日志的地方。更新控件只在设置弹窗里，只有更新包就绪时可点；由用户手动更新的安装
  方式（如 deb）点不开。
- **安装包不只来自 tag 构建。** 黄区包和本地公开包直接用 `scripts/package-desktop.ts` 打，CI 也用同一个脚本。只存在于
  tag 的日志会让这些包没有内容。

以上依据 desktop `main` 提交 `7a68e2db`。

## 决策

### D1：日志是 `main` 里的普通文件，每个正式版本一份 JSON

日志存放在 desktop 仓库 `main` 的 `release-notes/<版本>.json`，每个正式版本一份。文件只含四类内容：版本、日期、分类、
中英文条目；不含来源 PR、提交范围和省略列表。安装包、以及第二步的 `latest.json` 都从这份文件得到日志，没有第二处手写
来源。

放在 `main` 而不是 tag 里，是因为安装包不全从 tag 打，日志跟着源码走，任何检出都带着它之前的全部历史；tag 移动或
重建也不会丢日志。同一条目的中英文写在一起，两种语言的条数不会不一致。不记来源 PR，是因为日志不做自动核对（D2）；
以后要核对时再加字段，已有文件和客户端沿用。

字段名、分类取值和文件命名见待定 P2、P3。

### D2：准备发版的人本地用 AI 生成、人工改好，经普通 PR 合并

准备发版的人在本地让 AI 看上个版本到 `main` 的提交，生成日志并人工改好，从 fork 提普通 PR；owner 合并就是第二人审核。
tag 打在日志合并之后的提交上。生成只用本地 git，不依赖 GitHub 接口，不要求团队 AI 账号；用哪个 AI 工具、用什么提示词
不是系统承诺，系统只认合并后的文件。

只读成员因此也能准备日志，不需要为此授予写权限，也不需要为日志增加必过检查或 tag 规则。接受的代价：

- 没有自动防漏，靠写的人和审 PR 的人看。
- AI 主要依据提交和标题，面向用户的表述要人工多改。

日志 PR 合并之后、发版提交之前又合并的改动归哪个版本，见待定 P13。

### D3：带 `--tag` 打包时检查日志，不合格就不打包

| 打包方式 | 行为 |
|---|---|
| `package-desktop.ts --tag <版本>`，对应文件存在且格式正确 | 照常打包 |
| `package-desktop.ts --tag <版本>`，文件缺失或格式错误 | 失败，不产出安装包 |
| 不带 `--tag`（测试包、开发构建） | 不检查 |

CI 和本地共用这个脚本，所以 tag 触发的构建、带版本号手动运行的 `desktop-build`、本地公开包和黄区包走同一个检查，没有
另一条可以绕过它的正式打包路径。检查只看打包所用检出里的文件，不联网，也不核对日志是否写全，后者由 D2 的 PR 审核
负责。

带版本号但不发布的手动构建同样被检查。这样规则只取决于有没有 `--tag`，不取决于构建的目的。

### D4：安装包内置全部日志，离线可用

安装包内置打包所用检出里的全部日志，不只是本版本那一份。更新后提示和设置页历史只读内置内容，不联网，因此公开包和
黄区包的展示一致，跨多个版本更新的用户也能看到中间版本。

代价是已安装的内容不能单独修正：日志有误时，内置内容要到下个版本才更新。

内置方式和读取失败时的表现见待定 P6。

### D5：第一步展示更新后提示和设置页历史

| 时机 | 位置 | 来源 |
|---|---|---|
| 更新到新版本之后 | 更新后提示 | 安装包内置 |
| 随时 | 设置页的更新日志历史 | 安装包内置 |

两处都不依赖更新清单，所以不受网络环境和安装方式影响。提示的形式、何时出现、跨版本怎么排、语言怎么选见待定 P7–P9。

### D6：更新前弹窗放第二步，公开版 `latest.json` 从同一份文件写入

更新前弹窗要在安装之前拿到目标版本的日志，只能来自更新清单。第二步由公开版的 `latest.json` 带上日志，内容从
`release-notes/` 的同一份文件写入，不另写一份；客户端在更新前弹窗里展示。第一步不改清单，也不改更新模块。

先做第一步，是因为它不动更新通道，公开包和黄区包都能用；第二步只对能读到公开清单的安装有效（待定 P10）。

### D7：从 v0.6.0 之后的下一个正式版开始

第一个必须有日志的版本是 v0.6.0 之后的下一个正式版。v0.6.0 之后、日志流程生效之前已经合并的改动，由人工补写进这一版
的日志。v0.6.0 及更早的版本没有日志文件，历史页从这一版开始。

v0.6.0 客户端没有展示功能，所以更新后提示最早从第一个带展示功能的版本起出现。从 v0.6.0 升级上来的用户能否看到提示，
见待定 P8。

## 不变量

1. 每个版本的日志只有一个手写来源：`release-notes/` 下该版本的文件。
2. 带 `--tag` 的打包，日志缺失或格式错误时不产出安装包；CI 与本地使用同一个检查。
3. 不带 `--tag` 的打包不因日志失败。
4. 日志检查和内置不访问网络，不依赖 GitHub 接口或 tag 的存在。
5. 安装包内置打包所用检出里的全部日志；更新后提示和设置页历史在离线时内容相同。
6. 每个日志条目同时有中文和英文。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 每个 PR 写面向用户的说明，PR 检查必过，发版时汇总并逐个核对 | 写的人最了解影响；能自动防漏 | 每个 PR 多一步，要加必过检查和 GitHub 接口权限；步骤多且与 GitHub 绑定，违反不变量 4。以后需要时可以加上，文件格式和客户端沿用 |
| 日志提交只存在于 tag，一条命令打 tag 发版 | 操作少，`main` 不变 | 不从 tag 打的黄区包和本地包没有日志；日志历史依赖 tag 不被移动或删除，要另加 tag 规则和发版人名单 |
| 用提交或 PR 标题自动生成 | 没有额外负担 | 面向开发者、中英混杂，v0.4.0 就是这样 |
| 客户端直接读 GitHub Release | 改正即时生效 | 依赖网络和接口限额，黄区不一定能访问；要从 Markdown 里切分语言 |
| 中英文各一份 Markdown | 人直接编辑更顺手 | 两种语言条数可能不一致（不变量 6），客户端还要处理 Markdown 安全 |
| 先补 desktop 更新与发布的根决策，再写更新日志 | 领域完整 | 要先把现有更新机制补成 ADR，多一轮评审，日志并不改变那些机制 |
| 并入[支持平台](../platform/0-windows-and-linux-only.md) | 不用新叶子 | 平台集合与更新日志不是一个领域，归属不清 |

### P8：没有记录时怎么区分升级用户和全新安装

从 v0.6.0 等不写记录的版本升级上来，和全新安装一样，都没有“上次运行的版本”记录。现在没有经过验证的已有信号。讨论过的
信号是本机已有的 Ora 数据，没有实测：应用启动时自己会建数据，要在建数据之前判断，重装而保留了数据的用户也会被当成
升级用户。另外，更新缓存只在应用内下载过更新的安装上才有，手动更新的用户没有，启动时还会清理已经装上的版本，也没有
实测。只有此前运行过会写入记录的版本，才能依赖这条记录；从旧版直接升级、跳过首个支持版本的用户，同样适用下表。

| 选项 | 升级用户 | 全新安装 | 代价 |
|---|---|---|---|
| 8a 没有记录就不提示，只记下当前版本 | 这一次看不到提示，仍可看历史页 | 不提示 | 从不写记录的版本升级的用户被跳过一次 |
| 8b 没有记录就提示一次 | 看到提示 | 也看到提示 | 打扰全新安装的用户 |
| 8c 先实测本机已有数据等信号，可靠才据此区分；不可靠时按 8a 或 8b，要一并选定 | 信号可靠时看到提示 | 信号可靠时不提示 | 多一项实测；只要还有用户从不写记录的版本直接升级，这段判断就要保留 |

### P13：日志 PR 之后合并的改动归哪个版本

采用的方案原文把它写成代价：“日志 PR 之后又合并的改动要补写，否则归到下个版本”；owner 的结论没有单独谈这一条。评审
指出，按“否则归到下个版本”，随本版交付的修复在本版日志里看不到，下个版本又把它写成自己的变化。

| 选项 | 规则 | 代价 |
|---|---|---|
| 13a 方案原文 | 要补写；没补写的归到下个版本 | 没补写时日志与实际交付的版本不一致 |
| 13b 按打包所用的提交划分（评审提出） | 发版前按打包所用的提交再核对一次，补写已纳入本版且应向用户说明的改动；随下一版交付的才记入下一版 | 发版前多一次核对，补写要再走一次 PR，期间可能又有新改动合并 |
| 13c tag 打在日志 PR 的合并提交上（没有讨论过） | 从该 tag 对应的提交打包时，日志 PR 之后合并的改动不进本版，归下个版本；日志 PR 合并前仍要核对期间合入的改动 | 收紧 D2 的 tag 位置；急需带上的修复要先合并再更新日志。只约束从 tag 打的包：`--tag` 只设版本号，手动构建按触发时选的 ref 检出，从较新的 `main` 本地打包或手动构建同一版本仍会带上之后的改动；要覆盖这些入口，得同时约束它们的检出 |

## 本决策未解决的问题

- **desktop 更新与发布的根决策。** 更新生命周期、签名清单、发版与 tag 的约束不在本文范围；以后补时另写，本文的规则
  只在与它们的接口处（D3 的 `--tag`、D6 的清单）受影响。
- **自动防漏。** 按 D2 接受人工核对；需要时另写后续 ADR。
- **预发布通道。** 不在本文范围；P4 只问带预发布后缀的打包要不要日志。

## 风险

| 风险 | 说明 |
|---|---|
| 漏写或写成内部术语 | 没有自动核对，靠 PR 审核；是 D2 接受的代价 |
| 检查通过但内容不是合并后的版本 | 检查只看检出里的文件，本地打包时未提交的文件也能通过；发版仍以 `main` 的提交为准 |
| 起始版本的日志不全 | v0.6.0 之后已合并的改动靠人工补写（D7） |

## 落地顺序

1. **specs**：评审本文，待定项有结论后并入正文，改为 `approved`，并在镜像目录补核心测试用例。`proposed` 阶段不编写核心
   用例，镜像目录 `test-cases/desktop/release-notes/` 只有占位文件，随 P1 的结论一起移动。
2. **desktop，第一步**：日志文件格式、打包检查、内置、更新后提示和设置页历史，以及第一份日志。完成后带 `--tag` 的打包开始
   要求日志，更新通道保持不变。
3. **desktop，第二步**：公开版 `latest.json` 从同一份文件写入，更新前弹窗展示。
4. **specs**：按最终实现同步本文，改为 `implemented`，登记用例证据。

第一步不碰更新通道，可以独立验收；第二步依赖第一步的文件格式，单独评审清单字段和不可信输入的处理。
