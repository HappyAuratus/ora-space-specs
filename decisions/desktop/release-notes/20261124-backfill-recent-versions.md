# 回填 v0.3.0 到 v0.6.0 的更新日志，只进历史页，卡片只提示高于 v0.6.0 的版本

给已发布的 v0.3.0、v0.4.0、v0.5.0、v0.6.0 补上更新日志文件，用户在设置页历史里能看到它们；更新后卡片只提示高于 v0.6.0 的
版本，所以升级的用户不会再被提示他们早已有的内容。v0.1.0 和更早的版本不回填。

本文为 `proposed`，内容按 owner 的结论写，没有待定项。

- **涉及**：desktop 的 `release-notes/` 四个文件、更新后卡片的判断、中英文文档。
- **不涉及**：日志的字段和打包检查的规则、安装包内置的方式、设置页历史的排序与语言。
- **不承担的迁移**：不改写已发布的 Release、清单和安装包；已安装的旧版本看不到回填的日志。

## 继承与修改

前一个决策是[更新日志根决策](0-release-notes-in-main-bundled-at-packaging.md)。

| 约定 | 处理 | 处理后的规则 |
|---|---|---|
| D1 的 `date` | **修改** | 新版本仍是计划发布日期；回填的四个版本是实际发布日期（D1） |
| D2 由谁写、覆盖范围，不变量 9 | **修改**，只限回填的四个版本 | 回填事后整理，不按“打包所用提交相对上一个正式版 tag”逐项核对（D1） |
| D5 更新后卡片 | **修改** | 加上下限（D2）；其余规则不变 |
| D7 历史页从 v0.6.0 之后的下一个正式版开始 | **修改** | 历史页从 v0.3.0 起；必须有日志的起始版本不变，仍是 v0.6.0 之后的下一个正式版 |
| “不承担的迁移”里的不回填 v0.6.0 及更早版本 | **修改** | 只有 v0.1.0 及更早的版本不回填 |
| D1 其余、D3、D4、D6，不变量 1–8 | 继承，不变 | — |

## 背景

- 已发布的正式版有 v0.0.5、v0.0.6、v0.0.7、v0.1.0、v0.3.0、v0.4.0、v0.5.0、v0.6.0，没有 v0.2.0。v0.3.0、v0.4.0、v0.6.0 的
  Release 有正文；v0.5.0 为空。
- 根决策的卡片对“没有记录的升级”没有下限，列出全部不高于当前版本的日志。直接放进旧日志，从 v0.6.0 升级的用户会看到早已有的
  内容。
- 不带 `--tag` 的构建使用检入的版本号 0.1.0，它也是真实发布过的版本；根决策靠“有没有本版本的日志文件”区分两者。

## 决策

### D1：回填四个版本，`date` 是实际发布日期

| 版本 | 内容来源 | `date` |
|---|---|---|
| 0.3.0 | Release 正文改写成面向用户的中英文条目 | 2026-09-29 |
| 0.4.0 | 同上 | 2026-10-15 |
| 0.5.0 | Release 为空，从 v0.4.0 到 v0.5.0 的提交整理 | 2026-10-26 |
| 0.6.0 | 已有的双语 Release 正文改写，去掉内部术语 | 2026-11-20 |

日期按 Release 的发布时间（UTC）取。四份文件满足与新版本相同的格式和检查。它们事后整理，不保证覆盖当时的全部改动；仓库里的文件仍是
这些版本日志的唯一来源，Release 正文不回改。

v0.0.5、v0.0.6、v0.0.7、v0.1.0 不回填：早期开发版只能从提交事后拼凑，内容不可靠。仓库里也不放 `0.1.0.json`，否则版本号 0.1.0 的
开发构建会被当成有日志的正式版。

### D2：卡片只提示高于 v0.6.0 的版本

| 情形 | 卡片 | 记录 |
|---|---|---|
| 当前正式版本高于 v0.6.0 | 按根决策 D5 的规则，但列出的版本都高于 v0.6.0 | 按根决策 D5 |
| 当前正式版本不高于 v0.6.0 | 不提示 | 不写 |

没有记录的升级因此以 v0.6.0 为下限，不再列出全部适用的日志。第二行让装有旧版本号的构建不因为仓库里有旧日志而弹出卡片。v0.6.0 是
固定值，不随发版移动：它是最后一个没有更新日志功能的正式版。

设置页历史不受下限影响，仍显示不高于当前正式版本的全部日志。

## 不变量

1. 更新后卡片从不列出 v0.6.0 及更早的版本。
2. 当前正式版本不高于 v0.6.0 时，不提示也不写记录。
3. 仓库里没有 v0.1.0 及更早版本的日志文件。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 回填全部 8 个版本 | 历史最完整 | v0.0.x 的内容只能拼凑；`0.1.0.json` 会让版本号 0.1.0 的开发构建被当成正式版 |
| 不回填 | 不改 ADR | 用户希望在设置页看到旧版本 |
| 回填但卡片不加下限 | 不改 D5 | 从 v0.6.0 升级的用户会被提示早已有的内容 |
| 把旧日志放在另一个目录，只给历史页用 | 卡片规则不用改 | 同一种内容有两个来源和两套读取路径，违反根决策不变量 1 的意图；下限规则更小 |

## 本决策未解决的问题

- Release 正文是否从日志文件生成，根决策已推迟，本文不改。

## 风险

| 风险 | 说明 |
|---|---|
| 回填内容不准或不全 | 事后整理，没有逐个改动核对；合并前由熟悉产品的人看过，更正按根决策 D4 随下个版本发布 |
| 更新前展示的后续决策带上旧版本 | 清单会带最近的版本，可能包含回填的；展示区间不含当前及更低的版本，不会显示给已经装了它们的用户 |

## 落地顺序

1. **specs**：评审本文到 `approved`，修改“更新后卡片”和“区分全新安装与升级”的核心用例，补下限和回填的义务。
2. **desktop**：四份日志、卡片下限和文档一个 PR，一起交付，避免先有旧日志而没有下限。
3. **specs**：按最终实现同步本文，改为 `implemented`。
