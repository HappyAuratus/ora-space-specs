# 回填 v0.3.0 到 v0.6.0 的更新日志供历史页查看，更新后卡片只提示高于 v0.6.0 的版本

给已发布的 v0.3.0、v0.4.0、v0.5.0、v0.6.0 补上更新日志文件，用户在设置页历史里能看到它们；更新后卡片只提示高于 v0.6.0 的
版本，所以升级的用户不会再被提示他们早已有的内容。v0.1.0 和更早的版本不回填。

本文为 `proposed`，内容按 owner 的结论写，没有待定项。

- **涉及**：desktop 的 `release-notes/` 四个文件、更新后卡片的判断、中英文文档。
- **不涉及**：日志的字段和打包检查的规则、安装包内置的方式、设置页历史的排序与语言。
- **不承担的迁移**：不改写已发布的 Release、清单和安装包；已安装的旧版本看不到回填的日志。

## 继承与修改

前一个决策是[更新清单携带最近 10 个版本的日志](20261124-manifest-notes-before-update.md)（下称清单 ADR），它先于本文批准，修改了
[更新日志根决策](0-release-notes-in-main-bundled-at-packaging.md)的 D1、D3、D5、D6 和不变量 2、5。两份文件同一天，按文件名排序时本文在前，
先后以这里为准：根决策、清单 ADR、本文。现行承诺是根决策加上清单 ADR，下表在此之上修改。

| 约定 | 处理 | 处理后的规则 |
|---|---|---|
| 根决策 D1 的 `date` | **修改** | 新版本仍是计划发布日期；回填的四个版本是实际发布日期（D1） |
| 根决策 D2 由谁写、覆盖范围 | **修改**，只限回填的四个版本 | 回填事后整理，不按“打包所用提交相对上一个正式版 tag”逐项核对（D1） |
| 根决策不变量 9 | **修改** | 对高于 v0.6.0 的版本成立 |
| 根决策 D5 更新后卡片 | **修改** | 加上下限（D2）；其余规则不变 |
| 根决策 D7 历史页从 v0.6.0 之后的下一个正式版开始 | **修改** | 历史页从 v0.3.0 起；必须有日志的起始版本不变，仍是 v0.6.0 之后的下一个正式版 |
| 根决策“不承担的迁移”里的不回填 v0.6.0 及更早版本 | **修改** | 只有 v0.1.0 及更早的版本不回填 |
| 根决策 D1 其余、D3、D6 和不变量 2、5，以清单 ADR 修改后的为准 | 继承，不变 | 回填的文件同样受每版最多 50 条、每条最多 500 码点的限制（D1） |
| 清单 ADR 的 D1 版本范围、D3 展示区间、不变量 7 | 继承，不变 | 回填版本不进更新后卡片；清单照常携带不高于目标正式版本的最近 10 个版本，不排除回填的版本 |
| 根决策 D4，不变量 1、3、4、6–8；清单 ADR 其余 | 继承，不变 | — |

## 背景

- 已发布的正式版有 v0.0.5、v0.0.6、v0.0.7、v0.1.0、v0.3.0、v0.4.0、v0.5.0、v0.6.0，没有 v0.2.0。v0.1.0、v0.3.0、
  v0.4.0 的 Release 正文是 PR 标题列表（v0.3.0 有 80 条），v0.6.0 是人工整理的双语说明，v0.5.0 和 v0.0.x 为空。
- 根决策的卡片对“没有记录的升级”没有下限，列出全部不高于当前版本的日志。直接放进旧日志，从 v0.6.0 升级的用户会看到早已有的
  内容。
- 不带 `--tag` 的构建使用检入的版本号 0.1.0，它也是真实发布过的版本；根决策靠“有没有本版本的日志文件”区分两者。

## 决策

### D1：回填四个版本，`date` 是实际发布日期

| 版本 | 对应的 tag 范围 | 内容来源 | `date` |
|---|---|---|---|
| 0.3.0 | `v0.1.0..v0.3.0` | Release 正文合并成面向用户的中英文条目 | 2026-09-29 |
| 0.4.0 | `v0.3.0..v0.4.0` | 同上 | 2026-10-15 |
| 0.5.0 | `v0.4.0..v0.5.0` | Release 为空，从提交记录整理 | 2026-10-26 |
| 0.6.0 | `v0.5.0..v0.6.0` | 已有的双语 Release 正文改写，去掉内部术语 | 2026-11-20 |

`date` 取 GitHub Release 的 `publishedAt`（UTC）；v0.5.0 的草稿 10-23 创建、10-26 发布，取 10-26。四份文件满足与新版本相同的格式和检查，
包括每版最多 50 条、每条每种语言最多 500 码点；v0.3.0 合并成面向用户的条目，不按 PR 逐条改写。

回填的文件事后整理，不保证覆盖范围内的全部改动，也不按提交逐项核对；仓库里的文件仍是这些版本日志的唯一来源，Release 正文不回改。
**合并前由熟悉产品的人看过内容，这是合并条件。**

v0.0.5、v0.0.6、v0.0.7 不回填：只能从提交拼凑，内容不可靠。v0.1.0 也不回填，仓库里不放 `0.1.0.json`：根决策 D5“按有没有本版本的
日志文件判断”要独立于 D2 的下限继续生效，版本号 0.1.0 的开发构建的历史页也不应显示 0.1.0。v0.1.0 及更早的版本没有日志文件是本条
规则，由评审保证，没有自动检查。

### D2：卡片只提示高于 v0.6.0 的版本

| 情形 | 卡片 | 记录 |
|---|---|---|
| 当前正式版本高于 v0.6.0 | 按根决策 D5 的规则，但列出的版本都高于 v0.6.0 | 按根决策 D5 |
| 当前正式版本不高于 v0.6.0 | 不提示 | 不写 |

没有记录的升级因此以 v0.6.0 为下限，不再列出全部适用的日志。v0.6.0 是固定值，不随发版移动：它是最后一个没有更新日志功能的正式版。
当前正式版本仍按根决策 D3 去掉预发布后缀和 `+build`：

| 构建 | 结果 |
|---|---|
| 用新的 `main` 带 `--tag v0.3.0` 到 `v0.6.0` 重新打的包 | 有本版本的日志文件，落在上表第二行：不提示、不写记录 |
| `0.6.0-rc.N` | 按 0.6.0 处理：不提示、不写记录 |
| `0.6.1` | 高于下限，照常提示 |
| `0.7.0-rc.1` | 照根决策 D5：提示并把记录提高到 0.7.0 |
| 版本号 0.1.0 的开发构建 | 没有本版本的日志文件，按根决策 D5 不提示、不写记录，用不到下限 |

回填版本不进更新后卡片，只在设置页历史里显示；历史不受下限影响，仍显示不高于当前正式版本的全部日志。更新清单按清单 ADR 照常携带最近
10 个版本，不排除回填的版本；能读取清单日志的正式版都高于 v0.6.0，“可更新”区块只展示高于当前的版本，所以看不到它们。

**接受的代价**：从 v0.3.0、v0.4.0、v0.5.0 直接升级的用户，卡片上看不到 0.4.0 到 0.6.0 的变化，只能在历史页看。

## 不变量

1. 更新后卡片从不列出 v0.6.0 及更早的版本。
2. 当前正式版本不高于 v0.6.0 时，不提示也不写记录。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 回填全部 8 个版本 | 历史最完整 | v0.0.x 的内容只能拼凑；`0.1.0.json` 会削弱根决策 D5 的判断，并让开发构建的历史页显示 0.1.0（D1） |
| 不回填 | 不改 ADR | 用户希望在设置页看到旧版本 |
| 回填但卡片不加下限 | 不改 D5 | 从 v0.6.0 升级的用户会被提示早已有的内容 |
| 把旧日志放在另一个目录，只给历史页用 | 卡片规则不用改 | 同一种内容有两个来源和两套读取路径，违反根决策不变量 1 的意图；下限规则更小 |

## 本决策未解决的问题

- Release 正文是否从日志文件生成，根决策已推迟，本文不改。

## 风险

| 风险 | 说明 |
|---|---|
| 回填内容不准或不全 | 事后整理，没有逐个改动核对；合并前由熟悉产品的人看过，更正按根决策 D4 随下个版本发布 |
| 更新清单带上回填的版本 | 版本范围和展示区间由[清单 ADR](20261124-manifest-notes-before-update.md) 定。能读取清单日志的正式版看不到回填的版本；版本号仍是 0.1.0 的构建可能看到，它们本来就低于这些版本 |

   [卡片](../../../test-cases/desktop/release-notes/packaging-and-display.md#the-update-card-lists-each-unseen-version-once)与
   [没有记录的升级](../../../test-cases/desktop/release-notes/packaging-and-display.md#fresh-installs-and-upgrades-without-a-record-are-told-apart)
   补版本下限和不写记录；[历史页](../../../test-cases/desktop/release-notes/packaging-and-display.md#bundled-notes-need-no-network)
   补四个回填版本；[提交范围](../../../test-cases/desktop/release-notes/packaging-and-display.md#notes-cover-the-packaged-commit-range)
   限定为高于 v0.6.0 的版本。
2. **desktop**：四份日志、卡片下限和文档一个 PR，一起交付，避免先有旧日志而没有下限。
3. **specs**：按最终实现同步本文，改为 `implemented`。
