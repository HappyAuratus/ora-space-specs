# 更新清单携带最近版本的日志，更新确认弹窗在安装前展示

公开版的更新清单 `latest.json` 带上双语日志，内容从 `release-notes/` 的同一份文件写入；客户端在用户确认安装之前，于现有的更新
确认弹窗里展示当前版本到目标版本之间的变化。日志只是附带内容：缺失、损坏或超限时只隐藏日志，检查、下载、安装不变。

本文为 `proposed`。D1–D3 由根决策推出，其中“超限整体隐藏而不截断”（D2、不变量 5）是作者的提案，请一并评审；“待定”列出要由 owner 选的取舍，各项只给选项、代价和作者建议，
本文不替 owner 选。待定项有结论、并入决策之后才能改为 `approved`。

- **涉及**：desktop 的更新清单生成脚本、Tauri 更新模块与它交给前端的状态、更新确认弹窗。
- **不涉及**：日志的文件格式、打包检查、内置、更新后卡片和设置页历史；更新的检查、下载、安装行为；清单的平台集合与签名。
- **不承担的迁移**：已发布版本的清单不改写；已安装的旧客户端忽略新字段。

## 继承与修改

前一个决策是[更新日志根决策](0-release-notes-in-main-bundled-at-packaging.md)。

| 约定 | 处理 | 说明 |
|---|---|---|
| D1 文件格式与唯一手写来源，不变量 1 | 继承，不变 | 清单里的日志由文件生成，不另写 |
| D2 由谁写、覆盖范围 | 继承，不变 | — |
| D3、D4 打包检查与内置 | 继承，不变 | — |
| D5 更新后卡片与历史 | 继承，不变；与更新前展示的关系见 Q5 | — |
| D6 更新前弹窗放第二步，字段、版本数和手动更新由后续 ADR 定 | 由本文落实 | 可达性规则不变：能检查到更新的安装才看得到 |
| D7 起始版本 | 继承，不变 | 旧客户端没有这个弹窗，从第一个带它的版本往后才看得到 |
| 不变量 6、7、8（纯文本、失败只隐藏、清单日志不可信并限长限条数） | 继承，不变 | 本文给出数值（Q3） |
| 不变量 1–5、9 | 继承，不变 | — |

## 背景

- 清单由 `desktop-build` 的 `release` job 生成，这个 job 有自己的检出，能读到 `release-notes/`；只有配置了更新签名密钥才生成。
  现在 `notes` 写成 `Ora <tag>`。
- 更新器插件（`tauri-plugin-updater` 2.10.1）把清单的 `notes` 当字符串解析，类型不符会让**整份清单**解析失败；它同时保留
  原始 JSON，多余字段不影响解析。
- 只有更新包就绪时更新控件可点；由用户手动更新的安装（如 deb）显示红点，但按钮禁用。
- 清单不在安装包签名的范围内，应用的 `csp` 为 `null`。

以上依据 desktop `main` 提交 `7b2112af` 和插件源码。

## 决策

### D1：清单的日志由 `release-notes/` 生成，标准 `notes` 始终是字符串

生成清单时，从 `release` job 检出里的日志文件取内容，按打包检查同一套校验读取。同一次发布的打包已经要求日志合格，正常情况下
这里不会不合格；不合格时清单怎么办见待定 Q7。双语日志放进自定义字段，标准 `notes` 保持字符串：它的类型一旦变化，旧客户端和新客户端
都会检查不到更新，违反根决策不变量 7。

### D2：客户端把清单日志当不可信输入，单独解析

更新器先下载并解析整份清单。检查成功后，客户端从保留的原始 JSON 单独校验日志字段，结果只有“有日志”和“没有日志”两种，不产生
新的更新状态或错误。日志超出 Q3 的上限时整体隐藏，而不是截断，避免把残缺的内容当成完整说明。Q3 的上限只约束检查成功之后的
日志处理；整份清单的下载和 JSON 解析仍按更新器的规则执行。

### D3：更新确认弹窗展示当前版本到目标版本之间的日志

弹窗列出高于当前正式版本、不高于目标版本的日志，按版本倒序，按界面语言，只按纯文本；排版与更新后卡片相同，内容多时在弹窗内
滚动，确认按钮始终可见。没有日志时，弹窗与现在完全一样。清单里没有的中间版本不补，也不联网另取。

## 待定

| 编号 | 要定什么 | 选项与代价 | 作者建议 |
|---|---|---|---|
| Q1 | 清单字段 | a：自定义字段 `ora_release_notes` 放日志数组，元素与日志文件同格式，`notes` 写目标版本的英文纯文本；b：同 a，`notes` 仍为 `Ora <tag>`，改动最小，但公开清单的其他读者看不到内容 | b，没有已知的其他读者 |
| Q2 | 带几个版本 | a：只带目标版本，跨版本更新看不到中间版本；b：最近 10 个版本，跨更多版本时中间的看不到；c：全部版本，清单随版本增长，每次检查都下载 | b |
| Q3 | 客户端上限，以及生成端遇到合格但超限的内容怎么办 | 单条文字长度沿用日志文件的上限，另设版本数和每版条数上限（根决策不变量 8）；可再叠加整组日志的字节上限。打包检查不限每版条数，所以一份 51 条的日志能通过打包；写入清单而客户端上限是 50 条时，客户端会隐藏**整组**日志，即使超限的只是历史版本。超限的处理：a：打包检查加同样的每版条数上限，写日志时就发现，但这是对根决策 D1、D3 的修改；b：生成清单时按客户端上限只放装得下的最近版本，单版超限就不放该版；c：两端不对齐，接受整组隐藏 | 10 个版本、每版 50 条，不加字节上限；处理用 b，不改根决策 |
| Q4 | 手动更新的用户 | a：`manual_update` 时按钮可点，打开同一内容的弹窗，不给安装按钮，说明用什么方式更新；b：保持禁用，只有更新后卡片和历史页 | a，根决策的背景就把它列为问题 |
| Q5 | 更新前看过之后，更新后的卡片还弹不弹 | a：照弹，规则最简单，用户可能看两遍；b：更新前看过目标版本就不弹，要多存一个“更新前看过”的状态，且“看过”只能按打开弹窗算；Q2 选 a 或 b 时弹窗可能只有部分版本，这样会把根决策 D5 要提示的其余未读版本也一起跳过；c：只跳过弹窗里实际展示过的版本，其余照弹，要记住展示过哪些版本 | a |
| Q6 | 在哪里解析 | a：Rust 更新模块解析、限制、筛选，随 `Ready` 和 `ManualUpdate` 状态交给前端，前端拿不到原始清单；b：把原始 JSON 交给前端解析，Rust 改动少，但不可信输入进了 webview | a |
| Q7 | 生成清单时日志不合格怎么办 | 清单在 Release 草稿之前生成，这一步失败会让发布停住。a：照常生成基础清单，不带日志，并在构建日志里记录原因，符合不变量 1 和根决策不变量 7；b：失败，逼着修好再发，但会让日志挡住更新，与根决策不变量 7 冲突，选它要写成对根决策的修改 | a |

## 不变量

1. 更新器成功解析清单之后，更新的检查、下载、安装结果不因清单里有没有日志、日志是否合格而改变。
2. 标准 `notes` 在任何清单里都是字符串。
3. 清单里的日志只来自 `release-notes/` 的文件，与同一提交的内置日志一致。
4. 弹窗不展示高于目标版本或不高于当前正式版本的日志。
5. 客户端遇到超过上限的日志整体隐藏，不截断展示。

## 为什么不是这些替代方案

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 把日志写成 Markdown 放进标准 `notes` | 只用标准字段 | 两种语言要从一个字符串里切分，还要处理标记，违反根决策不变量 6 |
| `notes` 改成对象 | 不用自定义字段 | 插件解析整份清单失败，违反不变量 2 |
| 弹窗打开时再联网取日志 | 清单小，可随时改正 | 多一个网络依赖和失败路径；与更新检查的可达性不再一致 |
| 给日志单独签名 | 可以信任 | 要新增密钥用法和验证路径，而纯文本加限制已经限制了影响 |

## 本决策未解决的问题

- Release 正文是否从同一份文件生成，根决策已推迟，本文不改。
- 更新入口的位置（例如主界面红点）不在本文范围。
- 黄区能否访问更新清单的地址没有核实；访问不到时没有更新前日志，按根决策 D6 处理。

## 风险

| 风险 | 说明 |
|---|---|
| 篡改清单伪造说明文字 | 纯文本和上限只限制影响，不能防止文字本身是假的；安装包仍由签名保证 |
| 发布后发现日志有误 | 在 `main` 修正源文件，更正随下个版本的清单和安装包发布（根决策 D4） |
| 清单变大 | 每次检查都下载；由 Q2 的版本数控制 |
| 超大的清单 | 更新器先下载并解析整份清单，Q3 的上限管不到这一步；清单被篡改到很大时，检查更新本身可能变慢或失败。现在没有日志时也是如此，本文不新增也不消除这个风险 |

## 落地顺序

1. **specs**：待定项有结论后并入决策，改为 `approved`，补核心测试用例。
2. **desktop**：清单生成、更新模块解析与状态、弹窗，一个 PR。完成后公开版清单开始带日志；旧客户端行为不变。
3. **specs**：按最终实现同步本文，改为 `implemented`。

发布一个带日志的清单之后，才能从旧版本实测一次更新前弹窗；在此之前只有单元测试。
