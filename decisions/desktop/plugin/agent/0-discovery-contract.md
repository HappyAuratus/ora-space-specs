# Agent 插件用 `agent/discover` 一次返回模型和命令，取代只返回模型的 `agent/list_models`

Agent 插件的会话前发现改为一个方法 `agent/discover`：针对一个 Workspace，返回 Agent 可选的模型，以及调用方需要时 Agent
上报的命令。命令用 `Option` 表达，`None` 表示插件没有提供，`Some([])` 表示 Agent 明确上报了空列表，两者不可互换。发现由
插件完成：插件起一个独立的一次性 Agent 进程，不使用 Ora 正在使用的连接。插件作者只写一个 `discover()`；过渡期内 SDK
同时注册 `agent/discover` 和旧名 `agent/list_models`，Desktop 接受任意一个，且一次发现只调用其中一个。

行为变化：打开旧会话或新聊天、尚未发送第一条消息时，Desktop 可以展示 Agent 上报的命令，包括 Agent 自带的 skill。会话
何时连接 Agent 不变，打开会话仍不连接 Agent。

本文为 `approved`，尚未实现。等待上限是暂定值，实测后只可下调（D3）。

- **涉及**：desktop 的插件协议与生成绑定、插件 SDK、`ora-agent-runtime` 的契约检查与发现调用、公共契约、前端的模型与
  命令展示；各 Agent 插件的发现实现。
- **兼容边界**：新 Desktop 配旧插件、旧 Desktop 配新插件，**模型发现**都必须可用；兼容期见 D4。Skill 交付的跨版本行为以
  [Skill 会话清单决策](../../core/agent/session/skill/0-skill-catalog-from-storage-paths.md)为准，不由本文保证（见风险）。
  没有持久化数据，不需要迁移。
- **不涉及**：`agent/start`、`agent/stop`、`agent/acp` 的语义，会话的建立与恢复，会话自己上报命令的交付，MCP 的会话
  交付，插件清单与分发。
- 本文是 Agent 插件领域的根决策，只固定发现契约；Agent 插件的其他契约由后续决策补充。

## 背景

`agent/list_models` 已经是会话前发现：插件起一个一次性进程，`initialize` 后 `session/new`，从响应的配置项读出模型，
再清理并结束进程。ACP 的 `session/new` 响应没有命令字段，命令由随后的 `available_commands_update` 通知带来；插件读完
响应就结束，列表因此丢掉。CodeAgent 的两次录帧里，通知在 `session/new` 响应之后到达：冷进程 12 毫秒、热进程 3 毫秒。

于是首次发消息前，Desktop 不知道 Agent 有哪些命令，只能提示用户先对话一轮。在现有发现里多等一条通知就能得到列表，不
需要新的进程或连接。

本文关于 CodeAgent、OpenCode、Codex 的说法来自作者阅读代码和上述录帧，评审中**未独立核实**；Claude 插件与 Desktop 的
说法已核实。

## 术语

- **会话前发现**：在没有 Ora 会话 provider 的情况下，由 Agent 插件回答“这个 Workspace 里该 Agent 提供什么”。
- **发现进程**：插件为一次会话前发现启动的、独立的一次性 Agent 进程及其中的临时 ACP 会话。
- **命令**：Agent 通过 ACP `available_commands_update` 上报的条目，按上报渠道界定。Agent 自带的 skill、插件接入原生
  机制后的 Ora Skill，都可能以命令上报，它们都是命令。

## 决策

### D1：一个方法返回模型和命令，调用方声明是否需要命令

`agent/discover` 的输入是：Workspace 的工作目录、是否需要命令，以及 D5、D6 规定的 Skill 输入和修订号。输出是模型列表
和可缺省的命令列表。

```jsonc
// 仅说明语义，不是实现契约
{ "models": [{ "id": "m1", "displayName": "Model 1", "default": true }],
  "commands": [{ "name": "review", "description": "Review changes", "inputHint": "scope" }] }
```

1. 模型的含义与 `agent/list_models` 相同，空列表合法。
2. 每条命令有名称、描述和可缺省的输入提示，插件按 Agent 上报的内容和顺序转述，不增删，不按名称与 Ora 的 Skill 合并。
3. 调用方不需要命令时，插件不等待，命令为 `None`。只取模型的调用方（工作流编辑器的模型目录、定时任务的模型校验）不
   需要命令；SDK 的 `agent/list_models` 包装同样按不需要处理，所以旧 Desktop 不会为用不到的命令等待。不需要命令时，Skill
   输入和修订号可以省略，也不参与缓存键。
4. 发现按需调用，Ora 不缓存结果到持久存储。一次发现失败只影响这一次请求，不使 Agent 变为不可用。

用一个方法而不是两个：模型和命令来自同一个发现进程，拆成两个方法就要在插件里共享结果，否则起两次进程。改名而不是在
`agent/list_models` 上加字段：方法名说的是模型，返回命令后名实不符，以后再增加会话前信息会更不准。不叫
`capabilities` 类名称，避免与 ACP `initialize` 的 `agentCapabilities` 混淆。

### D2：`None` 与空列表是两个事实

| 值 | 含义 | 何时产生 |
| --- | --- | --- |
| `None`（字段缺省或 `null`） | 插件没有提供，不知道 Agent 有哪些命令 | 旧插件、调用方不需要、没有等到上报、平台冻结模型的路径 |
| `Some([])` | Agent 明确上报没有命令 | 收到的上报为空 |
| `Some([...])` | Agent 上报的列表 | 收到非空上报 |

没有等到上报时不得返回空列表。`None` 时 Desktop 的行为与没有本契约时相同，继续提示用户先对话一轮。把“不知道”写成
“没有”会让界面否认实际存在的命令。

### D3：发现进程等待第一条命令上报，但不让模型为命令付出失败

1. 使用独立的一次性进程和临时会话，不向 Ora 正在使用的连接注入请求。
2. 需要命令时，收到 `session/new` 响应后等待属于该临时会话的第一条 `available_commands_update`，收到立即继续；在响应
   之前已经到达的上报同样算数。后续上报不再等待。
3. 等待上限由契约统一规定，从收到 `session/new` 响应起算。契约上限和 SDK 默认值都是 **2 秒**，插件只能调低，不能调高。
   这是暂定值：在真实 CodeAgent 上分别测冷启动、热启动和不上报命令三种情况后，转 `implemented` 时可以下调；上调需要另立
   决策。
4. 到上限、进程退出或通道关闭时，模型照常返回，命令为 `None`。
5. 读取命令之后才清理临时会话：Agent 声明支持 `session/delete` 时尽力删除，最后无论如何结束进程。一次发现的总预算中
   为清理预留时间，等待截止于“上限”与“总预算减去清理预留”中较早的一个，**等待不得占用清理预留**。预留值不进契约，由 SDK
   或插件作为常量，建议 5 秒。清理超时不影响已经读到的模型和命令。
6. 不带 MCP（空 `mcpServers`）。Agent 若把 MCP 提供的提示词也作为命令上报，会话上报的列表会比发现结果多出这些条目，
   这是已知差异，不是错误。
7. 平台冻结模型的路径不启动发现进程，返回冻结的模型，命令为 `None`。

上限只影响需要命令、而 Agent 又不上报命令的发现。由契约统一而不是各插件自定，是为了行为一致、可以评审；只能调低，是
因为调高会让一个插件拖慢整个界面。预留清理时间，是因为 `session/new` 可能在预算末尾才返回，再等命令就没有时间删除临时
会话，原本可删的会话会留在 Agent 历史里；代价是预算末尾的发现可能拿不到命令。不改用现有连接，是因为在上面开临时会话会
触发 Agent 的会话启动 hook，并可能在不支持删除的 Agent 历史里留下空会话。

### D4：过渡期同时支持新旧方法名，一次发现只调用一个

| Desktop | 插件 | 行为 |
| --- | --- | --- |
| 新 | 注册 `agent/discover` | 调用 `agent/discover`，不调用 `agent/list_models` |
| 新 | 只有 `agent/list_models` | 调用 `agent/list_models`，命令为 `None` |
| 新 | 两者都没有 | 契约不完整，Agent 不可用 |
| 旧 | 新 SDK 构建 | 调用 `agent/list_models`，只得到模型，不等待命令 |

1. 契约检查要求 `agent/discover` 与 `agent/list_models` 至少有一个，其余必需项不变。
2. 有 `agent/discover` 时，它失败不退回 `agent/list_models`：两者是同一次发现，重试只会再起一个进程。
3. SDK 只让插件作者实现一个 `discover()`，并注册两个方法；`agent/list_models` 以不需要命令、没有 Skill 输入的方式调用
   它，只返回模型。
4. 删除分两层，破坏的组合不同，各有标准，届时各以后续决策记录：

| 层 | 破坏的组合 | 标准 |
| --- | --- | --- |
| Desktop 不再接受只有 `agent/list_models` 的插件 | 新 Desktop 配旧插件 | 官方来源的 Agent 插件都已发布支持 `agent/discover` 的版本，并经过一个 Desktop 稳定版本。错误必须点名“缺少 `agent/discover`，请更新插件” |
| SDK 不再注册 `agent/list_models` | 旧 Desktop 配新插件 | 插件能够声明最低 Desktop 版本，且该版本已支持 `agent/discover`。在有这样的声明机制之前不删除；该机制与 Skill 交付的跨版本处理一并决定，本文不另设 |

### D5：发现进程使用与会话相同的 Skill 输入

会话 setup 交付两类 Skill 输入：作为额外可读目录的 Skill 可读根，以及 `_meta` 中可选的 Skill 目录。前者只授予读取；让
Ora Skill 以 Agent 命令出现的是后者，插件可以把它接到 Agent 的原生机制。只传可读根，发现结果会系统性地缺少会话里会有的
命令。

所以需要命令时，发现进程的 `session/new` 与会话 setup 使用**同一个构造**，两类输入都传，值相同。它们由 Desktop 在 `agent/discover`
的输入中给出，插件不自己推断。额外可读目录仍只在 Agent 声明能力时发送，缺少能力不使发现失败；Skill 目录为空时不带。

Skill 输入依赖 Skill 会话清单决策的 host 扩展点与 setup 字段。两者落地前，`agent/discover` 的这部分输入为空。

### D6：Skill 变化用修订号使发现结果失效

Skill Catalog 变化后，下一次需要命令的发现不得返回变化之前的结果。此前这一点靠 Effect 引起的 Agent 进程替换，以及插件
处理 Effect 时清除自己的缓存，两条都随 Effect 退役消失。

1. 需要命令时，`agent/discover` 的输入带一个不透明的修订号。Desktop 每提交一次 Skill Catalog 变更（安装、卸载、改名、升级，
   以及本地 Skill 的原地编辑）就推进一次，不看清单内容是否与以前相同。修订号在 Desktop 进程内单调递增，只放在内存里。
2. 插件可以不缓存；如果缓存，必须以**完整的发现输入**为键，包括工作目录和是否需要命令；需要命令时还包括 Skill 输入和
   修订号。缓存只在插件进程内存在：插件进程随 Desktop 结束，所以修订号在缓存存续期内不会重复。
3. Desktop 的缓存也要区分是否需要命令：不需要命令的结果不得满足需要命令的请求；需要命令的结果可以满足不需要命令的请求。
   现在工作流编辑器和对话里的模型选择器共用一个缓存键，不区分就会让编辑器得到的 `None` 在有效期内挡住选择器的命令。
4. 推进修订号的同一时点，Desktop 发布现有的 Agent 发现失效事件（`AgentModelsInvalidated`），使界面上**需要命令的**发现
   结果失效。该事件此前唯一的发出者是 Effect 的进程替换，Effect 退役后由 Skill Catalog 变更发出。变化之前发出的请求即使
   随后完成，其结果也不得作为变化之后的结果展示或缓存。
5. Skill 变化不影响只取模型的请求。安装一个 Skill 不会使工作流编辑器为每个 Agent 各起一个发现进程。
6. `None` 与其他结果一样带有效期缓存；发现失败不缓存。
7. 失效不重启 Agent、不影响进行中的 turn。失效本身不启动发现进程；正在显示的界面可以立即重新发现。

修订号和事件缺一不可：界面短时间内不重复发现，插件也可能复用结果，只让其中一处失效仍会读到旧列表。修订号不用清单摘要：
Skill 清单只有路径、名称和描述，卸载后以相同的三项装上内容不同的版本，或只改 `SKILL.md` 的其他字段，摘要都不变，而接入
原生机制的 Agent 可能用这些字段生成命令。按 Catalog 变更推进就能覆盖这两种情况，不用读包内容：本地 Skill 目录只经 Catalog
事务修改，插件 Skill 升级时路径会变。绕过 Ora 直接修改 `atoms/skills/` 下的文件不在范围内，与 Skill 会话清单决策一致。

代价是任意 Skill 变化都会使全部 Agent 需要命令的发现结果失效，即使变化与命令无关。`None` 照常缓存的代价是一次偶然的慢启动
会让命令在有效期内缺失；不缓存则会让不上报命令的 Agent 每次展示都再起一个进程。

### D7：会话自己的上报优先，发现结果只用于会话之前

1. 没有待执行的 Agent 切换时，会话已经收到 Agent 上报的命令（包括空列表）就只使用会话的列表；没有时才用发现结果。
2. 存在待执行的 Agent 切换时，使用将要切换到的 Agent 的发现结果。
3. 前端必须保留命令列表的**来源**（会话上报或会话前发现）及所属 Agent。“Agent 不支持该命令”的提示只看当前发送目标自己的
   会话上报；存在待执行的 Agent 切换时不显示该提示，因为会话已有的列表属于切换前的 Agent。发现结果只用来展示，不参与
   判断：发现不带 MCP，用它判断会误报 MCP 提供的命令。
4. 发现结果不写入会话历史，不随会话持久化，不改变会话何时连接 Agent。
5. Node 没有会话前的选择界面，不调用发现；它与 Desktop 共用契约检查，所以接受同样的插件。

边界：现有会话 setup 的响应用同一个空列表表示“没有上报”和“上报为空”，恢复与切换时还会略过空列表。本文不改这一点：
setup 的空列表按“没有上报”处理，后续实时上报的空列表按“上报为空”处理。因此 Agent 只在 setup 时明确上报空列表、首轮又
被取消时，发现结果会多展示一轮。在会话契约上保留“是否上报过”，留到本契约落地时一并处理（见未解决的问题）。

### D8：命令是不可信文本

命令来自 Agent，常常取自仓库文件，并在用户没有发起任何会话时自动展示。以下展示规则对发现结果和会话上报两种来源都适用，
只约束展示，不改变会话交付：

1. Desktop 只按纯文本展示名称、描述和输入提示，不解释标记、链接或控制字符；不因展示而执行任何命令，选择命令只填入输入框。
2. Desktop 执行以下限制：

   | 对象 | 上限 | 超出时 |
   | --- | --- | --- |
   | 条数 | 500 | 按 Agent 上报的顺序保留前 500 条，插件日志记一次 `warn`，只记数量 |
   | 名称 | 128 bytes（UTF-8） | 丢弃这一条 |
   | 描述 | 4096 bytes（UTF-8） | 在字符边界截断并加省略号 |
   | 输入提示 | 256 bytes（UTF-8） | 在字符边界截断 |

3. 名称为空、含空白字符或控制字符的条目是非法的，逐条丢弃，不使整个发现失败，也不影响模型。除此之外不限制字符：`:`、`-`、
   `_`、`.` 和非 ASCII 字母都合法，真实的 Agent 会上报带插件前缀的名称，例如 `developer-test-agent:generate-dt-files`。
4. 界面标明这些命令来自 Agent，与 Ora 管理的 Skill 区分。
5. 插件日志在 `info` 及以上级别不记录完整的命令列表和 Skill 目录列表，只记数量等摘要。工作目录、Skill 路径等本机绝对路径
   可以出现在日志中，本文不为它们新增脱敏。

## 不变量

1. 一次发现最多启动一个 Agent 进程，最多调用 `agent/discover` 与 `agent/list_models` 中的一个。
2. 没有收到 Agent 上报时命令为 `None`，空列表只来自 Agent 的明确上报。
3. 命令没有到达不影响模型返回；发现失败不使 Agent 不可用。
4. 不需要命令的发现不等待命令。
5. 发现进程不使用 Ora 的共享连接，不带 MCP，结束后不留下进程。
6. 没有待执行的 Agent 切换时，会话已上报的命令优先于发现结果；有待执行的切换时，使用目标 Agent 的发现结果。
7. 发现不创建 Ora 会话、不写历史、不改变会话的生命周期状态。
8. 需要命令时，发现进程与会话的 Skill 输入出自同一个构造，值相同。
9. Skill Catalog 变化之后，需要命令的发现不返回变化之前的结果；变化之前发出的请求随后完成，也不得展示或缓存。失效本身
   不启动发现进程；正在显示的界面可以立即重新发现。
10. 兼容期内，新旧 Desktop 与新旧插件的任意组合都能列出模型。
11. “Agent 不支持该命令”只由当前发送目标自己的会话上报得出；存在待执行的 Agent 切换时不提示。
12. 命令只作为纯文本展示，单个非法条目不影响其余条目和模型。
13. 等待命令不超过契约上限，也不占用清理预留；清理超时不影响已读到的模型和命令。
14. 不需要命令的发现结果不满足需要命令的请求，也不受 Skill 变化影响。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 扩展 `agent/list_models` 的结果 | 改动最小，不需要兼容两个方法名 | 方法名与内容不符，后续增加会话前信息时更不准 |
| 新增独立的 `agent/list_commands` | 名字清楚 | 与模型同源，插件要共享结果，否则起两次进程（不变量 1） |
| Desktop 在现有连接上开临时 `session/new` | 只改 Desktop，覆盖全部插件，更快 | 违背发现归插件；可能触发会话启动 hook，并在 Agent 历史里留空会话 |
| 打开会话就连接 Agent | 能拿到与会话完全一致的列表 | 会话变为运行中而挡住删除，忽略连接前选的模型，并启动 MCP |
| 持久化上次会话上报的列表 | 立即可用，不起进程 | 会过期，需要新的持久化模型；从未对话过的 Workspace 仍然没有 |
| 没有上报时返回空列表 | 类型更简单 | 把“不知道”写成“没有”（不变量 2） |
| 直接替换，不保留旧方法名 | 没有兼容代码 | 新 Desktop 配旧插件、旧 Desktop 配新插件都会被判为契约不完整，Agent 不可用 |
| 带 MCP，使列表与会话完全一致 | 没有已知差异 | 会话前就启动 MCP 进程并暴露凭据，只为展示列表不值得 |
| 只传 Skill 可读根 | 输入稳定，缓存键简单 | 可读根不产生命令，接了原生机制的 Agent 会缺少会话里有的命令（不变量 8） |
| 宿主通知插件清缓存 | 语义直接 | 新旧插件要协商是否支持，还要处理通知与进行中发现的先后 |
| 用 Skill 清单摘要作修订号 | 修订号与清单内容一一对应 | 清单恢复旧值或原地更新时摘要不变，会返回旧列表（不变量 9） |
| 用包内容摘要作修订号 | 恢复到相同内容时可复用缓存 | 每次都要读包内容，Catalog 变更已能给出同样的失效 |
| 插件只保留当前修订号的缓存 | 不必保证修订号不重复 | 两次变化之间没有发现请求时插件看不到中间值，仍会命中旧结果 |
| Skill 变化也使只取模型的结果失效 | 只有一种失效 | 模型与 Skill 无关，装一个 Skill 会让工作流编辑器为每个 Agent 起进程 |
| 插件不缓存，只由 Desktop 缓存 | 失效点只有一个 | 改变“发现和缓存归插件”的约定，并发请求的合并要移到 Desktop |
| 命令为 `None` 时不缓存 | 偶然的慢启动能自愈 | 不上报命令的 Agent 每次展示都再起一个进程 |
| 先返回结果，后台清理 | 答复最快 | 清理失败不可见，插件停止时可能来不及删除 |
| 不为清理预留时间 | 最简单，不多一个数值 | 预算末尾的发现会在 Agent 历史里留下原本可删的会话（不变量 13） |
| 用发现结果提示“不支持” | 首次发消息前就能发现拼写错误 | 不带 MCP，会误报 MCP 提供的命令（不变量 11） |

## 风险

- **旧 Desktop 上 Skill 消失**：与 Effect 退役合并发版后，新插件不再声明 `effectResources`。旧 Desktop 仍会通过契约检查，
  但它只靠 Effect 物化 Skill，又没有会话清单，Skill 会整体消失。模型发现不受影响。这属于 Skill 会话清单的跨版本行为，
  是否需要最低 Desktop 版本由该决策处理，本文不替它决定。
- **首次展示变慢**：需要命令而 Agent 不上报时等满上限；由 D3 的上限和 D6 的缓存控制。
- **发现的副作用**：一次性会话可能触发 Agent 的会话启动 hook，或在不支持删除的 Agent 里留下空会话。这是现有发现已有的
  行为，本决策不增加启动次数，但 Skill 变化会使缓存失效而多一次。
- **旧 Desktop 与多出的方法**：兼容表假定旧 Desktop 接受插件注册多余的方法。目前没有发现拒绝的检查，实现时要用真实
  旧版本验证，不能只凭阅读代码。

## 本决策未解决的问题

- 会话 setup 区分“没有上报”和“上报为空”：需要改会话契约，随本契约的实现一并处理；在此之前按 D7 的边界。
- 会话前的推理强度等其他信息是否进入发现结果：取决于 Agent 是否在会话前提供，需要单独决策。
- 第三方插件契约版本的协商：本文用“注册了哪个方法”判断能力，没有引入版本号。D4 第二层的删除依赖可声明的最低 Desktop
  版本，该机制尚不存在，与 Skill 交付的跨版本处理一并决定。
- Agent 插件的启动、停止和 ACP 通道契约：不在本文范围。

## 落地顺序

1. **本 ADR 评审**：已通过，核心用例见 `test-cases/desktop/plugin/agent/`。等待的用例只断言不超过契约常量，不写具体数值。
2. **Desktop 支持 `agent/discover`**：协议、契约检查、调用与展示，以及 SDK 源码。完成条件是新 Desktop 配旧插件行为不变，
   配测试插件能展示命令。D5、D6 的 Skill 输入与修订号在 Skill 会话清单的 host 扩展点与 setup 字段进入主干之后接入。
3. **SDK 与插件发版**：与 Effect 退役合到同一次 SDK 和插件发版，SDK 在本决策与 Effect 退役的 Desktop 改动都进入主干后
   发布。首先是 CodeAgent 插件，完成条件是在真实 Agent 上首次发消息前能看到命令，并且 D3 的三种情况已实测、
   实测记录写在 circus issue、本文同步最终值；Claude、OpenCode、Codex 插件随后各自跟进。
4. **实现后**：按最终实现同步本文，删除背景中的核实说明，标记 `implemented`，登记核心用例证据。
5. **删除旧方法名**：按 D4 的两层标准，各以后续决策记录。

第 2 步之后没有更新的插件行为不变；从第 3 步开始，更新了的插件在首次发消息前提供命令。
