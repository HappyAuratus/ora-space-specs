# Agent 插件用 `agent/discover` 一次返回模型和命令，取代只返回模型的 `agent/list_models`

Agent 插件的会话前发现改为一个方法 `agent/discover`：针对一个 Workspace，返回 Agent 可选的模型，以及 Agent 自带的
命令。命令用 `Option` 表达，`None` 表示插件没有提供，`Some([])` 表示 Agent 明确上报了空列表，两者不可互换。发现由插件
完成：插件起一个独立的一次性 Agent 进程探测，不使用 Ora 正在使用的连接。插件作者只写一个 `discover()`；过渡期内 SDK
同时注册 `agent/discover` 和旧名 `agent/list_models`，Desktop 接受任意一个，且一次发现只调用其中一个。

行为变化：打开旧会话或新聊天、尚未发送第一条消息时，Desktop 可以展示 Agent 自带的命令和 skill。会话何时连接 Agent
不变，打开会话仍不连接 Agent。

本文为 `proposed`。已在立项时确定的是：由插件探测并等待第一条命令上报、`None` 与空列表的区别、方法改名与新旧名并存、
探测使用与会话相同的 Skill 根目录、Skill 变化要有新的失效信号、与 Effect 退役合并发版。其余规则（如超时仍返回模型、
会话上报优先）是作者的提案，供评审；未定的做法列在“待定”，没有预先选择。

- **涉及**：desktop 的插件协议与生成绑定、插件 SDK、`ora-agent-runtime` 的契约检查与发现调用、公共契约、前端的模型与
  命令展示；各 Agent 插件的探测实现。
- **兼容边界**：新 Desktop 配旧插件、旧 Desktop 配新插件都必须能用；兼容期见 D4。没有持久化数据，不需要迁移。
- **不涉及**：`agent/start`、`agent/stop`、`agent/acp` 的语义，会话的建立与恢复，会话自己上报命令的交付，MCP 的会话
  交付，插件清单与分发。
- 本文是 Agent 插件领域的根决策，只固定发现契约；Agent 插件的其他契约由后续决策补充。

## 背景

`agent/list_models` 已经是会话前发现：插件起一个一次性进程，`initialize` 后 `session/new`，从响应的配置项读出模型，
再清理并结束进程。ACP 的 `session/new` 响应没有命令字段，命令由随后的 `available_commands_update` 通知带来；探测读完
响应就结束，列表因此丢掉。一次采样中，通知在响应后 3–12 毫秒到达。

于是首次发消息前，Desktop 不知道 Agent 有哪些命令，只能提示用户先对话一轮。在现有探测里多等一条通知就能得到列表，不
需要新的进程或连接。

## 术语

- **会话前发现**：在没有 Ora 会话 provider 的情况下，由 Agent 插件回答“这个 Workspace 里该 Agent 提供什么”。
- **探测**：插件为一次会话前发现启动的、独立的一次性 Agent 进程及其中的临时 ACP 会话。
- **命令**：Agent 通过 ACP `available_commands_update` 上报的条目。ACP 不区分命令和 skill，Agent 自带的 skill 也以
  命令上报。Ora 自己管理的 Skill 不属于命令，不经本契约。

## 决策

### D1：一个方法返回模型和命令

`agent/discover` 的输入至少有 Workspace 的工作目录，以及 D5 规定的 Skill 输入；输出是模型列表和可缺省的命令列表。

```jsonc
// 仅说明语义，不是实现契约
{ "models": [{ "id": "m1", "displayName": "Model 1", "default": true }],
  "commands": [{ "name": "review", "description": "Review changes", "inputHint": "scope" }] }
```

1. 模型的含义与 `agent/list_models` 相同，空列表合法。
2. 每条命令有名称、描述和可缺省的输入提示，按 Agent 上报的内容和顺序转述，插件不增删、不与 Ora 的 Skill 合并。
3. 发现按需调用，Ora 不缓存结果到持久存储。一次发现失败只影响这一次请求，不使 Agent 变为不可用。

用一个方法而不是两个：模型和命令来自同一个探测，拆成两个方法就要在插件里共享探测结果，否则起两次进程。改名而不是在
`agent/list_models` 上加字段：方法名说的是模型，返回命令后名实不符，以后再增加会话前信息会更不准。不叫
`capabilities` 类名称，避免与 ACP `initialize` 的 `agentCapabilities` 混淆。

### D2：`None` 与空列表是两个事实

| 值 | 含义 | 何时产生 |
| --- | --- | --- |
| `None`（字段缺省或 `null`） | 插件没有提供，不知道 Agent 有哪些命令 | 旧插件、没有等到上报、平台冻结模型的路径 |
| `Some([])` | Agent 明确上报没有命令 | 探测收到的上报为空 |
| `Some([...])` | Agent 上报的列表 | 探测收到非空上报 |

插件没有等到上报时不得返回空列表。`None` 时 Desktop 的行为与没有本契约时相同，继续提示用户先对话一轮。把“不知道”
写成“没有”会让界面否认实际存在的命令。

### D3：探测等待第一条命令上报，但不让模型为命令付出失败

1. 探测使用独立的一次性进程和临时会话，不向 Ora 正在使用的连接注入请求。
2. 收到 `session/new` 响应后，等待属于该临时会话的第一条 `available_commands_update`，收到立即继续；在响应之前已经
   到达的上报同样算数。后续上报不再等待。
3. 等待有上限，并且不超过整个探测的剩余预算。到上限、进程退出或通道关闭时，模型照常返回，命令为 `None`。上限的
   数值见 Q1。
4. 读取命令之后才清理临时会话：Agent 声明支持 `session/delete` 时删除，最后无论如何结束进程。
5. 探测不带 MCP（空 `mcpServers`）。Agent 若把 MCP 提供的提示词也作为命令上报，会话上报的列表会比探测多出这些条目，
   这是已知差异，不是错误。
6. 平台冻结模型的路径不探测，返回冻结的模型，命令为 `None`。

上限只影响不上报命令的 Agent：它们的每次探测都会等满上限。不同步等待、也不改用现有连接，是因为在现有连接上开临时会话
会触发 Agent 的会话启动 hook，并可能在不支持删除的 Agent 历史里留下空会话。

### D4：过渡期同时支持新旧方法名，一次发现只调用一个

| Desktop | 插件 | 行为 |
| --- | --- | --- |
| 新 | 注册 `agent/discover` | 调用 `agent/discover`，不调用 `agent/list_models` |
| 新 | 只有 `agent/list_models` | 调用 `agent/list_models`，命令为 `None` |
| 新 | 两者都没有 | 契约不完整，Agent 不可用 |
| 旧 | 新 SDK 构建 | 调用 `agent/list_models`，只得到模型 |

1. 契约检查要求 `agent/discover` 与 `agent/list_models` 至少有一个，其余必需项不变。
2. 有 `agent/discover` 时，它失败不退回 `agent/list_models`：两者是同一次探测，重试只会再起一个进程。
3. SDK 只让插件作者实现一个 `discover()`，并注册两个方法；`agent/list_models` 只返回其中的模型，收到的输入没有
   Skill 信息。旧 Desktop 因此也会等待 D3 的上限，这是兼容期的代价。
4. 旧插件基本淘汰后删除 `agent/list_models`，判断标准见 Q4。删除是对插件契约的破坏性变更，届时以后续决策记录。

### D5：探测使用与会话相同的 Skill 输入

会话 setup 把 Skill 可读根作为额外可读目录交给 Agent，并可携带 Skill 目录供插件接原生机制。探测的 `session/new` 传与
会话 setup 同源、同值的 Skill 可读根，否则探测与会话的列表会不一致。额外可读目录仍只在 Agent 声明能力时发送，缺少能力
不使探测失败。值由 Desktop 在 `agent/discover` 的输入中给出，插件不自己推断。可选的 Skill 目录是否一并传递见 Q2。

Skill 输入依赖 Skill 会话清单决策的 host 扩展点与 setup 字段。两者落地前，`agent/discover` 的这部分输入为空。

### D6：Skill 变化必须使发现结果失效

Skill 安装、更新、卸载或改名后，下一次发现不得返回变化之前的结果。现在这一点靠 Effect 引起的 Agent 进程替换，以及插件
在处理 Effect 时清除自己的缓存，两条都随 Effect 退役消失，因此需要新的信号。

信号要同时作用于两处缓存：Desktop 界面短时间内不重复发现，插件也可能按 Workspace 复用最近的结果。只让其中一处失效，
仍会读到旧列表。失效不重启 Agent、不影响进行中的 turn，也不主动起探测，只让下一次展示时重新发现。具体做法见 Q3。

### D7：会话自己的上报优先，发现结果只用于会话之前

1. 会话已经收到 Agent 上报的命令（包括空列表）时只使用会话的列表；没有时才用发现结果。
2. 存在待执行的 Agent 切换时，使用将要切换到的 Agent 的发现结果。
3. 发现结果不写入会话历史，不随会话持久化，不改变会话何时连接 Agent。
4. Node 没有会话前的选择界面，不调用发现；它与 Desktop 共用契约检查，所以接受同样的插件。

发现结果能否用来提示“Agent 不支持某命令”见 Q6。

## 不变量

1. 一次发现最多启动一个 Agent 进程，最多调用 `agent/discover` 与 `agent/list_models` 中的一个。
2. 没有收到 Agent 上报时命令为 `None`，空列表只来自 Agent 的明确上报。
3. 命令没有到达不影响模型返回；发现失败不使 Agent 不可用。
4. 探测不使用 Ora 的共享连接，不带 MCP，结束后不留下进程。
5. 会话上报的命令始终优先于发现结果。
6. 发现不创建 Ora 会话、不写历史、不改变会话的生命周期状态。
7. 探测与会话使用同源、同值的 Skill 可读根。
8. Skill 变化之后的发现不返回变化之前的结果。
9. 兼容期内，新旧 Desktop 与新旧插件的任意组合都能列出模型。

## 待定

### Q1：等待上限取多少

需要在真实 Agent 上分别测冷启动、热启动和不上报命令的情况后确定。现有采样只有 3–12 毫秒的到达时间，单个 Agent、
样本很少，不足以定值。上限太小会让慢的 Agent 得到 `None`，太大会拖慢不上报命令的 Agent 的模型选择。

- **A**：契约给出统一数值，SDK 提供默认值。行为一致，可评审；代价是要兼顾最慢的 Agent。
- **B**：契约只规定“有上限且在探测预算内”，数值由各插件按实测决定。更贴合各 Agent；代价是行为不统一。

### Q2：除可读根外，是否传会话携带的 Skill 目录

- **A 传**：探测能反映插件接入原生机制后的 Skill 命令，与会话列表一致。代价是输入随 Skill 变化，插件缓存要以它为键。
- **B 只传可读根**：输入稳定。代价是接了原生机制的 Agent，其 Skill 命令在探测里可能缺失。

### Q3：用什么信号让发现结果失效

- **A 输入即缓存键**：Skill 变化时 Desktop 让界面上全部 Agent 的发现结果失效；插件以完整的发现输入为缓存键。没有新方法。
  代价是依赖 Q2 选 A；路径不变的改动（例如只改描述）不会改变输入，选它就要把 D6 与不变量 8 收窄到路径变化。
- **B 输入带不透明修订号**：Desktop 在输入里带 Skill 清单的修订号，任何变化都改变它，界面与插件都以它为键。不依赖 Q2，
  覆盖路径不变的改动。代价是多一个字段，且无关 Agent 的缓存也会失效。
- **C 宿主通知插件清缓存**：新增一个通知。语义直接；代价是新旧插件要协商是否支持，还要处理通知与进行中探测的先后。
- **D 插件不缓存**：缓存只留在 Desktop。失效点只有一个；代价是改变“发现和缓存归插件”的现有约定，并发请求的合并要移到
  Desktop。

### Q4：何时可以删除 `agent/list_models`

- **A 按插件**：官方来源的 Agent 插件全部发布支持 `agent/discover` 的版本，并经过一个 Desktop 稳定版本之后。
- **B 按版本**：约定 Desktop 的某个版本删除，提前公布。
- 无论哪种，第三方来源的旧插件在删除后会变为不可用，需要明确的错误提示。

### Q5：命令为 `None` 的结果是否缓存

- **A 与其他结果一样缓存**：简单；代价是一次偶然的慢启动会让命令在缓存期内都缺失。
- **B 模型照常缓存，命令为 `None` 时下次重新探测**：能自愈；代价是不上报命令的 Agent 每次展示都会再起一个进程。
- **C 只对旧插件和冻结路径缓存 `None`，等待超时的不缓存**：折中；代价是插件要区分两种 `None`，契约不暴露这一区别。

### Q6：发现结果能否用于提示“Agent 不支持该命令”

- **A 只有会话上报的列表可以**：不会因探测不带 MCP 而误报；代价是首次发消息前不提示。
- **B 发现结果也可以**：首次发消息前就能提示拼写错误；代价是 MCP 提供的命令会被误报。

## 为什么不是这些替代方案

| 方案 | 优势 | 否决理由 |
| --- | --- | --- |
| 扩展 `agent/list_models` 的结果 | 改动最小，不需要兼容两个方法名 | 方法名与内容不符，后续增加会话前信息时更不准 |
| 新增独立的 `agent/list_commands` | 名字清楚 | 与模型同源，插件要共享探测结果，否则起两次进程（不变量 1） |
| Desktop 在现有连接上开临时 `session/new` | 只改 Desktop，覆盖全部插件，更快 | 违背发现归插件；可能触发会话启动 hook，并在 Agent 历史里留空会话 |
| 打开会话就连接 Agent | 能拿到与会话完全一致的列表 | 会话变为运行中而挡住删除，忽略连接前选的模型，并启动 MCP |
| 持久化上次会话上报的列表 | 立即可用，不起进程 | 会过期，需要新的持久化模型；从未对话过的 Workspace 仍然没有 |
| 没有上报时返回空列表 | 类型更简单 | 把“不知道”写成“没有”（不变量 2） |
| 直接替换，不保留旧方法名 | 没有兼容代码 | 新 Desktop 配旧插件、旧 Desktop 配新插件都会被判为契约不完整，Agent 不可用 |
| 探测带 MCP，使列表与会话完全一致 | 没有已知差异 | 会话前就启动 MCP 进程并暴露凭据，只为展示列表不值得 |

## 风险

- **首次展示变慢**：不上报命令的 Agent 每次探测都等满上限；由 Q1 的数值控制。
- **探测的副作用**：一次性会话可能触发 Agent 的会话启动 hook，或在不支持删除的 Agent 里留下空会话。这是现有探测已有的
  行为，本决策不增加探测次数，但 Q5 选 B 会增加。
- **旧 Desktop 与多出的方法**：兼容表假定旧 Desktop 接受插件注册多余的方法。目前没有发现拒绝的检查，实现时要用真实
  旧版本验证，不能只凭阅读代码。

## 本决策未解决的问题

- 会话前的推理强度等其他信息是否进入发现结果：取决于 Agent 是否在会话前提供，需要单独决策。
- 第三方插件契约版本的协商：本文用“注册了哪个方法”判断能力，没有引入版本号。
- Agent 插件的启动、停止和 ACP 通道契约：不在本文范围。

## 落地顺序

1. **本 ADR 评审**：确定待定项，标记 `approved`，补充核心用例：新旧组合、三种命令值、等待与超时、探测清理、会话优先、
   Skill 输入与失效。
2. **Desktop 支持 `agent/discover`**：协议、契约检查、调用与展示，以及 SDK 源码。完成条件是新 Desktop 配旧插件行为不变，
   配测试插件能展示命令。D5 的 Skill 输入在 Skill 会话清单的 host 扩展点与 setup 字段进入主干之后接入。
3. **SDK 与插件发版**：与 Effect 退役合到同一次 SDK 和插件发版，SDK 在本决策与 Effect 退役的 Desktop 改动都进入主干
   后发布。首先是
   CodeAgent 插件，完成条件是在真实 Agent 上首次发消息前能看到命令；Claude、OpenCode、Codex 插件随后各自跟进。
4. **实现后**：按最终实现同步本文，标记 `implemented`，登记核心用例证据。
5. **删除旧方法名**：按 Q4 的标准，以后续决策记录。

第 2 步之后没有更新的插件行为不变；从第 3 步开始，更新了的插件在首次发消息前提供命令。
