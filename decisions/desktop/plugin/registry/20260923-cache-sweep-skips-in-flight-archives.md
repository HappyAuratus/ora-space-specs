# 插件分发：缓存清扫跳过其他安装已声明的归档

marketplace 安装仍然在真正开始传输前清扫 `plugins/cache/` 里的崩溃残留，但清扫不再删除另一路
安装已经声明的 `.orax`，并且“版本已安装”的拒绝发生在清扫之前。结果是：并发安装两个不同插件时，
后开始的那次不会把先下载完、尚未解包的归档删掉；进程崩溃留下的、当前没有安装在用的 `.orax`
仍会被下一次真正的传输清掉。

本 ADR 为 `implemented`，代码已随同一变更落地。只涉及 `ora-plugin-manager` 的缓存所有权。不改变
包内清单校验、错误契约、缓存路径布局，也不引入跨安装的下载互斥锁。

## 继承与修改

本决策直接继承
[安装期包内清单校验决策](20260922-install-time-package-validation.md)。

| 前序约定 | 本决策 |
| --- | --- |
| 包内清单校验、身份一致性、staging 提交、错误契约 | 继承，不变 |
| 缓存路径为 `<cache>/<namespace>/<name>-<version>.orax` | 继承，不变 |
| 成功与失败都删除本次下载的 `.orax`；清理只匹配 `*.orax` | 继承，不变 |
| 每次安装开始删除缓存中的全部 `*.orax` | 修改：只删除当前没有被本进程其他安装声明的 `.orax` |
| `AlreadyInstalled` 在下载之前 | 修改：同时在清扫之前。已安装拒绝不触碰缓存 |

## 决策

### D1：传输开始前声明本次归档路径，清扫跳过已声明路径

一次将会下载的安装，先把本次归档路径记入本进程的声明表，再删除缓存中其余 `*.orax`。声明在本次
安装删除自己的归档之后才释放。另一路安装的清扫因此看不到、也不会删除这份归档。

声明表放在进程内存里，而不是放在某个 `Installer` 实例上：生产代码每次调用都新建 installer，
实例锁盖不住两次并发安装。声明按归档的绝对路径计数。同一路径被两次安装同时声明时，要等两次都
结束，路径才重新可以被清扫；用集合的话，先结束的那次会把后一次的归档暴露给第三次安装。

进程崩溃会连同声明一起消失。残留文件重新变成“没有人声明的 `.orax`”，下一次真正开始传输的安装
会清扫它。这保留了前序决策里“崩溃残留有回收者”的承诺，回收者仍是安装本身，而不是新的 GC 任务。

### D2：已安装拒绝不触发清扫

`AlreadyInstalled` 在声明和清扫之前返回。这次调用不会下载，也不删除任何缓存文件。

前序决策把已安装检查提前，是为了避免白下载。检查若仍排在清扫之后，一次必然失败的重复安装会删掉
其他插件正在解包的归档，清扫的竞态窗口就被扩大到“任何安装请求”，包括那些根本不会传输的请求。

### D3：不把全部安装串行化

不同插件的下载和解包继续并发。同一归档路径上的两个写入者仍然共享那一个文件：路径就是这份传输的
身份，后写入的字节可能覆盖先写入的字节。本决策只保证清扫不会删掉别人的归档，不把同一路径的两次
传输变成互斥的。

## 为什么不是这些替代方案

| 替代方案 | 否决理由 |
| --- | --- |
| 维持“删除全部 `*.orax`”，接受并发安装失败后由用户重试 | 失败由一次无关安装引起，窗口是整段解包，大插件可以到数秒；已安装拒绝还会在不下载的情况下触发它 |
| 清扫只删除本次路径和旧扁平布局的同名文件 | 其他插件的崩溃残留没有回收者，除非用户再次安装那个插件；前序决策要求下一次传输清扫全部未使用残留 |
| 用一把安装互斥锁包住下载和解包 | 能消除竞态，但会把数百 MB 的下载串行化。需要互斥的只是删除，不是传输 |
| 把声明持久化到磁盘 | 崩溃后声明还在，残留就永远不会被清扫，和“崩溃残留由下一次传输回收”矛盾 |

## 不变量

1. 一个安装已经声明的归档路径，不会被本进程里另一次安装的清扫删除。
2. 没有安装在本进程中声明的 `*.orax`，会被下一次真正开始的传输清扫；`registry_index.json` 与
   `<destination>.tmp` 不在清扫范围内。
3. 对已提交版本的安装拒绝发生在清扫之前，不删除任何缓存文件。
4. 一次安装在自己的成功或失败路径上仍删除自己下载的 `.orax`。

## 落地顺序

1. 缓存声明与清扫顺序（D1、D2）。完成条件：并发的两次不同插件安装都能提交；已安装拒绝留下其他归档。
2. 文档与证据：本 ADR、核心用例与 `ora-plugin-manager` README 同步。

包内清单校验、错误码、缓存路径形状和单次安装的失败零残留保持不变。
