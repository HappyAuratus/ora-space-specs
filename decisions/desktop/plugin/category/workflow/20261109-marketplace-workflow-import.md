# Workflow 市场导入、依赖报告与卸载保留及来源提示

市场首次安装、升级及 pack 成员安装都导入包内工作流文档；已处理的来源路径持久跳过，保护用户编辑、
改名和删除的选择。已安装的 workflow 插件卡片提供「重试导入失败的文档」动作，升级也重试尚无终态
来源记录的路径。插件安装结局与逐文档导入结局分别呈现；市场安装、升级与重试在导入或失败时弹出逐
工作流依赖报告，卸载被工作流引用的 MCP / Skill 插件时列出依赖工作流并只警告不阻止，卸载 workflow
插件时保留已导入副本、在卸载确认中列出这些工作流，并在工作流库和创建运行菜单标出「来源插件已卸载」。

本决策为 `implemented`。Desktop 已支持从市场导入、报告依赖并提示卸载影响。卸载后的来源提示与
保留列表随 [desktop#792](https://github.com/ora-space/desktop/pull/792) 合入。前序 [Workflow 插件类别根决策](0-workflow-package-format.md)
保留 `implemented`，其包格式和本地导入仍是它自己的承诺。本决策只改变 desktop 的市场导入、安装/卸载
呈现与来源信息标记语义，不改变 Cloud 的取包、结果与运行契约，也不承担启动时全量回填旧安装的义务：
旧安装在首次升级时按 D2 补导入，无市场来源记录的历史工作流不按名称推断或回填来源。

## 继承与修改

| 前序约定 | 本文处理 |
| --- | --- |

| 根决策 D4：逐文档独立，一份文档创建工作流与首个已发布快照；图校验、发布版本派生、原文保存 | 继承，不变；新增市场来源记录与副本一致提交的要求（D3） |
| 根决策 D4：同名冲突使该文档失败 | **修改**：本地导入仍失败；市场导入持久记为「因同名冲突跳过」，只报告一次（D2） |
| 根决策 D5：只有本地 `.orax` 导入读取文档，市场安装与升级不读取 | **修改**：市场安装、升级、pack 成员安装读取并导入；升级只增不改，并提供显式重试入口（D1–D3） |
| 根决策 D5：副本是用户数据，卸载不移除、不改写；安装与导入结局分离 | 继承，不变（不变量 1 不动）；并将 D4 扩展到市场依赖报告、被引用插件卸载警告，以及 workflow 插件卸载保留提示与「来源插件已卸载」信息标记（D2、D4） |

## 决策

### D1：市场安装、升级和 pack 成员安装逐文档导入

成功安装的 workflow 插件读取包内 `assets/workflows/*.json`，按根决策的文档集合、校验与发布规则
逐文档导入。pack 按 `InstallOutcome::PackInstalled.members` 的成员各自身份与安装结局处理，
来源属于成员插件，不能用 pack 身份替代。未成功安装的成员不创建副本。

升级只处理没有终态来源记录的路径，包含新版本新增的文档和此前因其他原因失败的文档。已处理路径
即使内容改变也跳过；用户副本不会随包升级被覆盖或自动改名。一份文档失败不阻断其余文档，不撤销
成功安装，也不回滚其他成功文档或成员。

安装即导入让用户装完即可使用有效文档；将文档失败与安装失败分开，避免坏文档让有效包和其他文档
一起消失。发现阶段继续只枚举文档树，不把解析加入所有插件共用的发现路径。

### D2：终态来源记录跨版本、卸载重装和用户删除保留

自动导入的持久判定键为 `(source_namespace, identifier, document_path)`：前两项是完整 canonical
Plugin ID，`document_path` 是包内路径 `assets/workflows/<文件名>.json`。包版本、内容散列、文档
标题和副本当前名称不参与判定；不同来源的同名插件不共享记录。

| 来源记录 | 自动导入及显式重试行为 |
| --- | --- |
| 无记录，导入成功 | 创建工作流与首个已发布快照，并记录「已导入」 |
| 无记录，与已有工作流同名 | 保留已有工作流，记录「因同名冲突跳过」，报告一次冲突，不改名、不覆盖 |
| 已导入或因同名冲突跳过 | 跳过该路径，不再创建副本，也不重复报告名称冲突失败 |
| 无记录，其他原因失败 | 返回逐文档失败，不写终态来源记录，允许后续重试 |

「已导入」和「因同名冲突跳过」均为终态来源记录，跨升级、卸载重装和用户删除工作流保留，不随副本
删除级联清除。因此用户删除副本或冲突对象后，该路径仍不自动恢复或重新导入，显式重试也不会重置
该选择。来源记录不是副本所有权，不能限制用户编辑、改名、归档或删除。

旧安装没有来源记录时，在首次升级补导入无冲突文档。历史本地导入和用户自建的同名工作流都保留，
来源记为冲突跳过并只报告一次；不能仅凭名称推断它来自该包或补记为「已导入」。仅改来源判定键或
按名称回填成功会误认历史数据，因此不作这类迁移。

跨版本只增不改与 [Cloud 资产规则](../../../../cloud/plugin-marketplace/20261016-workflow-plugin-assets.md)
对齐；desktop 明确同名冲突持久跳过、只报告一次，不改变 Cloud 自己的结果规则。

### D3：已安装卡片显式重试，创建与来源记录保持一致

已安装的 workflow 插件卡片提供「重试导入失败的文档」动作，对该已安装插件的包内文档重新执行
导入判定，只处理没有终态来源记录的路径。pack 的 workflow 成员同样可从成员插件卡片触发；不要求
先卸载或获得新版本才能重试。升级时也顺带处理这些无终态记录的路径。

显式动作与升级使用同一套来源判定：已成功与冲突跳过项不再导入，其他失败在条件修复后可以重新
尝试；没有终态记录的路径也可能尚未尝试，不以先存在一条失败记录作为重试资格。

工作流、首个已发布快照与成功来源记录应原子提交，或提供等价一致性保障。失败或中断不能留下「副本
已经创建、没有来源记录，重试又创建一次」或「来源记录已成功、实际没有副本」的状态；发布失败也
不能留下妨碍重试的同名半成品。用户之后主动删除副本不属于提交不一致。

该入口处理暂时失败，不用于重新导入已成功或冲突跳过的路径。**本地 `.orax` 导入行为不变**：沿用
显式逐文档导入及同名失败，不受市场来源记录抑制，也不借该路径改写市场来源终态。

### D4：安装结果、依赖影响与卸载来源提示分别呈现

#### 安装、升级与重试的逐文档结果及依赖报告

`InstallPluginResponse` 与 `UpdatePluginResponse` 都回传逐文档结果，能区分成功、已处理路径
跳过、首次同名冲突跳过及其他失败，并定位成员插件与文档路径。前端安装和升级成功提示附导入摘要，
不能将插件安装成功表述为全部文档导入成功。

显式重试也返回并展示逐文档结果与摘要，使用相同的成功、跳过与失败语义；重试不是重新安装，不能
把文档失败伪装为插件安装失败，也不能仅在日志中保留失败信息。

市场安装与升级、Pack 安装及卡片显式重试的响应只要包含「已导入」或「失败」文档，前端
即弹出逐工作流的依赖报告弹窗，与本地 `.orax` 导入共用同一套依赖判定规则（`collectWorkflowDependencies`）
和报告组件：展示每个导入工作流的 MCP / Skill 就绪状态、引用的节点标题，以及「去安装 / 去配置 /
去查看」处理入口；所选入口在已打开的设置中立即进入市场搜索、配置编辑器、按插件 ID 筛选的已安装插件管理器或 Skills 设置，报告随之关闭。`agentConfig`
为 `null` 时视为未绑定任何插件，不抛出异常。当响应全部为已处理或冲突跳过时，保持一行摘要提示，
不弹出报告弹窗。

#### 卸载被工作流引用的 MCP / Skill 插件

卸载插件前，所有卸载确认入口（已安装插件管理器、插件详情页、Skills 设置页中的插件 Skill 删除，
以及 Pack 卸载确认）同时检查所有工作流的草稿图与已发布快照，列出引用了待卸载 MCP 或 Skill 插件
的工作流及节点标题并警告「卸载后这些工作流会缺依赖，运行到引用该插件的节点时会失败」。
本次已落地警告的身份边界是：MCP 按插件 ID 匹配；Skill 按 Skills 目录里归属待卸载插件的条目 `name` 与工作流
引用值精确、区分大小写匹配。该规则不采用运行时的前缀、大小写不敏感与本地优先匹配，因此可能漏报
真实依赖或误报；Agent 插件不在本次检查范围内。

该提示**只警告、不阻止**用户完成卸载：检查或缓存后台刷新期间禁用确认按钮，避免用户在影响未
算清前确认；检查完成后无论是否发现依赖工作流，用户都可选择继续卸载或取消。若个别工作流的图无法
读取或目录查询失败，必须显式提示部分或全部检查无法确认，不能把未知当作无依赖，也不因此永久阻断
卸载。待卸载插件没有可被工作流引用的 MCP / Skill 目标时，跳过逐工作流 `workflow.get` 扫描；此时
无需为确定无目标而读取每份图。

#### 卸载 workflow 插件的保留提示与「来源插件已卸载」标记

卸载 `kind = "workflow"` 的插件（包括 Pack 卸载计划中的 `remove` 成员；Pack 的 `preserve`
成员不会被卸载，不触发提示）时，卸载确认弹窗列出该插件此前导入过且当前仍存在（未删除）的工作流，
并明确说明卸载后这些工作流会保留在库中，仍可继续编辑和运行；列表加载检查期间同样禁用确认按钮。
若工作流库或来源记录读取失败，必须明确提示保留列表无法完整确认；检查结束后确认按钮保持可用，
不能把「读不到」当成「没有」，也不得因此永久阻止卸载。

后端在 `WorkflowSummary.sourcePluginId` 返回成功市场导入记录的规范插件 ID（`<namespace>/<identifier>`），无此记录时为空。工作流库和
工作区创建运行菜单消费同一份摘要，不由各前端使用方分别按名称或已安装目录 join 来源。「来源插件
已卸载」不是卸载时写入的一次性事件或持久标志，而是由成功导入记录与统一已安装插件目录共同派生的
状态：来源存在且对应 canonical Plugin ID 当前未安装时，两个入口在这些工作流旁展示信息性标记
「来源插件已卸载」。因此功能上线前已经卸载的来源插件也按同一规则显示，无需补写历史标志：

- **仅为信息，不限制操作**：标记不禁用编辑、重命名、导出、删除或创建运行，也不参与工作流运行前
  或画布上的缺依赖判定（workflow 插件无进程，工作流能否运行取决于其引用的 MCP / Skill，而非来源
  插件是否在装）。
- **重装同 ID 后自动消失**：重装同一个 canonical Plugin ID（`<namespace>/<identifier>`）后，
  来源插件重新处于已安装状态，「来源插件已卸载」标记随之消失；按 D2，终态来源记录仍然保留，
  不会重新导入文档，也不会产生重复副本。不同 `namespace` 下的同名 `identifier` 视为不同插件，
  不消除原标记。
- **不新增表，不反推历史**：副本到来源插件的映射直接从既有 `workflow_document_imports` 表的
  `state = 'imported'` 记录（以 `workflow_id` 关联）推出，不新增持久表，也不把插件身份写入
  `workflows.namespace`（仍恒为 `local`）。副本改名后关联保持不变；用户删除副本后，卸载确认不
  再列出该副本。历史无来源记录的旧安装、冲突跳过记录与本地 `.orax` 导入不带市场来源记录，不按
  名称反推来源。已安装插件目录处于加载中或读取失败时，不把有来源的工作流误标为「来源插件已卸载」。
  通过本地 `.orax` 安装 workflow 插件按 D3 不产生 `workflow_document_imports` 记录，因此卸载确认
  不列这些副本、后续也不打来源标记，但副本仍按不变量 1 保留；这是只从导入记录推出、不按名称反推
  的直接结果。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 只有显式导入按钮，或只提示用户另行导入 | 改动较小，但市场安装后工作流库仍可能为空，不能兑现安装即用；显式动作仅用于补充重试 |
| 市场安装与升级直接复用本地导入、不记录来源 | 同路径每次升级都再次尝试，同名冲突反复报错；用户改名后还可能多出副本 |
| 把包版本加入跳过键，或用工作流名称推断来源 | 版本变化会重新导入旧路径，名称无法区分历史本地导入、用户自建与市场来源 |
| 每次升级覆盖或自动改名 | 覆盖丢失用户编辑，改名产生重复副本；都破坏用户数据独立于包的承诺 |
| 将其他失败也记为终态，或仅在下次升级时允许重试 | 前者永久丢失可恢复文档，后者让已安装用户必须等新版本；卡片动作允许独立重试 |
| 卸载 workflow 插件时维持现状、不做任何提示 | 用户看不出工作流来自已卸载的插件，来源状态不透明 |
| 工作流库与创建运行菜单各自在前端 join 导入记录和已安装目录 | 同一来源投影会在多个使用方漂移，并让摘要消费者重复承担持久记录与目录匹配；由后端摘要统一提供来源 ID，两个入口共享同一语义 |
| 按 #1268 原始诉求将来源已卸载副本标为不可用、禁止运行 | 来源 workflow 插件无进程，副本能否运行取决于图内 MCP / Skill；禁止运行会把信息性来源状态误作执行依赖，并违背副本是独立用户数据的承诺 |
| 卸载 workflow 插件时勾选一并删除工作流 | 使卸载变成跨插件与工作流的复合操作，需处理部分失败与运行中/已修改副本，且误删用户数据不可恢复；按 #1286 先落地 B，确有需要时在 B 落地后单独评估 C，不在本次引入 |
| 卸载 workflow 插件时自动删除用户未改过的副本 | 「未改过」判定复杂易错，且推翻根决策 D6「副本是用户数据」的前提 |
| 卸载被工作流引用的 MCP / Skill 插件时硬阻止 | 依赖工作流可能已不再需要或用户正要替换插件，硬阻止会锁死卸载路径；改为只警告、不阻止 |

## 不变量

1. 副本是用户数据；升级、卸载和重试不删除、不覆盖、不改名已有副本。
2. 来源键跨版本稳定，已导入与冲突跳过记录跨卸载重装和用户删除保留。
3. 自动导入与显式重试只处理没有终态来源记录的路径；同名冲突只报告一次，其他失败可重试。
4. 成功副本、首个已发布快照与来源记录一致提交；失败和中断恢复不重复创建副本。
5. 逐文档结果彼此独立，插件安装结局与文档结局分别可见。
6. 本地导入、包格式、发现阶段职责及 Cloud 的既有规则保持不变。
7. 卸载被工作流引用的 MCP / Skill 插件只警告、不阻止；卸载 workflow 插件仅做保留提示与信息性
   「来源插件已卸载」标记，不删除、不禁用副本，重装同一 canonical Plugin ID 后标记消失。

## 落地与验收

市场文档导入、逐项重试、依赖报告和卸载警告均已在 Desktop 落地。工作流摘要、卸载时的保留列表、
工作流库和创建运行菜单的来源标记已在 [desktop#792 的合并提交](https://github.com/ora-space/desktop/commit/6824ff903cb9025f248b6e41473caa25a06819ff) 中验证。
[核心用例](../../../../../test-cases/desktop/plugin/category/workflow/workflow-package-and-import.md) 分列 SQLite、后端生命周期与界面交互证据，并标明缺少直接验证的边界。

## 本决策未解决的问题

- 编辑器自己的导出与目录导入协议不属于 workflow 插件语义，本文不统一两者的失败与命名规则。
- Cloud 来源存储和对账展示由 Cloud 决策拥有，本文不统一两端的数据结构或接口。
- pack 自身是否携带 workflow 文档和成员选择由 pack 领域决策拥有；成功安装的 workflow 成员遵循本文。
- 卸载警告与运行时一致的依赖匹配（前缀、大小写不敏感、本地优先）以及 Agent 插件检查归 #988；
  本决策只固定当前 MCP / Skill 警告边界，不把已知差异当作完整依赖证明。
