# Workflow 市场安装即导入、升级按来源路径只增不改

市场首次安装、升级及 pack 成员安装都导入包内工作流文档；已处理的来源路径持久跳过，保护用户编辑、
改名和删除的选择。已安装的 workflow 插件卡片提供「重试导入失败的文档」动作，升级也重试尚无终态
来源记录的路径。插件安装结局与逐文档导入结局分别呈现。

本决策为 `approved`，上述市场行为尚待实现与直接验证；前序
[Workflow 插件类别根决策](0-workflow-package-format.md)保留 `implemented`，其包格式和本地导入
仍是已实现的承诺。本决策只改变 desktop 的市场导入语义，不改变 Cloud 的取包、结果与运行契约，
不承担启动时全量回填旧安装的义务。旧安装在首次升级时按 D2 补导入。

## 继承与修改

| 前序约定 | 本文处理 |

## 决策

### D1：市场安装、升级和 pack 成员安装逐文档导入

成功安装的 workflow 插件读取包内 `assets/workflows/*.json`，按根决策的文档集合、校验与发布规则
逐文档导入。pack 按 `InstallOutcome::PackInstalled.members` 的成员各自身份与安装结局处理，
来源属于成员插件，不能用 pack 身份替代。未成功安装的成员不创建副本。

升级只处理没有终态来源记录的路径，包含新版本新增的文档和此前因其他原因失败的文档。已处理路径
即使内容改变也跳过；用户副本不会随包升级被覆盖或自动改名。一份文档失败不阻断其余文档，不撤销
成功安装，也不回滚其他成功文档或成员。

安装即导入让用户装完即可使用有效文档；将文档失败与安装失败分开，避免坏文档让有效包和其他文档
一起消失。发现阶段继续只枚举文档树，不把解析加入所有插件共用的发现路径。

### D2：终态来源记录跨版本、卸载重装和用户删除保留

自动导入的持久判定键为 `(source_namespace, identifier, document_path)`：前两项是完整 canonical
Plugin ID，`document_path` 是包内路径 `assets/workflows/<文件名>.json`。包版本、内容散列、文档
标题和副本当前名称不参与判定；不同来源的同名插件不共享记录。

| 来源记录 | 自动导入及显式重试行为 |
| --- | --- |
| 无记录，导入成功 | 创建工作流与首个已发布快照，并记录「已导入」 |
| 无记录，与已有工作流同名 | 保留已有工作流，记录「因同名冲突跳过」，报告一次冲突，不改名、不覆盖 |
| 已导入或因同名冲突跳过 | 跳过该路径，不再创建副本，也不重复报告名称冲突失败 |
| 无记录，其他原因失败 | 返回逐文档失败，不写终态来源记录，允许后续重试 |

「已导入」和「因同名冲突跳过」均为终态来源记录，跨升级、卸载重装和用户删除工作流保留，不随副本
删除级联清除。因此用户删除副本或冲突对象后，该路径仍不自动恢复或重新导入，显式重试也不会重置
该选择。来源记录不是副本所有权，不能限制用户编辑、改名、归档或删除。

旧安装没有来源记录时，在首次升级补导入无冲突文档。历史本地导入和用户自建的同名工作流都保留，
来源记为冲突跳过并只报告一次；不能仅凭名称推断它来自该包或补记为「已导入」。仅改来源判定键或
按名称回填成功会误认历史数据，因此不作这类迁移。

跨版本只增不改与 [Cloud 资产规则](../../../../cloud/plugin-marketplace/20261016-workflow-plugin-assets.md)
对齐；desktop 明确同名冲突持久跳过、只报告一次，不改变 Cloud 自己的结果规则。

### D3：已安装卡片显式重试，创建与来源记录保持一致

已安装的 workflow 插件卡片提供「重试导入失败的文档」动作，对该已安装插件的包内文档重新执行
导入判定，只处理没有终态来源记录的路径。pack 的 workflow 成员同样可从成员插件卡片触发；不要求
先卸载或获得新版本才能重试。升级时也顺带处理这些无终态记录的路径。

显式动作与升级使用同一套来源判定：已成功与冲突跳过项不再导入，其他失败在条件修复后可以重新
尝试；没有终态记录的路径也可能尚未尝试，不以先存在一条失败记录作为重试资格。

工作流、首个已发布快照与成功来源记录应原子提交，或提供等价一致性保障。失败或中断不能留下「副本
已经创建、没有来源记录，重试又创建一次」或「来源记录已成功、实际没有副本」的状态；发布失败也
不能留下妨碍重试的同名半成品。用户之后主动删除副本不属于提交不一致。

该入口处理暂时失败，不用于重新导入已成功或冲突跳过的路径。**本地 `.orax` 导入行为不变**：沿用
显式逐文档导入及同名失败，不受市场来源记录抑制，也不借该路径改写市场来源终态。

### D4：安装结果与文档结果分别呈现

`InstallPluginResponse` 与 `UpdatePluginResponse` 都回传逐文档结果，能区分成功、已处理路径
跳过、首次同名冲突跳过及其他失败，并定位成员插件与文档路径。前端安装和升级成功提示附导入摘要，
不能将插件安装成功表述为全部文档导入成功。

显式重试也返回并展示逐文档结果与摘要，使用相同的成功、跳过与失败语义；重试不是重新安装，不能
把文档失败伪装为插件安装失败，也不能仅在日志中保留失败信息。

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 只有显式导入按钮，或只提示用户另行导入 | 改动较小，但市场安装后工作流库仍可能为空，不能兑现安装即用；显式动作仅用于补充重试 |
| 市场安装与升级直接复用本地导入、不记录来源 | 同路径每次升级都再次尝试，同名冲突反复报错；用户改名后还可能多出副本 |
| 把包版本加入跳过键，或用工作流名称推断来源 | 版本变化会重新导入旧路径，名称无法区分历史本地导入、用户自建与市场来源 |
| 每次升级覆盖或自动改名 | 覆盖丢失用户编辑，改名产生重复副本；都破坏用户数据独立于包的承诺 |
| 将其他失败也记为终态，或仅在下次升级时允许重试 | 前者永久丢失可恢复文档，后者让已安装用户必须等新版本；卡片动作允许独立重试 |

## 不变量

1. 副本是用户数据；升级、卸载和重试不删除、不覆盖、不改名已有副本。
2. 来源键跨版本稳定，已导入与冲突跳过记录跨卸载重装和用户删除保留。
3. 自动导入与显式重试只处理没有终态来源记录的路径；同名冲突只报告一次，其他失败可重试。
4. 成功副本、首个已发布快照与来源记录一致提交；失败和中断恢复不重复创建副本。
5. 逐文档结果彼此独立，插件安装结局与文档结局分别可见。
6. 本地导入、包格式、发现阶段职责及 Cloud 的既有规则保持不变。

## 落地与验收

先确认来源状态与触发语义，再实现市场导入、卡片重试入口及响应展示；实现通过直接验证后将本决策
更新为 `implemented`，根决策保留原状态。核心验证义务见
[Workflow 插件包与文档导入](../../../../../test-cases/desktop/plugin/category/workflow/workflow-package-and-import.md)。
旧安装升级、冲突一次性提示、跨生命周期保留、卡片重试与升级重试、提交边界故障恢复需要分别证明，
不能用本地导入测试替代市场路径的证据。

## 本决策未解决的问题

- 编辑器自己的导出与目录导入协议不属于 workflow 插件语义，本文不统一两者的失败与命名规则。
- Cloud 来源存储和对账展示由 Cloud 决策拥有，本文不统一两端的数据结构或接口。
- pack 自身是否携带 workflow 文档和成员选择由 pack 领域决策拥有；成功安装的 workflow 成员遵循本文。
