# 市场工作流冲突可重试，成功重装可恢复已删除的副本

Desktop 的市场工作流遇到同名冲突时，安装和卡片重试会报告冲突的文档、工作流名称和恢复方法。后来改名或删除同名工作流，卡片重试、升级和重装都能重新尝试导入。成功重装还可以重新导入已删除的副本，同时保留存活副本及其来源。

本文为 `approved`：2026-11-24 经 owner 批准，尚未实现，作为 Desktop 实现的验收依据；核心用例见[Workflow 插件包与文档导入](../../../../../test-cases/desktop/plugin/category/workflow/workflow-package-and-import.md)。范围包括 Desktop 市场安装、升级、卡片重试及报告，也适用于 Pack 的 Workflow 成员。本地 `.orax` 导入沿用[根决策](0-workflow-package-format.md)，Cloud 沿用自己的[资产导入规则](../../../../cloud/plugin-marketplace/20261016-workflow-plugin-assets.md)。现有 Desktop 来源记录直接适用新规则，无需启动时全量回填或按名称推断来源。

## 决策

### D1 按安装周期与当前同名状态判定导入

**安装周期**从某个 canonical Plugin ID 的市场 `install` 成功开始，到该插件实际卸载时结束。已安装的插件调用 `install` 会返回 `AlreadyInstalled`，升级和卡片重试也继续使用当前周期。对 Pack，只有 `InstallOutcome::PackInstalled.members` 中本次实际安装成功的 Workflow 成员进入新周期，已经在装、安装失败或未安装的成员不受影响。

- **来源键**由 [canonical Plugin ID](../../../../../domain/glossary.md#canonical-plugin-id) 和包内文档路径构成。
- **存活副本**是 `workflows` 中存在 `id = workflow_id` 且 `is_deleted = 0` 的关联副本。行不存在或已软删除时，按副本已删除处理。
- **同名**按本地工作流库现有的 SQLite `COLLATE NOCASE` 规则，比较文档声明名与存活工作流的当前名称。
- **已知冲突**指本次操作读到的前状态为 `conflict_skipped`，且本次仍因同名跳过。结果里的已知冲突标记只按前状态计算、与操作类型（安装、升级、卡片重试）无关；是否打开报告弹窗由操作类型决定。当前阻挡导入的同名存活工作流可以不同于原先的冲突对象。

| 当前来源记录 | 市场安装成功（含重装） | 升级 | 已安装卡片重试 |
| --- | --- | --- | --- |
| 无记录 | 尝试导入。成功记为 `imported`，同名时返回 `SkippedConflict` 并记录 `conflict_skipped`。 | 同左。 | 同左。 |
| `conflict_skipped` | 重新检查当前库。冲突消除后尝试导入；仍冲突时保留记录并返回标明已知冲突的 `SkippedConflict`（按前状态标记）。 | 同左；已知冲突自身不触发弹窗（见 D3）。 | 重新检查并报告，规则同安装。 |
| `imported`，副本存活 | 返回 `SkippedProcessed`，即使副本已改名。 | 同左。 | 同左。 |
| `imported`，副本已删除 | 按未交付路径重新尝试。成功时与新副本同事务改写为新的 `imported`；遇同名时记录本周期的 `conflict_skipped`（可从卡片恢复）；遇非同名失败时，在同一次操作里以读到的前状态为条件删除该 `imported` 记录使其回到「无记录」（本周期内可经卡片重试或升级恢复）。 | 保留删除，结果与存活副本的 `SkippedProcessed` 可区分，不显示为「此前已处理」，并按 D3 计入中性摘要。 | 保留删除，结果同样与存活副本区分，提示「副本已删除，卸载后重装可恢复」。 |

旧版 `conflict_skipped` 直接参与重判，旧版 `imported` 读取当前副本是否存活。普通导入失败返回 `Failed`；当前状态为无记录或 `conflict_skipped` 时保留原状态，使其仍符合重试条件。重装恢复已删除副本时若遇到非同名失败，在同一次操作里以读到的前状态为条件删除该行已删除副本的 `imported` 记录，让文档回到「无记录」，之后的卡片重试和升级均按无记录处理（与冲突分支对称）；仅当该条件删除本身失败（例如失败本身来自数据库不可写）时，记录才保留为已删除副本的 `imported`，退回「修复失败原因后再次卸载重装」的兜底路径。

### D2 保留存活来源，恢复不依赖卸载清理

卸载保留用户的工作流和来源记录。重装时评估副本是否存活，涵盖先卸载再删除副本、0.6.0 上已经卸载的插件，以及卸载过程中没有修改来源记录的情况。已有存活副本时继续沿用原记录。同一 canonical Plugin ID 卸载或重装后，工作流库和创建运行菜单仍根据来源与已安装目录共同派生「来源插件已卸载」标记。

来源状态转换以读到的前状态为条件，包含关联副本及其存活状态；重装恢复遇非同名失败而清除旧 `imported` 记录时同样以该前状态为条件执行条件删除。创建副本时，来源改写与新工作流、草稿和首个已发布快照同事务提交。如果另一个操作先改写了来源，按最新状态重判，避免挂上第二份存活副本。名称检查后若另一个写入先占用同名，回滚创建，按 `SkippedConflict` 报告并保留或提交正确的冲突状态，不能把同名约束或已有来源记录误报为 `Failed`。

### D3 分别展示包状态、未交付文档和依赖

- 安装（含 Pack）和卡片重试只要返回 `SkippedConflict` 就打开报告弹窗。单列「未导入」分组，逐项展示 `source_file`、冲突的工作流名及恢复方法。Pack 条目同时显示成员身份，并指向该 canonical Plugin ID 的已安装卡片。引导用户改名或删除同名工作流，再从卡片选择「重试导入未导入的文档」。
- 自动升级遇到已知冲突（本次操作读到的前状态为 `conflict_skipped` 且仍同名）时，返回带工作流名且按前状态标明已知冲突的 `SkippedConflict`；摘要用中性的一行计数，例如「N 份仍因同名冲突未导入，可在插件卡片重试」，已知冲突自身不触发弹窗或错误样式。升级出现首次冲突时，按 D3 第一项打开报告弹窗，列入「未导入」分组。每当报告弹窗因 `Imported`、`Failed` 或首次冲突打开时，同批次中的已知冲突也列入「未导入」分组，标为「仍未解决」。
- 「未交付 → 非成功样式」只用于没有任何 `Imported` 且至少有一份本次操作新产生的 `Failed`、首次冲突，或安装/卡片重试中的冲突；标题和样式明确区分包操作完成与文档未导入。升级时，在装期间被用户删除的副本与已知冲突一并按中性处理：在结果里可与存活副本的 `SkippedProcessed` 区分，不显示为「此前已处理」，仅计入中性摘要（例如「N 份副本已删除，卸载后重装可恢复」），不改变成功样式；卡片重试时，已删除副本给出 D1 表格的提示（「副本已删除，卸载后重装可恢复」）。只有存活副本的 `SkippedProcessed` 或升级中性项时，仍保持普通成功提示。Pack 的成员摘要按同一规则判断。
- 「未导入」条目不参与 MCP / Skill 依赖判定。报告继续为本次成功导入的工作流展示依赖状态与处理入口，混合批次分别展示成功与未导入结果。

Desktop 与 Cloud 都允许用户解除冲突后再次导入。Cloud D4 将同名列为 `name_conflict`，每次遇到都报告失败，不持久化用于抑制重复报告的冲突状态。Desktop 保留 `conflict_skipped` 的用途是识别升级时仍存在的已知冲突，以简短摘要呈现。

## 为什么不是这些替代方案

| 方案 | 取舍 |
| --- | --- |
| 只调整恢复逻辑和摘要文案 | 界面改动较少，但摘要无法定位一批文档中的具体冲突，也无法把 Pack 的冲突指回各成员。 |
| 永久保留已删除副本的跳过资格 | 维持删除选择容易，但用户主动重装也无法取回副本。将恢复资格限于成功安装能区分这两种意图。 |
| 卸载时清理全部来源 | 清理逻辑简单，但会丢失存活副本的来源标记，重装可能给已改名的副本再建一份。 |
| 卸载时清理冲突和已删除副本的记录，以清理划定周期 | 安装判定较简单，但覆盖不了卸载后才删除的副本、已经卸载的旧版插件及卸载清理失败。生命周期操作与导入交错时也无法用一次清理可靠划界。 |
| Cloud 式不持久化用于识别重复冲突的状态 | 判定简单，但每次自动升级都会把同一条仍存在的冲突显示成一次新的失败。Desktop 的持久记录可以保留恢复入口，同时收敛重复提醒。 |

## 不变量

1. 同一来源键任一时刻至多关联一个存活副本，存活副本的来源经升级、改名和卸载重装仍可识别。
2. 任何一次导入都保留现有同名工作流。仍有同名时，已有 `conflict_skipped` 保持该状态，结果为 `SkippedConflict`，包括提交时发现的并发同名。
3. 升级和卡片重试继续尊重当前安装期间对已导入副本的删除。成功市场安装按当前存活状态决定是否重新尝试。
4. 来源转换和恢复失败清理均以读到的前状态为条件，新副本、初始快照和成功来源记录原子提交。
5. 包操作与逐文档结果分别可见。用户可以定位待处理的冲突并获得恢复入口。

## 本决策未解决的问题

直接覆盖同名工作流、为导入副本自动改名，以及对仍存活的副本提供手动覆盖或从来源刷新，都会改变用户对现有副本的控制边界。这些行为需要独立决策。当前的恢复入口是在工作流库解除同名冲突，再通过市场导入。
