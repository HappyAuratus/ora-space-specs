# Hook 插件：携带包内可执行工具，由宿主执行生命周期命令自行适配 Agent 配置

Hook 是一个携带**包内可执行文件**的独立 Plugin kind（`kind = "hook"`）。它不再声明需要由别的
组件解释的语义协议，也不再依赖 Agent Plugin 投递：包内的可执行工具自己知道支持哪些 Agent、
这些 Agent 的配置写在哪里、如何注册与撤销。宿主在安装、启用、更新与卸载时执行该工具声明的
生命周期命令（第一版为初始化与反初始化），并只负责授权、执行、记录结果与提示用户重启 Agent。

关键行为变化有三处。其一，适配知识从 Agent Plugin 移回 Hook 工具：宿主与 Agent Plugin 都不需要
理解某个 Hook 的语义，新增 Agent 或配置格式变化时，改动只发生在工具内。其二，不再有版本化协议与
能力矩阵：协议匹配、per-(Hook, Agent) 状态与投递回执整体消失，插件状态收敛为生命周期命令的
执行结果。其三，Hook 第一次有了真实执行面：宿主会以当前用户的权限执行包内程序，它**不在 Ora 的
插件沙箱内**，这必须在安装与启用时披露，而不是作为实现细节隐藏。

本文为 `implemented`：D1–D8 与不变量已按最终实现同步，描述的是当前系统承诺而非实现过程。清单
字段名、配置 shape 与命令参数形态以本文为准。涉及模块：`ora-plugin-config`（Hook 声明的编译与
校验）、`ora-plugin-manager`（包内可执行文件的存在性与 containment 校验）、`ora-plugin-lifecycle`
（Hook 不进入插件运行时的边界与权限表述）、`crates/backend`（生命周期命令的执行、结果记录与契约）、
`ora-contracts` 与 `packages/app-shell`（授权披露与结果呈现）。清单层（`ora-plugin-manifest`）与
分发层（`ora-plugin-registry`）不需要新字段。落地状态与仍然存在的证据缺口见文末。

本决策取代 hook 领域此前 `proposed`、未实现的投递模型提案（该提案正文已不保留），并且不再保留
按旧模型书写的 Hook 声明：带 `protocol` / `command` / `toolVersion` 的包被整包拒绝，错误指向被移除
的字段，作者据此重新打包（见「与既有实现的关系」）。`.orax` 归档布局、安装事务、`kind` 的封闭集合
与 `installed/<namespace>/<identifier>/<version>/` 目录布局均不变；本决策不新增任何持久化目录，
不把 Agent 配置文件纳入 Ora 的所有权，也不删除任何不属于 Ora 的用户文件与 Agent 配置内容。

## 术语与边界

- **Hook 插件**是 `orax.toml` 中 `kind = "hook"` 的 `.orax` 包；身份是完整 canonical Plugin ID
  `<namespace>/<identifier>`，按既有清单与 namespace 决策派生。
- **Hook 可执行文件**是 Hook 插件在其 `assets/` 下携带的原生程序，也是 Hook 的唯一载体。它由
  插件自己的声明指定，必须是当前 installed package 内的普通文件。
- **生命周期命令（lifecycle command）**是宿主执行该可执行文件的入口。第一版只有两个能力：
  `init`（注册 Hook，声明中必需）与 `deinit`（撤销 Hook，声明中可选）。命令只由可执行文件路径与
  固定参数组成，不经过 shell。
- **工具自述的 supported agents** 是插件的一项展示信息：它描述作者认为该工具支持哪些 Agent，
  供用户在 marketplace 与已安装列表中判断适用性。它不是兼容性协议，不参与任何宿主判定。
- **执行结果**是宿主对一次生命周期命令的记录：阶段、退出码、标准输出与标准错误。它证明命令被
  执行过，不证明 Agent 侧已经生效。第一版把结果保存在当前会话内并写入结构化日志，不作为跨重启
  的持久状态（见未解决问题）。
- Ora 的职责边界是授权、执行、记录与提示。宿主不解释工具语义、不读写 Agent 配置文件、不维护
  Agent 配置格式适配表，也不代理 Agent 的命令执行路径。
- Hook 插件如果有用户设置，沿用既有 `assets/config.json` 的 `settings` 声明与 host-owned
  Configuration Store；本决策不改变设置的存储与校验，也不规定实值如何进入命令执行环境。

## 继承与修改

本决策是 hook 领域的根决策。相邻规则仍由各自所有者定义，本文只固定 Hook 插件自身的系统承诺。

| 规则所有者 | 本决策 |
| --- | --- |
| [插件清单](../../manifest/0-versioned-dual-form-manifest.md) | 继承，不变：`kind` 封闭集合、`hook` 使用 target 形态、installed `[artifact].target` 必需、包内文件存在性由包发现而非清单判定 |
| [插件分发](../../registry/0-registry-distribution.md) | 继承，不变：`[[targets]]` 只允许 `hook` 与 `agent`，target 精确匹配、无隐式回退，选中资产校验 SHA-256 |
| [来源派生 Namespace](../../registry/20260831-source-derived-namespace.md) | 继承，不变：canonical Plugin ID 由宿主派生，清单不声明 namespace |
| [MCP 插件根决策](../mcp/0-static-mcp-configuration.md) | 继承 Settings 复用与 `assets/config.json` 的 shape 互斥；修改：`hook` shape 的成员由语义协议改为可执行文件与生命周期能力 |

此前 hook 领域 `proposed` 的投递模型提案被本决策取代，两者的差异如下。逐项都改变系统行为，不是
措辞调整；被取代的模型不保留为兼容层。

| 主题 | 被取代的投递模型 | 本决策 |
| --- | --- | --- |
| Hook 形态 | 无进程、无执行面的静态声明 | 携带包内可执行文件，由宿主执行其生命周期命令 |
| 适配知识归属 | Agent Plugin | Hook 工具自身 |
| 配置写入者 | Agent Plugin 投递，宿主与 Hook 都不写 | Hook 工具自己读写 Agent 配置（宿主仍然不写） |
| 协议 | 每种语义一个版本化 `protocol`，Agent Plugin 声明支持 | 不建立跨工具语义协议 |
| 兼容性 | Hook × Agent 能力矩阵 | 工具自行检测与适配；`supported agents` 仅作展示 |
| 触发时机 | Agent 进程启动时投递 | 安装、启用、更新、卸载时执行生命周期命令 |
| 状态 | per-(Hook, Agent) 的兼容与应用状态 | 生命周期命令的执行结果 |
| Agent 重启 | 作为统一生效边界由宿主调度 | 作为初始化后的用户提示，不抽象成宿主机制 |

## 决策

### D1：Hook 是携带包内可执行文件的独立 kind

`kind = "hook"` 与 `agent`、`mcp`、`skill` 并列，独立发布、独立安装、独立更新与卸载，不需要
任何 Agent 或 Agent Plugin 在场。它不创建插件 runtime、不参与 handshake、不注册 host method。

独立 kind 由**发布边界**决定，这条理由不随投递模型改变：Hook 的作者通常既不拥有 Claude Code
也不拥有 Codex。若 Hook 只能作为某个 Agent Plugin 的贡献存在，它要么必须被打包进每一个 Agent
Plugin（那些插件无权分发它），要么必须逐个修改 N 个 Agent Plugin。独立 kind 是第三方工具作者
得以存在的前提。

Hook 插件必须携带包内可执行文件，installed 形态继续用 `[artifact].target` 自述它面向的编译目标
（既有清单决策）。可执行文件在发现期按既有包内文件规则校验：路径落在当前 installed package
的 `assets/` 内、canonicalize 后仍是包内普通文件、拒绝 symlink 与 reparse point 逃逸。本决策不
新增第二套路径规则，也不接受 PATH 解析的裸命令。

与静态 kind 的关键区别必须显式记录：`mcp` 与 `skill` 承诺"安装不产生执行面"，Hook **不承诺**
这一点。宿主会在授权后执行它的程序，这个执行面是 Hook 能力的全部来源，不能用"无进程插件"来
描述它。

`assets/config.json` 的 `hook` shape 只接受下面四个成员，路径一律相对于当前 installed package：

| 成员 | 必填 | 取值 |
| --- | --- | --- |
| `executable` | 是 | 包内 `assets/` 下的可执行文件路径，例如 `assets/rtk.exe` |
| `supportedAgents` | 否 | 标识符列表，最多 16 项；只做形状校验（D3、不变量 9） |
| `lifecycle.init` | 是 | 该阶段的固定参数列表 `{ "args": [ ... ] }`，最多 16 个参数、每个最多 512 字节 |
| `lifecycle.deinit` | 否 | 同上；缺省表示工具不提供撤销入口（D6、不变量 11） |

三 shape 互斥与包内路径规则不变；未知字段、缺失必填字段一律整包失败。参数会被原样交给进程，宿主
不做 shell 转义，因此拒绝控制字符。`protocol`、`command`、`toolVersion` 不再是合法字段，出现时
给出专门指向被移除字段的错误并要求重新打包，而不是把它当作普通的未知字段。

### D2：生命周期命令是唯一的 Agent 适配入口

Hook 插件在声明中提供有限的生命周期能力，宿主在固定的插件生命周期事件上执行它们：

| 宿主事件 | 生命周期命令 | 触发条件 | 说明 |
| --- | --- | --- | --- |
| 安装 / 本地导入 | `init` | 用户在同一请求中已授权执行 | 工具检测支持的 Agent 并注册自己 |
| 更新 | `init` | 同上 | 每次更新都执行；版本迁移由工具在自己的 `init` 内完成 |
| 用户显式初始化 | `init` | 用户对该插件单独授权 | 失败重试与 pack 成员的延后初始化 |
| 卸载 | `deinit` | 用户在同一请求中已授权执行 | 在插件包目录被移除**之前**执行 |

触发点绑定在**单个插件**的用户操作上，不绑定在批量或后台流程上。具体地：

- pack 安装只落盘成员包，不执行任何成员的 `init`。成员中的 Hook 在已安装列表中显示为尚未初始化，
  用户可以对它单独授权并初始化。这样"执行授权"始终对应一个具体的 Hook，不会因为安装一个 pack
  而隐式获得多个第三方程序的执行许可。
- 卸载只有在移除该插件包目录之前执行 `deinit` 才有意义——包目录一旦进入卸载暂存，包内可执行
  文件已经不在原位。pack 卸载与安装回滚走的是另一条路径，因此不执行 `deinit`。
- 更新每次都执行 `init`。宿主不引入"是否需要迁移"的判定，也不提供版本迁移声明：工具知道自己的
  旧版本写过什么，幂等与迁移是工具的实现义务（D6）。
- 本机没有安装任何受支持的 Agent 时，`init` 照常执行，工具自行判断并可以什么都不做。宿主不
  参与"该不该执行"的判断——那需要一份它不打算维护的 Agent 存在性清单（D3）。

工具自己完成全部适配工作：检测哪些 Agent 存在、它们的配置在哪里、以什么格式注册 Hook、如何
判断已有配置是否由自己写入、如何升级、如何撤销。宿主不传递"要改哪个 Agent"的决策，也不检查它
实际改了哪些文件。

一次完整链路因此是：用户在确认对话框里授权 → 宿主安装包并执行包内工具的 `init` → 工具自己检测
支持的 Agent、按各 Agent 的格式读写配置文件 → 宿主记录退出码与输出、提示用户重启相关 Agent。
链路中没有任何一步需要宿主理解工具写了什么。

如果将来确有工具需要宿主逐个传入 Agent 标识（例如 `rtk --init --agent claude`），宿主可以为
命令增加一个"传入 Agent 标识"的参数边界。第一版不引入它：那需要先定义"已发现的 Agent"这一
集合，等于把被 D3 移除的能力矩阵重建一半，而当前没有任何工具提出该需求。

### D3：适配知识归 Hook 工具，宿主不建立语义协议与能力矩阵

Hook 声明不再需要 `protocol` 这样的跨方语义契约。宿主不计算 (Hook × Agent) 兼容性，Agent
Plugin 不翻译 Hook 声明、不生成配置、不回报 applied capability，也不存在 per-(Hook, Agent) 的
判定状态。

把 `protocol` 定义为 Hook 的语义契约会带来扩展性问题：每出现一种工具或行为，都要设计一个新协议
（`rtk-rewrite-v1`、`command-cache-v1`、`command-audit-v1`、`command-policy-v1`……）。Agent
Plugin 因此需要不断增加协议支持，工具作者与 Agent 作者需要协调协议版本，而"这个工具是什么"与
"Agent 如何接入 Hook"被混进同一个字段。对已经知道如何接入多个 Agent 的工具，这些抽象反而挡住了
最直接的实现路径。

代价必须明说：**工具与 Agent 之间存在适配耦合**。新增一个 Agent 时，已有工具可能需要更新。这个
代价是可见的、可局部处理的，并且落在最接近变化源的位置——Agent 配置格式变化时由工具作者更新
工具适配。它比在平台层提前建立协议矩阵、投递回执与多方生命周期模型更容易落地。

`supported agents` 因此只是展示信息：宿主不据此拒绝安装、不据此生成状态、不据此筛选执行对象。
真正支持哪些 Agent、如何识别、如何写配置，由工具在执行时自行决定。声明中它是一个可选的标识符
列表，宿主只做语法校验（形状合法即可），不校验这些标识符是否对应本机存在的 Agent，也不把它们
与宿主已知的 Agent 身份对齐——一旦对齐，宿主就重新拥有了一个它不打算维护的兼容性集合。

当多个真实插件之间出现稳定重复的模式时，再考虑抽象公共能力，例如统一的初始化命令接口、配置
片段所有权标记或受限的 Agent 配置 API。本决策不因为理论上的 M:N 关系提前引入协议生态。

### D4：宿主只做授权、执行与记录，不解释工具语义

权责按下面划分。宿主不理解任何工具语义，也不假装理解。

| 一方 | 负责 |
| --- | --- |
| Hook 插件 | 携带可执行文件；知道自身支持哪些 Agent；知道各 Agent 的配置位置、格式与注册方式；实现 `init` 与必要的迁移逻辑；尽可能实现 `deinit`；保证 `init` 幂等；保留自己写入配置的标记，不覆盖用户配置 |
| 宿主 | 安装、更新、启用与卸载插件包；校验可执行文件确实来自已安装的插件包；在明确授权后执行生命周期命令；传递必要的运行上下文；记录退出码、标准输出与标准错误；把失败展示给用户而不阻断核心功能；在界面明确披露插件可以读写用户文件和 Agent 配置 |
| Agent Plugin | 第一版不再承担 Hook 的通用适配责任。它仍然负责启动和管理自己的 Agent 进程，但不需要声明支持的协议、翻译 Hook 声明、为 Hook 生成配置或回报能力 |

宿主明确**不做**的事：不解析工具输出的语义、不推断它改了哪些 Agent 配置、不校验 Agent 配置
是否合法、不在失败时重试、也不回滚工具对宿主外文件已经写入的内容。宿主没有这些能力，声称拥有
它们只会产生一份与真实配置漂移的第二事实。

授权是**请求上的显式声明**，不是从"用户点了安装"推断出的隐含状态：安装、导入、更新与卸载请求
各自携带一个执行授权字段，缺省为拒绝。后端在没有该声明的请求上不执行任何生命周期命令，即使插件
包携带了完整声明。它是流程闸门——保证每一次执行都对应一次用户确认过的请求——而不是安全边界：
有权限的用户本来就能自己运行同一个程序，宿主也约束不了它。

授权的最小单位是插件在当前机器上的执行许可；本决策不产生 per-(Hook, Agent) 的授权或开关。

执行环境取最小集合，由宿主显式提供：

| 项 | 取值 |
| --- | --- |
| 可执行文件 | 当前 installed package 内、声明所指的那个文件，执行前重新校验（D1、不变量 2） |
| 参数 | 只有声明中为该阶段写下的固定参数。宿主不追加、不替换、不拼接任何内容，也不经过 shell |
| 工作目录 | 当前用户的家目录。工具可能写相对路径，落在用户目录比落在宿主进程的启动目录可预期 |
| 环境变量 | 继承宿主进程环境。工具要靠 `PATH` 与家目录判断哪些 Agent 存在，宿主不构造白名单环境 |
| 标准输入 | 关闭。命令不接受交互输入，避免安装流程被一个等待输入的进程挂住 |
| 标准输出与标准错误 | 由宿主捕获、限长并记录，用于诊断（D8）。每条流最多捕获 256 KiB，超出部分截断并标记 |
| 超时 | 120 秒内未结束即终止其进程树，并按失败报告（D8） |

宿主不传递 Agent 发现结果，也不把 Hook 设置实值或任何凭据拼进命令参数：前者等于把 D3 移除的能力
矩阵重建一半，后者会让凭据出现在进程命令行里，而那是本机任何进程都能读到的地方。

### D5：执行发生在 Ora 插件沙箱之外，安装与启用必须披露

生命周期命令以当前用户的权限执行，它**不在 Ora 的插件沙箱内**。Ora 对它的约束力为零：它能读写
当前用户可写的任意路径，其中包括 Agent 配置文件。

这与 D1 中"不创建插件 runtime、不注册 host method"不矛盾，两者说的是不同的事：Ora 不把它当作
插件进程启动，所以没有 Ora 侧的权限可授予；而它会作为宿主执行的程序运行，所以有真实权限。任何
把它描述为"无权限静态插件"的说法都会掩盖这一点。

安装与启用前必须清楚提示用户，例如：

> 此插件会执行包内程序，并可能读取或修改用户文件以及 Agent 配置文件。

这是产品的安全属性，不是实现细节。产品与文档必须让用户明白该程序不在 Ora 插件沙箱内，而不是让
用户误以为它仍受插件权限模型约束。

披露与 D4 的授权声明是同一件事的两面：披露发生在安装、导入与更新的前置确认里，那次确认产生的
就是请求上的授权字段。确认对话框必须出现在普通安装流程里，而不是藏在一个额外开关后面——用户
在按下安装时就应该知道接下来会发生什么。卸载的确认同样要说明会执行 `deinit`，以及在工具未提供
`deinit` 时其写入的配置会保留。

已安装列表与插件详情页必须让 Hook 与"无进程静态插件"在观感上可区分：前者会执行包内程序，后者
不会。把两者用同一套描述呈现，等于让用户以为 Hook 也在同样的沙箱与权限模型之下。

### D6：工具必须幂等、只拥有自己的配置片段、可被安全撤销

Hook 工具是 Agent 配置文件的实际写入者，因此下面的约束是插件契约的一部分，也是本决策对 Hook
插件的要求：

1. `init` 必须幂等。重复安装、重启 Ora 或重新启用插件不能无限追加相同配置。
2. 工具不能无条件覆盖用户已有配置。它至少应识别自己的配置片段、标记或备份边界。
3. 更新时要考虑旧版本写入内容的迁移，不能只覆盖文件而丢失用户手工修改。
4. 卸载时不能简单删除整个配置文件，只能删除自己明确拥有的配置片段；做不到时应保留配置并向
   用户说明，而不是猜测删除。
5. 执行失败要保留可诊断信息，包括执行阶段、退出码与错误输出。
6. 如果工具能修改任意路径，产品与文档必须说明这是插件权限，而不是 Ora 沙箱内的能力。
7. 命令必须在无人值守下完成：不读交互输入（宿主关闭标准输入）、不依赖宿主传来的上下文、不要求
   用户在命令执行期间做任何操作。需要用户确认的环节（例如 Agent 内的信任确认）只能在命令输出
   里提示，由用户在命令结束后自行完成。

声明层面，`init` 必需，`deinit` 可选但推荐：一个不提供撤销入口的 Hook 会让用户只能手工清理配置。
工具不提供 `deinit` 时，卸载不执行任何命令，工具此前写入的配置保持原样，宿主在卸载结果中说明
这部分内容未被撤销。宿主不代工具清理 Agent 配置，也不因为无法清理而拒绝卸载插件包本身。

### D7：`init` 成功不等于生效，第一版以用户重启 Agent 为生效边界

生命周期命令修改配置后，Agent 通常不会在已经运行的进程中读取新配置。因此第一版明确：

- 初始化成功只表示命令成功执行，不表示当前 Agent 已经生效；
- 用户可能需要重启 Agent 或创建新会话；
- Ora 提示用户重启，但不设计 Agent restart 调度、共享进程收敛或"何时重启"的策略。

Agent 进程可能被多个会话共享，让 Hook 变更生效的 restart 会影响该 Agent 的全部会话，这个调度
问题有用户可见代价，本决策不提前规定（见未解决问题）。如果某个 Agent 支持热加载，工具可以自行
利用；Ora 不把热加载抽象成所有 Agent 都必须实现的能力，也不据此宣称任何一个 Hook 已生效。

某些 Agent 对外部程序写入的 Hook 会要求用户在 Agent 内确认信任，且信任按 Hook 定义的哈希记录。
这是工具与 Agent 之间的环节：工具应在输出中提示用户，宿主不实现、也不假装实现该确认流程。第一版
因此不能承诺"安装后自动生效"，只能承诺"命令已执行、结果已呈现、需要时已提示用户"。

### D8：执行结果记录执行事实，不构成兼容或生效状态

宿主为每次生命周期命令记录执行事实：所属插件与版本、阶段（安装、更新、卸载、显式初始化）、退出
码、标准输出与标准错误，以及开始时间与耗时。这些记录支撑诊断与用户反馈，不表达兼容性、不表达
Agent 侧生效，也不产生 per-(Hook, Agent) 的行。

记录有两个去处，边界明确：

- **当前会话的内存状态**，供前端在已安装列表中呈现每个 Hook 最近一次执行的结果。写入状态、供
  界面呈现的输出再限长到 4 KiB，超出部分截断并在结果中标记；
- **结构化日志**，作为宿主自己的诊断事实保存，是完整输出的唯一去处。

第一版**不**把执行结果写进任何持久化状态。跨重启的持久化需要先定义"上次执行过但工具后来自己
改了配置"这类漂移如何收敛，在定义清楚之前，持久化只会制造一份与真实配置不一致的第二事实。
重启 Ora 后 Hook 显示为"本次会话尚未执行"，这只是未知，不是失败。

失败的处理边界：

- 初始化失败**不改变插件的安装状态**：包已经落盘、校验通过，插件保持已安装。失败属于执行事实，
  不属于包的有效性。
- 失败必须让用户可见，并带上可定位的诊断信息（阶段、退出码、错误输出）；只写日志不足以完成
  用户反馈。
- 失败可以通过"重新初始化"这一显式用户操作重试。宿主不自动重试，也不在后台定时重试。
- 失败不阻断会话创建、prompt 提交、插件管理、其他插件的安装或本次安装中其他 pack 成员的安装。
- 失败不回滚工具已经写入的文件。
- 工具在运行时失败（例如 Agent 真正调用 Hook 时）对宿主不可见，不在本决策范围内。

## 与既有实现的关系

本决策取代的既有形态是"不启动进程的 Hook kind"：它能安装 Hook 包、校验包内可执行文件的位置，但
从不执行它。差异因此集中在"包内可执行文件是否有唯一被授权的执行入口"。切换是一次性的，不存在
同时按两种语义解释同一份 Hook 声明的中间状态；既有 `hook` shape 的声明不构成本决策的合法输入。

| 既有部分 | 处置 |
| --- | --- |
| `PluginKind::Hook`、`may_ship_targeted_artifact`、installed `[artifact].target` 必需 | 保留，不变：Hook 就是那个二进制，主机兼容性仍在安装期判定 |
| `assets/config.json` 的 `hook` shape 与三 shape 互斥（混用即失败）、`validate_executable_containment`（首段必须是 `assets`、canonicalize 后仍是包内普通文件、拒绝链接逃逸） | 保留：包内可执行文件校验不变；声明成员由 `protocol` / `command` 收敛为 `executable` / `supportedAgents` / `lifecycle` |
| `HookProtocol`（当前只有 `rtk-rewrite-v1`）与契约中的 `protocol` 字段 | 移除：宿主不再据此判定兼容性，Agent Plugin 也不参与，没有任何消费方 |
| `HookCommand` 裸别名（拒绝路径分隔符）、`detect_hook_command_conflict`、`InstallOutcome::InstalledWithCommandConflict`、pack 成员结果与前端冲突提示 | 移除：别名模型随投递模型一起消失，本决策的入口是包内可执行文件的生命周期命令，不存在"与 PATH 上的同名命令冲突"这一概念 |
| 字符串形式的 `toolVersion` | 移除：工具自己的版本就是插件版本，`orax.toml` 已经承载它；再声明一个不参与任何判定的版本只会与包版本漂移 |
| "Hook 没有进程"的运行时表达：`PluginContribution::Hook` 拒绝注册、`entrypoint()` 为空、`stop_plugin` 对其为空操作 | 保留：宿主仍不把它作为插件 runtime 启动、不注册 host method。改变的是"宿主从不执行它" |
| Hook 贡献空权限集，以及契约投影中 `protocol`、`command`、`target`、`toolVersion` 的审计展示 | 重新表述：投影改为 `executable` / `supportedAgents` / `target`，以及本次会话的执行结果；可执行文件路径与 `supportedAgents` 属于展示信息，不是权限声明 |
| 已安装的带旧声明的 Hook 包 | 包发现阶段整包编译失败，错误指向被移除的字段（`hook.protocol` / `hook.command` / `hook.toolVersion`）并要求重新打包。不提供自动迁移：旧声明的语义（别名、协议）在新模型里没有对应物 |
| 用户文件与 Agent 配置中由旧工具写入的内容 | 属于工具，不属于 Ora。宿主不识别、不删除、不回滚，重新打包后的工具应在自己的 `init` / `deinit` 里处理它 |

## 为什么不是这些替代方案

| 方案 | 否决理由 |
| --- | --- |
| 为每种 Hook 语义设计版本化 `protocol`，由 Agent Plugin 声明支持并投递 | 协议数量随工具增长，Agent Plugin 被迫持续增加支持，工具作者与 Agent 作者需要协调协议版本；把"工具是什么"与"Agent 如何接入"混成一个字段 |
| 宿主自己把 Hook 翻译进各 Agent 的原生配置 | 宿主必须硬编码每个第三方 CLI 的私有配置格式，并把该格式的变更耦合进宿主发布节奏；宿主也不拥有 Agent CLI 的启动参数、`cwd` 与 `env` |
| Hook 绑定特定 Agent，或由 Agent Plugin 捆绑分发 Hook | Hook 作者被迫枚举现存 Agent，新增 Agent 需要修改全部已发布 Hook；发布边界不成立 |
| 保持无进程的静态声明，不执行任何命令 | 静态声明无法完成它承诺的适配：配置位置与格式由各 Agent 拥有，只有工具自己能读写；把适配留在宿主或 Agent Plugin 等于把耦合放在最不了解该工具的地方 |
| 每个 (Hook, Agent) 一份授权与状态 | 第一版没有真实的逐 Agent 需求；引入它必须同时引入 Agent 发现、协议匹配与投递回执，正是被本决策移除的复杂度 |
| 第一版就为每个已发现的 Agent 调用一次工具并传入 Agent 标识 | 需要先定义"已发现的 Agent"集合与逐 Agent 执行语义；没有工具提出该需求时引入它只是提前承担能力矩阵的代价 |
| 现在就抽象统一的初始化命令接口、配置片段所有权标记或受限 Agent 配置 API | 稳定重复的模式还没有出现；先抽象会把尚未被真实需求证明的边界固化进宿主 |
| 由宿主校验或回滚工具对 Agent 配置的修改 | 宿主不读 Agent 配置格式，无法判定"是否已存在""是否被用户改过""是否属于本工具"；声称能回滚只会制造与真实配置漂移的第二事实 |
| 安装 pack 时一并执行其成员的 `init` | 一次确认就替用户授权了多个不同作者的程序执行；用户没看到每个成员会做什么，却要为全部后果负责 |
| 在安装、更新、卸载之外增加"启用/禁用"这一独立开关作为执行触发 | 第一版没有真实需求，却要引入一个新的持久化开关状态与它在各个流程中的收敛规则；安装/卸载已经覆盖了配置的建立与撤销 |
| 把执行结果持久化，使其跨重启可见 | 工具可能在两次启动之间自己改了配置或失效，持久状态会与真实状态漂移；先定义漂移如何收敛，再谈持久化 |
| 接受 PATH 解析的裸命令，而不是包内可执行文件 | 命令身份、版本与来源都无法由插件包证明，安装结果依赖用户机器上的 PATH 与外部安装过程；包内文件是唯一能被包自身证明的来源 |
| 宿主自动重试失败的生命周期命令 | 失败通常来自用户环境而非瞬时故障，自动重试会把一次可见失败变成一串无人观察的重复副作用；重试必须是用户的显式决定 |

## 不变量

1. Hook 是独立 Plugin kind，可独立安装、更新与卸载，不要求任何 Agent 或 Agent Plugin 在场。
2. Hook 插件必须携带包内可执行文件；宿主执行的生命周期命令必须来自当前已安装包，拒绝包外路径、PATH 解析与链接逃逸；执行前必须重新校验一次。
3. 宿主只在请求显式声明授权时执行生命周期命令，缺省为拒绝；安装、导入与更新的前置确认必须披露"会执行包内程序，并可能读写用户文件与 Agent 配置"，卸载的确认必须说明会执行 `deinit`。
4. 宿主不建立 Hook × Agent 的协议匹配、兼容矩阵、投递通道或 per-(Hook, Agent) 状态。
5. 宿主自身不创建、不修改、不删除任何 Agent 配置文件；对 Agent 配置的修改只能由被执行的 Hook 工具完成。
6. 宿主不解释工具语义，不校验、不回滚工具对宿主外文件的修改，也不自动重试失败的生命周期命令。
7. 每次生命周期命令必须留下可诊断记录：插件与版本、阶段、退出码、标准输出与标准错误。记录只存在于当前会话内存与结构化日志中，不构成跨重启的持久状态。
8. 生命周期命令失败必须对用户可见，且不得阻断会话、prompt、插件管理或其他插件安装；失败不改变插件的安装状态，并可由用户通过显式初始化重试。
9. `supported agents` 只作为展示信息，不参与安装、执行、状态或任何宿主判定，宿主也不校验它是否对应本机存在的 Agent。
10. 初始化成功不等于 Agent 已生效；第一版不提供热加载抽象与自动重启，宿主以提示用户重启作为唯一的生效同步方式。
11. 卸载只在插件包目录仍位于原位时执行 `deinit`；工具未提供该能力时，宿主保留其写入的内容并如实说明，且不因此拒绝卸载插件包本身。
12. 批量流程不执行生命周期命令：pack 安装只落盘成员包，pack 卸载与安装回滚不执行任何命令。执行只发生在对单个插件的用户操作上。
13. 宿主不把 Hook 设置实值、凭据或 Agent 发现结果拼进命令；命令只由包内可执行文件与声明中为该阶段写下的固定参数组成，且不经过 shell。
14. `kind` 的封闭集合、target 形态、installed `[artifact].target` 必需与包内文件校验沿用既有决策，本决策不放宽其中任何一项。

## 本决策未解决的问题

以下边界明确留给后续决策。它们不改变 D1–D8 的结论，也不阻塞落地。

- **抽象时机。** 统一的初始化命令接口、配置片段所有权标记或受限 Agent 配置 API 是否、以及何时
  需要提取为公共能力。要在多个真实插件出现稳定重复模式之后才判断，见 D3。
- **配置归属与备份的记录方式。** 工具可以自行标记它写下的片段，但宿主目前不记录"哪些配置属于
  哪个插件"，也无法在撤销不完整时给出具体位置。
- **执行结果的跨重启持久化。** 需要先定义工具在两次启动之间自行修改或失效配置时，持久状态如何
  收敛；在那之前持久化只会产生第二事实（D8）。
- **逐 Agent 执行的参数边界。** 如果工具需要宿主逐个传入 Agent 标识（例如 `rtk --init --agent
  claude`），需要同时定义"已发现的 Agent"集合，那等于重建被 D3 移除的能力矩阵的一半。
- **Agent 重启的调度。** Agent 进程可能被多个会话共享，让 Hook 变更生效的重启会影响该 Agent 的
  全部会话。本决策只提示用户，不设计调度、共享进程收敛或"何时重启"的策略（D7）。
- **Agent 内的信任确认流程。** 部分 Agent 要求用户在 Agent 内确认由外部程序写入的 Hook，并按哈希
  记录信任。这是工具与 Agent 之间的环节，宿主目前只在输出里转述，不实现也不跟踪该确认状态。
- **已安装旧声明实例的自动迁移。** 当前处置是整包拒绝并要求重新打包；是否值得为已知的旧包提供
  一次性转换，取决于旧包的存量与作者配合程度。

## 落地状态

D1–D8 已全部落地：声明收敛、执行边界、授权披露与结果呈现、证据补齐都已完成，本文据此标记为
`implemented`。各验证义务的证据状态见核心测试用例；其中仍然存在缺口的验证义务是：

- 更新路径执行 `init`（安装与本地导入已有直接证据）；
- pack 卸载与安装回滚不执行 `deinit`；
- `deinit` 失败仍完成卸载（顺序与"可执行文件仍在原位"已有证据）；
- 失败不阻断其他插件与 pack 其他成员的安装；
- 跨重启后执行结果呈现为未知而非失败（会话内只保留最近一次已有证据）；
- `supportedAgents` 不参与任何宿主判定；
- 设置实值不进命令行、宿主自身不写 Agent 配置文件（目前只有代码约束，没有直接测试）。

这些缺口不改变本文的结论，属于后续验证工作；它们也不放宽任何一条不变量。

实现在落地时确定了三项本文未规定的取值，作为稳定规则记录在这里：生命周期命令超时 120 秒，每条
流最多捕获 256 KiB，写入执行结果供界面呈现的输出再限长到 4 KiB。失败语义、授权语义与执行环境
与本文一致，没有其他偏离。
