# 交互式节点按最终尝试的有效产出恢复

一个人工回合可以包含多次 ACP 发送。先前发送产出的半条消息或已接受的完成请求，可能让一次仅返回 `EndTurn` 的重试看起来已经交付。交互式节点必须能说明采用的是哪一次尝试的结果。

## 继承与修改

继承[完成信号的尝试绑定](20261110-agent-completion-signal.md)、[声明文件的实时校验](20261023-interactive-deliverable-contract.md)和[异常停靠与显式确认](20261102-first-turn-confirmation.md)。本决策替换[交互式节点完成契约](20261021-interactive-node-completion.md) D2 中自动重试没有持久化边界的限制。

## 决策

1. 同一用户回合只记录一次用户消息。每次静默取消得到原请求的响应、即将重发时，历史划出新的尝试边界。取消排空阶段的文本、工具结果及完成请求归入被放弃的尝试。重新发送的凭证只授权本次发送。新尝试复用工具或消息 ID 时，两次尝试仍独立。
2. park、普通完成、自动接受和强制完成从相同的最终尝试窗口取输出。按冻结契约校验最终文本、结构化输出、实际工具结果、声明文件与完成信号。一个只改文件的步骤可以通过声明的文件校验；需要 agent 信号时仍须有本次尝试的有效请求。等待中的工具、仅有思考、会话级更新和历时长短都不能证明步骤恢复。
3. 重试以 `EndTurn` 结束但缺少有效结果时，交互节点进入异常停靠，保留原会话。卡片和详情显示“节点运行失败”、原因和重试入口。持久化的失败原因在重启后可读。普通完成及自动接受都在后端拒绝，依赖成功的后继保持未启动。随后有效的人工回合按正常完成规则恢复，已有失败记录保留。
4. 用户仍可经既有的二次确认强制推进。完成审计单独标明空重试原因，并记录覆盖的 blocker。最终尝试没有文本时，强制采用的文本也为空。旧历史缺少新边界时沿用既有读取规则；保留既有审计和已经完成的节点。

## 不变量

1. 回合身份与最终尝试的输出窗口可以分别重建。
2. 后继调度以服务端验收为准，重复完成请求同样受门禁约束。
3. 只有显式强制完成可以覆盖未恢复结果的 blocker，并留下审计。

## 方案取舍与验证

转入引擎 Failed 会触发节点级失败策略及失败边，改变在原会话继续的既有交互方式。单靠界面告警则无法约束自动接受或旧客户端。异常停靠复用既有入口，完成服务负责调度保护。

先验证历史可重放与同一回合的凭证隔离，再从真实完成入口覆盖未恢复、强制采用及有效恢复。[核心用例](../../../../test-cases/desktop/core/workflow/interactive-retry-output.md)
