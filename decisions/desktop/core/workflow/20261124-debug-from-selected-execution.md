# Desktop 工作流调试从选中的节点执行继续

用户在运行页选择一次执行、编辑节点配置、预览影响，再在同一个 WorkflowRun 内继续。调度器复用能够证明仍然有效的结果，对受影响的执行创建新尝试。选择容器里的成员可以保留已经结算的轮或项，选择容器本身则从入口重新执行。

本提案适用于 Desktop 的运行内调试。预览样例用于并行验证行为，字段名为候选契约。普通失败恢复、重启、编辑器草稿与发布仍有各自的入口。本提案没有要求给历史运行补造执行事实。

## D1　选择一次执行，按运行记录修订

运行绑定发布快照。修订 0 使用该快照；每次成功确认生成一个递增的运行内修订，记录父修订、选中位置、补丁和生效范围。尝试绑定派发当时的实际配置与生产它的修订。查询历史可还原旧配置、输入来源、分支决定和尝试结果。两个 run 使用同一快照也各自拥有修订序列。

- 已执行位置用 `runId + nodeRunId` 选择。服务端解析根执行、定义节点、容器执行（若有）、轮/项位置及选中尝试。重试可能产生多条行；历史尝试可读，预览只接受该位置当前有效的尝试。前端不能用节点标题、数组下标或“最新一次”猜行。
- 对尚未派发的节点，候选选择器为 `pendingTarget:{rootScopeId,scopeId,nodeId}`，foreach 还须携带所属容器执行和零基项索引。与 `nodeRunId` 二选一。服务端必须能证明该位置存在、属于当前路径且输入就绪。未建立的未来轮次或被排除的分支只显示禁用原因。确认后由原依赖门派发。
- 建议允许 Running（含 AwaitingInput 投影）、Failed、Cancelled、Succeeded 中满足条件的目标。未启动的 Pending、已删除的 run、历史根执行和已有停稳操作阻止新预览。已终结 run 在新修订生效后重新进入调度。看到交互节点的旧完成按钮时，迟到的确认同样受尝试校验。
- 修改成员时，建议从选中位置起，在同一容器执行的当前及后续轮/项使用新配置，保留前缀原修订。对同一位置再次修改，按当前有效配置叠加。若回到更早位置修订同一字段，新确认的值覆盖其重算后缀里的旧覆盖；其他字段按其原有生效边界继承。重建容器入口产生新的容器执行，旧成员修订绑定旧执行；预览须展示新容器将采用的成员配置。

## D2　编辑和预览

表单以服务端返回的执行位置、当前修订、有效配置、作用域内变量目录和可选模型为初值。输出相对于该节点规范化 `data` 的有类型补丁。示例以 `replace` 表示替换已存在的字段；可选值应先经与编辑器相同的默认值和旧格式规范化。禁止越过字段白名单、改动节点身份、分支 ID、顺序、端口及连线。

| 节点 | 首版候选字段 | 预览前校验 |
| --- | --- | --- |
| Agent | `agentConfig.prompt`、现有 executor 的 `modelId` | 模型与执行器相容，模板变量在选定作用域可见且类型适用。 |
| Condition | 既有 `cases` 内的判断条件及组合逻辑 | 保留原分支身份和 ELSE，操作符、变量选择器及比较值类型符合该图。 |
| Loop | `loopConfig.until`、已有轮变量的反馈选择器、`maxIterations` | 保留轮变量声明，校验反馈类型、退出比较及既有轮数范围。 |
| Iteration | `iterationConfig.iteratorSelector`、`collectSelector`、`errorStrategy` | 源为数组，收集值来自区域内声明，与现有下游兼容，沿用原启动上限。 |

预览在发布快照与已生效修订组成的图上模拟，复核候选图、选中位置和新字段引用的全部输入。每个可复用值都要有该运行、有效执行作用域、生产尝试、已提交结果与仍可达的控制路径。轮内还要能还原轮入口、反馈或冻结项值，以及本轮目标之前的变量版本。当前全局变量池的同名值、文本日志或画布位置都不足以证明来源。有效的失败账本条目可在已结算的 foreach 前缀依原错误策略保留。

预览只读。成功返回绑定具体目标、规范化补丁、修订和计划所依赖事实版本的 `previewId`，列出复用、失效、待执行/重算范围、需停稳的在途尝试及工作区提示。旧路径的已提交值从当前投影失效，与再次调度哪个节点分别表达。无法预知的分支或后续轮次标为条件范围，用户确认的是这个边界。校验失败返回字段路径或缺失事实，且没有可提交凭据。若旧数据只够证明容器入口，可显示单独的入口选项，用户选中后须重新预览更大的范围。

## D3　两个接口样例

下列对象分别对应预览请求、预览结果和确认请求。`keep`、`invalidate`、`schedule` 在样例中列出事实或执行位置的简称；真实引用须能定位到运行内的具体记录或限定了作用域的范围。确认读取预览所绑定的不可变内容。文件提示对两个操作相同。

### foreach 五项中的第三项

Start 产生 `[a,b,c,d,e]`。旧 Agent 原样返回输入项。运行 F 中 it1 已结算 a、b，第 3 项的 f3 正在尝试 t3，输入为 c，项 4/5 尚未派发。

```json
{
  "preview": {"runId":"F","nodeRunId":"f3","baseRevision":0,"patch":[{"op":"replace","path":"/agentConfig/prompt","value":"返回 new- 加 {{#iter.item#}}"}]},
  "result": {
    "previewId":"pF","baseRevision":0,
    "target":{"nodeRunId":"f3","nodeId":"agent","containerNodeRunId":"it1","index":2},
    "keep":["start.items","it1.frozenItems","it1.entries[0..1]","it1.item[2].input"],
    "invalidate":["f3/t3"],"stop":["t3"],
    "schedule":["agent[2]","agent[3..4]","iter.collect","downstream"],
    "workspace":"keep","externalActionsMayRepeat":true
  },
  "commit":{"runId":"F","previewId":"pF","requestId":"kF"}
}
```

成功后 F 的修订为 1。t3 的迟到输出只可查历史。可控 Agent 的开始次数依次为 `[1,1,2,1,1]`，有效成功输出为 `[a,b,new-c,new-d,new-e]`。按冻结输入索引重建 entries，每项恰有一条有效账；output 仍仅投影成功项。若从已完成的第 5 项之后回看第 3 项，则原项 3–5 的账、汇总和消费者一并列入失效，前两项各只调用一次。

### Condition 重新选路

根作用域内，Start 已提交布尔值 flag=true。实例 c1 的 IF A 判断 flag is true，ELSE 通往 B。A 和 B 分别产生 a、b，汇合 J 是按可用变量选择的 Aggregator。旧 J 已读到 a，独立分支 S 已成功。

```json
{
  "preview":{"runId":"C","nodeRunId":"c1","baseRevision":0,"patch":[{"op":"replace","path":"/cases/0/conditions/0/value","value":false}]},
  "result":{
    "previewId":"pC","baseRevision":0,"target":{"nodeRunId":"c1","nodeId":"condition","scopeId":"rootC"},
    "keep":["start.flag","S.output"],"invalidate":["c1.decision","A.output","J.output"],
    "stop":[],"schedule":["condition","B","J"],"predictedBranch":"else",
    "workspace":"keep","externalActionsMayRepeat":true
  },
  "commit":{"runId":"C","previewId":"pC","requestId":"kC"}
}
```

确认后在同一 C 中重新判断，原 IF 标识和连线仍在。有效分支为 ELSE，J 只读到 b；S 的结果可复用。累计 Start/S/A/B 各执行一次，Condition/J 各执行两次。旧 A 与旧 J 仅用于历史展示。若旧 A 仍在执行，先将它列入 stop；B 的首次执行也必须等停稳成功。

## D4　其他起点

| 选择与修改 | 保留 | 重算及可观察结果 |
| --- | --- | --- |
| 顶层 Agent X 改模型，图为 Start → X → Output，独立 S 已完成 | Start 输入和 S 结果 | X 的新尝试从同一输入开始，Output 读取新值；历史可比较 X 的两个配置。 |
| Loop 第 3 轮实例 x3 改提示词 | 轮 1、2 的有效结果，轮 3 入口的 carried values、同轮中有效前置 | 从 x3 重算本轮后继及反馈/退出。若新结果令条件成立，发布第 3 轮导出，作废旧第 4 轮起的事实及外层旧消费者；不创建第 4 轮。若继续，按新反馈开启下一轮。遇到显式 LoopExit 仍依其独立退出协议。 |
| 选 Loop 容器行，将轮数上限从 5 改为 2 | 容器入口可证明的外层输入、独立工作 | 用初始值建立全新第 1 轮；即使旧轮数为 3 也不保留旧反馈。持续未命中退出时按冻结的达到上限策略成功或失败，无第 3 轮。改退出条件或反馈亦从入口重算。 |
| 选 Iteration 容器行，将源从 [a,b,c,d,e] 换成已有变量 [e,c] | 两个源的可见上游、独立工作 | 从入口重新冻结 [e,c]，索引 0/1 各重做一次并重新收集。相同元素也按新位置执行；仅改收集选择器或错误策略同样重建账本与外层汇总。 |

## D5　确认、停稳与重新调度

1. 确认提交 `runId, previewId, requestId`。按 run 和请求键先查已受理操作；同键同凭据返回同一操作和当前阶段，同键换凭据报 `request_conflict`。在同一运行门中重新验证预览读集（修订、根、目标尝试、输入与控制事实、影响范围和在途集合）。过期返回 `stale_preview` 并要求重新预览；零停稳、零新修订。与计划无关的兄弟进展可以继续。
2. 受理时持久保存意图、目标范围和待停稳清单，封住该范围的新派发、重试和旧尝试对当前事实的写入。门外等待活动 Agent、在途重试和待处理人工动作终止或得到可证明的隔离。允许独立兄弟继续；其结果经原尝试凭据提交。共享工作区文件仍可能变化，调度独立仅表示没有工作流数据/控制依赖。
3. 停稳成功在同一持久提交中写新修订、有效性、账本/轮状态、变量与选路的新投影和待调度位置。先提交再通知、派发。计划中尚无结果的节点保持依赖检查。旧尝试回调、延迟重试、人工确认即使携同一 nodeId 也不能推进新修订；独立兄弟仍可持原凭据完成。
4. 停稳失败返回可查的 `stop_failed`，标明未停稳尝试；已经停止的尝试如实记录，受影响范围保持阻塞，零新修订、零新派发。确认旧请求仍返回该失败；协调器确认阻塞尝试已终止/隔离后释放栅栏，用户可重新预览并用新键再试。外部动作可能已发生。
5. 重启后按持久意图续办。待停稳操作先重新核验旧尝试；已生效操作从持久的调度事实恢复，仅认领尚未派发的位置。无法判断在途外部工作是否结束时报告停稳失败。丢失响应时可按请求键重查，避免重复生效。新旧运行推进中的并发确认最多一个获得受理，其余须重查活动操作或重新预览。

工作流变量按有效生产者、作用域和分支重建；文件默认保留在同一 Workspace，预览提示可能读到上次生成的文件。调用外部工具、发送消息和写远端等动作可能重复，旧记录转历史不撤销这些效果。

## D6　历史、通知和事实所有者

确认受理响应举例为 `{"operationId":"opF","requestId":"kF","state":"stopping"}`。查询运行调试历史返回按提交顺序的操作、阶段、预览目标/补丁、父与生效修订、失败原因和尝试关联。例如生效后按 kF 重查得 `{"operationId":"opF","requestId":"kF","state":"applied","baseRevision":0,"revision":1}`。applied 表示修订已生效，节点自身状态由运行详情读取。尝试详情给出其实际配置、修订、有效性与替代关系；回看旧尝试不改变当前表单的编辑基线。

| 责任方 | 读取 | 唯一负责的写入或输出 |
| --- | --- | --- |
| 共享契约、repository | 冻结快照、历史修订、有效事实、类型化补丁 | 提供预览、确认认领、事务生效、历史/尝试查询端口。持久化修订、有效性、幂等键和操作阶段。 |
| 执行协调 | 受理意图、待停稳尝试、节点策略的影响计划 | 管理派发栅栏、停止结果和新尝试派发，经 repository 原子推进操作。 |
| 顶层 DAG 与 Condition | 有效根作用域、控制边和变量生产者 | 生成顶层重算计划，按新输入提交选择、变量及汇合。 |
| while / foreach 运行时 | 所选 scope 或容器执行、项索引、成员生产者、入口快照 | 各自生成保留/失效范围并结算轮池与导出、或对应项账本与汇总。 |
| 配置表单 / 运行页 | 当前有效配置、可用变量/模型、预览与历史 | 表单只交付已验证补丁；运行页选择实例、展示影响、确认、重查。取消编辑丢弃本地补丁。 |
| 跨包验收 | 固定输入、持久历史、调用记录、页面呈现 | 核对同一运行的调用次数、有效输出和副作用警示。 |

状态提交后沿用 `WorkflowRunInvalidated { run_id }`。事件表示该 run 应重查，失效的执行清单来自预览/持久查询。客户端在重连、漏收或重复事件后以运行详情和历史重建界面。

## 不变量与取舍

1. 同一运行、同一输入位置最多有一个当前有效结果；旧尝试可审计。
2. 预览和取消编辑均无执行副作用；一次确认最多生效一个修订。
3. 所有复用结果都有有效生产者；执行新路径或新轮次时只读取该路径/轮次可见的值。
4. 新派发以旧尝试停稳为前提；整工作区备份与外部工具撤销不在事务范围内。

| 备选 | 收益与代价 |
| --- | --- |
| 修改发布定义再重开运行 | 可直接使用既有启动入口，但会改变发布流程、重复上游工作，且打断运行内审计链。 |
| 所有成员都从容器入口重算 | 对旧数据要求较低，但会再调用已结算的前缀。适合作为用户另行确认的降级入口。 |
| 仅修改选中的一次尝试 | 适合逐项覆写，但用户要修复后续项时需逐项确认，预览与调用次数也不同。 |
| 暂停所有兄弟或回滚整棵工作树 | 减少局部协调，却可能中断无关会话或覆盖其已经提交的文件。 |

建议先验证两个接口样例，再验证轮内前缀、容器入口和停稳失败，最后从运行页重连并用持久历史核对。行为审批后，将这些验证义务登记到镜像核心用例目录；真实 Desktop 的证据随后按实现补入。
