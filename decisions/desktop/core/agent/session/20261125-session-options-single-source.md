# 会话选项以 session actor 为唯一来源，设置的响应也走会话事件流，取代返回值写选项

Agent 会话的选项（模型、推理强度等）由该会话的 actor 持有，actor 是当前选项的唯一来源。设置选项的响应和 Agent 主动推送的
选项走同一条会话事件流，actor 按宿主收到 ACP 帧的先后处理，再送给客户端视图。`setSessionConfig` 的返回值只表示成功或
失败。没有进行中的流时，宿主用现有的应用级广播通知「会话选项已变」，视图收到后从 actor 取当前选项，不新建通道。

行为变化：响应早于或晚于推送到达界面，结果都一样；视图不再把设置的返回值当作当前选项写入。

本文为 `proposed`，尚未实现。只定三件事：当前选项的唯一来源（D1）、按什么顺序处理（D2）、怎么送达（D3）。需要
owner 定的点列在[待定](#待定)，正文不预设结论。

- **涉及**：`ora-agent-runtime` 的 actor 与会话路由、公共契约里的 `setSessionConfig` 和 `AppEvent`、Desktop 宿主的应用
  事件、前端会话 store 与选择器。
- **兼容边界**：没有持久化数据，不需要迁移；ACP 与插件契约不变，Agent 不需要改动。
- **不涉及**：会话何时连接 Agent、附着与重建的条件、会话前发现、命令列表的送达、历史记录的内容。

## 背景

设置选项时，Agent 的答复作为 `setSessionConfig` 的返回值到达前端，Agent 自己推送的 `config_option_update` 经会话事件流
到达。两条路没有共同的先后，前端按到达顺序写，晚到的旧值会盖掉新值。宿主里同样有两条路：答复经命令队列交给 actor，推送
经事件队列；没有回合时，推送还会转成一条命令排到命令队列末尾，落到更晚的答复之后。

| 编号 | 场景 | 结果 |
| --- | --- | --- |
| P1 | Agent 先答复 B、再推送 C；前端先收到 C、后收到 B | 界面显示 B，Agent 实际是 C |
| P2 | 建会话时带模型意图，短收集窗口之后、设置答复之前到达的旧推送 | 旧推送在答复之后被采用，之后的加载得到旧值 |
| P3 | 会话空闲，旧推送转成命令，排在「采用答复」之后 | 旧推送盖掉答复 |
| P4 | 设置期间会话被重建，旧 provider 会话的答复晚到 | 调用方曾得到旧会话的值；现有实现已改为返回替代会话的选项 |

都只影响显示，不改变 Agent 实际使用的选项。P1 在前端复现过；P2、P3 按代码推断，没有复现；没有在真实 Agent 上观察到。

## 术语

- **会话选项**：有 provider 的会话由 Agent 报告的全部可配置项和当前值，每次报告都是完整集合。
- **绑定**：沿用词汇表的 `Agent Binding`，即 Ora 会话当前关联的 provider 会话。
- **视图**：持有一份会话副本的前端状态。一个视图可能正在接收这条会话的加载流或 prompt 流，也可能没有流。现在 Desktop 只有一个
  主窗口、一份会话副本，模型和推理强度选择器共用它；规则按可以有多个视图来写。

## 决策

### D1：actor 持有当前选项，视图只持有副本

1. 会话有 provider 时，当前选项只由该会话的 actor 持有。新视图加载、正在跟随的视图、空闲视图取到的都来自这一份。
2. 选项只由三种 ACP 帧更新：建立或恢复会话的答复、设置选项的答复、`config_option_update`。每种都是完整集合，整体替换，
   不逐项合并。刷新 MCP 的答复见 W13。
3. 只采用属于当前绑定的帧。绑定已更换时，旧 provider 会话晚到的答复和推送都不改变当前选项（P4）。
4. `setSessionConfig` 的返回值只表示成功或失败，不表示当前选项。答复属于当前绑定时，actor 处理完它之后才返回成功；其余情况
   见 W11、W12。
5. 视图不把返回值当作选项写入，不按用户点击的值乐观写入。

为什么：顺序问题出在有两个写入者。只留一个持有者，视图就不需要各自判断新旧；答复先由 actor 处理再返回，保证调用成功之后
打开的视图能看到这次改动，这一点和现有行为相同。

反例：会话被重建，旧会话答复「已设为 A」，替代会话是 B。当前选项是 B，视图显示 B；用户选的 A 不在替代会话上重发，也不报错。

### D2：响应和推送按宿主收到 ACP 帧的先后处理

1. 同一绑定内，答复和推送进入同一条有序的会话事件流，先后以宿主从该连接读到帧的先后为准，actor 逐个处理。
2. 顺序在任何时候都成立：回合中、空闲、标题轮询、MCP 刷新，以及建立和恢复会话的阶段（P2、P3）。不得把其中一类帧改走另一条
   队列，再插回到别的帧之后。
3. 建立会话时应用模型意图的答复和其他设置的答复同等对待：在它之前到达的推送，不会在它之后被采用或送给视图。
4. 绑定之间没有先后比较。换绑定时当前选项由新绑定建立或恢复的答复重新确立，旧绑定的帧按 D1.3 处理。

为什么：同一连接上读帧的先后是宿主能得到的、最接近 Agent 更新先后的唯一事实。按处理时刻、墙钟时间或到达前端的时刻排序，都会
引入第二个顺序。需要应答的请求已有「答复随会话事件有序送达」的机制，设置选项改用它即可，不需要新的排序字段。

| Agent 发出的顺序 | 当前选项 |
| --- | --- |
| 答复 B → 推送 C | C |
| 推送 C → 答复 B | B |
| 旧推送 A → 答复 B（建会话的模型意图） | B |
| 旧绑定的答复 A，在换绑定之后到达；新绑定报告 B | B |

### D3：有流时随流送达，空闲时用应用级广播通知后再取

1. 有进行中的加载流或 prompt 流时，actor 把每次变化按处理的先后随流送出，接收该流的视图按流内先后写入。
2. 空闲（没有进行中的加载流或 prompt 流）时，宿主发出应用级广播「会话选项已变」，参照现有的会话标题更新通知，只带 Ora
   会话 id，不带选项。视图收到后从 actor 取当前选项。不新建通道。
3. 广播是尽力而为的失效通知，可能丢失或合并。视图（重新）订阅应用事件之后，对正在展示的会话重新取一次当前选项，补上断开
   期间的变化。
4. 取回的是 actor 当时的当前选项。从流得到的更新和取回的结果之间也有先后：取回的结果不能盖掉更新的选项。用什么规则保证见
   [待定](#待定) W3。
5. 通知和取当前选项都是只读的，不访问 Agent，不改变会话何时连接 Agent，不写历史。

为什么：空闲时没有流，为选项单独建会话级通道要处理订阅、重连和与现有流的先后，代价大于收益。广播只说「变了」，值由视图去
唯一来源取，丢一次通知不会让错误的值留在某处被当成事实。

## 不变量

1. 任一时刻一条会话至多有一份当前选项，由 actor 持有。
2. 同一绑定内，当前选项等于 actor 处理的最后一个携带选项的 ACP 帧的内容，处理的先后就是宿主读到帧的先后。
3. 旧绑定的帧不改变当前选项。
4. 答复属于当前绑定时，`setSessionConfig` 返回成功意味着 actor 已处理完它。
5. 流静止且视图取到最新结果之后，展示同一会话的所有视图和之后的加载显示同一份选项。
6. 会话选项不写入历史，广播不携带选项。

## 为什么不是这些替代方案

| 方案 | 优势与否决理由 |
| --- | --- |
| 响应和推送带同一份单调序号，各方只接受更大的 | 不改返回值的语义。但契约多一个字段，连接或会话重建后要说明怎么接续，新旧仍由每个消费方各自判断 |
| 保持现状，等真实 Agent 触发再处理 | 没有改动成本。但规则只在代码里，以后新增写入者或消费方会再次出现两个顺序 |
| 为空闲会话新建会话级通道 | 空闲时也能直接带值送达。但多一条通道的订阅、重连和与现有流的先后；应用级广播已经覆盖同类通知 |
| 广播直接携带选项 | 少一次取值。但广播可丢、可合并、与流没有先后，等于再多一个来源 |
| 前端按发起设置的先后过滤晚到的返回值 | 改动最小。但只能比较前端自己的请求，判断不了 Agent 的推送，其他视图也看不到 |

## 风险

- **广播丢失或积压**：视图可能短暂显示旧值，由重新订阅后的重取（D3.3）和下一次加载收敛。它不影响 Agent 实际使用的选项。
- **发起设置的视图也依赖事件**：空闲时返回值不再写选项，发起设置的选择器要靠通知才更新，通知一旦丢失就停在旧值。W5 要覆盖
  这一点。
- **答复和事件共用队列**：队列溢出、会话停止时通道被释放，途中的答复不再经 actor 处理。这次设置返回什么见 W11。

## 本决策未解决的问题

- 命令列表等其他会话级更新是否也按同样的规则送达空闲视图。它们没有「返回值」这条路，不在本次的问题里。
- 会话 setup 区分「没有上报」和「上报为空」，由[发现契约](../../../plugin/agent/0-discovery-contract.md)的落地处理。

## 验收

转为 `approved` 时依此补充核心测试用例：

1. 同一回合内「答复 B → 推送 C」「推送 C → 答复 B」，发起设置的视图、跟随的视图和之后的加载都显示 Agent 最后的值；把答复和推送到达前端的先后交换，结果不变（P1）。
2. 建会话带模型意图时，收集窗口之后、设置答复之前到达的旧推送不被采用，也不随第一条 prompt 送给视图（P2）。
3. 空闲时旧推送与设置答复相继到达，当前选项是后到的帧（P3）；标题轮询、MCP 刷新进行中同样成立。
4. 设置期间会话被重建，旧绑定的答复在回合中或回合后到达，当前选项、所有视图和之后的加载都是替代会话的选项（P4）。
5. 会话空闲时在一个视图设置选项，另一个展示同一会话的视图收到通知并取到新值；通知丢失时，重新订阅后取到新值。
6. 取回的结果晚于流中更新的选项到达时，不盖掉后者；反过来，流结束之后的变化不会被旧的取回结果盖掉。
7. 设置成功返回之后打开的视图看到这次改动；Agent 返回错误时返回失败，当前选项不变。通道释放、没有 provider 时按 W11、W12 的结论。
8. 通知和取当前选项不访问 Agent，不改变会话状态，不写历史。

## 落地顺序

1. **宿主**：设置的答复改走有序的会话事件流，actor 成为唯一写入者，去掉空闲排空改排命令队列的路径；建会话阶段同样按 D2。完成
   条件是验收 2、3、4、7，此时前端仍写返回值。
2. **通知与读取**：增加广播和取当前选项的方式，前端按 D3 更新空闲视图。完成条件是验收 5、6、8。
3. **前端改由事件写入**：`setSessionConfig` 的返回值不再写选项，按 W5、W7 的结论处理。完成条件是验收 1。

第 1 步单独合入时，可见变化只有 P2、P3 不再显示旧值；第 3 步之前返回值和事件并存，规则以本文为准。
