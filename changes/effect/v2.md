# Effect v2 数据库表设计讨论目录

以下顺序按“结构由简到繁、模块由外到内”排列，作为逐表讨论顺序。已经讨论完成的表
记录当前结论；尚未讨论的表只保留标题。

本次设计不为 `TEXT` 字段添加数据库 `CHECK`。枚举值、格式和非空字符串等规则写入
SQL 注释，并由领域类型与 repository 写入边界校验；非文本约束仍可按需使用
`CHECK`。

Effect Source 是最小可选择单元，Managed target 是最小 ownership 与 mutation 单元。
一个 Plugin package 可以提供多个 Effect Sources，一个 Surface 也可以包含多个 Managed
targets；package 和 Surface 都不是用户选择或 ownership 的最小粒度。

## 01. `effect_sources` — Effect 来源

保存 Effect 来源的稳定业务身份及其生命周期。它不保存具体版本、内容位置、digest、
Workspace Desired 引用或物化状态。

```sql
CREATE TABLE effect_sources (
    id          TEXT PRIMARY KEY,             -- UUID
    effect_kind TEXT NOT NULL,                -- skill | mcp
    source_kind TEXT NOT NULL,                -- local | plugin
    namespace   TEXT NOT NULL COLLATE NOCASE, -- non-empty namespace
    identifier  TEXT NOT NULL COLLATE NOCASE, -- non-empty identifier within namespace
    lifecycle   TEXT NOT NULL,                -- active | retired
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    UNIQUE (effect_kind, source_kind, namespace, identifier),
    CHECK (updated_at >= created_at)
);
```

`id` 是 Effect 自己生成的 UUID，作为 Source 实体身份和其他 Effect 表引用的外键。
`(effect_kind, source_kind, namespace, identifier)` 是 SourceKey，只负责表达业务唯一性和
防止重复创建：

- `effect_kind` 表示 Effect 是什么，第一版支持 `skill` 和 `mcp`；
- `source_kind` 表示来源机制，第一版支持 `local` 和 `plugin`；
- `namespace` 隔离同一来源机制下的不同发布者或命名空间；
- `identifier` 是 Effect 在该 namespace 内的稳定名称；
- `lifecycle` 中 `active` 表示可用于新 Desired，`retired` 表示停止接受新引用但保留
  历史身份。

Source 的可用性不属于生命周期。具体 Revision 当前能否读取和物化，由
`effect_source_revisions` 记录。

## 02. `effect_source_revisions` — Effect 来源版本

保存 Source 已发布的确切内容状态，以及该状态当前是否仍可读取。Revision 的内容身份
发布后不可修改；可用性可以随底层 artifact 的存在性和完整性变化。

```sql
CREATE TABLE effect_source_revisions (
    id                 TEXT PRIMARY KEY, -- UUID
    source_id          TEXT NOT NULL REFERENCES effect_sources(id),
    revision           TEXT NOT NULL,    -- opaque source revision; equality only
    state_digest       TEXT NOT NULL,    -- algorithm-prefixed digest
    payload_json       TEXT NOT NULL,    -- immutable adapter-owned revision payload
    availability       TEXT NOT NULL,    -- available | unavailable
    unavailable_reason TEXT,             -- absent when available
    created_at         INTEGER NOT NULL,
    updated_at         INTEGER NOT NULL,
    UNIQUE (source_id, id),
    UNIQUE (source_id, revision),
    CHECK (updated_at >= created_at)
);
```

`id` 是 Effect 内部 Revision UUID；`revision` 是来源系统提供的不透明版本标识，只允许
完全相等比较，不解析或排序。`state_digest` 和 `payload_json` 与 `(source_id, revision)`
共同确定已发布内容：同一 `(source_id, revision)` 被再次登记时（幂等），state_digest 和
payload_json 必须与已有记录完全一致，否则属于制品完整性错误。

`payload_json` 由对应 Effect adapter 定义和校验。它保存不可变状态或稳定 artifact
reference，不保存会随安装位置变化的临时路径。Effect Core 不解析其中的类型专属
字段。

`revision`、`state_digest` 和 `payload_json` 发布后不可修改。`availability`、
`unavailable_reason` 和 `updated_at` 是可变的运行状态；旧 Revision 的 artifact 丢失或
校验失败时可以标记为 `unavailable`，但不能修改其内容身份。

## 03. `effect_source_heads` — Effect 来源当前版本

为每个已有当前版本的 Source 保存唯一 Head。Source 尚未发布任何合法 Revision 时可以
没有 Head；Head 可以指向当前暂时 unavailable 的 Revision。

```sql
CREATE TABLE effect_source_heads (
    source_id   TEXT PRIMARY KEY REFERENCES effect_sources(id),
    revision_id TEXT NOT NULL,
    updated_at  INTEGER NOT NULL,
    FOREIGN KEY (source_id, revision_id)
        REFERENCES effect_source_revisions(source_id, id)
);
```

复合外键保证 `revision_id` 所属的 Source 与 `source_id` 一致。`effect_source_revisions`
中的 `UNIQUE (source_id, id)` 专门为该外键提供数据库约束。

发布新版本时，在同一个数据库事务中插入或确认 Revision、推进 Head，并创建对应的
propagation request。Head 不通过 revision 字符串排序推导，也不在 Revision 上保存
`is_current` 状态。

## 04. `workspace_effects` — Workspace Effect 聚合根

作为 Workspace Desired State 的一对一聚合根，保存完整 Desired Effect 集合的
generation。每个 Workspace 创建时同步创建该记录，避免“没有记录”和“generation 0
的空 Desired”形成两种等价状态。

```sql
CREATE TABLE workspace_effects (
    workspace_id TEXT PRIMARY KEY REFERENCES workspaces(id),
    generation   INTEGER NOT NULL DEFAULT 0,
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL,
    CHECK (generation >= 0),
    CHECK (updated_at >= created_at)
);
```

`workspace_id` 同时是主键和 Workspace 外键，不再创建等价的 WorkspaceEffect UUID。
这使一个 Workspace 最多只有一个 Effect 聚合根成为数据库约束。

`generation` 属于完整 Desired Effect 集合，而不属于某个 Effect kind 或 Surface：

- 新 Workspace 从 generation 0 的空 Desired 集合开始；
- 规范化后的完整 Desired 集合发生变化时增加 1；
- 提交相同集合是 no-op，不增加 generation；
- Source 自动传播导致 Desired Revision 变化时增加 generation；
- Managed、Observed、Surface status 和 Consumer status 变化不增加 generation。

Desired replace 使用 expected generation CAS。检查 generation、替换规范化 Desired
rows、推进 generation，以及创建或合并 reconcile requests 必须在同一个数据库事务
完成。CAS 未命中时返回包含 expected/current generation 的 typed conflict。

该表不保存 Desired JSON、lifecycle、phase、conditions 或 applied/observed generation；
它们分别由规范化 Desired 子表、Workspace、Surface/Consumer status 和 conditions 表
负责。

## 05. `effect_surfaces` — Effect 投影面

表示 Effect 被投影、扫描和修改的一个具体目标边界。Surface 是独立实体：目标路径或
Workspace 实际位置变化时，旧 Surface 可以进入 Retiring，同时由一个新 Surface
承接新的投影目标。

```sql
CREATE TABLE effect_surfaces (
    id           TEXT PRIMARY KEY, -- UUID
    workspace_id TEXT NOT NULL REFERENCES workspace_effects(workspace_id),
    adapter_kind TEXT NOT NULL,    -- filesystem_directory | filesystem_document
    locator_key  TEXT NOT NULL,    -- canonical physical-target identity
    locator_json TEXT NOT NULL,    -- immutable adapter-owned target descriptor
    format_kind  TEXT NOT NULL,    -- skill_directory.v1 | mcp_config.v1
    lifecycle    TEXT NOT NULL,    -- active | retiring
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL,
    UNIQUE (workspace_id, adapter_kind, locator_key),
    CHECK (updated_at >= created_at)
);
```

`id` 是供 Managed、Status、Consumer 和 Operation 引用的 Surface UUID。
`adapter_kind` 决定使用哪种机制扫描和修改目标；`format_kind` 决定目标内部如何表示
Effect items。Surface 不保存 `effect_kind`，因为一个 materialization format 未来可以
承载多种 Effect。

`locator_key` 用于比较和唯一约束，`locator_json` 用于实际访问、恢复和安全清理。JSON
不参与目标相等判断；adapter 必须先安全规范化 locator，再生成稳定的 `locator_key`。
例如 filesystem adapter 可以根据已确认的 Workspace root 和规范化相对路径生成 key，
并保存如下 descriptor：

```json
{
  "workspace_root": "...",
  "relative_path": ".agents/skills"
}
```

`locator_json` 和 `format_kind` 创建后不可修改。路径、Workspace 实际位置或 format
发生变化时，旧 Surface 进入 `retiring`，安全清理其 Managed items 后再结束生命周期；
新目标使用新的 Surface UUID。

唯一约束故意不包含 `format_kind`。多个 Consumer 声明同一目标且 format 兼容时共享
一个 Surface；同一目标的 format 不兼容时不能创建两个 writer，而是报告
`IncompatibleSurfaceDeclarations`。同一物理目标需要切换 format 时，必须先完成旧
Surface 的安全清理。

Consumer、generation、phase、conditions、ownership、fingerprint 和 Source 信息不
保存在该表，分别由后续 Consumer、Status、Managed 和 Source 表负责。

## 06. `effect_surface_consumers` — Surface Consumer 声明

保存 Surface 与运行时 Consumer 的当前声明关系，以及修改 Surface 前必须使用的协调
策略。Consumer 是读取 Surface 物化结果，并可能在 mutation 前后需要暂停、关闭或恢复
的运行时组件；它不是 Session、用户或 Source。

```sql
CREATE TABLE effect_surface_consumers (
    surface_id        TEXT NOT NULL
                      REFERENCES effect_surfaces(id) ON DELETE CASCADE,
    consumer_id       TEXT NOT NULL, -- globally unique runtime/plugin identity
    coordination_kind TEXT NOT NULL, -- uninterrupted | wait_for_idle_and_restart
    created_at        INTEGER NOT NULL,
    updated_at        INTEGER NOT NULL,
    PRIMARY KEY (surface_id, consumer_id),
    CHECK (updated_at >= created_at)
);
```

该表是关联关系，不创建额外 UUID。`consumer_id` 使用全局稳定的 runtime/plugin identity，
例如 Plugin ID；复合主键保证一个 Consumer 对同一 Surface 只有
一条声明，并可作为后续 Consumer status 的父键。

第一版协调策略为 `uninterrupted` 和 `wait_for_idle_and_restart`。Surface 的有效协调策略
不落库，而是从所有当前 Consumer 声明中选择最严格者；只要一个 Consumer 要求等待空闲
并重启，整个 Surface mutation 就必须采用该策略。

Consumer 暂时启动或恢复失败时保留声明，由 Consumer status 记录失败。Consumer 永久
撤销声明时删除关联行；删除最后一个 Consumer 后，Surface 进入 `retiring`，不能立即
删除。待 Managed items 安全清理完成后才删除 Surface，残留关联行随 Surface cascade
删除。

Retiring 过程中相同 Consumer/Surface 声明重新出现时，若尚无 Prepared 文件操作，可以
重新激活原 Surface；若已有 Prepared operation，必须先完成恢复，再根据最新声明决定
是否重新激活。

该表不重复保存 locator、format、effect kind、ready generation、phase、conditions 或
Session 列表；这些信息分别属于 Surface、Consumer status 或运行时协调器。

## 07. `workspace_effect_desired_items` — Workspace Desired Effect 集合

保存用户在 Workspace 中持续选择的 Effect Source，以及该选择在当前 Workspace
generation 要求的确切 Revision。

```sql
CREATE TABLE workspace_effect_desired_items (
    id           TEXT PRIMARY KEY, -- UUID
    workspace_id TEXT NOT NULL
                 REFERENCES workspace_effects(workspace_id) ON DELETE CASCADE,
    source_id    TEXT NOT NULL REFERENCES effect_sources(id),
    revision_id  TEXT NOT NULL,
    created_at   INTEGER NOT NULL,
    updated_at   INTEGER NOT NULL,
    UNIQUE (workspace_id, source_id),
    FOREIGN KEY (source_id, revision_id)
        REFERENCES effect_source_revisions(source_id, id),
    CHECK (updated_at >= created_at)
);

CREATE INDEX workspace_effect_desired_items_source_workspace
    ON workspace_effect_desired_items(source_id, workspace_id);
```

`id` 是一次持续用户选择的 Desired item UUID。Source Head 从一个 Revision 推进到另一
Revision 时，更新 `revision_id` 并保留 Desired item UUID；用户删除该 Source 后重新
添加，或替换为另一个 Source 时，创建新的 Desired item UUID。

`source_id` 表示用户持续选择了什么，`revision_id` 表示当前 Workspace generation
要求的确切状态。复合外键保证 Revision 属于该 Source；
`UNIQUE (workspace_id, source_id)` 保证一个 Workspace 不能重复选择同一个 Source。
Desired 必须持久化 `revision_id`，不能在读取时动态跟随 Source Head，否则 Head 更新会
在不推进 Workspace generation 的情况下改变 Desired 内容。

Source propagation 读取最新 Head，查找仍指向旧 Revision 的 Desired items，并按
Workspace 执行 generation CAS。在同一事务中更新 `revision_id`、保留 Desired item
UUID、推进 Workspace generation，并创建或合并 reconcile requests。

`workspace_effect_desired_items_source_workspace` 支持 propagation 按 Source 查找并按
Workspace 稳定分批处理 Desired items，也支持 Source 引用查询和删除保护。已有
`UNIQUE (workspace_id, source_id)` 的列顺序不能高效服务以 `source_id` 为首要条件的查询。

该表不重复保存 Effect kind、SourceKey、revision、digest、payload、Workspace
generation、Surface locator 或 applied 状态。若未来某类 Effect 需要 Workspace 专属
参数，增加该 Effect 类型的 Desired 扩展表，不向所有 Desired items 添加含义不明确的
通用 JSON。

## 08. `effect_managed_items` — Managed Effect ownership ledger

保存每个 Surface 的 ownership ledger，记录 Ora 当前拥有的目标、该目标已应用的 Source
Revision，以及最后一次确认的内容 fingerprint。Managed item 在对应 Desired item 删除
后仍然存在，直到安全清理完成。

```sql
CREATE TABLE effect_managed_items (
    id                  TEXT PRIMARY KEY, -- ManagedIdentity UUID
    surface_id          TEXT NOT NULL REFERENCES effect_surfaces(id),
    source_id           TEXT NOT NULL REFERENCES effect_sources(id),
    applied_revision_id TEXT NOT NULL,
    target_key          TEXT NOT NULL,    -- canonical target identity within surface
    target_json         TEXT NOT NULL,    -- immutable adapter-owned target descriptor
    applied_fingerprint TEXT NOT NULL,    -- excludes ownership marker and platform noise
    applied_generation  INTEGER NOT NULL,
    created_at          INTEGER NOT NULL,
    updated_at          INTEGER NOT NULL,
    UNIQUE (surface_id, source_id),
    UNIQUE (surface_id, target_key),
    FOREIGN KEY (source_id, applied_revision_id)
        REFERENCES effect_source_revisions(source_id, id),
    CHECK (applied_generation >= 0),
    CHECK (updated_at >= created_at)
);
```

`id` 是 ManagedIdentity，必须写入目标侧 ownership marker，并与数据库 ledger 双向
匹配。只有 marker UUID 等于 Managed item UUID 且当前 fingerprint 等于
`applied_fingerprint` 时，Effect 才能覆盖或删除目标；任一不匹配都报告冲突。

`target_key` 是 adapter 规范化后的 Surface 内目标身份，用于 collision 和唯一约束；
`target_json` 保存扫描、物化、更新、删除和恢复所需的目标描述。数据库不统一为
`target_key` 使用 `NOCASE`，具体大小写规则由 adapter 在生成 canonical key 时处理。
`target_key` 和 `target_json` 创建后不可修改；目标改变时清理旧 Managed item，并为新
目标创建新的 ManagedIdentity。

`UNIQUE (surface_id, source_id)` 保证同一个 Source 在一个 Surface 中只有一个
ownership unit；`UNIQUE (surface_id, target_key)` 保证一个物理目标只能由一个 Managed
item 拥有。复合外键保证 `applied_revision_id` 属于记录的 Source。

Managed item 不引用 Desired item UUID，因为 Desired row 删除后 ledger 必须继续存在。
Reconciler 使用 `source_id` 与当前 Desired 集合匹配：同一 Source 更新 Revision 时保留
ManagedIdentity，并原子更新目标内容、`applied_revision_id`、fingerprint 和 applied
generation；替换为另一 Source、清理完成后重新添加，或改变目标时使用新的
ManagedIdentity。

`applied_fingerprint` 覆盖 adapter 认定的完整 owned resource，但排除 ownership marker
和无业务意义的平台元数据。若某种 Surface format 无法在目标侧保存并恢复
ManagedIdentity，它不能提供安全的 Managed adapter，已有内容只能作为 Preserved。

Managed item 的父表外键不使用 delete cascade。Surface 在 Managed items 清理完成前
不能删除，Source 和 Revision 在仍被 ledger 引用时也不能删除，防止任何父记录在
Managed 目标尚未安全清理时，通过级联删除移除 ownership ledger。

Desired item 可以 cascade 删除，因为 Managed ledger 不依赖 Desired row；Surface
Consumer 也可以 cascade 删除，因为它只是声明关系，不是 ownership 证据。

## 09. `effect_surface_status` — Surface 收敛状态

保存每个 Surface 对 Workspace Desired generation 的当前收敛水位和生命周期阶段。每个
Surface 恰好有一条 status；创建 Surface 时必须在同一事务中创建初始 status，避免“尚无
状态记录”和“尚未开始收敛”成为两种等价状态。

```sql
CREATE TABLE effect_surface_status (
    surface_id          TEXT PRIMARY KEY
                        REFERENCES effect_surfaces(id) ON DELETE CASCADE,
    desired_generation  INTEGER NOT NULL DEFAULT 0,
    observed_generation INTEGER NOT NULL DEFAULT 0,
    applied_generation  INTEGER NOT NULL DEFAULT 0,
    phase               TEXT NOT NULL, -- pending | reconciling | current |
                                       -- retiring | recovery_required
    status_version      INTEGER NOT NULL DEFAULT 1,
    created_at          INTEGER NOT NULL,
    updated_at          INTEGER NOT NULL,
    CHECK (desired_generation >= 0),
    CHECK (observed_generation >= 0),
    CHECK (applied_generation >= 0),
    CHECK (applied_generation <= observed_generation),
    CHECK (observed_generation <= desired_generation),
    CHECK (status_version > 0),
    CHECK (updated_at >= created_at)
);
```

三个 generation 是单调不减的收敛水位，含义不同：

- `desired_generation` 是该 Surface 已被要求评估到的 Workspace generation。Workspace
  Desired 集合推进时，即使变化最终与该 Surface 无关，也应通知 Surface 评估新的完整
  generation；
- `observed_generation` 表示 adapter 已对该 generation 完成实时扫描，并完成 Desired、
  Managed ledger 与 Observed targets 的比较。它只保存扫描完成的水位，不持久化 Observed
  snapshot；扫描失败时不得推进；
- `applied_generation` 表示整个 Surface 已被最终扫描确认与该 generation 的 Desired
  投影一致。没有 mutation 的 no-op generation 也可以推进；只完成部分安全 mutation、
  存在冲突，或最终扫描失败时不得推进。

因此 `applied_generation <= observed_generation <= desired_generation` 始终成立。Managed
item 各自的 `applied_generation` 记录单个 ownership unit 最后应用的 generation；本表的
`applied_generation` 是整个 Surface 的一致性水位，不能通过取 Managed items 的最大值或
最小值推导。

`phase` 只描述 Surface 的控制状态，不同时承担健康等级、Consumer 协调步骤或 worker
lease：

- `pending`：Surface 已创建，但尚未完成第一次收敛尝试；
- `reconciling`：Surface 对某个 Desired generation 仍负有未完成的收敛义务。它可以正在
  执行、等待 durable retry，或被一个可重试 Condition 阻塞；是否存在正在运行的 worker
  不由 status 表表达；
- `current`：`desired_generation`、`observed_generation` 和 `applied_generation` 相等，且
  没有阻止 Surface 收敛的当前 Condition；
- `retiring`：最后一个 Consumer 已撤销声明，Surface 正在安全清理其 Managed items 和
  Operations。进入此阶段后 generation 水位冻结在最后一次确认的 Workspace generation，
  退休清理进度不伪装成新的 Desired generation；
- `recovery_required`：外部目标既不匹配 operation 的 previous state，也不匹配 planned
  state，自动 mutation 已停止，必须通过显式恢复决策重新建立可信状态。

`degraded` 不作为持久化 phase。它是展示层从仍存在的 Surface/Consumer Conditions 派生
出的健康状态；Condition 保存稳定 reason，并由领域映射得到 retry policy，同时保留
Surface 实际所处的 phase。`waiting_for_idle`、`quiescing` 和 `resuming` 也不是 Surface
phase：等待原因属于 Condition，逐 Consumer 的协调进度属于 `effect_consumer_status`，
mutation 的崩溃恢复边界属于 `effect_operations`。

Surface materialization 与 Consumer readiness 分开。目标已通过最终扫描时，Surface 可以
推进 `applied_generation` 并进入 `current`；某个 Consumer 随后恢复失败时，只阻止该
Consumer 的 `ready_generation`，不能回退 Surface 的 applied 水位。多个 Consumer 协调时
必须分别持久化进度，例如 Consumer A 已 quiesce、Consumer B 尚未 idle，不能只保存一个
聚合的 Surface 等待状态。

`status_version` 是 status watch 和并发更新使用的单调版本，不是 Source Revision。任何
phase 或 generation 水位变化，以及任何 Surface-scoped Condition 的新增、更新或解除，
都必须在同一数据库事务中推进 `status_version` 和 `updated_at`。仅重复写入完全相同的
规范化状态是 no-op，不推进版本。

Desired replace 或 Source propagation 推进 Workspace generation 时，应在创建或合并
reconcile request 的同一事务中推进相关活动 Surface 的 `desired_generation` 和
`status_version`。Reconciler 完成扫描或应用后，以 status version CAS 写入新的水位，防止
较旧 worker 覆盖更新的 Desired 通知；CAS 失败时重新读取当前状态并保留 durable request。

该表只保存当前收敛事实，不保存 Conditions、Observed snapshot、worker lease、重试退避、
Operation 恢复 payload 或历史事件。它们分别属于 `effect_conditions`、实时 adapter 扫描、
durable request、`effect_operations` 和 Audit。

`ON DELETE CASCADE` 只清理已经失去主体的 status，不是 ownership 清理机制。Surface 必须
先完成 Operations 和 Managed items 的安全处理才能删除；满足该前置条件后，级联删除
status 不会丢失 ownership 证据。

## 10. `effect_consumer_status` — Consumer 就绪状态

保存共享 Surface 上每个 Consumer 的当前协调状态，以及该 Consumer 最后成功确认可消费的
Surface generation。Consumer readiness 可以独立落后于 Surface materialization，也可以
在兄弟 Consumer 之间不同步；它不是 Surface status 的聚合字段。

```sql
CREATE TABLE effect_consumer_status (
    surface_id       TEXT NOT NULL,
    consumer_id      TEXT NOT NULL,
    ready_generation INTEGER NOT NULL DEFAULT 0,
    phase            TEXT NOT NULL, -- pending | quiescing | quiesced |
                                    -- resuming | ready
    status_version   INTEGER NOT NULL DEFAULT 1,
    created_at       INTEGER NOT NULL,
    updated_at       INTEGER NOT NULL,
    PRIMARY KEY (surface_id, consumer_id),
    FOREIGN KEY (surface_id, consumer_id)
        REFERENCES effect_surface_consumers(surface_id, consumer_id)
        ON DELETE CASCADE,
    CHECK (ready_generation >= 0),
    CHECK (status_version > 0),
    CHECK (updated_at >= created_at)
);
```

Consumer 声明与初始 status 必须在同一数据库事务中创建。复合主键与父表声明保持相同
身份，不再创建等价 UUID；初始 phase 是 `pending`，初始 `ready_generation` 是 0。

`ready_generation` 表示协调器最后一次确认该 Consumer 可以安全消费的 Surface
`applied_generation`。它不是 Workspace Desired generation，也不是 Consumer 正在处理的
业务 generation。始终满足：

```text
consumer.ready_generation <= surface.applied_generation
```

这是跨表约束，由 repository 在同一事务中验证。`ready_generation` 单调不减：quiesce、
mutation 尚未结束或 resume 失败时保留原值；resume 成功后推进到 Surface 当前
`applied_generation`。Consumer 可以跳过从未实际消费的中间 generation，例如从 G1 直接
ready 到 G4；失败时不得把已有水位重置为 0。

`phase` 使用独立于 Surface 的 Consumer 协调状态机：

- `pending`：Consumer 声明已创建，但尚未完成第一次 readiness 确认；
- `quiescing`：已持久化暂停意图，但尚未确认 Consumer 到达安全 mutation boundary；
- `quiesced`：已确认 Consumer 不再以需要协调的方式访问 Surface，可以安全执行 mutation；
- `resuming`：Surface 已稳定，已持久化恢复意图，但尚未确认 Consumer 成功恢复；
- `ready`：没有未完成的协调动作，Consumer 已确认可以消费 `ready_generation` 对应的
  Surface 内容。

典型状态转换为：

```text
pending ──→ resuming ──→ ready
ready ──→ quiescing ──→ quiesced ──→ resuming
```

`quiescing` 和 `resuming` 是跨数据库与 runtime coordinator 调用的 durable intent。协调器
必须支持查询实时状态或幂等重试；调用协议为先持久化 intent phase，再执行外部调用，最后
持久化确认后的 phase。若进程在外部调用成功后、数据库确认前崩溃，重启后可以根据 intent
安全查询或重试，而不会把可能已经 quiesced 的 Consumer 错误报告为 `ready`。

不保存单独的 target generation。一个 Surface 严格串行协调与 mutation，resume 应始终
面向该 Surface 最新的 `applied_generation`；因此长期 quiesced 的 Consumer 可以直接恢复
到最新稳定内容，不必逐个经过中间 generation。

失败不写成含义模糊的 `degraded` phase，而是保留实际协调位置并写入 Consumer-scoped
Condition：

- 等待 idle 或 quiesce 调用失败时保持 `quiescing`，Condition 记录稳定 reason 和 retry
  policy；
- resume 失败且无法确认最终 runtime 状态时保持 `resuming`；
- resume 失败但协调器能确认 Consumer 仍安全暂停时回到 `quiesced`；
- 成功重试后删除对应 Condition，再进入下一个 phase。

展示层可以从 phase、`ready_generation`、Surface `applied_generation` 和当前 Conditions
派生 ready、lagging 或 degraded 等健康状态，不再持久化第二套健康枚举。

多个 Consumer 必须独立持久化协调进度。若 Consumer A 已经 quiesced，而 Consumer B 尚未
idle，A 保持 `quiesced`，B 保持带 `WaitingForIdle` Condition 的 `quiescing`，Surface 保持
`reconciling` 且不能开始 mutation。进程崩溃后不能丢失 A 需要恢复的事实。Surface 最终扫描
确认 G2 后可以推进 applied 水位；随后 A resume 失败只阻止 A 的 ready 水位，不能阻止 B
ready G2，也不能回退 Surface applied G2。

`status_version` 是 Consumer status watch 和 CAS 使用的单调版本，不是 Source Revision。
phase、`ready_generation` 或任何 Consumer-scoped Condition 的新增、更新和解除，都必须在
同一数据库事务中推进 `status_version` 与 `updated_at`；重复写入完全相同的规范化状态是
no-op。CAS 失败时协调器必须重新读取 Consumer 和 Surface 当前状态，不能用旧结果覆盖新
一轮协调。

该表不保存 Session 列表、runtime process identity、Surface locator、协调策略、Conditions
内容或历史事件。实时 Session/process 状态由 coordinator 查询，策略由
`effect_surface_consumers` 声明，其他事实分别属于 Surface、Conditions 和 Audit。

永久删除 Consumer 声明时可以 cascade 删除 status，因为二者属于同一声明生命周期；但
删除前必须确认 Consumer 已永久停止或不再需要恢复。不能通过删除声明来遗忘一个仍处于
`quiesced` 或 `resuming` 的 Consumer。Surface 删除时的级联只发生在 Managed items 与
Operations 已安全结束之后。

## 11. `effect_conditions` — Effect 条件与阻塞原因

保存 Surface 和 Consumer 当前尚未解除的结构化条件。Condition 解释一个 status 为什么
仍在收敛、等待协调或需要恢复；它不是错误日志，也不承担历史回放。条件被证明解除后从
当前表删除，其出现、变化和解除历史由 Audit 记录。

```sql
CREATE TABLE effect_conditions (
    id                TEXT PRIMARY KEY, -- UUID
    surface_id        TEXT NOT NULL
                      REFERENCES effect_surface_status(surface_id)
                      ON DELETE CASCADE,
    consumer_id       TEXT,             -- NULL = Surface-scoped
    subject_kind      TEXT NOT NULL,    -- desired_item | managed_item | surface |
                                        -- consumer | source_revision | operation
    subject_id        TEXT NOT NULL,
    reason            TEXT NOT NULL,
    failed_generation INTEGER,
    message           TEXT NOT NULL,
    first_observed_at INTEGER NOT NULL,
    last_observed_at  INTEGER NOT NULL,
    FOREIGN KEY (surface_id, consumer_id)
        REFERENCES effect_consumer_status(surface_id, consumer_id)
        ON DELETE CASCADE,
    CHECK (failed_generation IS NULL OR failed_generation >= 0),
    CHECK (last_observed_at >= first_observed_at)
);

CREATE UNIQUE INDEX effect_conditions_surface_unique
    ON effect_conditions (
        surface_id,
        subject_kind,
        subject_id,
        reason
    )
    WHERE consumer_id IS NULL;

CREATE UNIQUE INDEX effect_conditions_consumer_unique
    ON effect_conditions (
        surface_id,
        consumer_id,
        subject_kind,
        subject_id,
        reason
    )
    WHERE consumer_id IS NOT NULL;
```

Condition 的 scope 表示它改变哪个 status 的可观察状态和 `status_version`。scope 不再使用
`scope_kind/scope_id` 两个通用字符串，而由外键结构表达：

- `consumer_id IS NULL` 表示 Surface-scoped Condition；`surface_id` 必须引用真实存在的
  Surface status；
- `consumer_id IS NOT NULL` 表示 Consumer-scoped Condition；复合外键保证该 Consumer
  status 确实属于同一个 Surface。

SQLite 普通 `UNIQUE` 对包含 `NULL` 的键允许重复，因此分别使用两个 partial unique index
约束 Surface 和 Consumer scope。删除 Consumer status 只级联删除该 Consumer 的当前
Conditions；删除 Surface status 则删除整个 Surface 的当前 Conditions。

subject 表示导致阻塞或降级的具体对象，与 Condition 属于哪个 status 是两个独立概念。
`subject_kind/subject_id` 保持通用键，第一版支持：

- `desired_item`：`workspace_effect_desired_items.id`；
- `managed_item`：`effect_managed_items.id`，即 ManagedIdentity；
- `surface`：`effect_surfaces.id`；
- `consumer`：全局稳定的 Consumer identity；
- `source_revision`：`effect_source_revisions.id`；
- `operation`：`effect_operations.id`。

subject 不建立多态数据库外键。为每种 subject 增加 nullable 外键列或拆分多张 Condition
扩展表会扩大 schema，却仍需要 repository 理解跨 Surface 和 Workspace 的业务一致性。
repository 写入时必须校验：Desired item 属于 Surface 对应 Workspace；Managed item 和
Operation 属于该 Surface；Surface subject 等于 scope Surface；Consumer 是该 Surface 的
有效声明；Source Revision 被相关 Desired 或 Managed item 引用。未来新增 subject kind 时
必须同时增加领域类型和相应校验，不能把任意字符串直接写入数据库。

Condition 的逻辑身份是：

```text
scope + subject_kind + subject_id + reason
```

`id` 是这一段连续 Condition 生命周期的 UUID。同一条件再次被观察到时执行 upsert：保留
`id` 和 `first_observed_at`，更新 `last_observed_at`、`failed_generation` 以及安全的
`message`。条件被证明解除后删除；以后再次出现时创建新的 UUID 和新的
`first_observed_at`。多个底层现象若具有相同 scope、subject 和 reason，应聚合为同一个
Condition，而不是依赖 message 区分身份。

Condition 只有在获得足够的新证据后才能删除。一次扫描失败不能证明此前的 ownership、
drift 或 Preserved conflict 已经解除；此时保留尚未重新验证的 Conditions，并新增或更新
`ScanFailed`。完整扫描和比较成功后，Reconciler 才能在同一事务中删除已不再成立的条件。

`failed_generation` 表示该 Condition 最近在哪个 generation 被确认，可以为 `NULL`：

- Desired 或 Managed 冲突记录被阻塞的 Workspace Desired generation；
- Consumer resume 失败记录试图恢复到的 Surface applied generation；
- Operation recovery 问题记录对应 Operation generation；
- 与 generation 无直接关系的声明或生命周期条件使用 `NULL`。

它不是重试次数、status 水位或 Condition identity 的组成部分。同一 Condition 在新的
generation 继续成立时保留 UUID，并更新 `failed_generation`。

`retry_policy` 不持久化。领域层从稳定 `reason` 唯一派生：

```text
RetryPolicy = on_change | backoff | manual
```

例如 transient I/O 和 Consumer resume failure 使用 `backoff`，Preserved/ownership conflict
使用 `on_change`，无法自动判定的 recovery requirement 使用 `manual`。同时持久化 reason
和 retry policy 会允许互相矛盾的组合；API 可以返回派生值，但调用方不得自行解析
`message`。退避的 attempt count 和 `not_before_at` 属于 reconcile request，不属于
Condition。

Condition 与对应 status 的可观察版本必须原子更新：Surface-scoped Condition 的新增、
内容变化或解除，与 Surface `status_version` 在同一事务提交；Consumer-scoped Condition
则与该 Consumer `status_version` 在同一事务提交。完全相同的规范化结果是 no-op，不推进
版本。CAS 失败时重新读取当前 status 和 Conditions，不能用旧快照覆盖较新的结果。

`message` 只保存安全的人类可读摘要，不得包含 secret、敏感绝对路径、制品原文或完整
error chain。稳定程序行为只依赖 reason、派生 RetryPolicy、subject 和 generation；详细
诊断使用结构化日志。该表不保存 retry schedule、Observed snapshot 或历史事件。

## 12. `effect_reconcile_requests` — Surface Reconcile 请求

持久化“一个 Surface 至少还需要执行一次 reconcile”的事实，并把连续唤醒合并为每个
Surface 一条 request。该表是 durable wakeup，不是任务历史、Condition、worker lease 或
mutation journal；request 存在只表示调度器未来仍应尝试一次。

```sql
CREATE TABLE effect_reconcile_requests (
    surface_id           TEXT PRIMARY KEY
                         REFERENCES effect_surfaces(id) ON DELETE CASCADE,
    requested_generation INTEGER NOT NULL,
    request_token        TEXT NOT NULL, -- UUID; replaced on every wake/reschedule
    attempt_count        INTEGER NOT NULL DEFAULT 0,
    requested_at         INTEGER NOT NULL,
    not_before_at        INTEGER NOT NULL,
    updated_at           INTEGER NOT NULL,
    CHECK (requested_generation >= 0),
    CHECK (attempt_count >= 0),
    CHECK (not_before_at >= requested_at),
    CHECK (updated_at >= requested_at)
);

CREATE INDEX effect_reconcile_requests_due
    ON effect_reconcile_requests(not_before_at, requested_at, surface_id);
```

`surface_id` 同时是主键和 Surface 外键，保证每个 Surface 最多有一个待处理 request。
Desired、Surface descriptor、filesystem watcher、Consumer 状态变化和显式 retry 都可以
创建或合并 request；连续 G1 → G2 → G3 与多个同 generation watcher events 不需要逐事件
处理，只需要可靠保证至少再运行一次。

`requested_generation` 是唤醒时已知的最高 Workspace Desired generation。合并时取已有值
与 incoming generation 的最大值，但它只是调度提示，不是 reconcile 的权威输入。worker
取得执行权后必须重新读取 Surface、status、Workspace Desired、Managed ledger 和实时
Observed targets，不能仅凭 request payload 执行旧计划。

`request_token` 是每次 request 发生可观察变化时重新生成的随机 UUID，也是完成或重排请求
的 CAS token。它不使用递增 `request_revision`：request 不需要对外 watch 或排序，而随机
token 可以同时防止处理期间的新唤醒被旧 worker 删除，以及 row 删除后重新创建产生的 ABA
问题。

worker 读取 token 快照后，只有以下 CAS delete 成功才表示消费了该次 wakeup：

```sql
DELETE FROM effect_reconcile_requests
WHERE surface_id = ?
  AND request_token = ?;
```

同 generation 的 watcher 唤醒也必须生成新 token。若唤醒发生在 worker 处理期间，旧
worker 的 delete 或 backoff update 因 token 不匹配而失败，新请求将继续保留。

外部事实变化或显式请求的典型合并结果为：

```text
requested_generation = max(existing, incoming)
request_token        = fresh UUID
requested_at         = now
not_before_at        = now
updated_at           = now
```

是否重置 `attempt_count` 由 repository API 的强类型 wakeup kind 决定，而不持久化一个仅供
日志展示的 cause：Desired 或 Surface lifecycle 变化、能够证明外部事实变化的 watcher、
以及用户显式 retry 重置 backoff；纯重复通知可以保留 backoff；worker 自身的 backoff
reschedule 增加 attempt。最终调度行为已经完整体现在 `attempt_count` 和
`not_before_at` 中。

一次 reconcile 尝试完成后的 request 处理取决于结果：

- Surface 已收敛：使用 token CAS delete；
- 遇到 `on_change` Condition：CAS delete，等待相关 watcher 或 Desired/Source/Consumer
  变化产生新 request；
- 遇到 `manual` Condition：CAS delete，等待显式恢复动作或 retry；
- 遇到 `backoff` Condition：以旧 token 为 CAS 条件增加 `attempt_count`、计算新的
  `not_before_at`、生成新 token，并更新 `updated_at`。

Condition 表示为什么没有收敛，request 表示是否已安排再次尝试。不能因为 Condition 尚未
解除就永久保留一个立即到期的 request，否则 `on_change` 和 `manual` 条件会形成热循环。
若 backoff reschedule 的 CAS 失败，说明期间已有更新的 wakeup；旧 worker 不得覆盖新请求
已选择的 generation、attempt 或执行时间。

`attempt_count` 是当前 request episode 中，自最近一次有效外部唤醒重置后连续发生的
backoff 失败次数。它不是 Surface 的总 reconcile 次数，也不是审计统计。成功、
`on_change`/`manual` 阻塞后 request 被删除；以后新建的 request 从 0 开始。

显式 retry 只重置 backoff 并要求重新扫描：它不修改 Desired、不推进 Workspace
generation，也不能绕过 ownership、drift、Preserved conflict 或把 `RecoveryRequired`
自动解释为安全恢复许可。需要改变不可信外部状态时，必须使用对应的显式恢复操作。

第一版是单进程调度，不在表中加入 lease、owner、heartbeat 或 running phase，但 worker
仍必须遵守以下协议：

1. scheduler 选择 `not_before_at <= now` 的 request；
2. 获取该 Surface 的严格串行执行权；
3. 获取执行权后重新读取 request，避免使用排队前的旧 token；
4. 重新读取全部权威事实，并优先安全完成已经 Prepared 的 Operation；
5. 原子更新 status 与 Conditions；
6. 使用 request token CAS delete 或 reschedule。

不同 Surface 可以并行，同一 Surface 不能并行 reconcile。未来若引入多进程 worker，必须
另行设计 lease；不能把 `request_token` 当作执行所有权。

Desired replace 或 Source propagation 推进 Workspace generation 时，必须在同一数据库
事务中更新 Desired rows、推进 `workspace_effects.generation`、推进相关活动 Surface 的
`desired_generation/status_version`，并创建或合并 reconcile request。这样不会出现新
Desired 已提交但 durable wakeup 丢失的状态。

Surface 进入 `retiring` 时，以其冻结的最后一个 `desired_generation` 创建 request。后续
Workspace generation 不再更新或唤醒该 Retiring Surface；filesystem watcher 和显式 retry
仍使用冻结 generation 唤醒清理流程。Surface 只有在 Managed items 与 Operations 安全结束
后才能删除，满足该前置条件后 cascade 删除剩余 request 不会丢失 ownership 或恢复证据。

时间字段分别表达：`requested_at` 是最近一次外部唤醒或显式重置当前 request episode 的
时间；`not_before_at` 是 scheduler 最早可再次选择该 row 的时间；`updated_at` 是包括
backoff reschedule 在内的最后一次 row 变化时间。due index 只用于有效选择，不提供公平性
或执行所有权保证。

## 13. `effect_propagation_requests` — Source 传播请求

持久化“一个 Source Head 已变化，仍可能有 Workspace Desired items 尚未传播到该 Head”
的事实，并把连续 Head 更新合并为每个 Source 一条 request。它是按 Source 调度的 durable
wakeup，不保存 Workspace 任务列表、处理 cursor 或传播历史。

```sql
CREATE TABLE effect_propagation_requests (
    source_id        TEXT PRIMARY KEY
                     REFERENCES effect_sources(id) ON DELETE CASCADE,
    head_revision_id TEXT NOT NULL,
    request_token    TEXT NOT NULL, -- UUID; replaced on every wake/reschedule
    attempt_count    INTEGER NOT NULL DEFAULT 0,
    requested_at     INTEGER NOT NULL,
    not_before_at    INTEGER NOT NULL,
    updated_at       INTEGER NOT NULL,
    FOREIGN KEY (source_id, head_revision_id)
        REFERENCES effect_source_revisions(source_id, id),
    CHECK (attempt_count >= 0),
    CHECK (not_before_at >= requested_at),
    CHECK (updated_at >= requested_at)
);

CREATE INDEX effect_propagation_requests_due
    ON effect_propagation_requests(not_before_at, requested_at, source_id);
```

`source_id` 同时是主键和 Source 外键，保证每个 Source 最多只有一个传播 wakeup。复合外键
保证 request 指向的 Revision 属于同一个 Source。`head_revision_id` 是触发当前 wakeup 的
Head 快照和诊断信息，不是传播权威；worker 每次执行时仍必须重新读取
`effect_source_heads`。

发布新 Revision 或显式切换 Head 时，插入或确认 Revision、更新 Source Head 和 upsert
propagation request 必须在同一数据库事务完成。连续 R1 → R2 → R3 直接合并为：

```text
head_revision_id = R3
request_token    = fresh UUID
attempt_count    = 0
requested_at     = now
not_before_at    = now
updated_at       = now
```

Revision 是不透明标识，不允许按字符串比较顺序；若 Head 从 R3 显式切回 R1，传播目标就是
R1。重复设置完全相同的 Head 是 Source write no-op，不创建新 request；用户显式 retry 或
启动一致性 sweep 可以为相同 Head 重新生成 wakeup。

`request_token` 与 reconcile request 使用相同的随机 UUID CAS 协议。worker 只有在完成
最终一致性检查后才能执行：

```sql
DELETE FROM effect_propagation_requests
WHERE source_id = ?
  AND request_token = ?;
```

处理期间 Head 再次变化时，Source write transaction 会替换 `head_revision_id` 和 token；
旧 worker 无法删除新 request，也不能用旧 backoff 状态覆盖新 Head。随机 token 同时避免
request 删除再创建造成的 ABA，不使用无排序需求的递增 `request_revision`。

worker 以 request 唤醒后，按 `workspace_effect_desired_items_source_workspace` 查找仍选择
该 Source 的 Workspace，并稳定分批处理。每个 Workspace 使用独立数据库事务，在事务内：

1. 重新读取当前 Source Head，并确认 request token 未被替换；
2. 重新读取该 Workspace 中仍选择此 Source 的 Desired item；
3. 若 `revision_id` 已等于 Head，按 no-op 结束；
4. 否则保留 Desired item UUID，只更新确切 `revision_id`；
5. 推进 `workspace_effects.generation`；
6. 推进所有相关活动 Surface 的 `desired_generation/status_version`；
7. 创建或合并对应 reconcile requests，然后提交。

如果用户已经删除或替换该 Source，Desired item 不存在，传播必须是 no-op，绝不能恢复用户
选择。传播和用户 Desired replace 都修改 Workspace generation，由 Workspace transaction
串行：传播先提交时，使用旧 expected generation 的用户写入得到 typed conflict；用户先
删除时，传播重新读取后跳过。Head 在 Workspace transaction 前变化时采用新 Head，在事务
提交后变化时由新 token 保证后续再次传播。

传播允许按 Workspace 部分成功并在崩溃后重跑。例如 Workspace A、B 已推进到 R3，C 仍是
R1；重启后 A、B 是 no-op，只继续处理 C。request 不保存处理 cursor，因为 Desired rows
自身就是持久化进度，批次查询可以直接排除已经等于当前 Head 的 rows。

完成批次后，worker 必须在一个最终数据库事务中重新确认：request token 未变化；request
的 `head_revision_id` 仍等于当前 Source Head；不存在仍选择该 Source、但 Revision 不等于
当前 Head 的 Desired item。三个条件全部成立后才能 CAS delete。任一不成立都保留 request
或让新 token 对应的 worker 接手。

若单个 Workspace 因暂时性数据库错误或 generation 竞争失败，worker 可以继续处理其他
Workspace，并在仍有未完成项时以旧 token CAS reschedule：增加 `attempt_count`、计算新的
`not_before_at`、生成新 token，并更新 `updated_at`。CAS 失败说明期间已有更新的 Head 或
显式 wakeup，旧 worker 不得覆盖它。

`attempt_count` 是当前 Head request episode 中，自最近一次 Head 变化、显式 retry 或一致性
sweep 重置后连续发生的 backoff 失败次数，不是总传播次数。Source propagation 通常只有
durable backoff：它是全局后台工作，没有可挂载的 Surface/Consumer Condition。错误写入
安全日志，长期积压可以由后台任务监控或 Audit 表达。

Head Revision 暂时 `unavailable` 不阻止 Desired identity 传播。propagation 只推进确切
Revision 引用，不读取或物化 artifact；后续各 Surface reconcile 会针对无法读取的制品产生
`SourceUnavailable` Condition。制品完整性问题在 Revision 发布边界处理，不能通过跳过
传播让部分 Workspace 永久停留在旧 Head。

不同 Source 的 propagation 可以并行，同一 Source 严格串行。两个 Source 分别更新同一
Workspace 时，可以顺序产生两个 Workspace generations；每一次都对应规范化 Desired 集合
的一次实际变化，不要求跨 Source 合并。第一版不在 request 表中加入 lease 或 owner，未来
多进程 worker 需要另行设计执行所有权，不能把 `request_token` 当作 lease。

`retired` Source 不接受新的 Desired 引用，但已有 Desired items 继续保持选择，并可以完成
最后一次 Head 传播。Retirement 本身不表示从 Workspace Desired 中删除 Source。正常生命
周期长期保留 retired Source；若未来支持显式物理删除，必须先确认不存在 Head、Desired、
Managed 和 Revision 引用。满足这些前置条件后 cascade 删除遗留 propagation request 是
安全的。

时间字段与 reconcile request 相同：`requested_at` 是最近一次 Head 变化或显式重置当前
request episode 的时间；`not_before_at` 是 scheduler 最早可再次选择该 row 的时间；
`updated_at` 是包括 backoff reschedule 在内的最后一次 row 变化时间。due index 只用于
调度选择，不表示公平性或执行所有权。

## 14. `effect_operations` — 跨数据库与外部目标 mutation journal

记录一个 Managed target 跨越 SQLite 与外部目标的 durable mutation journal，使进程在
任意边界崩溃后都能仅依据持久化 intent、实时目标状态和 ownership ledger，决定安全重试、
Finalize 或停止自动操作。Operation 只用于确实需要 adapter 外部 mutation 的 target；纯
数据库状态推进不创建 Operation。

```sql
CREATE TABLE effect_operations (
    id              TEXT PRIMARY KEY, -- UUID
    surface_id      TEXT NOT NULL REFERENCES effect_surfaces(id),
    generation      INTEGER NOT NULL,
    target_key      TEXT NOT NULL,
    operation_kind  TEXT NOT NULL, -- create | update | replace | delete
    phase           TEXT NOT NULL, -- prepared | applied | finalized
    payload_version INTEGER NOT NULL,
    payload_json    TEXT NOT NULL, -- immutable adapter-owned recovery plan
    prepared_at     INTEGER NOT NULL,
    applied_at      INTEGER,
    finalized_at    INTEGER,
    updated_at      INTEGER NOT NULL,
    CHECK (generation >= 0),
    CHECK (payload_version > 0),
    CHECK (applied_at IS NULL OR applied_at >= prepared_at),
    CHECK (
        finalized_at IS NULL
        OR (applied_at IS NOT NULL AND finalized_at >= applied_at)
    ),
    CHECK (updated_at >= prepared_at),
    CHECK (applied_at IS NULL OR updated_at >= applied_at),
    CHECK (finalized_at IS NULL OR updated_at >= finalized_at)
);

CREATE UNIQUE INDEX effect_operations_active_target_unique
    ON effect_operations(surface_id, target_key)
    WHERE phase <> 'finalized';

CREATE INDEX effect_operations_recovery
    ON effect_operations(surface_id, prepared_at, id)
    WHERE phase <> 'finalized';
```

`id` 是 Operation UUID。`surface_id/target_key` 标识本次 mutation 的准确目标；target key
使用与 Managed item 相同的 adapter canonical identity。partial unique index 保证一个
target 同时最多只有一个未 Finalized Operation，Surface worker 仍必须在应用层严格串行，
不能把唯一索引当作调度锁。

`generation` 是创建 Operation 时的 Workspace Desired generation。已经进入 Prepared 的
Operation 必须安全完成或进入 `RecoveryRequired`，不能因为 Workspace 出现更新 generation
就丢弃。旧 Operation 结束后重新读取最新 Desired 和实时 Surface，再为最新 generation
计划；旧 Operation Finalize 只提交自己的精确 ledger transition，不能顺便宣称 Surface 已
收敛到更新 generation。

四种 `operation_kind` 表达不同的目标和 ownership transition：

| Kind | Previous target | Planned target | Ledger transition |
|---|---|---|---|
| `create` | Missing | Present with new identity | Insert Managed item |
| `update` | Missing or Present X | Present X | Update existing Managed item |
| `replace` | Present X | Present Y | Delete X and insert Y atomically |
| `delete` | Present X | Missing | Delete Managed item |

`update` 保留 ManagedIdentity，可用于 Source Revision 更新，也可重建 ledger 仍存在但目标已
安全确认为 Missing 的资源。`replace` 表示 ownership lifecycle 改变，例如同一 target 从
Source A 改由 Source B 拥有，必须生成新的 ManagedIdentity。目标已是 Missing 时删除
ledger，以及只推进 Managed item `applied_generation`，都是纯数据库事务，不创建
Operation。

每个 Operation 的 previous target state 必须不同于 planned target state；否则没有跨外部
mutation 边界，不需要 journal。target state 不能只保存 fingerprint，必须同时验证 ownership
marker：

```text
TargetState =
  | Missing
  | Managed {
      managed_identity,
      fingerprint
    }
```

fingerprint 按 Managed item 约定排除 marker 和无业务意义的平台噪声，因此它不能独立证明
ownership。具有相同内容但错误 ManagedIdentity 的目标不等于 previous 或 planned state。
Preserved、marker 缺失或 marker 无法解析的目标也不属于合法 Operation state；Reconciler
必须在 Prepare 前将其报告为冲突，不能创建一个可能覆盖它的 Operation。

`phase` 只能按以下顺序前进，不能回退：

```text
prepared ──→ applied ──→ finalized
```

- `prepared`：完整且不可变的 mutation intent 已持久化，但不能断言外部目标已经改变；
- `applied`：adapter 已实时扫描并确认目标等于 planned state，但 ledger transition 尚未
  提交；
- `finalized`：ledger transition 和 phase 已在同一个 SQLite transaction 中提交。

Phase 更新使用 expected phase CAS。`applied` 只是 durable progress hint，不是永久可信的
外部事实；进程从 Applied 恢复时仍必须重新扫描 marker 和 fingerprint，不能仅凭 phase
Finalize。若恢复时目标已经等于 planned state，但数据库仍为 Prepared，应先记录 Applied
事实，再执行 Finalize，使时间和 phase 不变量保持一致。

Prepared 必须先于任何 adapter-owned 外部副作用，包括创建 staging 或 backup artifact。
安全协议为：

1. 扫描并验证目标状态与 ownership ledger；
2. 构建完整 mutation plan、artifact locators 和预期 fingerprint；
3. 在同一数据库事务插入 Operation 及其 artifact rows；
4. 创建或重建 staging，并在 mutation 前再次确认目标仍等于 previous state；
5. 执行 adapter mutation；
6. 实时扫描并验证目标等于 planned state；
7. CAS 推进到 `applied`；
8. 原子更新 ledger 并推进到 `finalized`；
9. 独立清理 recovery artifacts。

若先创建 artifact、后写 Operation，崩溃会留下没有 durable recovery authority 的外部资源。
Prepare 后、mutation 前再次验证 previous state，则防止初次扫描和实际 apply 之间的外部
修改被静默覆盖；adapter 还必须使用自身可提供的安全原子原语缩小检查与 mutation 之间的
竞态窗口。

每次初始执行和崩溃恢复都使用同一判断：

```text
current == previous → RetryApply
current == planned  → Finalize
otherwise           → RecoveryRequired
```

四类操作分别得到以下恢复边界：

- Create：Missing 时重试创建；新 identity 与新 fingerprint 同时匹配时 Finalize 插入 ledger；
  其他状态进入 RecoveryRequired；
- Update：journaled Missing 或旧 identity/fingerprint 匹配时重试；相同 identity 与新
  fingerprint 匹配时 Finalize ledger update；其他状态进入 RecoveryRequired；
- Replace：旧 identity/fingerprint 匹配时重试；新 identity/fingerprint 匹配时原子替换
  ledger；其他状态进入 RecoveryRequired；
- Delete：旧 identity/fingerprint 匹配时重试删除；Missing 时 Finalize ledger delete；其他
  状态进入 RecoveryRequired。

adapter 的 apply 必须可在精确 previous state 上安全重试。若 current 已是 planned state，
不得再次 mutation，只执行验证和 Finalize。判断既不能信任 watcher payload，也不能通过扫描
未知同名 staging/backup 资源猜测发生过什么。

`payload_json` 在 Prepared 后不可修改；phase 和时间只存普通列，不在 payload 内复制。
现有 v1 会把包含 phase 的完整 Operation JSON 随 phase 一起重写，v2 不保留这种双重状态。
payload 必须使用与 Surface adapter/format 一起解释的版本化 tagged enum，至少保存：

- exact previous/planned target state；
- previous/planned ManagedIdentity；
- exact expected ledger state 与 planned ledger transition；
- Source、Revision 和 materialization input references；
- adapter 执行及验证 mutation 所需的 target descriptor；
- artifact roles/IDs，以及重建或验证 staging 所需的不可变信息。

`payload_version` 选择 payload schema；读取未知版本时不得猜测，应停止自动 mutation 并要求
兼容的恢复程序。payload 不保存 secret 或大段制品原文，只保存不可变 reference、digest 和
恢复所需描述。repository 在 Prepare 时验证 JSON 与 `surface_id`、`target_key`、
`generation`、`operation_kind` 和 Surface adapter/format 一致。

Finalize 必须在一个 SQLite transaction 中完成：重新验证 Operation 仍处于预期 phase；
验证 ledger 仍等于 Prepared payload 中的 exact previous ledger state；执行
insert/update/replace/delete；将 Operation 更新为 `finalized`；追加必要 Audit event；最后
提交。ledger transition 必须使用 expected identity、Revision 和 fingerprint 做 CAS，不能
只按 ManagedIdentity 无条件 delete/upsert，否则旧 Operation 可能覆盖异常 ledger 状态。

当 current 既不等于 previous，也不等于 planned 时：保留未 Finalized Operation；Surface
进入 `recovery_required`；创建 subject 为 Operation UUID 的 `RecoveryRequired` Condition；
停止该 Surface 的后续自动 mutation；不删除或改写 target、backup、staging；等待显式恢复
决策。Condition 不应只笼统指向 Surface，因为 Operation 才是需要处置的具体对象。

`finalized` 表示业务状态已经提交，不表示 artifacts 已清理。Finalize 后可以释放 active
target unique constraint，并允许后续 Operation；artifact cleanup 可以独立重试，失败不能
回滚 ledger。Operation 只有在全部 artifacts 已清理或显式移交、相关 Condition 已解除且
Audit 已写入后才能删除。

该表不是长期历史表。完成 cleanup 后删除 Finalized row，业务历史由 Audit 保存。Surface
外键不 cascade；Surface 删除前必须先解决未完成 Operation，并清理 artifacts 后删除所有
Operation rows，避免通过删除父记录丢失恢复计划。

## 15. `effect_operation_artifacts` — Operation 受控恢复资源

保存 Operation 为安全 apply、崩溃恢复或补偿而拥有的临时外部资源。Artifact 可以是
filesystem staging directory、backup，也可以是未来 adapter 的 rollback snapshot 或
remote draft；它不是 Managed target，也不建立长期业务 ownership。因此表名使用
`artifacts`，不把 Effect Core 限制为 filesystem path。

```sql
CREATE TABLE effect_operation_artifacts (
    id                   TEXT PRIMARY KEY, -- UUID
    operation_id         TEXT NOT NULL REFERENCES effect_operations(id),
    artifact_role        TEXT NOT NULL, -- staging | backup | adapter-defined
    locator_kind         TEXT NOT NULL, -- filesystem_path | adapter-defined
    locator_key          TEXT NOT NULL,
    locator_json         TEXT NOT NULL,
    expected_fingerprint TEXT NOT NULL,
    state                TEXT NOT NULL, -- reserved | retained |
                                        -- pending_cleanup | cleanup_failed
    created_at           INTEGER NOT NULL,
    updated_at           INTEGER NOT NULL,
    UNIQUE (
        operation_id,
        artifact_role,
        locator_kind,
        locator_key
    ),
    UNIQUE (locator_kind, locator_key),
    CHECK (updated_at >= created_at)
);

CREATE INDEX effect_operation_artifacts_cleanup
    ON effect_operation_artifacts(state, updated_at, id)
    WHERE state IN ('pending_cleanup', 'cleanup_failed');
```

`id` 是 Artifact UUID；`operation_id` 指向唯一授权访问它的 Operation。`artifact_role`
描述资源在 mutation plan 中的用途，第一版 filesystem adapter 使用 `staging` 和 `backup`；
未来 adapter 可以增加领域类型明确支持的 role，不能把任意字符串直接写入数据库。

Artifact state 表示 durable authority 与外部资源的关系：

- `reserved`：精确 locator 和预期 fingerprint 已持久化，但尚未确认 artifact 存在；
- `retained`：adapter 已确认 artifact 存在且匹配 `expected_fingerprint`，Operation 仍可能
  需要它；
- `pending_cleanup`：Operation 已不再需要该 artifact，允许清理；
- `cleanup_failed`：对精确 locator 的清理失败，或无法安全确认当前资源仍是预期 artifact，
  等待 backoff retry 或显式处置。

典型状态流为：

```text
reserved ──→ retained ──→ pending_cleanup ──→ row deleted
    └───────────────────→ pending_cleanup
                              │
                              └──→ cleanup_failed
```

Artifact 从未创建时，`reserved` 可以直接进入 `pending_cleanup`，确认 locator 不存在后删除
row。`cleanup_failed` 不授权强制删除；后续重试仍必须重新执行 locator 和 fingerprint
验证。

Operation Prepare 必须先建立 durable authority，再创建外部资源：

1. 计算 immutable mutation plan；
2. 生成 Operation 与 Artifact UUID；
3. 计算 artifact locator 和预期 fingerprint；
4. 在同一 SQLite transaction 插入 Prepared Operation 与全部 `reserved` artifact rows；
5. 创建或重建 staging/backup；
6. 验证 artifact 后推进为 `retained`；
7. 执行 target mutation。

现有 v1 会先执行 `adapter.stage()`，再写入 Operation，而且 artifact paths 只嵌在 Operation
JSON 中；若进程在两者之间崩溃，会留下没有独立 durable authority 的 staging 资源。v2
不保留这个顺序，也不能通过启动时扫描同名前缀来补偿缺失的 journal。

`locator_kind/locator_key` 是 artifact 的全局物理资源身份，`locator_json` 是 adapter 实际
访问与安全验证所需的不可变 descriptor。全局唯一约束防止两个 Operation 同时声明同一个
artifact，否则旧 Operation 的 cleanup 可能删除新 Operation 的恢复资源。filesystem
descriptor 例如：

```json
{
  "operation_root": "...",
  "relative_path": "staging"
}
```

`operation_id`、`artifact_role`、`locator_kind`、`locator_key`、`locator_json` 和
`expected_fingerprint` 创建后不可修改。位置改变时，只能在确认旧 reservation 尚未物化后
删除旧 row，并创建新的 Artifact UUID；已存在或状态未知的 artifact 不能通过修改 locator
转移 durable authority。

Artifact fingerprint 与 Managed item fingerprint 的边界不同。Managed fingerprint 排除
ownership marker 和平台噪声；Artifact fingerprint 必须覆盖 adapter 判断“这是 journal 中
那个恢复资源”所需的完整状态。只有 locator 和 fingerprint 同时匹配时，Operation 才能
使用或删除 artifact。

`expected_fingerprint` 第一版保持 `NOT NULL`。无法在外部副作用前计算或可靠验证 artifact
fingerprint 的 adapter，应把恢复数据完整放入 immutable Operation payload，或设计可按
Operation identity 查询的幂等外部协议；不能以 nullable fingerprint 降低清理安全边界。

cleanup 只能访问 durable row 精确记录的 locator：

```text
load artifact row
→ resolve locator_json
→ validate adapter safety/containment
→ verify current fingerprint
→ delete exact resource
→ verify absence
→ delete artifact row
```

不得扫描目录或外部系统并批量删除类似 staging/backup 的资源，不得按名称前缀猜测
artifact，也不得清理数据库没有记录的“疑似 orphan”。没有 row 的资源属于未知外部内容，
默认保留并报告。locator 存在但 fingerprint 不匹配时，不得覆盖或删除：未 Finalized
Operation 进入 `RecoveryRequired`；已 Finalized Operation 保持 `cleanup_failed`，并以
Operation UUID 为 subject 记录需要显式处置的 Condition。

Filesystem artifacts 还必须满足：staging/backup 位于 adapter 明确保留的 Operation root；
需要原子 rename/swap 的资源与 target 位于同一文件系统；所有路径使用 `Path/PathBuf` 构造，
并通过 `ora-utils::path` 执行 containment、symlink/reparse 和规范化验证。即使 locator 来自
数据库，也必须重新完成安全验证，数据库内容不能代替 filesystem containment proof。

Artifact 与 Operation phase 的关系为：Prepared 时可以是 `reserved` 或 `retained`；
Applied 后继续保留恢复资源；Finalized transaction 提交后可以把全部 artifacts 推进为
`pending_cleanup`。Cleanup 失败不回滚 ledger、不回退 Operation phase，也不回退 Surface
applied generation；通过 reconcile request 的 durable backoff 继续重试。

Operation Finalized 后释放 active-target unique constraint，允许同一 Managed target 开始
后续业务 mutation。旧 artifacts 仍能独立安全清理，因为 locator 全局唯一、包含 Operation
identity，且 cleanup 只访问精确 row；新 Operation 不得复用仍由旧 row 声明的 locator。

外键不使用 `ON DELETE CASCADE`。Operation 只有在全部 artifact rows 已经安全删除或完成
显式 authority 移交后才能删除；Surface 又必须先删除 Operations。因此任何父实体删除都
不能绕过恢复资源的验证与清理。Artifact rows 是当前恢复事实，不是长期历史；清理历史由
Audit 保存。

## 16. `effect_audit_events` — Effect 审计事件

保存追加式、可裁剪的 Effect 业务历史，回答过去发生过哪些重要领域变化。Audit 不参与
reconcile、ownership 判断、Operation 恢复或当前状态推导，也不是完整的 event sourcing
log；删除历史事件不得改变系统当前行为。

```sql
CREATE TABLE effect_audit_events (
    id              TEXT PRIMARY KEY, -- UUID
    workspace_id    TEXT,             -- snapshot UUID
    surface_id      TEXT,             -- snapshot UUID
    source_id       TEXT,             -- snapshot UUID
    subject_kind    TEXT NOT NULL,    -- source | source_revision |
                                       -- workspace_effect | desired_item |
                                       -- surface | consumer | managed_item |
                                       -- condition | operation | artifact
    subject_id      TEXT NOT NULL,
    event_kind      TEXT NOT NULL,
    generation      INTEGER,
    initiator_kind  TEXT NOT NULL,    -- user | system | plugin
    initiator_id    TEXT,
    payload_version INTEGER NOT NULL,
    payload_json    TEXT NOT NULL,
    occurred_at     INTEGER NOT NULL,
    CHECK (generation IS NULL OR generation >= 0),
    CHECK (payload_version > 0)
);

CREATE INDEX effect_audit_events_workspace_time
    ON effect_audit_events(workspace_id, occurred_at, id)
    WHERE workspace_id IS NOT NULL;

CREATE INDEX effect_audit_events_surface_time
    ON effect_audit_events(surface_id, occurred_at, id)
    WHERE surface_id IS NOT NULL;

CREATE INDEX effect_audit_events_source_time
    ON effect_audit_events(source_id, occurred_at, id)
    WHERE source_id IS NOT NULL;

CREATE INDEX effect_audit_events_subject_time
    ON effect_audit_events(subject_kind, subject_id, occurred_at, id);

CREATE INDEX effect_audit_events_kind_time
    ON effect_audit_events(event_kind, occurred_at, id);

CREATE TRIGGER effect_audit_events_no_update
BEFORE UPDATE ON effect_audit_events
BEGIN
    SELECT RAISE(ABORT, 'effect audit events are append-only');
END;
```

`id` 是 Audit event UUID。`workspace_id`、`surface_id` 和 `source_id` 是事件发生时的查询
维度快照，不建立父表外键，使 Workspace、Surface、Source 及其子实体安全删除后仍能查询
历史。repository 在 append 时验证这些 UUID 与当时业务实体的关系，但事件提交后不再跟随
父实体变化。

三个 snapshot columns 与 primary subject 相互独立。例如 Source Revision 发布事件设置
`source_id`，subject 是 Revision；Desired propagation 同时设置 Workspace 和 Source，
subject 是 Desired item；Operation Finalized 可以同时设置 Workspace、Surface、Source，
subject 是 Operation。独立 `source_id` 使一个 Source 的 Revision、Desired propagation 和
Operation 历史可直接查询，不需要解析 payload 或假定它总是 primary subject。

`subject_kind/subject_id` 表示事件主要描述的对象。第一版支持 `source`、
`source_revision`、`workspace_effect`、`desired_item`、`surface`、`consumer`、
`managed_item`、`condition`、`operation` 和 `artifact`。subject 保存 snapshot identity，
因此 Condition、Managed item、Operation 或 Artifact 删除后仍可查询。其他相关 identity
放入顶层 snapshot columns 或 versioned payload，不增加任意数量的多态列。

`event_kind` 是稳定领域枚举，不是日志消息。第一版至少覆盖以下业务边界：

- Source：`source_created`、`source_revision_published`、`source_head_changed`、
  `source_retired`；
- Desired：`desired_replaced`、`desired_revision_propagated`；
- Surface/Consumer：`surface_created`、`surface_retiring`、`surface_deleted`、
  `consumer_declared`、`consumer_revoked`；
- Condition：`condition_raised`、`condition_changed`、`condition_resolved`；
- Operation：`operation_prepared`、`operation_applied`、`operation_finalized`、
  `operation_recovery_required`；
- Artifact：`artifact_cleanup_failed`、`artifact_cleaned`；
- 显式恢复：`recovery_decision_applied`。

Audit 不记录 watcher 每次唤醒、request 每次合并、每次 backoff attempt、无变化扫描、单纯
status version 增加，或 Condition 只有 `last_observed_at` 变化但语义没有改变的事件。此类
高频执行细节属于结构化日志；写入 Audit 会制造容量噪声，并模糊真正的业务历史。

Condition history 使用 Condition UUID 串联一个连续 episode：首次出现写
`condition_raised`；reason、message、failed generation 或其他语义字段改变时写
`condition_changed`；删除当前 row 前写 `condition_resolved`。Condition 解除后再次出现会
获得新 UUID，因此形成新的 history episode。仅刷新 `last_observed_at` 不产生 Audit event。

`initiator_kind/initiator_id` 回答谁发起了业务变化。用户 Desired replace 使用 `user`，
propagation/reconcile 和自动 recovery 使用 `system`，Plugin 声明或撤销 Consumer 使用
`plugin`。没有稳定 identity 时 `initiator_id` 可以为 `NULL`。initiator 是审计 attribution，
不是授权证明；写入端必须来自可信应用边界，不能直接持久化未经验证的客户端字符串。
watcher、retry 或 recovery 等更具体 cause 放入 payload，不扩展成相互重叠的 initiator
kinds。

`event_kind + payload_version` 唯一确定 `payload_json` schema。无额外数据的事件使用 `{}`；
payload 创建后不可修改。它可以保存 old/new Revision IDs、added/removed Desired item IDs、
old/new generation、Operation kind/phase、Condition reason、安全计数、digest 和 recovery
decision，但不得保存 secret、敏感绝对路径、制品原文、完整 error chain，或大规模复制
当前实体快照。

读取未知 `payload_version` 时仍应返回可查询的基本 envelope，并把 payload 作为 opaque
JSON；不得猜测未知字段。领域类型与 repository 写入边界限制 payload 大小并验证 event
kind/version/schema 组合。

`generation` 表示事件直接关联的 Workspace Desired generation：Desired replace 或
propagation 保存新 generation；Operation 保存其创建 generation；Surface status/Condition
保存被观察或阻塞的 generation；全局 Source 事件和与 Workspace generation 无关的 cleanup
使用 `NULL`。它不是 Audit 排序序号。

时间线按 `(occurred_at, id)` 稳定分页。UUID 只提供相同时间戳下的确定性顺序，不表达业务
因果；因果关系由 subject、generation、相关 identity 和 versioned payload 表达。Audit 不
用于重放，因此不要求创建一套全局 event sequence。

凡数据库业务状态发生变化，对应 Audit append 必须在同一个 SQLite transaction 提交，
包括 Source Head 更新、Desired replace/propagation、Condition upsert/delete、Operation
Finalize 与 ledger transition，以及 Surface 删除。删除事件在删除主体的事务中先构造并
插入，因为 commit 后父实体可能已不存在。

外部 mutation 无法与 SQLite 原子提交，但 Audit 必须与 durable phase 对齐：adapter 验证
planned target 后，在更新 Operation Applied 的 transaction 追加 `operation_applied`；
Finalize transaction 同时更新 ledger、Operation phase 并追加 `operation_finalized`。如果
外部 mutation 已完成但数据库事务失败，Operation recovery 会重新识别 planned state，再
安全推进 phase 和追加事件。

Audit event UUID 在对应业务 transition 开始前生成，并在数据库重试时复用。同一
transition 的 expected-state CAS 与 event insert 位于同一事务：CAS 成功才插入；CAS 未命中
且状态已经完成时不再追加第二个事件；事务结果不确定时使用同一 event UUID 重试。不能在
事后解析 payload 去重，也不能为同一 Operation phase 生成多个业务历史事件。

普通 repository API 只提供 append 和 query，不提供 update；数据库 trigger 进一步禁止
UPDATE。DELETE 只允许专门的 retention maintenance 使用，因为 Audit 必须可裁剪。第一版不
在 schema 中硬编码保留天数或行数，而由应用配置最大保留时间、数据库容量或事件数，以及
分批删除大小。

后台 maintenance 按 `(occurred_at, id)` 分批删除最旧事件，不在业务 transaction 中执行
大规模清理。Audit 不参与正确性，因此裁剪不会改变 Desired、ownership、recovery、
Conditions 或 requests；清理失败也不能阻止 reconcile。若 append 属于一个要求审计的业务
transition，append 失败则整个数据库 transaction 失败，不能提交未记录的状态变化。

Audit 不得用于回放 Surface/Consumer status、重建 Managed ledger、判断 target ownership、
恢复 Operation、调度 retry、推导当前 Conditions 或代替结构化日志。当前事实始终来自
Status、Condition、Request、Managed、Operation 和 Artifact tables；Audit 只保存已经发生
的业务历史。
