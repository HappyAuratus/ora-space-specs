# 插件 Capability 与存储布局

## 代码与数据分离

Ora 将插件的安装制品、运行期数据、注册表来源和下载缓存分开存放：

```text
~/.ora/
└── plugins/
    ├── sources/      # 注册表源（Git 仓库或清单）
    ├── installed/    # 已安装的插件主体
    ├── data/         # 插件运行期持久化数据
    ├── logs/         # 插件运行期日志文件
    └── cache/        # 下载的 .orax 压缩包缓存
```

这不是单纯的目录整理，而是插件权限模型的基础。它类似程序在内存中的布局：可执行代码与只读数据位于受保护区域，可变状态位于独立的数据区或堆中。代码不会为了保存运行状态而改写自身，运行期数据也不会被误认为可执行制品。

对应到 Ora：

| 目录 | 类似的内存区域 | 所有者与性质 |
| --- | --- | --- |
| `sources/` | 装载器的符号与来源信息 | Ora 管理的注册表元数据，用于发现可安装版本，不属于任何运行中插件 |
| `installed/` | 代码段和只读数据段 | 已校验、按版本安装的插件主体；运行期间视为不可变、只读 |
| `data/` | 可写数据段和堆 | 插件运行期状态；按插件隔离，可持久化并独立于代码升级 |
| `cache/` | 装载器的临时缓冲区 | 已下载的 `.orax` 制品；可重新获取，不作为安装或运行状态的事实源 |

## `installed/`：不可变插件主体

`installed/` 保存经过下载、摘要校验、安全解压和清单校验后的插件版本，包括 `main.js`、随包资源以及插件附带的可执行文件。

该区域遵守以下约束：

1. 安装完成后，插件版本目录在其生命周期内不可变。
2. 插件不能把配置、日志、模型缓存、Session 状态或其他运行期数据写回安装目录。
3. 同一插件升级时安装新版本，不在原版本目录上原地修改文件。
4. 插件随包附带的二进制只能作为已安装制品被宿主解析和校验。插件通过 SDK 请求创建进程时，由 Ora 从可信安装记录中确定实际可执行文件，而不是接受插件提供的任意宿主路径。
5. 完整性校验只覆盖安装制品；可变运行数据不会使代码摘要失效。

把安装主体视为不可变代码区，可以让版本身份、摘要、回滚和运行中引用保持一致，也能防止插件通过修改自身改变已经审核过的行为。

## `data/`：插件私有运行数据

`data/` 保存插件在运行期间产生且需要跨重启保留的可变状态。每个插件拥有独立的数据目录：

```text
~/.ora/plugins/data/<namespace>/<plugin_name>/
```

典型内容包括配置、缓存索引、下载结果、Agent 适配状态和其他插件私有数据。该区域遵守以下约束：

1. 插件只能通过 Ora SDK 访问自己的数据空间，不能直接取得宿主文件系统权限。
2. Ora 根据当前插件身份解析数据目录；插件 API 使用逻辑路径，不允许用 `..`、绝对路径、符号链接等方式逃逸目录边界。
3. 插件之间默认不能读取或修改彼此的数据。
4. 升级插件代码时保留数据目录，使代码版本与持久状态具有独立生命周期；若需要迁移，由明确的版本化迁移流程完成。
5. 卸载时是否删除数据必须由卸载语义明确决定，不能因为移除安装主体而隐式丢失用户数据。

## `sources/`：注册表来源

`sources/` 保存 Ora 已配置的插件注册表源，例如同步下来的 Git 仓库或注册表清单。它描述“有哪些插件版本可以安装”，不代表某个版本已经安装，也不参与插件运行。

该目录由 Ora 的插件管理器独占管理。运行中的插件不能读取或修改它，否则插件可能影响市场索引、伪造更新或改变其他插件的安装来源。

## `cache/`：可丢弃的下载制品

`cache/<namespace>` 保存从注册表来源下载的 `.orax` 压缩包。缓存只用于减少重复下载，不能成为安装状态或插件数据的权威来源。

缓存文件在进入安装流程前仍是不可信输入，必须重新进行摘要校验和安全解压检查。清空 `cache/` 不应影响已安装插件及其运行数据；需要时 Ora 可以从来源重新下载。

## Capability 与目录边界

Agent 插件等插件类型确实需要创建进程、访问文件或使用网络，但这些能力不等于向 Deno `main.js` 开放对应的原生权限。插件仍通过 Ora SDK 发起受控请求，由宿主在明确的资源边界内执行。

存储布局为这些请求提供了稳定的授权范围：

- 执行插件附带程序时，代码来源限定在该插件的 `installed/` 版本目录；
- 读写插件状态时，目标限定在该插件的 `data/<namespace>/<plugin_name>/` 目录；
- 安装、更新和校验流程由 Ora 访问 `sources/` 与 `cache/`，运行中插件无权操作；
- 创建的子进程由 Ora 管理，并继承 Ora 为该 Agent 实例建立的沙盒，而不是继承不受约束的用户权限。

因此，Capability 表达的是“插件可以请求 Ora 完成哪一类受控操作”，而不是“插件进程直接获得哪一项操作系统权限”。代码与数据分离使每项授权都能指向明确的所有者、目录、生命周期和完整性规则。

## 在 `orax.toml` 中声明权限

插件所需权限必须声明在包内的 `orax.toml` 中。清单描述该插件版本可能向 Ora 请求的宿主能力及其最大作用域，作为安装审查、用户授权和运行时鉴权的共同输入。

`orax.toml` 中的权限声明不会被翻译成 `deno run --allow-*`。无论声明了哪些权限，运行 `main.js` 的 Deno 进程始终保持零权限。声明只控制插件可以调用哪些 Ora SDK 方法，以及 Ora 代为创建的资源或子进程可以获得什么边界。

下面是 Agent 插件的示例：

```toml
resolver = 1
name = "ora-space.opencode"
namespace = "official"
kind = "agent"
version = "0.1.0"
description = "Ora Space OpenCode Agent"
homepage = "https://github.com/ora-space/opencode-agent"
license = "Apache-2.0"

[permissions.plugin_data]
access = "read-write"

[permissions.process]
executables = ["bin/opencode"]
stdio = true
signals = ["terminate", "kill"]

[permissions.process.sandbox]
workspace = "read-write"
network = true
environment = []
```

该示例表达：

- 插件可以通过 Ora SDK 读写自己的 `data/<namespace>/<plugin_name>/`；
- 插件可以请求 Ora 启动安装包内的 `bin/opencode`，但不能启动任意绝对路径或系统命令；
- Ora 可以把受管子进程的标准流交给插件，并允许插件请求终止该进程；
- Agent 子进程可以在该 Agent 实例的权威 workspace 中读写并访问网络；
- 子进程默认不继承 Ora 的环境变量。需要的配置、凭据或环境值必须通过单独的受控输入机制注入。

### 权限字段

#### `permissions.plugin_data`

声明插件通过 Ora Storage SDK 对自己数据目录的访问级别：

```toml
[permissions.plugin_data]
access = "none"       # 默认值
# access = "read"
# access = "read-write"
```

它不允许插件访问其他插件的数据、`sources/`、`cache/` 或宿主的任意文件。

#### `permissions.process`

声明插件是否可以请求 Ora 创建和控制子进程：

```toml
[permissions.process]
executables = ["bin/tool"]
stdio = true
signals = ["terminate"]
```

- `executables` 中的每一项都是相对于当前插件不可变安装目录的包内路径；禁止绝对路径、父目录穿越和符号链接逃逸。
- Ora 只允许执行清单列出的普通文件，并在启动前验证文件仍属于当前已安装版本。
- `stdio` 控制插件能否通过 SDK 读写受管进程的标准流。
- `signals` 是允许插件请求 Ora 发送的信号集合；插件不会获得原生进程句柄。

仅声明 `permissions.process` 不代表子进程可以任意访问宿主。子进程的实际边界由 `permissions.process.sandbox` 继续限定。

#### `permissions.process.sandbox`

声明由 Ora 代为启动的进程可获得的沙盒资源：

```toml
[permissions.process.sandbox]
workspace = "read"    # "none" | "read" | "read-write"
network = false
environment = ["TERM"]
```

- `workspace` 只指 Ora 为当前 Agent 实例指定的权威 `cwd`，插件不能自行把它替换成其他路径。
- `network` 控制受管进程是否可以访问网络；默认关闭。
- `environment` 是允许 Ora 从经过净化的宿主环境中传入的变量名白名单；默认空列表。
- 凭据不应通过普通环境继承获得。Secret 必须来自 Ora 的安全输入引用，并按单次实例最小化注入。

后续增加文件选择器、HTTP 请求、系统通知等宿主能力时，应在 `permissions` 下增加各自的强类型配置，而不是退化成一个无边界的 `all = true` 或任意字符串权限列表。

### 解析与执行规则

1. **默认拒绝：**未声明的权限一律不可用，缺省字段采用最小权限值。
2. **严格解析：**未知权限、未知字段、未知枚举值和非法作用域均使插件安装失败，不能静默忽略。
3. **按插件类型校验：**权限必须与 `kind` 相容。例如只有需要管理受管进程的插件类型才能声明进程权限。
4. **安装时审查：**Ora 在安装或启用前向用户展示规范化后的权限及作用域，而不是展示原始 TOML 文本。
5. **版本级授权：**权限属于精确插件版本。更新版本扩大权限时必须重新获得授权，不能沿用旧版本授权静默提权。
6. **运行时强制：**每次 SDK 调用都由宿主根据调用插件身份、当前版本、已声明权限、用户授权和当前资源归属重新校验。
7. **作用域不可由调用方扩大：**插件传入的路径、URL、可执行文件或实例 ID只能进一步收窄清单授权，不能扩大清单声明的边界。
8. **授权不超过声明：**用户或管理员可以拒绝、撤销或收窄清单权限，但不能在不更新清单的情况下为插件附加未声明能力。

因此，权限的有效范围是以下条件的交集：

```text
orax.toml 声明
∩ 用户或管理员授权
∩ 插件类型规则
∩ 当前调用的资源归属与运行上下文
```

任何一层不允许，Ora 都必须拒绝请求并返回稳定、可诊断的权限错误。
